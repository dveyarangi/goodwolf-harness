# harness — a project that is not the origin holds core whole, at the ref it announces, and can take a later one

- **instruction** `.agents/skills/harness/SKILL.md` — the four commands, install, update, check and the per-clone links, each refusal and what the person does, the first install's last step
- **state** installed
- **record of** what must always hold
- **owner** core

## How it works

Core reaches a tree from a fresh clone of its repository at a ref and never from a working tree,
so what a recipient holds is what a commit holds. The manifest is everything under the core
directory plus the entry file, the host stub, the license, and the front page beside the harness
skill — what an installing agent introduces the harness from, the origin's own document rather
than core text, shipped as written with its links the origin's, which the leak rule does not
read; the project's local file is never
in it, which is what lets a redeploy overwrite core's content and nothing of the project's. Nor
is a mechanism the origin declares local: its directory, the folders of its skills and its parts
stay behind, and the blocks it installed leave what ships as the origin's local blocks do. A
ship is refused where a declaration that ships still names a file left behind, or a rules file
that ships installs into one. What ships is
transformed before a byte is written: the origin's local blocks removed, every straw-dog wrapper
and every `TODO`'s question binding sheared with the content kept, the announce line stamped, and
the whole held to the leak rule the origin's check applies.

**Two things outside the manifest are written, each only when absent**, both read by a fresh
tree's first session before anything has been written into it: a store's roots, into a store
holding no entry, which the questions mechanism's script writes from its shelf, the install only
calling it; and the product document, which the product mechanism's script writes from its shelf
the same way. A tree that already has either keeps it untouched, overwrite included: from its
first line each is the instance's. A product
document there in another form is named in the report, since its check fails *(the user,
2026-10-14)*. **A third is
merged rather than written**: each host's shared, committed hook file, never a local settings
file, receives core's hook entries beside the project's own *(the user, 2026-10-09)*. The entries'
words are the questions mechanism's shelf, shipped as core; an update replaces core's entries and
removes one that left core, and a check compares core's entries alone, so a project's own hook is
never drift. A host file that is not valid JSON is refused, not rewritten.

**A target is a Git repository**, because every script of core reads a tree through Git's listing
— tracked and untracked-but-unignored files, in Git's exact case — and the top level of its work
tree is where one installation's tree ends. An install into an empty folder inside no repository
runs `git init` there first and reports it: the root is not in question, and the person asked for
an install *(the user, 2026-10-07)*. Anything else that is not the top level of a work tree is
refused with the step — `git init` for a folder with files of its own, where the root is the
person's decision; the parent for a subfolder of a repository. An install also refuses a target
that already holds any manifest path, or that is the source itself — unless asked to replace a
clone of it that holds nothing of the person's: no change, no ignored file beyond the loader links
and bytecode caches running the script leaves, no commit on any ref that no remote-tracking branch
of its origin holds, whatever ref the run names; such a clone is emptied, its repository with it,
and the install runs as into an empty folder. A target Git refuses for
dubious ownership is refused with that cause and Git's own command. An update refuses over a core
file the recipient edited unless told to overwrite, and then reports what it replaced; it refuses
likewise a path the new ref adds where the project already holds a file of its own, naming it,
and passes one already holding what ships; it never
touches a file under the core directory the manifest does not name, and reports it as the
recipient's own; it refuses an entry file still carrying a retired `<project-local>` block, whose
content is the project's.

**The announce line is the revision.** A recipient's entry file reads
`Entry contract: <repository>@<ref>, <date>.`; a session there announces it while debugging's D1 stands in its entry file, the check reads
it, and the shape check reads its `@` to know it stands in a recipient — where a `not yet`
standing alone, unbound, is upstream's gap and draws nothing. No record file: integrity is asked of the source,
by cloning the announced ref again and comparing. A change to the transformation therefore reads
as an edit in every recipient installed before it, until it updates. What the announced ref
shipped is read under the transformation alone, never held to today's shipping refusals: those
govern what may leave now, and a rule added after a ref shipped would otherwise strand every tree
that took it. A missing copy of the license or the front page is no edit: the source held both at
its root before either shipped, so a ref from before is read as naming copies its trees never
received.

**An update is run by the incoming ref's installer** *(the user, 2026-10-14)*. The tree's own copy
is as old as its last install and cannot know what a later ref brings; the incoming one reads what
an earlier one left, as above. So the tree's installer, asked to update, resolves the ref, unpacks
that ref's core beside its clone and hands it the run, pinned to the resolved commit and marked
handed off so it hands it to no one; its report is the run's and says so. A tree whose installer
predates the hand-off cannot learn it before its next update, so the skill names a clone of the
source as what runs an update.

**The repository line is the source, as the announce line is the ref.** The harness skill carries
`Repository: <url>`, the only authored home of where core comes from: the script keeps no
constant and reads its default there, an install stamps a recipient's copy with the source the
run actually read — a URL verbatim, a path resolved absolute — and a fork edits the line once and
everything it installs names the fork. Both lines are the recipient's own facts living in core
files, so both are set aside when a copy is compared: a check or an update run from another
`--from` reads no edit in core. So is every block the recipient's own installer put in a core
file: its local block, and the block of a mechanism of its own, one whose rules file stands in
the tree and never shipped. A block no rules file owns is an edit. A shipped mechanism's block
is set aside too, on both sides, where it differs by the settings alone: the origin ships its
blocks as its own settings rendered them, a recipient's installer renders the same rules under
the recipient's, and whether a block is the one the settings call for is the injector's gate to
say. A `.py` line that differs by a `TODO`'s question id alone is no edit either: the comparison
shears the id on both sides, so a copy written by an installer older than its ref reads clean.
A stamped source is never a citation either, which the citation
reader settles for every reader of it, so a clone kept under a `docs/` directory does not make a
recipient fail its own shape check.

**Every refusal writes nothing**, and the loader links are the one step a person may finish by
hand: where the platform refuses to create a symlink, the run finishes everything else and ends
with the exact elevated command. Nothing is substituted for a link; a junction, a directory or a
file in a link's place is refused by name, and a link that already resolves is left alone. A link
that stands is removed only once its replacement exists, and one written to the skills directory
is kept even by a process that cannot see through it. The links are made in each work tree and
never committed, so a fresh clone of a recipient gets them from `--links`, the link step run
alone from the clone's own copy with no source; whatever plans a link names it in the clone's
exclude file, which Git locates. The same step records the interpreter that ran it in the
clone's common Git directory, which its worktrees share and no commit carries: every core hook
runs through a wrapper that reads it, so a hook needs no `uv` and no `python` on the path, and
a clone without the record is told which step makes it *(the
user, 2026-10-09)*. <straw-dog question="q-t3p7na">The same step writes the clone's
`pre-push`, which checks a push in a copy of what it sends and refuses it on any finding in that
copy, a push of code starting no interpreter: only inside the project — its Git
directory, or a hooks folder of its own work tree — and only where none or core's stands; beside
another's hook, in husky's folder or in one outside the project it writes nothing, and the report
gives the line and its place *(the user, 2026-10-26 and 2026-10-29)*.</straw-dog> A worktree of a
clone shares what the step wrote for the clone and lacks the links: where its host's link is
missing at a session's start, the wrapper runs `--links --line`, which makes the links and their
exclude entries alone and never fails the hook; its one line joins the installer's in the wake —
the command where the platform refused, or that the skills load from the worktree's next session,
a host reading them before its start hook runs. A run that fails after it began writing stops,
reports what it wrote, what was pending and the path that failed, and rolls nothing back: the
person recovers from the files as they stand.

**The gate is the check, and it takes seconds.** Arrival and any later day's question are one
function: the copy against the ref, the injector's check clean with the local block last, the
shape check — the target's own scripts, run as subprocesses, so what is checked is what arrived.
The loader links are reported beside the verdict and never decide it: a link the platform refused
is the person's one remaining step, and its command is already in the report. Whether a host reads
a link is not observable from inside a tree and is reported as unverified. The shipped suite is not run here —
it costs minutes, and an install is seconds — a recipient that wants it names it in its own
verification set *(the user, 2026-09-21)*. The gate itself clones the source whole, over the
network, at every run. A copy drifting from its ref is maintenance's to find, never
verification's *(the user, 2026-10-09)*; <straw-dog question="q-7caadu">no maintain pass runs the
gate: one is offered to the person, with its reason, only once the comparison reads no network and
takes no clone.</straw-dog>

**A running session is shown what changed in the entry file.** A host loads the entry file at a
session's start and after a compaction, and a session reasons from that text whatever the file
has become. The mechanism's hook line, run by the hooks' wrapper before the store's hook,
remembers per session the file's text as the session's context holds it, outside the tree beside
the window's memory. In a host whose message hook reaches the agent, a message that finds the
file other than the memory is shown, leading the store's own text, each passage that differs as
it was and as it is now, and the memory moves — before the text is handed on, so a notice a host
cut short is read on from the output the host saved, as its first lines say: one
change is shown once, several between two messages as one notice, and never a request to read
the file again while the passages fit — the old text stays in the context, and adding to its end
keeps what a re-read would replace *(proposed in session and agreed by the user, 2026-11-22;
the user's own words asked only that a session take the change silently, at its next turn)*. Past its budget the notice asks for
the read. A context that took the file in anew, and a session whose start no hook saw, are shown
nothing. The line never fails the host and never speaks of its own trouble. It ships as core, to
every tree *(the user, 2026-11-24: "хук во всех проектах")*.

It is **installed**; a tree without it holds no core at all. The repository's root `README.md`
is not a part: it ships as the front page beside the harness skill, and a recipient's root has
its own.

## What it produces, and who reads it

- **The recipient's core** — *what exists* — read by its every session, through the loader links its hosts
  follow.
- **The stamped announce line** — *what exists* — announced by the recipient's first reply while debugging's D1 stands there; read by `--check` and
  `--update` to know what was installed, and by the shape check to know it stands in a recipient.
- **The report** — *what exists* — read by whoever ran the script. Its `pending` lines are read by
  the person who runs them.
- **The stamped repository line** — *what must always hold* — read by the script whenever a run is given no `--from`,
  including the recipient's own copy at its own `--check`; and by a person or a fork asking where
  this tree's core comes from, or pointing it somewhere else.
- **Each host's hook file, core's entries merged in** — *what exists* — read by that host at session
  start and before each message, and by `--check`, which compares core's entries alone.
<straw-dog question="q-t3p7na">
- **The clone's `pre-push`** — *what exists* — in its Git directory or a hooks folder of the
  project's own work tree, run by Git at each push, which it refuses on any finding in a copy of
  what the push sends; made by the link step, never where husky keeps its
  hooks nor outside the project, where the report gives the line and its place.
</straw-dog>
- **The interpreter record**, in the clone's common Git directory — *what exists* — shared by the
  clone's worktrees and read by the hooks' wrapper before every hook that starts the interpreter;
  made by the link step, so `--links` is the one step a fresh clone runs, and a worktree of the
  clone runs none: its links are made, or their command given, at its session's start.
- **The pending command** — *what exists* — read by a person, once, in an elevated prompt.
- **The notice of a changed entry file** — *what happened* — read by a running session with its
  next message, once.
- **The entry file's text as each session's context holds it**, outside the tree — *what exists*
  — read by the hook line alone, at each message.
<straw-dog question="q-n3pc22">
- **The report**, in a tree that has a method — *what happened*, what the harness would change
  there — a working document kept where the host keeps the session's files, never written into
  the tree by the study; read by the person at the second stop, and on a yes by the migration for
  its plan, entering the tree with it; its ledger read again after the migration, on the same
  sample, and by the method's own measure *(the user, 2026-10-24)*.
</straw-dog>

No record of its own in this tree. The two stamped lines are the recipient's, and the report, once
a migration takes it in, is the recipient's record, never this mechanism's.

## Not yet at the shape

<straw-dog question="q-4xda6k">
**A mechanism that leaves core leaves its block behind.** Where a later ref no longer ships a
mechanism — removed, or declared local after it shipped — an update deletes its files in a
recipient and reads the block it installed there as the recipient's own, so the gate fails on a
block nothing owns. A mechanism is declared local before its first ship, never after.
</straw-dog>

**The transformation is unguarded.** A change to the shear, the stamp or the local-block strip
reaches every recipient as a reported edit; nothing checks a change against the recipients that
exist.

## What retires this

A host that reads a repository directly at a ref, so that nothing need be copied and the ref is
the tree's by construction. Until then a copy is the only way core reaches a tree, and the copy
needs a revision and a check.

## What would show it working, graded by someone who did not build it

**The user, in a tree that took the harness by hand** at a version its entry file still announces
and has built on the copy since. It writes its answers into a local file, takes an update from the
repository, and the user grades: its local file survives byte-identical and its blocks are
restored last; its `docs/` is untouched; its links resolve; its announce line names the ref; the
gate passes, or says which of the three did not. An install that had to be hand-finished to reach
`arrived: true` reads identically to success in the report, and only the grader can say which it
was.

**The study, graded by its trial runs.** The shelf ran twice on a stranger tree with a method of its
own before any live meeting, each run a fresh agent given the shelf alone: both produced the report
in its form, in the tree's language; neither proved a key wrong; the two together found eighteen
places where the shelf was unclear, each amended. The live meeting, the person at the stops, is the
grade the ticket waits on.
