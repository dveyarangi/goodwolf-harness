PART: The draft routes the destructive wipe through a script the agent runs, on the premise that the agent's own deletion was blocked by the permission mode, without examining whether that block also covers the script or whether the script then bypasses the control; it also leaves the guard for "this is a pristine clone of the origin" at a one-clause check.
CONTRACT CHANGE: If the permission layer treats a script that wipes a tree as the same blocked deletion, the shape does not solve the failure and a different shape is needed (for example a refusal plus a person-run step, or no clone-first path). If the script is allowed to circumvent the block, the installer's contract changes: it becomes a deletion primitive whose authorization must come from the person, and the guard must prove the tree holds nothing of theirs, not merely that it is clean.
REASONING: The draft commits to an installer mode, behind an explicit flag, that wipes a clone sitting where the project should be, runs git init and installs core at the clone's commit. Its stated justification is that the agent cannot delete but the script can. That is the central assumption, and the earlier exchange only says deletion "was blocked by the auto-permission mode"; nothing examines whether running a deleting script is the same blocked act or an end-run around it. It decides whether the shape works at all and who must authorize it, so it fails the counter-test. The guard (clean tree, HEAD equals the repo commit) is stated in one clause. Only the first-run case was considered, and the pristine-clone claim has to hold for the installer's wipe to be safe, which makes it part of the same boundary question. The cost and the developer's-own-clone risk were weighed, so those are not the gap. The README line and the refusal message are local detail.
