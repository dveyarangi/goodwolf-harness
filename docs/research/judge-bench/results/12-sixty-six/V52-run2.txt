PART: The draft makes the question store "an index of the product's answers" by pointing found questions at places in code and docs that stay untouched and unmarked, but never examines what keeps those pointers true once the recipient project's code changes outside the harness (and the generated question's state is framed as a new closure kind without checking the store's open/suspect grammar).
CONTRACT CHANGE: The store stops being a standing index and becomes a snapshot unless a re-derivation or staleness path is designed. That changes what the product document derived from it promises, who owns pointer validity (the project's code owners versus the harness), and whether a found question is a closed question with a new kind or an open or suspect one. It would also change the store's state grammar and the install contract.
REASONING: The draft commits to a two-stage arrival. An align seeds the upper levels, then a pass writes each load-bearing finding as a question under the cause it answers, pointing at code or docs with no marks, and the product document derives from that. Its answer to "no marks possible" is exactly that the code stays untouched. Pointer rot is not examined anywhere. The earlier exchanges and the record cover why, volume, the seed and the marks, not what happens when the unmarked code moves. Existing mechanisms (q-0001.0023 on a changed answer reaching what stood on it) concern changes inside the store, not code outside it, so the boundary is uncovered. I also checked the "no such closure kind" claim. questions.py has KINDS = decided, pruned, merged, deferred, moot, superseded, plus an open state with a suspect flag. A found-not-decided question is not a closure at all, so the premise behind the proposed decision is shaky, though that part alone could be settled locally. Other candidates (the abstraction/rationalization risk, the seed-approval child question, the experiment on harness rules) are detail the person can settle later without changing the commitment. The staleness of the index decides whether the derived product doc is true, so it is load-bearing.
