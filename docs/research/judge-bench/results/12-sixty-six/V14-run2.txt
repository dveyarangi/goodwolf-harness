PART: The fix's trigger, "re-check at later messages while the new session is still empty (no position, no history)", is never examined against what the first message of a resumed session itself does, which is to place the turn with `at`, so the session stops being empty before the second message.
CONTRACT CHANGE: The criterion for "same conversation" cannot be "nothing done yet" (it would almost never hold); it has to be the transcript-uuid match alone, or a match that is allowed to override and merge a position the new id has already acquired. That changes what the resume link promises (when a new id takes over an old position, what happens to a position the new id already wrote) and what the "unchanged window"/"registered now" replies must say in between.
REASONING: The draft commits to a shape: keep the one-shot link at start, but retry it on later messages while the new id counts as empty, then carry the old position over and end the old row. In the tree, `_started` links only at the start event (questions.py ~1287-1303), and the message branch (~1246-1252) only draws a window. The first message's window reply tells the agent to say what the turn is with `at q-N` (~1030-1033), and the entry rule Q1 requires that call every turn, so the new id gets a position on the first turn. A retry gated on "no position and no history" would therefore never fire for the very case that motivated it, which defeats the fix and changes its contract: the trigger must be the uuid match, and the takeover must define what happens to a position the new id already holds. The cause analysis (race with transcript creation) and the test plan are detail on top of this; the empty-session gate is the load-bearing part, because the whole proposal and the "a genuinely new session won't be glued" safety claim depend on it.
