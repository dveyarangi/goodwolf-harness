PART: The draft's whole mechanism rests on the claim that a script may wipe the tree because "the rights are given to the script", but the block that stopped the agent was the host's permission layer on the agent's own actions. The draft never checks whether that layer lets the agent run a script that does the same deletion, and a script-run deletion of the person's folder is exactly what it blocked.

CONTRACT CHANGE: If the host treats a script that wipes the folder as the same blocked deletion, `--replace-clone` can never run unattended, and the shape stops being "the installer converts the clone in place". It becomes either a person-run step or a non-destructive route that deletes nothing and does not install into the origin clone. The change also reaches the standing install contract. Today `--install` refuses a target that holds manifest paths or is the source itself, and the person decides where a root goes. This flag turns those refusals into a destructive action chosen by the agent, so the refusal text, the README line and the tests would all be rewritten around whichever route survives.

REASONING: The draft commits to an installer branch: given an explicit flag and a clean clone at the repository's HEAD, it wipes the tree, runs a fresh `git init` and installs core. It weighs one alternative (teaching the person another phrase) and names one risk (a developer running it in their own clone). The parts I considered:
- Premise that the clone happens before any text is read. The person's message shows this directly, so it holds.
- Developer-clone risk. The draft names it and answers it with a clean-and-HEAD check plus the explicit flag, so it passes.
- Whether the script can delete when the agent could not. I checked harness.py and the harness skill. The tree has no word on host permissions. It does say that where a root goes is the person's decision, and that the origin is never installed into (RFC 0130, 0155, architecture.md:213). The block the agent hit in the fourth run was the auto-permission mode on its own command. Routing the same deletion through a script is the circumvention such classifiers usually refuse, and the draft treats "the script has the rights" as fact. If the premise fails, the draft's cost, risk and README text describe a mechanism that cannot run, and the options put to the person are the wrong ones. This part fails the counter-test.
- Source clone versus target. The installer reads core from a fresh clone of the repository, and here the target is itself that clone, so the install would run from the tree it is wiping. On Windows the running script and the working directory are open handles. That is real, but it can be settled locally in the implementation.
