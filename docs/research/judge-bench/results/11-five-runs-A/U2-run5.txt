PART: The draft makes answers the ends of the relation and proposes a "fingerprint of the answer text" to detect change, but the store never holds an answer's text (a closed entry's answer is a link to the doc/ADR/code that decided it, parent decision 43), so what the fingerprint covers, and what an "answer" is as a stored thing, is unexamined.
CONTRACT CHANGE: What "assumes" ends point at changes. Either it fingerprints the pointer line, which only changes on a re-close and so adds nothing over the earlier event-driven trigger, or it fingerprints content in the docs the answer links to. The second makes the store depend on doc contents, so any unrelated doc edit would fire it, and the boundary between store and docs moves. Alternatively the store would have to start holding answer text, which reverses decision 43. The "detection by script not memory" promise, the "link dies with its answer" lifecycle and the date-vs-fingerprint choice all depend on this.
REASONING: The draft commits to a relation `assumes` whose subjects and objects are answers (or the leans of open questions), a script that detects drift by a recorded fingerprint, and agent judgement on whether the assumption actually broke. I checked the tree: the questions script validates a closed entry's `answer` as a pointer (a link for decided, an id for merged or superseded, a condition for deferred), and its docstring says a closed question points to its answer and never holds it. So "answer B's text" is not a store object: a lean is a one-line field, but a decided answer's content lives in a linked doc. The draft's own claims that a script finds the changes, and that the link cannot outlive the answer that made it, rest on answers being fingerprintable, addressable store values. That premise fails for closed questions and was not examined. It is put to the person only as a choice between a date and a fingerprint, which leaves the premise untouched. I checked and rejected other candidates as local detail: the claim that `depends on` already carries a little `assumes` is true (the check reports a closed entry whose dependency is open again), and clearing links when a lean is rewritten is a writing-call detail. The answer-pointer versus answer-content question crosses the store/docs boundary and could reshape the relation's contract, so it fails the counter-test.
