PART: How a session's identity reaches the agent in Cursor (and wherever hook injection fails): the draft has the hook register the session under the host's conversation_id, but the agent must then pass that id as --session on every call, and the draft never says how the agent learns it or what happens to the registration when it does not.
CONTRACT CHANGE: The sessions model changes. The store's current contract has --wake mint the tag, the agent hold it in context, and a tag-less call register a new session. If Cursor's sessionStart additional_context does not arrive, the Q1 fallback "otherwise run it yourself" mints a second session beside the hook's ghost one. The draft's "one tested table" then cannot be the whole host difference. Either the tag must be host-supplied in a way the agent can see (for example Cursor's postToolUse context, which the draft overlooked), or registration moves to the agent, or Cursor is not wired for registration at all. That also changes what the "wire all three" decision promises, and what decision 39 and RFC items 8 and 9 must say.
REASONING: The draft commits to wiring all three hosts to one questions.py --hook, with Cursor only registering at sessionStart and everything else left to the AGENTS.md rule. I checked the RFC's sessions design. The tag is minted by --wake and held in the agent's context, every later call carries --session <tag>, and --wake registers only when called with no tag, so that one conversation never gets two sessions. The draft replaces tag-minting with host ids, so the tag the agent must pass depends on the injection channel working. Cursor's docs say sessionStart is fire-and-forget (the agent loop does not wait for it). The draft lists "does it reach the agent" as a later live check but never says what the shape does if it fails: the hook registers a session the agent cannot name, and the agent's own run mints a duplicate. Cursor's docs also list postToolUse as another injection point, which contradicts the earlier claim that sessionStart is the only one. That undermines the Cursor row of the matrix and may remove the need for the rule-only fallback. I considered the Codex trust and desktop-hook uncertainties and the cross-OS command wiring. These are flagged by the draft or can be settled locally in config, so they pass the counter-test. The identity handoff crosses the hook, script, store and AGENTS.md rule boundaries, and the sessions-file contract depends on it, so it fails the counter-test.
