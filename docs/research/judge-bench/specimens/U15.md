Виноват — начал с формы, не с задачи. С начала, на одном примере.

**Что есть сейчас.** У каждого механизма есть док — например `harness.md` описывает, из чего сделан harness: скрипт `harness.py`, его тесты, скилл, файл входа. Есть «часы» — `maintain.py --check`. Они говорят `/maintain`: «этот док пора перечитать». Работают так: когда maintainer перечитал док, он ставит метку — отпечаток файлов, против которых читал. Если потом эти файлы изменились, часы говорят «due» и называют, какой файл сдвинулся.

**Задача.** Сегодня часы следят за неправильными файлами. Док становится «due» только когда изменились *правила написания доков* — файл входа, правила mechanism-shape, скилл `/mechanism`. А когда меняется сам `harness.py` — то, что док описывает — часы молчат. Так на этой неделе `harness.md` несколько дней врал про две строки файла входа, и никто не узнал, пока не наткнулись руками. Вы это уже решили на align: **док должен быть due, когда сдвинулась часть, которой механизм владеет** — его скрипт, тесты, скилл. Для этого новый уровень, `parts`. Тикет .0080 — это и есть «научить часы следить за частями».

**Моё предложение, по шагам.**

1. У каждого механизма две строки в метках: `parts` и `output`.
2. **`parts`** — отпечаток файлов из таблицы «Install adds, uninstall removes» в доке (кроме самого дока). Изменился `harness.py` → часы говорят: «перечитай `harness.md`, сдвинулся `harness.py`». Файлы из таблицы «Relies on» не считаются — за них отвечает док их владельца, иначе одно изменение делает due пять доков.
3. **`output`** — как сегодня: отпечаток дока, правил и скилла механизма. Эти три файла правят *записями* механизма — тикетами, вопросами, метками; изменился формат тикета → перечитай тикеты. Сюда же я **добавляю файлы mechanism-shape** (его док, правила, скилл и формат). Зачем: раньше за «док против правил написания доков» отвечала отдельная третья строка `rules`. Вы сказали: это не третий уровень, а проверка выходов самого shape — ведь shape производит доки и скиллы. Чтобы не плодить вид строк, я кладу файлы shape в ту же строку `output`: часы называют, какой файл сдвинулся, и maintainer понимает направление — сдвинулся файл shape → читай док и скилл против него; сдвинулся свой док → читай записи против него.
4. **Три исхода** перечитывания, которые вы решили: за сдвигом стоит решение, а док отстал → правим док; решения нет → правим часть обратно под док или идём на `/align`; сдвиг не трогает ничего, что док говорит → ничего не менять. В метках для второго случая появляется слово `repaired`, чтобы было видно, какую сторону правили.
5. **Переход**: старые строки `rules` удаляются руками в коммите приземления. Все `output` сразу станут due, все `parts` — «ещё не проверялись». Это нормально: due — новость, не дефект.
