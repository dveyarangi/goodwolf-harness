A **result** is one line in a sidecar: **one host's answer to one check**. The hosts record lists ten checks under `Extending`. Each host's sidecar answers each check with one bullet in its `Conformance` section, so there are 10 results per host and 30 in all.

Two of Cursor's, for example:

> - **Wake** — absent: `sessionStart`'s `additional_context` never reaches the agent … the entry file's rule stands in …

A result opens with one of four words: `observed <date>` (someone watched it happen), `documented` (only the host's docs say so), `unobserved` (nobody has looked), or `absent` (the host can't do it, plus what stands in).

With that word, the two open decisions are:

1. **Staleness.** A result doesn't say which pieces of code it depends on. So when anything in the sidecar's `Integration` list changes, E2 and E4 mark all ten of that host's results stale. Since `hook.sh` is listed in every sidecar, one edit to it would mark all 30 stale. My recommendation: each result names the pieces it depends on, and only those results go stale.
2. **Verdict.** `observed` says someone watched, not that the host passed. Cursor's **Registration** is "observed" and still fails half of its check. My recommendation: replace `observed` with `passed`, `failed` or `partial`, each with a date.

The word is unclear because it's defined nowhere. The format uses it, and the glossary doesn't have it. (💡 [*A capable reader*](AGENTS.md:35): state the rule and point at the definition the glossary owns)

Agreed. "Result" is a plain word, and a narrow mechanism shouldn't capture it. I'm withdrawing the proposal.

**On staleness: we don't need it. I over-built it.** (💡 [*Occam*](AGENTS.md:32))

The problem it tries to solve: a sidecar says "observed 2026-10-03: Cursor's hook registers the chat under its id". Later someone changes Cursor's code in `questions.py`. The observation describes the old code, but the record still reads as if it were current.

But that problem is already solved by the **date**. Every observation is dated, and git shows when the code changed. If you read "observed 2026-10-03" and see a commit to `_cursor_answer` on 2026-10-12, you know what the observation is worth. Marking it "unobserved since…" adds nothing the date doesn't already say. Meanwhile it has real costs:

- a judgment call at every landing that touches `questions.py`;
- the risk of wiping out real observations by mistake;
- a pending decision about per-result dependencies;
- one `not yet` row and one paragraph in the doc.

Nobody acts on staleness anyway. Only the next live check does, and it runs when someone deliberately adds or updates a host. /edge's *Extend* goal already covers that.

Here's what actually matters in E2 and E4, and what should stay:
- a promise the code no longer keeps is a finding, and the record is never rewritten to fit the code;
- a deliberate change gets written into the record when it lands;
- a live observation goes into the sidecar, not only into the ticket.

The second decision, the `passed` / `failed` verdict, goes the same way. Cursor's Registration line already says in words that it fails half of the check, so it doesn't need a new vocabulary.

🧩 **Proposed rule — edge.rules.md, E2**
> An edge record is of the code and configuration it names. When the scope moves a part that a record under `docs/edge/` names, re-read what it says of that part. A promise the code no longer keeps is drift, reported with its evidence and never rewritten to fit.

🧩 **Proposed rule — edge.rules.md, E4**
> When the landed work changes an edge — a promise in its Contract or Invariants, an invariant's validator, or a check of its Extending — the same commit writes its record under `docs/edge/`. A promise the landing makes true loses its `⚠ pending` mark, and the record leaves `Normative (tentative)` when no mark is left; a landing that breaks a promise no decision changed is a finding, never written into the record. The Roadmap entry of the ticket that landed is removed. An extension observed live in this work has what was seen written in its sidecar, dated, not only in the ticket or the session record.

✏️ **Proposed change — EDGE-FORMAT.md, Rules**
> - **An observation is what was watched.** Nothing unwatched is written `observed`, and a partial watch says which part. An observation keeps its date; a later one replaces it.

Along with that, these come out: the `not yet` moment "a named file moved outside every landing and every pass", the doc paragraph "Staleness is judged, not derived", and the two pending decisions (staleness per result, and the verdict).
