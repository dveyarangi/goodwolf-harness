**Person:**

what is cursors beforeSubmitPrompt , though?

**Agent:**

It's the hook Cursor runs at the moment you press send, after you've written the message and before Cursor sends it to the model. According to [Cursor's hooks docs](https://cursor.com/docs/hooks):

- **What the hook receives:**
  - your prompt text and its attachments;
  - `conversation_id`, a stable id for the whole conversation;
  - `generation_id`, an id for this one turn.
- **What it can send back:** only `continue: true | false`, plus a `user_message` that is shown to you when it blocks.
- **What it's for:** checks on what you're about to send. Examples are blocking a prompt that contains a secret, enforcing a policy, or logging prompts.

So it can watch and veto your message, but it can't change the message or add anything to what the model sees. That rules it out for the window: the hook could run `questions.py --window`, but the output would have no way into the agent's context.

One inconsistency in the sources: a couple of third-party guides call it observe-only, meaning it can't even block. Cursor's own docs list `continue: false` as blocking, so I'd trust the docs. For our purpose it doesn't matter either way, since neither reading lets it inject context.

The only Cursor hook that can add context is `sessionStart`, through its `additional_context` field, and that runs once when the conversation opens, not on every message. On Cursor, then, a hook could register the session using `conversation_id` as the tag, but the window before each reply would still have to come from the `AGENTS.md` rule.
