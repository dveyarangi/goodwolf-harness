## Plan question 3: the script's name and commands

**Context:** the ticket asks for one command that reports what's due, one command that moves a mark (and is the only writer), and a checker that reports a malformed row. The accepted spec says a record-bearing mechanism's maintainer script *"carries the slug in its filename"*, the way `tickets.py` does for the ticket mechanism.

**Proposal: one script, `.agents/scripts/gw/maintain.py`, with two modes:**

| Command | Does | Exit status |
|---|---|---|
| `maintain.py --check` | Reads the marks and every declaration. Reports each mechanism and level as **due** (and why: meta-rules moved, or its own doc, rules file or skill moved), **current**, or **never maintained**. Also reports any malformed row, or a file it can't fingerprint, such as a hand-edited installed block. | `1` only for a malformed row or a file it can't fingerprint. **Something being due never fails it**, so `/verify` doesn't break every time a rule changes. |
| `maintain.py --mark <mechanism> <level> <outcome>` | Fingerprints what that level is checked against as it stands now, and writes or replaces that one row with today's date. Refuses a mechanism that isn't declared, a level other than `rules` or `output`, and an outcome other than `amended` or `"nothing to change"`. | `1` on refusal, and nothing is written. |

**Why two modes, not three:** the due report and the format check read the same file and the same declarations. Folding them into `--check` means the verification set runs one command, and `/maintain` runs the same one. That's the pattern of `inject_rules.py --check`.

**Where `--check` runs:** `/maintain` runs it at the start of every pass, and `/verify` runs it as part of the project's verification set (L3 in `local.rules.md`).
