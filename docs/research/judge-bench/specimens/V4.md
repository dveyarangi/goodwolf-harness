## The agent's draft reply

Sure. Start from the mechanism rule, then the three cases.

**The rule.** Every rule has one owner, and it is written once, in the owner's rules file. When another skill needs to read that rule while doing its own work, the installer copies it into that skill's body as a marked block. The copy is called an installed block. The skill it is copied into is a **target**. The block is visibly owned, and the checker fails if the block and the rules file ever differ.

`/maintain` already has one such block today: four rules from the mechanism shape, sitting in its body under "Installed from other mechanisms", because `/maintain` applies them but does not own them.

**Why `/ticket` needs targets at all.** `/ticket` owns the rules about what a ticket is and how it lives and dies. But `/ticket` is not the skill doing the work at three of those moments. Someone else is holding the pen:

| Moment | Who is acting | The `/ticket` rule they need in front of them |
|---|---|---|
| Closing a finished ticket | `/maintain` | Finished means every box checked. Move ticket and RFC together to `done/`. Update the header yourself. |
| Writing an RFC | `/plan` | Name the RFC by the ticket's basename, under `docs/rfc/`. It moves with the ticket. |
| Resolving a decision | `/align` | Land the decision in its durable home, rewrite the ticket in place, keep only what is still open. |

In each row the rule is about the ticket, so `/ticket` owns it. But the person reading it is inside another skill at that moment. If the rule stays only in `/ticket`'s files, it does not reach them. That is exactly how five tickets were lost: the archive duty was written in `/ticket`'s files and `/maintain` never saw it.

**What is there now, per row.**

- `/maintain` has the four P rules, but as a hand-typed copy inside a straw dog, which no checker compares to anything. This ticket replaces that copy with an installed block. This target was always in the ticket.
- `/plan` has the basename rule as a restated bullet with a link. Question 2 made this the second target: the bullet becomes an installed block.
- `/align` has the "strike and answer inline" sentence as its own text. If the stage model changes how a resolution is recorded, that sentence is wrong, and fixing it by hand in `/align` creates a second home again. Making `/align` the third target means the rule is written once in `ticket.rules.md` and installed into `/align`.

**What it costs.** Each target needs one anchor line in its body where the block goes, and `/plan` and `/align` have no such heading yet, so each gains one. The rules file grows by one section per rule. Nothing else.

**What it does not mean.** It does not make `/plan` or `/align` parts of `/ticket`. It does not change what they do. It only moves where one sentence each is authored.

Does that clear it? If so, the question stands: confirm the stage model, and `/align` as the third target.
