## Problem Statement

One harness, more than one project, and today a person hand-repairs it on every trip and steps on
what the project already had.

The harness was built for twelve sessions in the one tree where its defects are invisible: here core
and instance are the same repository, so every reference from `.agents/` into `docs/` resolves and
nothing can tell a rule from a fact about this project. The first copy into another tree —
[frost_map, 2026-09-09](../research/separation-probe-frost-map.md) — produced 35 diagnostics inside
an hour, and by 2026-09-10 the recipient had merged it to `main`, built on it, and refused one of
its checks by leaving it unrun. Eight concrete things went wrong, and they are the whole problem:

1. The recipient's `.claude/skills` link, which pointed at its own 21-skill corpus, was repointed
   silently. The install had no stated place to land, so a person improvised.
2. Fourteen `<straw-dog>` blocks arrived that can never expire there, each naming a ticket the
   recipient does not have, under an entry-file rule that says to obey them until the condition is
   visibly met.
3. Eleven `not yet` links in the mechanism docs point at tickets only this repository has.
4. Three `evidence` bullets point at files only this repository has — inside `<project-local>`
   blocks, correctly, and nothing replaced them because nothing existed to.
5. Every one of the recipient's seven tickets fails `tickets.py` on `Status` and `Type`, fields its
   Notion board owns. Its answer, in its own commit: *"a second copy in a file is what that rule
   exists to prevent. The check is wired into nothing, so the tickets are untouched and it goes
   unrun."* No override was expressible, so the rule was dropped.
6. `AGENTS.md` and `CLAUDE.md` had to be typed by hand: the artifact carrying every tier-1 rule is
   the one thing outside every mechanism.
7. Nobody can tell what version the recipient has, or whether it has been edited since. Its core is
   byte-identical to ours after normalising line endings and differs in all 41 files before.
8. An improvement made in the recipient has no road back.

Two months earlier the same defect ran the other way: `/commit` arrived here carrying another
project's `ruff`, `pyright`, `pytest` and a `docs/cicd.md` this tree does not have — a project's
answers written into a core file, travelling as if they were core's.

**What is deliberately not a defect.** `docs/`-substituted-whole and the rules injector both made
the trip intact; `inject_rules.py --check` passed in the recipient with nothing to repair.
[ADR-0001](../adr/0001-agents-is-runtime-docs-is-construction.md) and
[ADR-0002](../adr/0002-core-may-not-depend-on-the-instance-half.md) were stressed and held. What
failed was that nothing *enforced* them, and that the one seam which worked was never asked to
carry the project's side.

## Solution

**Every project's local content lives in one file, in the format the injector already reads, and
the injector puts it back after every deployment.** Core owns every slot it installs into; the only
question is who owns the content, and redeployment overwrites only what core owns.

An install is one act by one mechanism: it copies core to a defined place, records what it copied
and where from, makes the host's loader link or stops, installs the entry file, shears what cannot
travel, and then calls the injector with the recipient's local rules file so the recipient's own
answers land last. A redeploy is the same act again; the local file was never in core's directory,
so it survives, and the injector restores its blocks. Arrival is verified from inside the recipient
by the checks that already ship, plus a revision it can compare against its source, plus a link it
can resolve. The one thing it cannot verify from inside — whether the host reads what was installed
— is named as such and owned elsewhere.

Before any of this can be trusted, every reference from core into the instance half is accounted
for and gone, except the path conventions a recipient creates for itself. That is the precondition,
and it is a check that runs at home, on every change, so the next port finds nothing.

## User Stories

**A recipient maintainer** — a person installing the harness into a project that is not this one.

1. As a recipient maintainer, I want the install to put the harness in one defined place, so that
   I do not improvise a location and silently break every script's notion of the tree root.
2. As a recipient maintainer, I want the install to make the host's loader link as a symlink or
   stop and tell me why, so that I never end up with a junction that every tool reports as success
   and counts twice.
3. As a recipient maintainer, I want `AGENTS.md` installed rather than typed, so that the file
   carrying every tier-1 rule is a part of a mechanism like everything else.
4. As a recipient maintainer, I want to write my project's answers — its verification commands, its
   switches, where its delivery state lives — in one file, so that I have one place to answer and
   not a corpus to edit.
5. As a recipient maintainer, I want to override any core rule my project cannot follow and have the
   override survive the next deployment, so that the alternative is never "stop running the
   check."
6. As a recipient maintainer, I want an override to name the rule it overrides, so that a reader can
   see the disagreement rather than infer it from position.
7. As a recipient maintainer, I want a redeploy to overwrite core's content and nothing of mine, so
   that taking an update is not an archaeology of what I changed.
8. As a recipient maintainer, I want to know which core revision I have and whether it has been
   edited since, so that "is this current" and "did someone touch it" are two questions I can ask.
9. As a recipient maintainer, I want the arrival checks to run and pass before the install reports
   done, so that a broken install is loud at install time and not at the first `/verify`.
10. As a recipient maintainer, I want no rule to arrive that names a ticket or document I do not
    have, so that nothing in my tree tells the agent to wait for something it cannot see.
11. As a recipient maintainer, I want a straw dog's *content* to arrive as an ordinary rule, so that
    the rule still governs and only the expiry I could never observe is gone.
12. As a recipient maintainer, I want a stated shape for sending a change back to core, so that
    "we'll upstream it later" has a file to land in rather than a hope.

**An agent session in a recipient** — the reader of the installed text.

13. As an agent in a recipient, I want a project's answer to reach me in the skill that needs it, as
    an installed block, so that I never resolve a path into a `docs/` the project does not have.
14. As an agent in a recipient, I want core's rule and the project's override in the same skill with
    the override last and citing the rule, so that I follow the project's answer and can see why
    it differs.
15. As an agent in a recipient, I want the entry file to tell me that a local rule change goes in the
    local file, so that I never write one into a skill body where the next deploy erases it.
16. As an agent in a recipient, I want the local file to be the only place local content is authored,
    so that a hand-edited block in a skill is a diagnostic and not a second opinion.

**The core maintainer** — this repository.

17. As the core maintainer, I want a check that fails at home on any reference from core into the
    instance half, so that the next port finds nothing that a link resolver could have found here.
18. As the core maintainer, I want the exemptions — path conventions the harness imposes — stated as
    one list the check cites, so that "explained or accounted for" is a rule and not a review.
19. As the core maintainer, I want this repository to be the first recipient of its own installer,
    converting its eight `<project-local>` blocks to the local file, so that the design is exercised
    where a defect is cheap before it is exercised where it is not.
20. As the core maintainer, I want the revision computed with line endings normalised, so that a
    Windows checkout is not reported as forty-one edits.
21. As the core maintainer, I want the manifest — what ships — to be gated by which skills are
    claimed by a mechanism or allowlisted, so that "what ships" and "which skill is claimed" stay
    one question with one owner.
22. As the core maintainer, I want the installer to refuse a workspace-level layout rather than
    guess, so that the case for one harness over several children is decided when a second project
    needs it and not by accident.

**A host** — Claude Code, Codex, Cursor.

23. As a host, I want the loader link to resolve to a directory of `SKILL.md` files, so that what I
    load is what was installed.
24. As a host, I want the fact that I read the link at all to be recorded as unverifiable from inside
    the tree, so that nobody mistakes a resolved link for a loaded skill.

## Implementation Decisions

### Ownership: one axis

Core owns every slot it installs into. What differs is who owns the content in it. Core's content in
core's slot — an installed rule — is overwritten on redeploy, and that is the point. The project's
content in core's slot — an answer or an override — is preserved on redeploy, and the installer that
overwrites one must never overwrite the other. *(The user, 2026-09-10.)*

A second axis, who owns the slot, was adopted and retracted the same day: it rested on the loader
link read as a seizure, and the user ruled repointing correct. Recorded on `.0110`.

The harness asks the instance to run its loop; that is the whole purpose. The instance may override,
and the override survives. An override that cannot be written is a rule that gets silently dropped —
frost_map is the case.

### The local rules file

One file per instance. It lives **outside the core directory**, beside the entry file, because a
redeploy that replaces the core directory wholesale would otherwise delete the file that restores the
local content. Its entries are in **installed-rules format** — the same target-and-anchor grammar
the mechanism rules files use — and the injector installs from it exactly as it installs from a
mechanism's rules file, as one more source.

- **Rules only.** Nothing else needs injecting; `commit=ask` is a rule. *(The user.)*
- **Both install, local last.** A skill may carry core's block and the local block. A local entry
  that overrides a core rule **cites that rule's id**, so the override is explicit and auditable
  rather than positional. *(The user.)*
- **`<project-local>` is retired.** Instance content reaches a core file only as an installed block
  owned by the local file. The tag stops being something an author writes, and the *Core and
  instance* exemption that let such a block carry a `docs/` reference goes with it.
- **A tier-1 rule** in the entry file requires every local change to a rule to be written in the
  local file. It is enforced by the existing check, which already fails on a block that differs from
  its source and on a block nothing owns — so obedience is not the mechanism.
- **The file's name, its grammar beyond the rules-file format it reuses, and how the injector tells a
  local block from a mechanism's are the RFC's.** *(The user, 2026-09-10.)*

### The precondition: core stands alone

Every reference from core into the instance half is accounted for and **none survives deployment
unless it is a painted door** — a path convention the recipient creates for itself
(`docs/tickets/`, `docs/glossary.md`, `docs/adr/`, and their siblings). *(The user, 2026-09-10.)*
The 2026-09-10 probe over core puts the split at 47 painted doors against 27 references to a
particular document, and the 27 go *(counts corrected 2026-09-14; the first read-out said 52 and
22)*. This is [01-0010.0140](../tickets/done/01-0010.0140-core-stands-alone.md)
and it blocks both owning tickets. Of the 27, eleven are `not yet` referents whose form
[01-0011.0050](../tickets/done/01-0011.0050-shape-checked.md)'s align decides — two core documents
contradict each other there, and that ticket says which gives.

### What the installer does, in order

One mechanism, relying on the injector rather than owning localisation. *(The user, 2026-09-10.)*
Manifest-and-revision does not separate from loader-links: neither is useful alone, and the first
real install was one person doing one sequence and failing inside it twice. The seam is preserved:
what would split it is a recipient needing to re-link without re-installing, or the reverse, and
nothing does today.

1. **Refuse a target it cannot satisfy.** One installation is one tree: the core directory sits
   directly under the directory holding the entry file, because every script computes its root as
   two levels above itself with no override. A workspace holding several projects is refused, not
   guessed at. *(The user, 2026-09-10.)*
2. **Copy the manifest.** What ships is what the allowlist and the mechanism parts tables name;
   `.0050` gates it. **Amended at `.0130`'s `/implement`, 2026-09-21: `.0050` built no allowlist
   — every skill claims or is named, checked at the origin — so the manifest is every file under
   the core directory at the ref plus the entry file and the host stub.**
3. **Record the revision.** Two facts: the **source commit** — provenance, what this was installed
   from — and a **content hash over the manifest with line endings normalised** — integrity, whether
   the copy has been edited since. A commit hash alone cannot answer the second; a content hash
   alone reports a Windows checkout as forty-one edits. *(The user proposed the first; the second is
   the align's correction from evidence.)* **Amended 2026-09-20 at `.0130`'s second align *(the
   user)*: the source is a repository cloned at a ref, never a working tree, so integrity is asked
   of the source rather than of a stored hash — the recipient's announce line carries
   `<repository>@<ref>`, and the check clones that ref again and compares, line endings normalised.
   No record file is written. The decision is on the ticket.**
4. **Make the loader links.** A symlink, or stop and escalate. No junction, no copy, no substitute:
   nothing sees through a junction and the shared corpus view double-counts under one. *(Binding,
   the user, 2026-09-09.)* Repointing an existing link is correct. *(The user, 2026-09-10.)*
   **Amended 2026-09-21 *(the user, on ADR-0003)*: the escalation is the exact elevated command
   in the report, and the run finishes everything else first; arrival stays false until the link
   resolves. Nothing is substituted. Both links are needed, observed the same day.**
5. **Install the entry file.** `AGENTS.md` and each host's entry stub become parts of this
   mechanism. Two consumers already want to inject into the entry file — this design's local file,
   and [01-0017.0010](../tickets/01-0017.0010-terms-defined-before-they-land.md)'s tier-1 rule —
   which makes it a target with anchors like any skill.
6. **Shear.** A `<straw-dog>` wrapper is removed and its content stays as an ordinary rule: the
   recipient gets the rule, not a condition it can never observe. *(The user, 2026-09-10.)* Any
   `docs/` reference the precondition's check would flag is refused here, not repaired here.
7. **Inject.** Mechanism rules files first, the local file last.
8. **Verify arrival** — below — and report done only when it passes.

### Verification of arrival

Verifiable from inside the recipient, with one structural exception. *(The user, 2026-09-11.)* The
install's exit evidence: the shipped tests green — the scripts arrived intact; the installed-blocks
check clean — every block matches its source; the recorded revision — what arrived is what was sent;
the loader link resolved — a symlink, resolving, its target holding skill files, which is the check
the one silently-wrong link never met. The exception is whether the host *reads* what was installed;
nothing inside a tree can observe what a host puts in front of an agent, and that is
[01-0010.0120](../tickets/01-0010.0120-host-delivery-surfaces.md)'s.

The shipped suite is in the recipient's default verification set, because a recipient's first run of
it is its arrival check; a recipient that does not want it on every `/verify` overrides, and the
override survives. *(2026-09-11, following from the override rule.)* **Superseded 2026-09-20 at
`.0130`'s second align *(the user)*: there is no default set and no rule to override — the
project's verification set is the project's, defined generically in `/verify`, and core checks
itself through the harness mechanism's own check, which a recipient may list in its set. The
decision is on the ticket. And at the live run of 2026-09-21 *(the user)*: the shipped suite is
not part of arrival at all, since it costs minutes and an install is seconds; nor is the loader
link, which the report names as resolving or pending and never lets decide the verdict.**

### Core's record formats and the recipient's loop

A core record format may demand a field — the harness asks the instance to run its loop — and the
instance may override it. The `tickets.py` case is the first override this design must be able to
express: a project whose delivery state lives elsewhere says so once, and the check reads that answer
rather than failing seven times and being switched off.

### Modules

Sketched for the RFC, not decided here. Each is a deep module: one interface, testable in a
temporary tree, rarely changing.

- **The installer** — one command with install, update and check; the sequence above. Relies on the
  injector and the arrival checks; owns the manifest, the revision, the links, the entry file and the
  shear.
- **The injector, extended** — reads the local file as one more source, installs its blocks after
  every mechanism's, validates that an override cites an id.
- **The revision** — normalised content hash over a manifest, plus a recorded source commit;
  written on install, compared on update and on check.
- **The shear** — a pure transformation over shipped text: wrapper off, content kept.
- **The core-stands-alone check** — `.0140`'s: every reference out of core classified against the
  exemption list, a diagnostic for any that is not a painted door, in the verification set.

## Testing Decisions

A good test here builds a temporary tree and observes what the tool does to it — never reads the
tool's internals. Prior art is the whole existing suite: every case in `.agents/scripts/test/`
stamps its own repository from a template and asserts on files, exit codes and JSON output.

- **The installer** is tested into an empty temporary tree: it lands the manifest at the defined
  place, refuses a wrong target, records the revision, makes the link or stops, and reports done only
  after the arrival checks pass. An update over a tree with a populated local file leaves that file
  byte-identical and restores its blocks.
- **The injector's local source** is tested the way its mechanism sources are: install, check, drift
  detected, retract leaves the target byte-identical; plus the new case — a local entry that names a
  core rule id lands after that rule's block, and one that names nothing is refused.
- **The revision** is tested on the one fact that found it: a tree whose only difference is line
  endings hashes equal; a tree with one byte changed does not.
- **The shear** is tested on content: a wrapped rule comes out unwrapped and otherwise identical; a
  nested wrapper is handled or refused, never half-done.
- **The core-stands-alone check** is tested in both polarities: a planted reference outside every
  exemption fails the run; a path convention does not; a `docs/` link inside a `<straw-dog>` fails
  too *(the user, 2026-09-20, at `.0140`'s align — this bullet had exempted it in the source tree,
  which only deferred the failure to step 6's refusal)*; content inside an instance-owned block is
  skipped.
- **The first slice** — this repository converting its own eight `<project-local>` blocks — is
  graded by the checks going green here with the tag gone, and by the local file's blocks being
  installed, checked and retracted by the injector like any mechanism's.

## Out of Scope

- **The host delivery surface** — what each host puts in front of an agent without being asked —
  is [01-0010.0120](../tickets/01-0010.0120-host-delivery-surfaces.md)'s. This spec owns the loader
  *link* only.
- **The allowlist** that gates the manifest is [01-0011.0050](../tickets/done/01-0011.0050-shape-checked.md)'s,
  as is the form of a `not yet` referent.
- **The injector's existing contract** in [architecture.md](../architecture.md#installed-blocks) —
  extended by one source, not reopened.
- **Contribution back.** Parked with a shape the user named: a rule copied into every instance that
  a change to a skill is written as a pull request into core, a `pull-request.md` in a named
  directory to begin with. Under the shear it arrives as a plain rule. The parent's promise, not
  this spec's build.
- **A workspace-level harness** — one installation whose children own none. Recorded on `.0130` as
  a case worth seeing; refused by the installer until a second project in one workspace needs
  different switches or a different verification set. Where children share one `docs/`, one queue
  and one set of switches they are one project in several directories and this spec already covers
  them.
- **The entry-contract version.** Its hand-bumped number is scaffolding the user has called a straw
  dog; its successor is the revision this spec records, and retiring it is `.0130`'s decomposition
  to place.

## Further Notes

**The recipient already exists and has already disagreed.** frost_map merged the probe to `main`
on 2026-09-09, tracks the loader links deliberately, calls the arrangement vendored, and refused
`tickets.py` in a commit that cites core's own one-home-per-fact rule. This spec is aligned after
that adoption, not before it, and its first real test is an *update* into a tree with a history,
not an install into an empty one.

**Two rules that were true of one shape.** The straw-dog exemption in *Core and instance* was
granted because a dog "is bound to a ticket and expires" — true here, false in every recipient. The
`<project-local>` tag was the designated place for local facts, which is exactly what let another
project's facts look legitimate when they arrived inside one. Both are retired by this design rather
than patched.

**The probe's arithmetic, corrected 2026-09-11.** The 35 day-one diagnostics are `mechanisms.py`'s
14 plus `tickets.py`'s 21; the 14 straw dogs are a listing, not diagnostics, and the four bare
`docs/process.md` links in `/verify` and `/implement` are in neither count. Re-measured in the
recipient tree; corrected on the probe record and its two echoes.

**Where the eight blocks here go.** `AGENTS.md` carries three — the glossary split, the note that
this repository's `docs/` is the instance half doing its job, and the five switches; the three
mechanism docs carry their evidence paths; `/maintain` carries the verification set and two
architecture links; and `MECHANISM-FORMAT.md` carries one that is not a local fact at all but a
template line wearing the tag, which the conversion retires as a mis-tag. The blocks sit outside
`.0140`'s count — the probe masked them — but the three evidence bullets and `/maintain`'s three
links are the same kind of reference, and converting the blocks is what makes them injectable
rather than authored.
