# Every written thing has a source of truth

"What kinds of written thing does a tree hold, and which of them does /maintain hold in

[q-0030](../questions/q-0030-how-does-a-reply-show-the-principles-each-of-its-claims-stands-on-and-where-are-the-principles-named-for-it.md)
"How does a reply show the principles each of its claims stands on, and where are the principles
named for it?" — whose decisions and the `/impact` of the same day sit in those entries' bodies.
A child of [the mechanism shape](01-0011-mechanism-shape.md): it amends what a mechanism declares
of its records. Acceptance is the user's; decomposition is `/ticket`'s.

## Problem Statement

The tree holds many written things — architecture, mechanism docs, tickets, the queue, RFCs,
question entries, session records, evidence, marks, research — and treats them by their role:
documentation, record, evidence. That sort says who writes a thing and under what format. It does
not say **who is right when the written thing and the thing it is about disagree**, and so it
does not say which way a repair goes. `/maintain` holds *docs to their implementation, both
ways*, and *both ways* is where two opposite repairs hide: a doc the code must obey, repaired at
the code; a doc that describes the code, repaired by regenerating it. With no sort to say which
is which, the agent decides by feel, and the records drift into mixtures:

- the queue carries a two-page *completed step* narrative that the session records already hold,
  a candidate, and a table copied from ticket headers — three sources of truth in one file, each
  repaired differently, none of them marked;
- a ticket carries its outcome and criteria, the decisions its align landed, and the story of what
  went wrong, and when it closes someone has to sort the three by hand;
- ai-game-1's verification set was a copy of core's command list in a rules file, and broke at the
  first move of the scripts it named; the tree had no way to say that a command list is derived
  from the tooling and should never be a hand-held copy;
- three recommendations in one day's align were overturned by one sentence each, because each
  stood on the absence of a recorded failure — and nothing in the reply showed what it stood on.

The last is a second face of the same problem. A reply is written for a reader who thinks in
pictures and reads a glyph before a sentence. The turn's rows already show which *question* a
reply stands on; nothing shows which *principle* a paragraph reasons by, which *classification*
it sorts by, or which *record* it rests on. The principles themselves have three homes and no
names, so they cannot be cited, and a reply that stands on none of them looks exactly like one
that does.

## Solution

**Every written thing is sorted by its source of truth**, on two axes: which side is right when
the record and the thing it is about disagree — the record, the thing, or neither — and whether
the record's authority expires once the thing reaches it. Four kinds follow:

| kind | source of truth | repair when they disagree | examples |
|---|---|---|---|
| **what it intends to become** | the record, until reached | the thing moves toward it; the person refines it | ticket, RFC, spec, open question's lean |
| **what must always hold** | the record, standing | the thing is repaired to it; the record changes only by decision | architecture, mechanism doc, the verification set, glossary |
| **what exists** | the thing | the record is regenerated from the thing | queue table, marks, a `--check` report |
| **what happened** | neither — the referent is past | never | session record, evidence, `done/` |

A kind is a relation, so a record names what it is a record *of*; where every record of a format
is of one kind, the format says so once; a document with no format says it on itself. The thing
an agent edits carries a mark back to the record of the second kind that governs it, so the
agent meets the invariant where it works; a thing a script derives carries none. The draft
before the sort — the whiteboard — is the body of the question the task stands on, and is no
kind: the ticket is minted from it once the form is seen and holds the first kind alone; the
queue holds the first kind alone, its table rendered; core owns the ticket's contract and the
file is its default form, a project's own board admitted.

**Every paragraph of a reply that claims or recommends shows what it stands on**, under
`debug=on`, before its words: `💡` the principle it reasons by, `🗂️` the classification it
sorts by, `⚓` the footing it rests on; where no principle fits, a boxed line says so, and the
box is the signal that a principle is missing or the reasoning has none. For that, every
principle and every classification an agent applies by judgement carries a name at its authored
home, and the method's glossary says what each is: *an instruction says what to do; a principle,
what to prefer when it is unclear what to do; a classification, where a thing goes when it is
unclear what it is; an invariant, what must hold; a definition, what a word means.*

## User Stories

1. As an agent at `/maintain`, I want each record's kind to tell me which way a disagreement is
   repaired, so that I never regenerate a doc the code should have obeyed, or edit code to match
   a table that should have been re-rendered.
2. As an agent at `/recall`, I want the queue to hold only the order and the candidate, so that
   what I read first is what is next and not two pages of what was.
3. As an agent at `/implement` changing a file, I want the file itself to name the record that
   governs it, so that I meet the invariant without searching the tree.
4. As an agent closing a ticket, I want the ticket to hold nothing but its outcome, its plan and
   its criteria, so that nothing has to be sorted out of it before it is archived.
5. As an agent in an align, I want a place to write everything bearing on the task before its
   form is known, so that nothing is lost and nothing is minted early.
6. As an agent minting a ticket, I want to mint it from the question's body once the form is
   seen, so that a ticket never starts as a draft.
7. As an agent closing a question, I want the close to refuse while a decision in the body has
   no durable home, so that a whiteboard is never archived with a decision still on it.
8. As a reader of a mechanism's doc, I want each output to say its kind beside its reader, so
   that I know whether to obey it, regenerate it, or leave it be.
9. As the maintainer's check, I want the kind of each declared output to be parsable, so that a
   doc that names an output without a kind is a diagnostic.
10. As a project owner, I want my own board — issues, Linear, Jira — to stand in for the ticket
    file where it reads as the ticket's contract, so that the harness fits the tracker I have.
11. As a recipient of core, I want the kinds and the marks to arrive with an update and the
    entry contract to say so, so that my agents read replies and records the same way.
12. As a person reading a reply, I want each claim to open with the principle it reasons by,
    so that I see the reasoning's shape before its words.
13. As a person reading a reply, I want a claim that stands on no principle to be boxed, so that
    the gap is loud and I can name the missing principle or refuse the claim.
14. As a person reading a reply, I want a claim that sorts a thing into a kind to name the
    classification, so that I can check the sort and not only the conclusion.
15. As a person reading a reply, I want a claim to name the record or the word it rests on, so
    that I can follow it to its footing.
16. As an agent writing a reply, I want every principle to have a name at its home, so that I can
    cite it in three words and never paraphrase it.
17. As an agent, I want the method's glossary to tell instruction, principle, invariant,
    definition and classification apart by a test, so that I can place a sentence I am about to
    write and know which mark, if any, it may carry.
18. As a reader of the glossary, I want *documentation, record, evidence, provenance* and the
    four kinds to be one sort or two declared axes, so that one object never has two names for
    the same property.
19. As an agent at `/conclude`, I want the session record to be of the fourth kind and nothing
    else, so that history is never repaired and never duplicated into the queue.
20. As an agent at `/align`, I want the rules that today say *record it in the ticket* to say
    *record it in the question's body*, so that the whiteboard and the rules agree.
21. As a maintainer of the harness, I want a core file never to point into a project's `docs/`,
    so that a mark back from core code goes to its mechanism's doc and a recipient's tree resolves
    it.
22. As a reader of this project's architecture, I want its *Installing* section to point at the
    harness mechanism's doc rather than restate it, so that the install contract has one home.
23. As an agent touching a live ticket written before this spec, I want to bring it to its kind
    at that touch and not before, so that thirty-one tickets are not rewritten in one pass.
24. As a person grading the marks, I want to read replies and say whether the marks were honest,
    so that the rule is graded by its reader and not by its author.

## Implementation Decisions

**The sort, and where it is declared.**

- Four kinds by source of truth, named *what it intends to become*, *what must always hold*,
  *what exists*, *what happened*; the two axes are the definition, and expiry is the test between
  the first two. The method's glossary holds the four, the axes and the test.
- A kind is a relation; every record of a kind names its referent. A format whose every record
  is of one kind declares the kind once, in the format; a document without a format carries its
  kind and referent on itself. Per-record declaration is for formats admitting more than one kind.
- The whiteboard is the body of the question the task stands on. It is no kind; it is sorted
  into kinds. The body's format gains a decisions section the mover and the close respect; a
  `close` refuses while a decision in the body cites no durable home.
- The glossary's roles — documentation, record, evidence, provenance — are reconciled with the
  kinds: a mechanism's doc is of the second kind, its evidence of the fourth, a record of the kind
  its format declares, provenance a part of a rule and no kind. Where a role adds nothing the
  kind does not say, the role goes; where it does — *record* as *written under a declared
  format* — it stays as a second axis and says so.
- The things an agent edits carry a mark back to the record of the second kind that governs
  them: a `TODO`-shaped comment in code naming the doc and its section, the installed block's
  owner in a skill, the straw dog's binding in text — three existing cases, named as one
  convention. A thing a script derives carries none. **Core code marks back to its mechanism's
  doc, never into `docs/`**: the architecture's *Installing* points at the harness mechanism's
  doc instead of restating it.

**The mechanism shape and maintain.**

- A mechanism's format gains the kind of each output in *What it produces, and who reads it*;
  the shape check reads it and reports an output with no kind.
- `/maintain`'s A1 splits *docs to their implementation, both ways* into two repairs by kind:
  the second kind repairs the derivative, the third regenerates the record. The levels and marks
  are unchanged.
- An instruction — a skill, a rule — is the mechanism itself and no record; for the mechanism
  shape, which produces instructions, a skill is a record of the second kind and its invariants
  are `/skill-up`'s.

**The ticket and the queue.**

- The ticket holds the first kind alone: outcome, what to build, criteria, and its header. The
  format's admitted sections lose the decisions section and the narrative; a decision lands
  from the question's body into its durable home before the ticket closes, the story goes to
  evidence or a session record, and the ticket links.
- Core owns the ticket's contract — what a unit of agreed work must state, and that done is
  every criterion holding with verification among them. The file under `docs/tickets/` is its
  default realization; a project's own board is admitted where it reads as the contract, by an
  adapter the project supplies. This spec builds the contract and the seam, not an adapter.
- The queue holds the first kind alone: the order, the candidate, what follows what, hand-written.
  Its table is rendered from the ticket headers — 01-0011.0040's decision, which this absorbs —
  and its counts with it; the completed-step narrative becomes one pointer at the last step and
  its session record; the ordering rule goes to the rules file of the mechanism that owns it when
  one is declared, and stays a straw dog until then.
- `/align`'s three rules that target the ticket — land a resolved decision and rewrite the ticket
  (P7), open on what the ticket is (P10), sweep the ticket (P11) — are retargeted: the draft is
  in the question's body, the ticket is minted from it, and the sweep is of the body.
- Records written before this spec are brought to their kind at their next touch, by
  `/maintain`; the queue first, being one file.

**Names and marks.**

- Every principle carries a name at its authored home — in the entry file's general section the
  bullet opens with it in bold; in a mechanism's doc and the glossary the term is the name — and
  is cited by that name only. The same for every classification an agent applies by judgement:
  the kinds of record, of turn, of statement, of moment; the tiers. Classifications a script
  reads — closure kinds, statuses, mark outcomes — are enums in their formats and need no name.
- The method's glossary rewrites *Principle* and adds *Instruction*, *Invariant*,
  *Classification* and *Definition*, each with the test that tells it from the others.
- Under `debug=on`, a paragraph that claims or recommends opens with the marks it earns, in this
  order: `💡 *<name>*` the principle it is governed by, one; `🗂️ *<name>*` the classification
  it sorts by; `⚓ *<footing>*` what it rests on — a decision, evidence or the user's word, by its
  record or by who and when. Where no principle fits, a blockquote `> ⬜ no principle fits —
  <what it rests on>` stands in place of the lamp. A paragraph that links, narrates or restates
  carries no mark. The rule lives at tier 1, by hand, wrapped as a straw dog bound to q-0030
  until a mechanism owns principles; the entry contract bumps.
- The glyphs are this tree's by its local rule L6's precedent; core states the marks with its
  own glyphs and a project overrides them as L6 does the rows.

**Order of the slices**, from the `/impact`: names first, since every later slice cites them;
the marks second, cheap and the user's first ask; the mechanism shape and maintain; the ticket
and the queue; the mark back on agentic things last, since it resolves the core/instance edge.

## Testing Decisions

A good test exercises what a reader or a script sees — a diagnostic raised or not, a file
rendered or refused — never how the script arrived there. Every scripted check is tested in
both polarities: the diagnostic fires on the defect and stays silent on the repaired file.

- **The shape check** (`mechanisms.py`): an output declared without a kind is a diagnostic; one
  with a kind is not; a kind outside the four is a diagnostic. Prior art: `test_mechanisms.py`.
- **The question store** (`questions.py`): a `close` on a question whose body holds a decision
  with no home is refused with the decision named; one whose decisions all cite a home closes;
  the mover carries the body's decisions section unchanged. Prior art: `test_questions.py`.
- **The ticket records** (`tickets.py`): a section the format no longer admits is a diagnostic
  on a ticket minted after the format moved, and not on one minted before — the grandfathering
  reads the mint date from the header; the rendered table equals the headers it is rendered
  from, and a hand edit to it is reported. Prior art: `test_tickets.py`, `test_paired_close.py`.
- **The installs** (`inject_rules.py`): the marks rule installed at tier 1 round-trips through
  `--check` with a local override of its glyphs. Prior art: `test_inject_rules.py`.
- **The marks themselves** are not tested by a script: the user grades them by reading replies,
  as Q1's rows were graded, and the grade is the slice's last box.
- Modules that take no new tests: the glossary and the names (prose), `/maintain`'s split rule
  (a rule, verified by the next maintenance pass), the mark-back convention (a convention, with
  one repair in `harness.py` verified by the leak check already in the set).

## Out of Scope

- An adapter to any board — GitHub Issues, Linear, Jira. The contract and the seam only.
- Rewriting the thirty-one live tickets in one pass. Each at its next touch.
- A mechanism that owns principles. The marks rule is a straw dog at tier 1 until one is
  incepted, which is q-0030's to decide after the marks are graded.
- The environment mechanism, `docs/cicd.md`'s door and `setup-devops` —
  [q-0018.0022](../questions/q-0018.0022-is-a-projects-environment-its-toolchain-its-checks-its-pipeline-a-mechanism-of-the-method-and-what-does-it-own.md)'s,
  which waits on this spec's names and takes nothing else from it.
- The load-bearing factors' threshold (q-0024.0002.0001) and the abstraction heights (q-0007):
  classifications named here as open, not settled.
- The rule on who may change the verification set — the environment's.

## Further Notes

The sort was not designed; it was found. The user raised it when *an agent can read the files a
month later* argued against an architecture doc exactly as it argued against a description of
the environment, and the four kinds came out as four reasons a document exists, each drifting a
different way. Two pairs the tree already held apart — a mechanism's doc from its evidence, and
the queue's table from the tickets it copies — are the two shapes that force the generalisation.
The marks are the same move turned on the reply: the row names the question a turn stands on;
the lamp, the folder and the anchor name what a paragraph stands on. The user's three
corrections that shaped them are in q-0030's body, in their words.
