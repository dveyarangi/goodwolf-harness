# A first install says what actually stopped it — implementation plan

**Last amended:** 2026-10-06

- **The install contract** — [architecture § Installing](../../architecture.md#installing): every

- **The harness mechanism** — [its doc](../../../.agents/mechanisms/harness/harness.md): *making a

- **The tree's own copy is a run's home** — the skill already says a check or an update runs from

## `/impact`, 2026-10-06

**Impact.** `harness.py`: the work-tree check, the argument parser and its usage, `main`'s
source-less branch, the link step's notes. Its suite: a refusal case, a command-line case, the
link cases, and the install case that reads the notes. The harness skill: the usage block, the
refusal list, when to run `--links`. The installed tree's README and the front page: one sentence
each, both straw dogs bound to this ticket's question. The harness doc: the fourth command in its
instruction line.

**Hidden edges.** The suite patches the Git runner with a stub for in-process cases, so an
ownership refusal can only be proved on a real-process case. `Report.arrived` is the gate's
verdict and nothing else's; a mode that runs no gate must not print it as `false`. `--links` has
no source, and the work-tree check today takes one to refuse the origin as target. The pending
note tells the person to run `--check` afterwards, which needs the network; `--links` can
confirm offline. `_git_in` discards stderr, which is where Git names the ownership cause.

**Leave alone.** `arrived` and the three gates. The junction refusal and the refusal of a file or
directory where a link goes. The repoint-by-swap. The origin's `.gitignore`, which does not ship.
The empty-folder bootstrap, which is 01-0010.0170's.

**Recommendation.** Proceed. Each piece is demonstrated by issue 1 and again by the workshop
update of 2026-10-04; no new abstraction is introduced — the mode reuses the link plan, the
making and the resolve check as they stand.

## What changes, by boundary

### The ownership refusal

`_work_tree_root` reads a failed `rev-parse --show-toplevel` as a wrong shape. It will read Git's
stderr: when it names dubious ownership, the refusal is
`target: Git refuses <target> for dubious ownership — <Git's own safe.directory command>; run it,
then run again`, the command taken from Git's message, which prints it on its own line. Any other
failure keeps today's wrong-shape refusal. Nothing is written in either case, as before, since the
check runs before anything else.

Local choices: how stderr reaches the check — a second runner beside `_git_in`, or `_git_in`
returning both — is `/implement`'s; `_git_in`'s callers keep their contract.

### The fourth mode

`harness.py <target> --links`, with no `--from`, `--at` or `--overwrite`; usage otherwise.

- Runs with no source: `main` does not open a `Source` or read `home()` for it. The work-tree check
  runs without the origin test, which needs a source and guards a copy, not a link.
- Refuses a tree that holds no core: `links: <target> holds no <SKILLS> — --install first`, before
  anything is written.
- Then the link plan, the making with its elevated fallback, the exclude entries, and the resolve
  check, exactly as an install runs them.
- Its report carries `links`, `pending`, `excluded`, `links_resolve`, `notes` and `refusals`, and no `arrived`,
  `ref` or `gates`: no gate ran, and the gate's verdict is not a link's to print.
- Exit status: 0 when nothing is pending and nothing refused; 1 otherwise. A pending link is an
  accepted state, and a non-zero exit is how a caller learns the person has a step left.

### The exclude entries

Whatever plans a link names it in the clone's exclude file: for every link the plan holds — made,
repointed, kept or pending — the line is present once in the file Git names by
`rev-parse --git-path info/exclude`, created if absent. Idempotent; a line already there is not
repeated. A pending link is excluded too, so the person's later `mklink` is excluded before it
exists. Install, update and `--links` all do it, since all three plan links.

### The notes

- The pending note becomes: *run the pending command(s) once in an elevated prompt, then
  `harness.py . --links`, which reports whether each resolves* — offline, where `--check` clones.
- The `core.symlinks is false` note and its `TODO` go: nothing is tracked, so no clone checks a
  link out as text.
- The `TODO` on the ownership refusal goes with the refusal that answers it.

### The words

- **The harness skill:** the usage block gains
  `python <target>/.agents/scripts/gw/harness.py . --links`; a line under *Run the script* says a
  fresh clone of a project holding core runs it once; the refusal list gains *Git refuses the
  target for dubious ownership* with what the person does, and its pending-link bullet says
  `--links` confirms.
- **The installed tree's README and the front page:** their straw dogs bound to this ticket's
  question are rewritten to *a fresh clone gets them by running `harness.py . --links`* and
  unwrapped, since nothing then waits.
- **The harness doc:** its instruction line names the fourth command; its moments table is already
  right.
- **The architecture § Installing:** one clause, that a clone gets its links from `--links` without
  a source, beside the sentence that says the links are made in each clone.

## Stages, by `/tdd`

Each stage lands red then green and leaves the suite green.

1. **The ownership refusal.** A real-process refusal case runs the install with
   `GIT_TEST_ASSUME_DIFFERENT_OWNER=1` in the child's environment and asserts the refusal names
   dubious ownership, carries `safe.directory` and the target's path, and that nothing was
   written. Then the check reads stderr. The `TODO` on it goes.
2. **`--links`.** Command-line cases: `--links` with `--from`, `--at` or `--overwrite` is usage.
   An install case, then `--links` on the same tree: links kept, report without `arrived`, exit 0
   where the platform makes symlinks and 1 with two pending commands where it does not — read from
   a run, as the install case already does. A tree without core is refused with `--install first`.
   A `--links` run opens no source: the case proves it by giving no `--from` and no reachable
   repository line.
3. **The exclude entries.** A real-process case installs and asserts `git check-ignore` accepts
   both link paths and that a second run leaves the file with each line once. A case where the
   platform refuses the symlink asserts the pending link is excluded too.
4. **The notes.** The install case that reads the notes asserts the pending note names `--links`
   and that no note names `core.symlinks`; the `TODO` goes.
5. **The words.** The skill, the two READMEs, the harness doc and the architecture; the straw
   dogs unwrapped. The verification set, then `/verify`.

## Resolved at `/plan`

- **A mode without a source, through a check that wants one.** `_work_tree_root` takes a source to
  refuse the origin as target. The origin test guards copying core into itself; `--links` copies
  nothing. The check takes an optional source and skips that test without one. Not a new shape:
  the function already does two things.
- **`arrived` on a report with no gate.** Printing `arrived: false` would read as a failed install.
  The report of `--links` omits it. `Report.as_record` stays one dict; which keys a mode prints is
  local.
- **Where the exclude file is.** Not `.git/info/exclude` by path: a work tree made by `git
  worktree` has its `.git` as a file. Git names the file; the script asks it.
- **The suite's stubbed Git.** In-process cases replace the Git runner with a stub that answers
  only `rev-parse`; the ownership case and the exclude case are process cases, where Git is real.
