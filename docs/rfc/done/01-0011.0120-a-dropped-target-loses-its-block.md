# A rule's block leaves a file once its rules file stops naming it — implementation plan

**Authored:** 2026-10-10

Implements [01-0011.0120 a-dropped-target-loses-its-block](../../tickets/done/01-0011.0120-a-dropped-target-loses-its-block.md).

## Governing decisions

- [Architecture — Installed blocks](../../architecture.md#installed-blocks): one generic installer;
  it validates every target before writing anything and a refusal changes no file; retraction
  removes exactly what installation added; a block nothing owns — its owner has no rules file, or
  that file does not name the file the block sits in — is a diagnostic of the check.
- The ticket: installing removes the installing source's own blocks from files it no longer names,
  and says which *(the user, 2026-10-09)*.

## Shape

`install` plans, beside each named target, every other file of the tree holding a block of its
own slug — found the way the check finds a block nothing owns, over the same listing — and plans
its removal with `without_block`, the retraction's own cut, so the file returns to what it was
before that block was installed. The removal is planned with the rest: any refusal, on a named
target or on a dropped one (a block that never closes, one not spaced as the installer writes it),
writes nothing anywhere. The report names each with the state `removed` and the text it held, as
an overwrite names what it replaced — the block is installed, never authored, so nothing is asked
first, and the person still reads what left.

Only the installing source's slug is touched. A block of another source, or of a slug with no
rules file, stays what the check reports.

One sentence lands in the architecture's *Installed blocks*: installing a rules file also removes
its blocks from files it no longer names.

## Impact

**Impact.** `inject_rules.install` gains one planning pass over the listing; `--retract` and
`--check` unchanged; one sentence in the architecture; tests.

**Hidden edges.** The listing is Git's, so a block in an ignored file is neither found by the check
nor removed — the same blind spot, kept consistent. Retracting a slug walks its named targets only;
a dropped target's block outlives a retraction until the next install. A recipient's local file is
installed by the harness on every update, so the update now clears a target the local file dropped.

**Recommendation: proceed.**

## Stages

1. `test_inject_rules`: a target dropped from the rules file loses its block on the next install,
   is byte-identical to its state before the first install, and is named `removed` with its text;
   `--check` then passes; a block of a slug with no rules file in that file stays; a refusal on a
   named target leaves the dropped target's block in place. Then the pass in `install`.
2. The architecture's sentence; the verification set.

## Out of scope

- Retraction clearing a dropped target — no case asks for it yet.
