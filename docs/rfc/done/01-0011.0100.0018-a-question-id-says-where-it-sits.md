## The shapes

### The id

`q-NNNN(.NNNN)*`: four digits per level, as ticket positions are. Every pattern that reads an id —
the title, the file name, a relation, a session line, a call's argument — takes the nested form.
The store's order is the id's levels compared as numbers, so a child follows its parent and
precedes the parent's next sibling: the listing, the window's lines and `--tree` read in tree
order.

A new id takes the next free position at its level — under its parent, or among the roots — over
the live store and `done/` together: the highest position there, rounded down to ten, plus ten,
as ticket positions step. The first child is `.0010`. A flat id from before ids nested counts at
the root level until a rename gives it its place. A level whose next position would pass `9990`
refuses the call: four digits
are the form, as they are for tickets. An id freed by a rename may be handed out again; nothing forwards it
(decision 6), and the commit messages and transcripts that hold old ids are not rewritten.

### A rename

`move q-K --under q-P`, `move q-K --to-root` and `open … --between q-U q-L` rename the subtree that
moves: the moved question takes the next free position at its new place, and each question below
it keeps its own last position under its renamed parent — `q-K.0020` becomes `q-NEW.0020` — unless
its id never had one, as the store's flat ids today, in which case it takes the next free position
there. The subtree includes entries in `done/`, which keep their folder. A `move` to the parent a
question already has renames it only if its id disagrees with that parent; otherwise it writes
nothing.

One call does, in order:

1. **Validate whole, in memory** — the draft applies the clause, gives each moved entry its new id
   and record path, and rewrites every id the store's entries hold in *part of*, *depends on* and a
   *merged* or *superseded* answer; then the interference recheck over every entry it changed,
   with every id the rename gives checked still free as an opened one is — so two sessions
   renaming under one parent at once draw again rather than collide — and the mover's own
   `refusal` over the renames. Any refusal writes nothing.
2. **Write the entries** with their new ids, at their old paths.
3. **Move them** with the mover's `perform`, in one invocation, which repairs every link to them
   across the tree and re-aims theirs.
4. **Rewrite bare ids**: every renamed id written outside a link, in the records under `docs/` —
   the entries' bodies among them — and in the sessions file's positions and recent lists, each
   file re-read just before its write and replaced in one rename. An id is matched whole: never
   inside a longer id, never a prefix of one. It is rewritten wherever it is written, code spans
   and fences included: an id in the rename's map names this store's question, unlike a link
   the mover leaves alone in a fence. `.agents/` and the entry file are left alone: core names no
   record of this tree, and the ids its rules show are examples.

The call prints each rename, `renamed q-K → q-NEW`. A failure after step 2 stops and says what was
written, as `WriteInterrupted` and the mover's `CloseInterrupted` do today; nothing is rolled back,
and `--check` names what disagrees. Steps 3 and 4 write files outside the recheck, as the mover
already does; a person editing the same record at that moment can lose the race.

The function that moves entries with the mover is the seam `.0020`'s move at closure reuses.

### A stale id

A call naming an id no entry holds is refused: *no entry holds q-K; an id changes when its question
is re-parented — draw the window again, `--window --session <tag> --full`*. Nothing is written.

### The check

`--check` reports an entry whose id disagrees with its *part of*: a child whose id is not its
parent's id and one more position, and a root whose id is nested. The renamed store passes.

### The path

`PATH_LIMIT`, 259 characters of absolute path — Windows' limit less its terminating null — is
measured for the entry's place in `done/`, the longer of its two homes. A slug that would pass it
is cut at a word boundary until the path fits; the id is never cut. The filename check accepts
such a cut: the slug is the whole question, or a word-boundary prefix of it that is the longest
fitting at this root.

### The texts

- The questions skill: *The id is placement and never hierarchy* becomes *the id is the place: a
  root `q-NNNN`, a child its parent's id and one more position; a re-parent renames the subtree*;
  the record example's ids nest; the call table's `move` and `--between` rows say they rename the
  subtree; `--help`'s id form.
- The questions doc: the `Store` and relation lines that say an id is placement and never a path.
- The script's docstrings saying the same.

## Stages

Each stage keeps the verification set green.

1. **The grammar and the order.** Tests: a nested id reads in a title, a file name, a relation and
   a session line; a malformed one is still refused; the tree draws a child after its parent and
   before the next root. Then the patterns and `_order`. Flat ids still read, so nothing else
   moves.
2. **Opening.** Tests: `open --under q-P` gives `q-P.0010`, then `.0020`, counting a child in
   `done/`; a root takes the next ten past every root-level id; a level past `9990` is refused;
   two sessions opening under one parent at once take `.0010` and `.0020`. The base fixture's
   child is nested; the rendered fixture keeps the flat ids a store held before decision 6, which
   still read — its window, wake and tree expectations stand — and its open, move and between
   tests expect nested ids.
3. **The rename.** Tests: a `move` renames a subtree of three levels, one of them in `done/`, and
   keeps each descendant's position; a ticket's link to a moved entry resolves; a bare id in a
   ticket's prose and in an entry's body is rewritten while a longer id that starts the same way
   is not; another entry's *depends on* and another session's position and recent list name the
   new id; `--between` renames the lower subtree under the new question; a `move` to the parent a
   fitting question already has writes nothing; a mover refusal writes nothing at all.
4. **The path.** Tests, with `PATH_LIMIT` patched small: an opened question's slug is cut at a word
   boundary to fit, the id whole, and `--check` passes it; a rename that deepens past the limit
   cuts the same way.
5. **The store renamed.** On this tree: one `move q-X --under <its parent>` for each topmost entry
   whose id disagrees with its parent — its subtree follows — each a recorded call; then every
   link resolving and the verification set green. It precedes the check, which would otherwise
   report the live store.
6. **The check and the stale id.** Tests: a child whose id is not under its parent's, and a nested
   root, are reported; an orphan's id is not judged, since its parent is already reported missing;
   a call on a renamed-away id is refused with the redraw instruction and writes nothing. Then the
   check, which passes the renamed store.
7. **The texts**: the skill, the doc and the docstrings; the skill's record example takes ids the
   store does not hold, nested.

## Impact

### Impact

- **Must change:** `questions.py` — the five patterns, `_order`, `_next_free`, the draft's
  `_opens` and `_moves`, `_existing`'s refusal, `_name_problems` and `_slug`, a new check for id
  against parent, and the rename's write path; `test_questions.py`'s fixtures wherever a child is
  built with a flat id, and the rendered expectations that print those ids; the questions skill
  and doc.
- **Must verify:** the mover called as a function keeps its contract — preflight, one invocation,
  nothing staged; the window, the wake, the hook and `--tree` render nested ids in tree order; a
  `Taken` retry under one parent draws the next position.
- **May simplify:** `_files_holding`'s glob, `{id}-*.md`, stays exact: a nested id's file starts
  with a dot after the parent's id, never a hyphen.

### Hidden edges

- **Every session's window redraws once** after a rename, since its fingerprint keys on names.
- **Other sessions' positions** are rewritten in the sessions file by a session that does not own
  those lines — the one write that crosses lines. It re-reads just before its write and replaces
  only ids, never a line's tag, state or date.
- **History rewritten.** Session records, done tickets and RFCs, the dreams and the findings
  record name questions by id; step 4 rewrites them, as the mover rewrites their links.
- **`.0020`'s RFC** names the store's entries by id in its fold tables; step 4 rewrites them.
- **An id written as an example is rewritten too.** Step 4 cannot tell a reference from an
  illustration: a flat id used as an example, or a range such as *q-A to q-B*, comes out naming
  real nested entries or reading oddly. Observed on this store's own rename — a done RFC's sample
  entry and this RFC's order example; this RFC's were repaired by hand, the done records left as
  rewritten.
- **Recipients** have no store yet, so nothing of theirs is renamed; their first entries are born
  nested.

### Leave alone

Ticket ids. The window's contents and form. The strike stamps, which move with their entries. The
sessions file's form apart from the ids it holds. `.agents/`'s example ids.

### Recommendation

Proceed. The rename is the one new flow; it reuses the mover for files and links and adds only the
id map and the bare-id pass. Narrowing considered: leaving bare ids in prose stale — refused by
decision 6, which counts them in the rename.

## Limits and follow-ups

- An id freed by a rename may come back on another question *(the user, 2026-10-03: renames are
  rare)*; a new id never collides with an entry live or in `done/`. An old commit message naming
  a freed id then reads wrongly, and — the one risk that is not cosmetic — a stale id in another
  session's context lands silently on the question it went to instead of being refused. Deferred
  as q-0001.0130; when it strikes, the remedy is designed afresh.
- Ids inside fenced blocks are examples and are never rewritten *(the user, 2026-10-03)*; the one
  sample the store's rename had rewritten, in `.0010`'s RFC, was restored.
- A person editing a record, or a second rename rewriting the same record's bare ids, while a
  rename runs can lose the race: each file is re-read just before its write, which narrows the
  window and does not close it, as with the mover today.
- A deeper clone path than this one shortens what fits; a slug cut here may be cut further there.
