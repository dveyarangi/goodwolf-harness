## What governs it

[q-0036.0004's decision](../../questions/done/q-0036.0004-how-do-session-lines-written-at-once-all-survive-when-the-harness-locks-nothing.md#decision):
one folder shared by all sessions, `docs/questions/sessions.d/`, a file per session named by its
tag; a store holding the single file carried over at its first write. The questions mechanism's doc and skill state the folder.
[Interruption and recovery](../../architecture.md#interruption-and-recovery): nothing is locked.

## The change, in `questions.py`

- **Reading.** `_sessions` reads the folder: each file one line in today's form, its tag the
  file's name; a file of another form, or naming another tag, is a diagnostic on that file, and one
  not UTF-8 is skipped and reported, as the single file was. A store still holding the single file
  is read with it: its lines stand for the sessions that have no file yet. Sessions are listed by
  when their line was last written, then by tag. A `Session` remembers the record it was read from,
  so the check names the session's own file or the single file's line.
- **Writing.** `_write_line` writes the session's own file through a staging file beside it and
  one rename. The only writes to another session's file stay the two there are today: the wake
  ending a silent session, and a rename rewriting ids.
- **Carrying over.** The folder has its own name, beside the single file, so the two never share a
  path. At a write into a store that holds the single file, the writer places each of its lines in
  that session's file by a link that refuses an existing name — a session that wrote its own file
  since is newer, and a line is never half-written — then removes the single file. Every step may
  run twice at once and lands the same. A line the form does not admit is kept under a name of its
  own, for the check to report. Where Windows refuses the removal because a reader holds the file,
  it is left: every line is shadowed by its file, and the next write removes it.
- **Renames.** `_records_naming_ids` names each session's file; `_rewrite_ids` treats them as it
  treated the single file.
- The docstrings that describe the single file say the folder.

## Stages

1. **Red.** `test_questions.py`: twenty registrations started at once, on threads released
   together, leave twenty sessions; today some are lost. Two first writes at once over a store
   holding the single file keep every line it held and both new ones.
2. **Green.** The folder read and written, the carry-over.
3. **The suite moves to the folder.** The tests that read the sessions file whole read the folder
   through one helper that gives its lines in the store's order; those that write the single file
   to set a case up keep doing so, which proves the legacy read and the carry-over on every one of
   them.

## Impact

**Impact.** `questions.py`'s sessions read, write and rename paths; `test_questions.py`.
`mechanisms.py`'s painted door already names the folder. **Hidden edges.** Every installed tree
holds the single file and is carried over by its first session after the update, in place; a
folder at the single file's own path would have made that carry-over a rename that races a second
writer's, so the folder is named apart (amended at implementation, 2026-10-13). A case-insensitive file system folds two tags differing by case into one file; host ids are not
cased that way. The committed tree changes shape once: the conclude stages the folder by the same
path. **Leave alone.** The line's form; the silent-session rule; the window. **Recommendation.**
Proceed.
