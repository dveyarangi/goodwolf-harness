## Shapes

### The installer — `.agents/scripts/inject_rules.py`

Standard library only, `main(argv, root=None) -> int` like its siblings, JSON on stdout, exit
`0` clean, `1` refused or drift found, `2` usage.

```
inject_rules.py <slug> --install [--overwrite]
inject_rules.py <slug> --retract
inject_rules.py --check
```

**Modes.** Exactly one, always named. No mode, two modes, a slug with `--check`, no slug with
the others, or `--overwrite` with retract is usage: exit `2`, nothing read.

**Reading** `.agents/mechanisms/<slug>/<slug>.rules.md`:

- prose before the anchor table is preamble, not read;
- the **anchor table**, `| target | anchor |`, one row per target: a backticked repo-relative
  path and a backticked verbatim line; a target named twice is a refusal;
- one **`## ` section per rule**: id is the heading's first token before ` — `;
  `- **target** `path`` one or more, each a table row; `- **authority** text` exactly one, read
  and never interpreted; the body is the span between a line exactly `<rule>` and a line exactly
  `</rule>`, byte for byte.

**Parse refusals** — reported, nothing installed, a `--check` diagnostic: a section missing a
target, the authority or the span; two spans; a target with no table row; a duplicate id; no
sections; a body containing `<installed`, `</installed>`, a markdown
citation (`docs_corpus.citations` returns anything), or a heading line (`^#{1,6} `).

**Rendering**, per target: every rule targeting it, file order, one paragraph each, blank line
between, the id written from the heading, the body unreshaped:

```
<installed by="<slug>">
**<id>** <body>

**<id>** <body>
</installed>
```

**Locating** by the opening tag with the slug exact, to the first `</installed>`; never by body,
since an edited block must still be found to be refused. Two opening tags of one slug in one
file, or no close, is a refusal.

**Looking through code.** Section headings in a rules file, anchor lines and opening tags in a
target are all searched over `docs_corpus.without_code`, which blanks code spans and fences
position for position, and act on the raw text at those positions. So `/mechanism`'s body may
show the tag and an anchor heading in a fence as its own example, and the installer never takes
the example for the thing. This is the same reason the orphan scan looks through code.

**Comparing** found against rendered, `\r\n` normalised to `\n` on both sides, one function,
every mode.

**Anchoring.** The anchor matches exactly one whole, newline-terminated line; none, several, or
an unterminated last line refuses. Install inserts, directly after that line's newline, one
newline, the block, one newline. Retract removes exactly that. No other spacing is computed,
and blocks from different mechanisms at one anchor stand in install order, which nothing
depends on.

**Install** preflights every target — exists, anchor unique, block absent or matching or with
`--overwrite` differing — and writes nothing if any check fails, reporting all. Present and
matching is reported and left alone. With `--overwrite` a differing block is replaced whole and
the report carries what it replaced, whole.

**Retract** preflights every block present-and-matching or absent, writes nothing on a differing
one, removes the block and the two newlines install added. Absent is reported, not refused.

**`--check`** walks every rules file and every file in `docs_corpus.corpus(root)`, reporting per
rules file × target `present`, `drifted`, `absent`, `target missing`, `anchor missing`, `anchor
ambiguous`; per unparseable rules file its refusal; per `<installed by=>` block in the corpus
whose slug has no rules file or whose rules file does not target that file, `orphan`; and the
count of rules files read. Everything but `present` is a diagnostic; exit `1` on any. A tree
with no rules file reports the count `0` and exits `0`, the way `mechanisms.py` reports a skip
rather than failing a recipient that injects nothing; the person at `/verify` reads the count.
The orphan scan runs over `docs_corpus.without_code`, so every example of the tag in a doc sits
in a code span or fence, on one line. **Absent is a diagnostic**: the rules file says where its block must
be, and the shape's block absent from `/mechanism` is the signal that the always-on mechanism
was damaged.

**Mid-write failure** follows the mover's contract: stop, report done and pending with the
failed path, roll nothing back. **Never writes a doc.**

### The tests — `tests/test_inject_rules.py`

On `RepositoryCase`: a mechanism with a two-rule rules file, a target skill with an anchor
heading. Each test bends one thing and names the failure:

- round trip byte-identical on `snapshot()`, index included; install writes the block after
  the anchor in the shelf's form, both rules, ids written, bodies unreshaped; installing twice
  changes nothing;
- an anchor heading or a tag inside a fence in the target is not an anchor and not a block;
- every refusal writes nothing, `snapshot()` unchanged and the reason named — the usage cases,
  the anchor cases (missing, ambiguous, unterminated), the table cases (target twice, no row),
  the section cases (missing field, two spans, duplicate id, no sections), the body cases
  (closing tag, citation, heading line), two blocks of one slug in one file;
- preflight is all-or-nothing across two targets when the second is missing;
- a drifted block refuses install and retract naming the file; `--overwrite` replaces it whole
  and reports the replaced text whole; adding a third section then plain install reports
  `drifted`, `--overwrite` yields a three-rule block;
- CRLF: matching modulo line endings is `present`; a real edit under CRLF is `drifted`;
- an edited block is found and `drifted`, never `absent`;
- `--check`: `absent` is a diagnostic with exit `1`; `orphan` for a slug with no rules file and
  for a file the rules file does not target; `present` and exit `0` once installed; the count
  of rules files read;
- retract of an absent block is not a refusal.

Every diagnostic is watched failing in both polarities before it passes.

## Stages

Each stage leaves the set green: 115 tests, `mechanisms.py --check`, and from stage 3
`inject_rules.py --check`.

1. **Contract before code.** The shelf's *The rules file*; the architecture surface, landed at
   this plan, verified; the entry file's bullet and v4 line; the findings record's v4 entry.
   Tests derive from the shelf, not from this plan.
2. **The installer, one behavior at a time.** Tracer bullet: install a two-rule block, retract
   it, `snapshot()` equal. Then the list above, vertically. `--check` last.
3. **Run it over what already exists.** Write both rules files. `--check` over the live tree
   before installing; record the count in both evidence files — expected three `absent`, no
   orphan, no refusal; anything else is a finding. Amend `/mechanism`'s *Records*. Take byte
   copies of the two targets. Install both slugs; `--check` clean; `--retract` both, the targets
   byte-equal to the copies; install again.
4. **Declarations, bodies, the set.** Both docs; `/mechanism`'s body sentences; process document
   and README; evidence sections. `mechanisms.py --check` true without changing. Add `--check`
   to the set; run the set.
5. **After `/verify`, at `/maintain`:** retire the two wrappers with the enumerator; paired
   close.
