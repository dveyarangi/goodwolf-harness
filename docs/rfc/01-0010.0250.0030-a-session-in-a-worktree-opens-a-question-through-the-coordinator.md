## The shape

**One seam: the scripts' own command lines.** Every call on the store is already an argument list
handed to `questions.main(argv, root)` — `open`, `at`, `close`, `--window`, `--wake`, `--hook`,
`--check`, `--tree`, `--path` — and its answer is what it prints and its exit code. The coordinator
is a small server, Python's standard `http.server`, bound to the loopback address, that takes an
argument list and runs that same `main` over the main checkout, one call at a time, and returns
what it printed and its code. A session's script, run anywhere, sends its argument list and prints
the answer; it does not open the store itself. So the code that writes a question is the code that
writes it today, and a call over the network later is the same call. The session script's calls
— `--hold`, `--take`, `--release`, `--end` — go the same way.

**Where it runs.** The main checkout, found as `01-0010.0250.0010`'s withdrawn plan found it —
in Python from `.git` and `commondir`, with no process — is the coordinator's root. A tree with no
main checkout (a bare common directory) has the coordinator's root in the session's own tree,
which is today's behaviour; it is said in the window.

**Raised on demand, one at a time.** A call that finds no coordinator answering starts one: a
process of its own, detached from the caller's — on Windows with the flags that leave the caller's
console and job, elsewhere in a new session — its Git environment cleaned of the caller's
worktree, its output to a log in the common Git directory. Before it serves it takes a lock, an
exclusive create of `gw-coordinator.lock` beside `gw-interpreter`; a second one finding the lock
held by a live coordinator exits, and the caller waits for the address to appear, a bounded wait
well under the hook's 30 seconds. The address file `gw-coordinator` holds its port, its process
id and a token each call must carry; a stale file — no such process, or no answer on its port —
is replaced. It stops itself after thirty minutes with no call, removing both files.

**When it does not answer.** Started and still silent within the wait, or failing mid-call: a write
is refused with one plain line and nothing written; a read — the window, the wake — is drawn from
the main checkout's files by the session's own script, marked *coordinator not answering*. The
next call starts it again.

**Seen.** Every window carries one line — the coordinator, since when, its root.

**Commits.** After a write, the coordinator commits the paths it wrote in the main checkout,
naming them (S5); while that checkout's index is held — a merge under way — the commit waits for
the next write, the files already written. It pushes as the project's way with git says, in the
background, one push at a time, so no call waits on the checks.

## Docs

The architecture's *it locks nothing* and its straw dog on one shared checkout, and the questions
mechanism's moments, rewritten to what then holds: a coordinator serialises the store's writes;
the host still keeps two agents' edits of one file apart. Its address file, lock and log join the
interpreter record in the common Git directory.

## Stages

Each keeps the store's, the session's and the harness's tests green; the store's tests call
`main` directly and stay as they are.

1. **The server and its client, in process.** The handler that runs `main` over a root; the
   client that sends an argument list and prints the answer; a test that two clients' `open`s at
   once give two ids, and that output and exit code come back as `main` gave them.
2. **Raised and found.** The lock, the address, the token, the detached start, the idle stop;
   tests: none running, the first call raises one; two at once, one; a stale address replaced; a
   call with no token refused. The detached start observed on Windows and on POSIX by someone who
   did not build it, the hook's process ended under it.
3. **Every call through it.** The scripts send when they are not the coordinator; a refused write
   and a marked window when it does not answer; the window's line.
4. **Commits.** By path after a write; the held index; the background push.
5. **Said.** The architecture and the mechanism docs.

## Impact

**Must change:** a coordinator script (its owner the session mechanism, which keeps how sessions
coordinate, decision 6 of q-0037.0017); `questions.py` and `sessions.py` (sending their calls);
`hook.sh` unchanged — it runs `questions.py --hook`, which sends; the architecture; the session
and questions mechanism docs; tests.
**Must verify:** every store and session test green, calling `main` directly; the window and its
one unchanged line as before; the pre-push copy, whose checks call `main` in the copy and must not
send — they run with the coordinator off; a recipient's update taking the script.
**Hidden edges:** a host that kills the hook's whole process tree, or a job without breakaway on
Windows, takes the coordinator with it — measured in stage 2; another program on the loopback
port — the token refuses it; the checks' own calls inside the coordinator, which must not send to
themselves; a session's `--hold` naming a question the coordinator's store does not hold yet.
**Leave alone:** bodies (.0070), rows' storage (.0090), the networked mode, messages, the web page.
