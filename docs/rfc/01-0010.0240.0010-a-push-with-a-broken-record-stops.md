## Shapes and flow

```
git push
  └─ .git/hooks/pre-push <remote> <url>          one guarded line, written by --links
       └─ sh .agents/scripts/gw/hook.sh pre-push  (stdin: <local ref> <local sha> <remote ref> <remote sha>…)
            ├─ no ref lines, or only deletions: exit 0
            ├─ each ref's carried paths listed; none under the method's roots: exit 0, no interpreter
            ├─ no interpreter recorded: a warning, exit 0
            └─ the ref lines handed on → "$python" .agents/scripts/gw/harness.py . --pre-push
                 sweep the dead copies this mode marked
                 for each distinct local sha whose own listing woke the checks:
                   ├─ git worktree add --detach --lock <copy named by its mark> <sha>
                   ├─ the checks the copy's core has, each `--check` there, all started at once
                   └─ every check's process tree ended, then git worktree remove -f -f <copy>
                 any finding: refused (exit 1), each named; else exit 0
```

**What the push carries** (decisions 1 and 8). Git hands `pre-push` one line per ref. A line whose
local sha is all zeros is a deletion and sends nothing; a ref naming a tag is peeled with
`^{commit}`, and one that names no commit sends nothing to check. **No ref lines at all** — a push
with nothing to send, or a tool that hands the hook none — is nothing to check, and exits 0: the
hook never guesses what a push sends from `HEAD`, which checked what an up-to-date push did not send
and missed a branch pushed by name. A dry run hands its ref lines and is checked like a push.

For a ref the remote already has, what lands is the remote's tree moved to the local one: its paths
are `git -c core.quotepath=off diff --no-renames --name-only <remote sha> <local sha>`, so a force
push back to an older, never checked tree is listed by what it changes. For a ref the remote lacks,
they are `git -c core.quotepath=off log --root --no-renames --diff-merges=first-parent --name-only
--format= <local sha> --not --remotes=<remote>`. A path in any script is read as written, a root
commit's files and a merge's resolution count. The shell reads a listing whole — one `grep`, never a
loop a line at a time, which took 4.2 s over 8925 lines — keeping Git's own exit status; its patterns
allow the quote Git still puts round a path holding `"` or a tab. A listing decides only whether
anything is woken, so listing too much costs a check and never a false refusal — a push by URL, or to
a remote with no tracking refs, lists the whole history and is checked. A listing that fails — a
remote sha this clone never fetched — wakes the checks: what cannot be listed is checked.

**What wakes the checks** (decision 8). A carried path under `docs/`, `.agents/`, `AGENTS.md`,
`CLAUDE.md` or `local.rules.md` wakes them; none, nothing. The roots stand in `hook.sh` with a
`TODO q-0037.0006.0005.0001`: each mechanism's table of its records, decided there, is to carry
them. A read past the roots — a project's own test file an edge record names as its validator — is
CI's to catch (decision 1).

**The copy** (decision 8). For each distinct local sha whose own listing woke the checks,
`git worktree add --detach --lock` makes a copy in a fresh folder under the system's temporary
directory, named `gw-push-<pid>-<start time>-<random>` — the name is the mark, since `add` has no
`--reason` before Git 2.33 — with the clone's hooks off, `core.hooksPath` pointed at the empty
output folder for the add, and `GIT_LFS_SKIP_SMUDGE=1`, so no
post-checkout hook runs in it and no smudge filter reaches the network. On Windows a folder whose
path would pass the 128 the tree's names are fitted to refuses the push saying so — Git fails such an
add with *Filename too long* — since a push that cannot be checked is not passed as clean. The
checks run with the copy as their working directory, so what is judged is what is sent, by the
checks the push itself carries, and no other session's unfinished write is in it. Copies are made one
after another; one costs about 5.5 to 6.5 s here all told, the add about 1.5 to 2 s, the checks 3.4 s
and the removal about 1 s.

**What the launcher reads from the working tree.** `hook.sh` and `harness.py` run from the clone's
working tree, and `harness.py` imports `inject_rules`, `product`, `questions`, `docs_corpus`,
`mechanisms` and `straw_dogs` as it loads: another session's half-written edit of one of them crashes
the mode, and the push is refused — shown, never passed. That is the one write of another session a
push still meets.

**Running the checks.** The mode starts every check before it reads any, each writing its output to
a file of its own in a folder beside the copy, named by the copy's mark with `-out` after it, since `tickets` and `mechanisms` print 78 KB and 94 KB
on this tree, past a pipe's buffer; a check's 60 s limit counts from its start. On Windows each check
is started in a Job Object (`ctypes`: `CreateJobObject`, `AssignProcessToJobObject`) and the job is
terminated before removal, since `Popen.kill()` left a grandchild holding a file open and
`taskkill /T` cannot reach an orphan once its parent has gone — a check the job would not take is
ended by `taskkill /F /T` instead; elsewhere each starts in a session of
its own and its process group is ended.

**Removing the copy.** After every check's process tree has ended, the copy is removed in a
`finally` with `git worktree remove -f -f`, its lock overridden. Git deletes its own record of the
copy even when the folder will not go, so the folder is then deleted by the mode, retrying read-only
files as the harness already does (`_writable_then_retry`); `remove -f -f` has already dropped
Git's record, so nothing is pruned. A removal that still fails is reported in the push's output with the folder's path, and the
verdict stands. Each run first sweeps the temporary directory, and Git's own list of the clone's worktrees, for
folders named by this mode's mark
whose process is dead — on Windows `OpenProcess` and `GetExitCodeProcess` through `ctypes`, the start
time in the name telling a reused pid from its first owner; elsewhere `os.kill(pid, 0)` — removing
each the same way; a sweep that finds a copy already gone takes it as removed, and a copy a live push
holds is never touched; a copy whose `.git` names another clone is left to that clone's next push,
and the output folders are swept by the same mark. No other worktree of the clone is pruned or
removed.

**Git's environment.** Git exports to its hooks what would redirect another Git call: `GIT_DIR` from
a linked worktree, `GIT_CONFIG_PARAMETERS` from any `git -c … push`, `GIT_INDEX_FILE` to a push a
commit hook starts, under which `git worktree add` wrote the copy's index into that file and left the
copy none. The listing runs in the clone as the hook was started, so a clone run with an explicit
`--git-dir` is listed where it is. `GIT_INDEX_FILE` is cleared for the add, and Git's own list,
`git rev-parse --local-env-vars`, for every call made in the copy and for the checks, so each finds
the copy's own repository. `_python` sets `PYTHONUTF8=1` for the checks: the recorded interpreter
writes a piped stdout in the platform's code page on Windows, so a check printing *—* gave its parent
no stdout, and one printing a character outside that page crashed — a fix the gate's `--check` takes
too, its report otherwise unchanged. The mode reconfigures its own stdout and stderr to UTF-8, as
`questions.py` and `sessions.py` do, since it prints the paths its checks name through the pipe an
agent's tool reads.

**The verdict.** Any check that exits non-zero refuses the push, its entries under `diagnostics` and
`skipped` named — read by the mode itself, not through the gate's `_diagnostics`, which returns
`diagnostics` alone and whose report the gate keeps as it is; a check without a `skipped` key is read
without it. One whose output cannot be decoded, or one past its limit, refuses with its last lines — for one
past its limit, those it had written: a
check that cannot be read is never taken as clean. A check's `findings`, which never fail it, are not
shown. Each refusal names the check, the file and line where the entry has them, and the problem;
entries of `inject_rules` and `maintain` are strings and `mechanisms` names a mechanism, so they are
printed as they come. **The checks the copy's core has** are the ones run: a commit made before core
had `sessions.py` or `product.py` runs the others and the output says which it lacks; a commit with no
`.agents/scripts/gw/` has nothing to check and passes, said in a line. A commit that weakens or
deletes a check is judged by what it carries, and CI is its catch (decision 1).

**The mode.** `--pre-push` takes the target and reads the ref lines from its standard input — a push
of hundreds of files would not fit an argument list — listing each ref itself with `-z`; no `--from`,
no network, no `Source`. `main` hands it the target and the remote before the other modes' parser,
since a mode read from a hook takes no option of theirs. Its time limit is a module value the tests
set. Outside a tree that holds core it says there is nothing to check and passes, as a commit
without core does — the hook's guard never starts it there.

**The hook** (decision 4):

```sh
#!/bin/sh
# goodwolf: written by harness.py --links; the checks of the method's records at push
[ -f .agents/scripts/gw/hook.sh ] && [ -f .agents/scripts/gw/harness.py ] || exit 0
exec sh .agents/scripts/gw/hook.sh pre-push "$@"
```

The guard lets a branch without core, or a tree the harness was removed from, push. A file whose
text is exactly this form, of this or an earlier core, is core's and is rewritten to the current
form; any other file — one that holds the mark beside lines a person added, as `git lfs install`
tells them to, included — is another's and is left byte-identical. `link()` writes the hook after the
interpreter record, in LF with the executable bit where the platform has one, at
`git rev-parse --git-path hooks/pre-push`.

**Only inside the project** (decision 9). The hook is written where that path lies inside the
common Git directory (`--git-common-dir`), or inside the project's own work tree — a `.githooks/` it
named, where the hook is committed with the project and every clone takes it. Where the path lies in
husky's `.husky/_`, which husky writes anew at each install, or outside the project — a global folder
a person's own Git config names for every repository of the machine — nothing is written, and the
report gives the line and its place.

**Beside another's hook** the report gives the line and its place, and the hook entry's state:

| what stands | how it is told | where the line goes | the line |
|---|---|---|---|
| husky | `core.hooksPath` at `.husky/_` | `.husky/pre-push`, first | the shared-input form below |
| lefthook | its marker in `.git/hooks/pre-push` | `lefthook.yml`, a `pre-push` command with `use_stdin: true` | `sh .agents/scripts/gw/hook.sh pre-push {1}` |
| the pre-commit framework | its marker in `.git/hooks/pre-push` | — | none: it hands a hook no ref lines and passes file names as arguments, so the report says this clone is checked by CI alone |
| any other hook file in the Git directory | its contents | that file, first | the shared-input form below |
| a hooks folder outside the project | `core.hooksPath` | — | none written: the report names the folder, and this clone is checked by CI alone until a person places the line |

Only one command of a hook file can read the ref lines; git-lfs's `git lfs pre-push` reads them too.
The shared-input form reads them once and hands them to core's line and, by the report's instruction,
to every other command of the file that reads them:

```sh
refs=$(cat)
printf '%s\n' "$refs" | sh .agents/scripts/gw/hook.sh pre-push "$@" || exit 1
# then, for each command below that reads the ref lines:  printf '%s\n' "$refs" | <that command>
```

The report's `hook` entry carries its path and one of `written`, `kept`, `beside` — with the tool,
the line and its place — or `outside`, for a `core.hooksPath` outside the project; none of
them changes `--links`'s exit. The install and the update do not call `link()`; they reach the hook
with [.0030](../tickets/01-0010.0240.0030-an-install-wires-the-checks.md).

**Worktrees.** The `pre-push` branch of `hook.sh` reads the worktree's interpreter record, then the
common directory's, so a push from a linked worktree is checked; the hook path resolves to the common
directory from any worktree.

**Failure semantics.** With no interpreter the hook warns and passes: it cannot start the check at
all, and CI is the last gate (decision 1). Once started, what cannot be checked refuses — a listing
read as waking, a copy past the depth bound, a check that cannot be read — and a crash of the mode
exits non-zero and Git refuses the push: a fault of core's is shown, not hidden. The host branches of
`hook.sh` keep their promise never to fail the host; its header says that the `pre-push` branch is
the one that refuses by design, and no longer that every hook is launched by a Git alias.

**Windows.** Git for Windows runs the hook under its own `sh` from any shell (tried 2026-10-26, the
question's *On Windows*); the interpreter path is quoted.

## Rollout, and what it reaches

- **Here.** The hook turns on for every session in this clone the moment `--links` writes it. The
  last stage runs it, after the user is told; removing `.git/hooks/pre-push` turns it off. A broken
  commit any session leaves on the shared branch refuses every session's push until a commit mends
  it — the gate doing its work, the refusal naming the record. Session rows are committed with the
  work, and a committed row naming an id no entry holds fails the session check: a commit that drops
  a question another session's committed row names refuses pushes until a row is rewritten, which the
  session script does from any session.
- **Recipients.** A recipient that updates and runs `--links` before .0030 lands gets the hook with
  only the report's `hook` entry to tell it; the install's sentence comes with .0030.
- **Removal.** [01-0010.0200](../tickets/01-0010.0200-a-project-can-remove-the-harness.md) removes
  the hook among what the install made; until it lands, the guard lets a tree without core push.

## Stages

Each keeps the suite green; `/tdd` allocates the tests, each proving its behaviour and its reason.
Every test lands in `test_harness.py` or `test_questions.py`, whose parts the shape check already
holds, so no stage fails it before the docs stage.

   *—* and a character outside cp1252 reads both back; the gate's `--check` report unchanged on this
   tree.
2. **`harness.py --pre-push`.** Tests on a fixture clone with a bare remote, ref lines on stdin, the
   time limit set low: a commit carrying a broken ticket refuses and names file and line; mended, it
   passes silently; a record broken only in the working tree passes; one broken in the commit and
   mended only on disk refuses; a failure only in `skipped` refuses; string entries print without a
   traceback; a non-zero exit with nothing readable refuses with its last lines; a check printing
   past a pipe's buffer is read whole; a hung check refuses at its limit; every check started before
   any is read, shown by stub checks that meet at a barrier; a stub check that leaves a grandchild
   holding a file open leaves no copy behind; the copy is gone after a pass, a refusal, a crash and
   a limit; a folder of this mode's mark whose process is dead is swept, a live one left, one already
   gone taken as removed; a removal that fails — a file held open, the platform's way — is reported
   with its folder and the verdict stands; a warning naming a Cyrillic path prints through a piped
   stdout; with `GIT_DIR`, `GIT_INDEX_FILE` and `GIT_CONFIG_PARAMETERS` set as Git sets them, the
   copy gets its own index and the checks the copy's repository; a commit without core passes saying
   so, one whose core lacks a script runs the rest and names it; on Windows a copy folder past the

3. **`hook.sh pre-push`.** Tests through a real `git push` to a bare repository, the recorded
   interpreter a stub that logs its calls: a push of code calls it never; a push of a record calls

## Impact

Must change: `hook.sh`, `harness.py` (`_python`, `_parsed`, `main`, `link()`, the mode, the report),
their tests, the harness and mechanism-shape docs. Must verify: every host event still launches
through `hook.sh`; the gate's `--check` reads checks as before. Hidden: the copy's folder depth on
Windows; Git's exported environment; a process tree outliving its check on Windows; a broken commit
on the shared branch refusing every session's push until mended; the launcher's own modules read
from the working tree; recipients taking the hook before .0030; tools that hand a hook no ref lines;
the guard of [01-0010.0125](../tickets/01-0010.0125-the-host-blocks-what-a-rule-forbids.md) refusing
the agent's commit for its own reason, earlier. Leave alone: the checks themselves, the host hooks'
merge, any project hook. Recommendation: proceed.
