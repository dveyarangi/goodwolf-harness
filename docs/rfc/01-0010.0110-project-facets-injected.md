## Governing boundaries

- **The install spec** — [*The local rules file*](../spec/01-0010.0130-harness-installs-into-another-tree.md#the-local-rules-file):
  one file per instance, outside the core directory, in installed-rules format, read by the
  injector as one more source; rules only; both install, local last; an override cites the rule's
  id; the tag retired; a tier-1 rule; the file's name, its grammar beyond the rules-file format and
  how the injector tells a local block from a mechanism's are this RFC's *(the user, 2026-09-10)*.
- **Ownership** — [*one axis*](../spec/01-0010.0130-harness-installs-into-another-tree.md#ownership-one-axis):
  core owns every slot it installs into; the project's content in it is preserved on redeploy.
- **The injector's contract** — [installed blocks](../architecture.md#installed-blocks), extended
  by one source and not reopened: one block per source per target, after the anchor line the
  source names, found by its tag, compared whole, refused rather than guessed, retracted
  byte-identically. The rules-file grammar is
  [the format shelf's](../../.agents/skills/mechanism/MECHANISM-FORMAT.md#the-rules-file).
- **The shape** — [`/mechanism`](../../.agents/skills/mechanism/SKILL.md): a rule's only authored
  home is a rules file; a hand-written copy is drift; the entry file holds meta-rules and a
  mechanism's rules only as installed blocks (R5, 2026-09-20); a meta-rule that is a line in the
  entry file is a mechanism's anchored part, never injected.
- **Core and instance** — [the entry file](../../AGENTS.md#core-and-instance) and
  [ADR-0002](../adr/0002-core-may-not-depend-on-the-instance-half.md): instance ownership is the
  one exclusion the leak check reads, from the enclosing block, and the `<installed by="local">`
  row is already [`.0140`](../tickets/done/01-0010.0140-core-stands-alone.md)'s.
- **The sibling claimant** — [01-0017.0010](../tickets/01-0017.0010-terms-defined-before-they-land.md)
  also injects into `AGENTS.md`; whichever lands first sets the anchor convention and the other
  adds a row.
- **The entry contract's version record** —
  [what a version covers](../research/entry-contract-findings.md): *Core and instance*, the
  *Autonomy* sentence and the *Project-local* section are core; the local block's values are not.
- **Testing** — the spec's *Testing Decisions*: a temporary tree, files, exit codes and JSON;
  never the tool's internals. Prior art is every case in `.agents/scripts/test/`.

## Impact

Run at `/plan`, 2026-09-20: **proceed, narrowed by two decisions taken first.**

*Blast radius.* `inject_rules.py` gains the local source, the placement rule, the `overrides`
field and two check questions; `test_inject_rules.py` the cases; `docs_corpus.py`'s
instance-owned grammar drops the retired tag; `mechanisms.py` gains one diagnostic and
`test_mechanisms.py` two fixture changes. Nine blocks in seven core files go: four in `AGENTS.md`,
three evidence bullets, `/maintain`'s links block, the format shelf's template line. Six
documents describe the tag as something an author writes. Entry contract v13. The core README
and this project's architecture doc each gain a sentence.

*Hidden edges.* The evidence bullet is a header field the check parses before the first `## `,
and an installed paragraph opens with an id, so an injected bullet does not parse. The
`/maintain` links block is not among the ticket's seven and has no home. "One naming none is
refused" is not decidable by a tool that cannot tell an override from an answer. One place per
target applies to the local file, so the facts for the entry file are one block. Install order
now matters where the injector's RFC said nothing depends on it. A mechanism directory named
`local` would collide with the reserved slug. The tier-1 rule's sibling is a hand-authored part
line, not an installed block.

*Leave alone.* The injector's contract; the block form and refusals; the lister, the mover and the
shear; the painted-door list; the evidence files; `/implement` and `/verify`, which name the
entry file and not the tag.

*No generalisation.* The local file is a second concrete source read through the grammar the
first already has. The override field is one optional bullet on the existing section. Nothing is
built for a third source.

## For the user

Three choices shape observable behaviour and are not the spec's or this plan's to make. Each is
stated with the answer the shapes below assume.

1. **The evidence bullet.** It cannot be injected as a header bullet. **Recommended:** the doc
   stops carrying it; the evidence is declared as a record of the shape in the format shelf's
   *Records* section with its three fields — one file per mechanism under `docs/mechanisms/`,
   named by the slug; read at amend time; removed with the mechanism — which is what makes
   `docs/mechanisms/` a painted door rather than a path the check happens to allow; and the
   check drops its "named must resolve" clause. Three blocks go with no injection at all.
   **The alternative:**
   the local file carries each path as a rule targeting the doc, and the check reads `evidence`
   from the doc's local block rather than its header. That keeps the field and adds a second way
   to read a header.
2. **`/maintain`'s links block.** Two architecture links, not a rule, not in the ticket's seven.
   **Recommended:** the block is deleted and nothing replaces it. The body's C2, C3 and D4 already
   carry the judgment half; the contracts stay in this project's architecture doc, which is the
   instance's to keep, and whether they later move into the mechanism docs that own the scripts
   is a `/maintain` pass over those docs, not this slice. **The alternative:** the two links
   become a local rule targeting `/maintain`, which keeps core reading its own contract through
   the instance half, which is the finding.
3. **The override criterion's wording.** The ticket says an override that names no rule id is
   refused. The tool cannot know an entry is an override unless it says so. **Recommended:** the
   criterion reads *an override names a rule id that resolves to a rule installed in the same
   target; one naming a rule that does not is refused, and the refusal says which entry*. A
   silent override — an answer that contradicts a core rule without naming it — is a reading
   defect the reader catches, not the tool.

## Shapes

### The local rules file

**`local.rules.md`, beside `AGENTS.md`**, outside `.agents/`. The name is the rules-file grammar's
own — `<slug>.rules.md` with the slug `local` — so the file, the block tag `.0140` already
reserved and the installer's operand are one word. The injector reads it as it reads a
mechanism's file: `read_rules_file(root, "local")` resolves to the root-level path, every other
slug to its mechanism directory. **A mechanism directory named `local` is refused** wherever a
slug is read, since its rules file would be found at two places.

Its grammar is the shelf's, with one optional bullet per section:

```md
## L3 — the verification set

- **target** `AGENTS.md`
- **authority** the user, 2026-09-05

<rule>
…
</rule>

## L4 — the pair need not close together here

- **target** `.agents/skills/maintain/SKILL.md`
- **overrides** `ticket/P2`
- **authority** the user, 2026-09-21

<rule>
…
</rule>
```

- **`overrides`** names a core rule as `<slug>/<id>`, at most once per section. The injector
  refuses the section when the slug has no rules file, the id is not in it, or that rule does
  not name every target this section names — read from the cited rules file's declared targets,
  not from whether its block is present, since an absent mechanism block is that mechanism's
  diagnostic and not the override's. The refusal names the local entry. So an override always
  sits in the same target as the rule it overrides, and by the placement rule below, after it.
- **Rendering** carries the citation into the target so a reader sees the disagreement where
  they meet it: `**L4** *(overrides ticket/P2)* <body>`. A section without the bullet renders
  as any rule does.
- Everything else the shelf refuses, this file's sections refuse: no citation in a body, no
  heading, no tag, no straw dog inside a body.

The file is the instance's. It is not in the core manifest, the leak check does not read it, and
its bodies may name any path the project has. A local rule may target any file, a mechanism doc
included: the doc's header reader takes `- **` lines before the first heading and an installed
paragraph is not one, so a local block in a doc's header states nothing to the check — which is
both why the evidence bullet cannot ride there unread and why nothing else there can either.

### Local last

The injector inserts a block directly after its anchor line, so a block installed second stands
first. For `local` the insertion point is instead **after the last installed block that follows
the anchor**, blank lines between them included. Every other source keeps inserting directly
after the anchor, which leaves an installed local block last without knowing it is there.

Install preflights the same fact and **refuses a local install that would not be last** — *a
block of `<slug>` follows the anchor at line N* — so a wrong anchor is a refusal that writes
nothing, not a block installed and then failed by the check.

`--check` asks one more question per local block: **no other `<installed>` block in that target
starts after it, anywhere in the file** — the ticket's *after every mechanism's block in the
same target*, not merely at one anchor. The state is `not last`, a diagnostic, beside `present`,
`drifted` and the rest. It reads offsets on the code-blanked text, as every tag is found.

So the local anchor in a target is constrained: it sits at or after the last anchor any
mechanism uses there. In `/maintain` every mechanism anchors at one heading and any local row
there is fine; in `/mechanism` the shape's block sits under *Records* and `/maintain`'s M1 under
*Incept*, so a local row for `/mechanism` anchors at *Incept* or later, and one at *Records* is
`not last`. A core update that adds a later anchor to a file makes a recipient's local block
`not last` at arrival — loud, and one row to move.

The local file's anchor table names its own anchor per target, and one place per target holds:
a project's facts for the entry file are one block of as many rules. With this placement the
installer's inject order — mechanisms first, local last — no longer decides where anything lands;
it stays as the sequence's stated order and nothing depends on it.

### `AGENTS.md` as a target

Nothing in the injector distinguishes the entry file; it is a row in an anchor table. What this
slice sets is the **anchor convention** the sibling claimant reuses: *in the entry file, the
anchor is the `## ` heading of the section the block belongs to, and the block follows the
heading.* The local block's row is `| `AGENTS.md` | `## Project-local` |`; 01-0017.0010 adds its
own section's heading when it lands.

Under this convention the block precedes the section's prose, so the *Project-local* section is
written to read whole in either order and names no position.

The entry file's text changes in three places, all core and all covered by the version:

- ***Autonomy*** — *the project sets each switch in its local block below* becomes *in the local
  block under Project-local*, since the block sits there.
- ***Core and instance*** — *content inside a `<project-local>` block is the instance's* becomes
  *content inside the local block — `<installed by="local">` — is the instance's, not core's*.
- ***Project-local*** — rewritten to describe the file: one file beside the entry file,
  `local.rules.md`, in the rules-file format, installed by the injector after every mechanism's
  block; the recipient writes every local answer and every override there, an override naming the
  rule it overrides; **a local change to a rule is written in the local file** — the tier-1 rule,
  whose teeth are `inject_rules.py --check` failing on a block that differs from its source and
  on a block nothing owns. The bullet *an unavoidable core reference into `docs/` goes in one* is
  gone with the tag; the leak check already skips the local block.

The tier-1 rule is **R7 of the mechanism that owns the injector**, installed from
mechanism-shape's rules file into the entry file under *Project-local* and into `/verify` under
*The verification set*, where the check runs and a drifted block would otherwise be edited in
place. *(Planned as a hand-authored part line beside the hand-edit rule; the user overruled that
at `/implement` — a rule that is not installed is not delivered, and a hand-written paragraph is
the copy the check cannot compare.)* It is the first mechanism block in the entry file and sets
the anchor convention there. The local block follows it under the same heading.

## Flows

**Install, this tree.** `inject_rules.py local --install` reads `local.rules.md`, preflights
`AGENTS.md` at `## Project-local` (present, unique, no `local` block), renders one block of three
paragraphs, inserts it after the last installed block following the heading — today, directly
after it — and reports `installed`. `--check` then reports the block `present` and last.

**Update, a recipient.** Core files are overwritten, mechanism blocks re-installed and found
`present`, then `inject_rules.py local --install` restores the recipient's block from a file the
copy never touched. An edited local block refuses as any block does, and `--overwrite` replaces it
from the file, which is the local file's authority over the copy.

**An override.** A recipient writes L1 with `- **overrides** `ticket/P2``. Preflight finds
`ticket`'s rules file, P2 in it, `/maintain` among P2's targets, and the local anchor in
`/maintain`; the rendered paragraph opens `**L1** *(overrides ticket/P2)*` and lands after the
ticket block. A recipient writing `ticket/P9` is refused: *L1 overrides ticket/P9, which ticket's
rules file does not define*. Writing `mechanism-shape/R6` into `/maintain` is refused: *L1
overrides mechanism-shape/R6, which is not installed in .agents/skills/maintain/SKILL.md*.

**Retract.** `local --retract` removes exactly the block and its two newlines, byte-identical, as
for any source.

## Stages

Each stage keeps the suite green; tests first, in the shape of `test_inject_rules.py`.

1. **The local source.** Cases: `local --install` from a root-level file installs and `--check`
   reports it; `local --retract` leaves the tree byte-identical; a mechanism directory named
   `local` is refused by every mode that reads a slug and is a `--check` diagnostic; a
   `<installed by="local">` block with no local file is an orphan. Code: the path resolution and
   the reserved slug.
2. **Local last.** Cases: with two mechanism blocks after one anchor, `local --install` lands
   third and `--retract` gives the file back byte-identical; a mechanism installed after the
   local block lands before it; a local anchor that precedes another mechanism's block in the
   file is refused at install naming that block, and nothing is written; a local block written
   by hand ahead of a mechanism's is `not last` under `--check`. Code: the placement rule, the
   preflight and the check question.
3. **Overrides.** Cases: a valid `overrides` renders the citation and lands after the cited
   block; an unknown slug, an unknown id, and a rule not installed in that target each refuse
   naming the entry; two `overrides` bullets refuse. Code: the bullet, the validation, the render.
4. **The entry file as a target.** One case: a fixture `AGENTS.md` with `## Project-local`
   takes the block and gives it back. No code; the case proves the convention has no special
   path.
5. **The conversion.** Write `local.rules.md`; delete the nine blocks and the template line;
   install; rewrite the entry file's three places and the six documents; apply the user's three
   answers, the evidence's record declaration and painted-door row among them; add the local file
   to `/maintain`'s T1; bump to v13 and record it. Verification set green with the tag gone.
6. **Teeth.** After the conversion: `_INSTANCE_OWNED` narrows, the retired-tag diagnostic lands
   with its two-polarity cases, and `test_mechanisms.py`'s two fixtures move to the new tag or the
   new diagnostic. Ordered after stage 5 because narrowing the grammar before conversion turns
   the live tree's evidence paths into leaks.

**Validated a third time, 2026-09-20.** Install-time behaviour was only implied: a local anchor
earlier than another mechanism's block now refuses at preflight rather than installing and
failing the check, and stage 2 proves it. The override's target test reads the cited rules file's
declared targets, not block presence, so one defect is reported once by its owner. A local block
in a mechanism doc's header is inert to the declaration reader, which is stated where the file's
reach is. The spec anchors this RFC cites resolve.

## Limitations and follow-ups

- **No installer runs this yet.** Step 7 of the install sequence is `.0130`'s; until it lands,
  `local --install` is typed. The `/maintain` moment *installing this mechanism* stays `not yet`.
- **A silent override** — an answer that contradicts a core rule without naming it — is caught by
  a reader, not the tool. The third answer records this as the accepted limit.
- **The sibling's anchor.** 01-0017.0010 adds its row under this slice's convention; nothing here
  reserves it a place.
- **A later anchor in core** makes a recipient's local block `not last` on update. The check
  says so at arrival and the fix is one row; nothing here automates it.
- **The evidence files' own pointers** at their heads name the architecture doc for the contracts;
  they are the instance's and follow the second answer at `/maintain`, not here.
