# The sessions' rows and the window memory live in a database, out of git — implementation plan

- **record of** what it intends to become

**Authored:** 2026-10-30

Implements [01-0010.0250.0090](../tickets/01-0010.0250.0090-the-rows-and-the-window-memory-live-in-a-database.md).

## What it keeps

[q-0037.0017.0005.0003](../questions/q-0037.0017.0005.0003-do-the-sessions-rows-stay-tracked-in-git-once-a-coordinator-can-hold-them.md),
decisions 1 and 2 and *Where it stands*: the rows leave git for one SQLite database in the
project's common Git directory, in either mode, with the window memory, the sign of life and
(for [.0080](../tickets/01-0010.0250.0080-a-branchs-links-follow-a-move.md)) the coordinator's map
of renames; the questions stay files. The row keeps what it holds and how it lives —
[the session mechanism's doc](../../.agents/mechanisms/session/session.md), *How it works*;
only where it is kept changes.

## The shape

**One database, one owner.** The session script alone opens it; everything else reaches a row,
the window memory or the sign of life through the session script's functions, as today. It lives
at `<common Git directory>/gw-sessions.sqlite`, beside `gw-interpreter`, found by
`git rev-parse --path-format=absolute --git-common-dir` — so every worktree of a clone reads one
file, and no branch carries it. `sqlite3` is Python's standard library. Several hooks write at
once: each write is one short transaction, the connection waits on a busy database rather than
failing (a wait well under the hook's 30 seconds), and the journal is the write-ahead one, so a
reader never waits on a writer. A take that moves a unit and marks the holder is one transaction —
today two file writes.

**The row's form stays.** The fields a row holds — tag, running or ended, the time it last wrote,
the position, up to four recent, the unit it holds or the mark of one taken — are columns;
`ROW_FORM` remains the form a row is shown in, and `sessions.py --rows` prints every row in it,
one line each, so a person or an agent can read the registry without SQL. Its schema beyond
those fields is the implementation's.

**The window memory and the sign of life.** Today a file per session in the temp folder, keyed by
the tree's path: the fingerprint of the last window, a `.counted` file of the counters, and the
file's time as the sign of life. All three become the session's own fields in the database —
`seen` a time written by `seen()`, read by `last_seen()`; the fingerprint and the counted
memory read and written through two functions of the session script that the question script's
window and counters call in place of `sessions.memory()`. Keyed by the tag alone: a session lives
in one tree, and two worktrees of a clone now share what they remember of each other's sign of
life. `WINDOW_MEMORY`, the tests' override, becomes the database path's override.

**Renames.** A rename rewrites the ids the rows name through the session script — one call over
the database — instead of the question script rewriting row files it listed through
`sessions.records()`, which retires. The question script's own row write keeps `renamed()`.

**Removal.** `tend` deletes a row that read ended for seven days, as it removes a file today.

**What leaves git.** At its first call in a tree whose rows are files — under `docs/sessions/rows/`,
or the older `docs/questions/sessions.d/` and `docs/questions/sessions` — the session script
carries every row into the database, a row the database already holds by its tag left as the
database has it, and then deletes the files; the deletions are the tree's change to commit, said
once on the hook's line. In this tree the implementing commit carries them; in a recipient, its
first session after the update. The carry-over code stays for recipients that have not run since.

## Who else changes

- **The question script.** Its window and counters read and write the memory through the session
  script; its rename calls the session script; `WriteInterrupted` names the database, not the
  folder.
- **The push check.** `sessions` among the pre-push checks checked row files in the pushed copy;
  rows are no longer pushed, so it checks only that the pushed tree carries no rows' folder.
- **The shape check.** The painted door for `docs/sessions/rows/` in `mechanisms.py` goes.
- **The rules and the skills.** S3, the maintain pass committing rows another wake changed,
  retires from `session.rules.md` and is retracted from `/maintain`. `/conclude`'s declaration of
  the row and `/questions`'s opening line say where the row is kept. These are instructions: their
  text is drafted through `/skill-up` and shown to the person before it lands — the
  self-improvement ladder's *a rule*, at this tree's dial.
- **The docs.** The session mechanism's doc: the row, the sign of life, the moments and its
  straw dogs on *one folder in the working tree* — now one database in the clone's Git directory,
  still unseen by sibling clones and other machines, their binding to q-0037.0017.0005 kept.

## Stages

Each leaves the store's, the session's, the harness's and the installer's tests green.

1. **The rows in the database.** The session script's row functions over the database; the
   carry-over from the three old places; `--rows`; `--check` over the database's rows, its
   findings on positions naming no entry kept. `test_sessions` reads rows through the script
   rather than files: each test that read a file now fails first for the reason it names, then
   passes. A test that two writers at once both land, and that a take is all or nothing.
2. **The window memory and the sign of life.** `seen`, `last_seen`, `forget_window`, the
   fingerprint and the counted memory in the database; the question script's window and counters
   through them. Tests: a session silent past the limit in one worktree is ended by a wake in
   another; one that keeps talking in a worktree is not; an unchanged window still prints its one
   line.
3. **Renames.** The rename through the session script; `records()` retired; the store's rename
   tests read the ids from the database.
4. **Out of git.** The carry-over run on this tree, its row files deleted in the same commit; the
   push check and the painted door; S3 retired and reinstalled; the skills' and the doc's text,
   shown to the person first.

## Impact

**Must change:** `sessions.py`; `questions.py` (window memory, counters, rename, the interrupted
write); `harness.py`'s push check of `sessions`; `mechanisms.py`; `session.rules.md`;
`session.md`; `/conclude`, `/questions`, `/maintain` through the installer; `test_sessions`,
`test_questions`, `test_harness` where they read row files or the memory folder.
**Must verify:** the window drawn and its one unchanged line as before; the wake's read; holds and
takes; `--end`; a recipient's update carrying its rows; the questions' 249 tests, the sessions'
128.
**Hidden edges:** the pre-push check runs in a detached copy sharing the common directory, so it
would read the live database, not what is pushed — hence the narrowing above. `session.rules.md`
stands changed and uncommitted by another session: the implementation edits its own rule and
commits by path. A host may run two hooks at one moment on Windows, where a file lock is
mandatory — the busy wait covers it; measured before stage 1 closes. A database file in `.git`
is lost with a fresh clone, as the rows are meant to be; the session records stay in
`docs/sessions/`.
**Leave alone:** the session record `/conclude` writes; the row's fields and lifetimes; the store;
messages between sessions; a question's counters, [q-0037.0001.0026](../questions/q-0037.0001.0026-do-a-question-strike-count-and-last-time-stay-in-its-file.md).
