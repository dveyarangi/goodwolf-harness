## Shape

### The shelf — the questions mechanism's

`.agents/skills/questions/HOOK-WIRING.md`, beside `STORE-ARRIVAL.md` and in its form: a short
preamble saying it is machine input for the install, then one fenced block per host file, the info
string `hook-wiring <host file>`, the body a JSON object in that host's own schema:

    ```hook-wiring .claude/settings.json
    {"hooks": {"SessionStart": [...], "UserPromptSubmit": [...]}}
    ```

Its content at authoring is exactly what this tree's three host files hold today — the commands
keep their form; `.0174` changes them. `questions.py` exports the shelf's path and one reader,
`hook_wiring(text) -> {host file: object}`, which refuses a shelf with no block, a block whose
body is not a JSON object, or a host file named twice. The installer holds no host file path and
no entry: every host file it touches is one the shelf names.

### The merge — the installer's

One pure function in `harness.py`: given a host file's current text (or none), the shelf's object
for it, and the previous ref's object for it (or none), it returns the new text, or refuses.

- Under `hooks`, per event: each entry of the previous ref's that the current shelf no longer
  holds is removed; each current entry not already present is appended, in the shelf's order. An
  entry already present, anywhere in that event's list, stays where it is — the file does not
  churn, and a recipient that copied core's hooks by hand holds them once.
- Entries are compared as JSON values. What is core's is what the shelf says, so nothing is
  written into a host file to mark ownership — JSON has no comments, and a marker key would be a
  field the host may reject.
- A top-level key the shelf carries besides `hooks` (Cursor's `version`) is written when absent;
  present with another value, the file is refused naming the key.
- Refused: text that is not JSON, a top level that is not an object, a `hooks` that is not an
  object, an event whose value is not a list.
- Unchanged content writes nothing. A changed file is written as two-space-indented JSON with a
  final newline, LF; the reformatting of a file the project wrote is accepted *(the `/impact`)*.

### Where it runs

| mode | what it does with host files |
|---|---|
| `--install` | plan every host file before anything is written — the shelf from the shipment, previous none — so a refusal changes no file; write after the core copy, beside the delivery status and the store's seed |
| `--update` | the same, previous the announced ref's shelf when that ref had one; a ref without one, or a tree announcing none, removes nothing and appends what is missing |
| `--check` | the ref gate lists a host file in `differs` when an entry or a top-level key of the announced ref's shelf is missing from it; the project's own entries are never read |
| `--links` | untouched: the host files are committed, so a clone already has them |

The plan runs beside `_link_plan`, before `_write`; the merged texts are written after
`_seed_store`. `report.written` names each host file written. Nothing is added to the gate:
`_ref_gate` already holds "what core shipped, the recipient's own set aside", and the shape check
already reads each host file for its `--hook` anchor.

## Impact

**Impact.** `harness.py`'s install, update and check gain one planned write and one comparison;
`questions.py` gains a shelf path and a reader; the questions mechanism's doc gains a part and
loses a `not yet`; the harness doc gains a moment and a relied-on row; the architecture's
*Installing* gained its paragraph in this pass. No record format moves; no recipient's existing
file loses anything but core's own removed entries.

**Hidden edges.** A project hook placed inside one of core's Claude Code groups makes that group
differ, so core's group is appended again and core's hook runs twice there — reported nowhere;
kept out of scope, since separating a group is guessing. A recipient that edited core's entry in
place gets core's appended beside its edit and `--check` fails until the edit is removed — the
same answer as an edit in a core file, without `--overwrite`'s reach. Removing the harness
([`.0200`](../tickets/01-0010.0200-a-project-can-remove-the-harness.md)) must take core's entries
out; it reads the shelf the same way.

**Leave alone.** The commands themselves and how they find an interpreter
([`.0174`](../tickets/01-0010.0174-each-hook-finds-its-interpreter.md)); the gate's reporting
([`.0176`](../tickets/01-0010.0176-a-failed-gate-says-why.md)); `questions.py --hook`; the loader
links; the straw dogs bound to q-0018.0020.0005 in `docs/product.md` and the front page, which stay
true until `.0174` — an installed project receives the hooks but runs them only where `uv` is.

**Recommendation: proceed.**

## Stages

Each stage leaves the suite green.

1. **The shelf's reader** — `test_questions`: the reader returns each block's object under its
   host file; refuses a shelf with no block, a non-object body, a host file twice. Then the
   reader and the path.
2. **The merge** — `test_harness`, pure: into no file; into a file holding only the project's
   hooks, which stay first and unchanged; an entry already present is not appended; a previous
   entry left out of the shelf is removed and the project's equal-looking neighbour is kept;
   Cursor's `version` written when absent and refused when it differs; each malformed shape
   refused naming the file; unchanged content returns no write. Then the function.
3. **The modes** — `TwoTrees`: the fixture source gains a shelf for the three host files, and its
   sample mechanism declares one host file as a part with its anchor, so the shape gate depends
   on the merge as it does in core. Tests: an install into an empty target arrives with the three
   files holding core's entries; a target already holding a host file with a hook of its own keeps
   it and arrives; an update to a ref whose shelf dropped an entry and added one replaces them and
   keeps the project's; `--check` passes with a project hook added and fails with core's entry
   edited, naming the host file; a host file that is not JSON refuses the install with the target
   byte-identical. Then the wiring in `run` and `_ref_gate`.
4. **Core's own records** — author `HOOK-WIRING.md` from this tree's three host files; the
   questions doc's parts table names the shelf, its *carrying the hook wiring* moment is instructed
   by `harness.py` and its straw dog retired; the harness doc gains the moment *merging core's hook
   wiring into each host's file* and relies on the shelf and its reader, owned by `questions`; a
   test that this tree's host files hold everything its shelf names, so the origin cannot drift
   from what it ships. `mechanisms.py --check`, `inject_rules.py --check`, the suite.
5. **Live** — the cheapest real example that could prove this wrong: `--install --from` a local
   clone of this tree at its committed head into an empty temporary folder ends `arrived: true`
   with the three host files; then a copy of a tree holding hand-copied hooks, as the study tree
   does, takes `--update` and its host files come out unchanged.
