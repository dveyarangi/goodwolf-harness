## The shape

**The interpreter, one per clone.** `hook.sh` already holds `interpreter()` — the worktree's own
record, then the common directory's — for its `pre-push` branch; the host branch reads only
`--git-path gw-interpreter`, the worktree's own. The host branch takes `interpreter()` too. And
`harness.py`'s `_record_interpreter` writes the record in the common Git directory
(`--git-common-dir`), where every worktree's hook finds it; a record already standing in a
worktree's own directory is still read first, so nothing that works today changes. The record's
comment at `INTERPRETER_RECORD` — "per clone by construction" — then holds as written.

**The links, made by the session that lacks them.** The loader links are ignored by git and made
by `harness.py . --links`, so a new worktree has none. At a session's start — where the hook
already tells a start by the payload and runs the installer's check — a tree that holds core and
lacks the link its host reads (`.claude/skills` for Claude Code, `.cursor/skills` for Cursor; the
host is the hook's first argument) has the link step run for it, and its result handed to the wake
in one line, as the installer's check is: *the skills are linked now and load from this
worktree's next session* — a host may have read its skills before its start hook ran — or, where
the platform refused the link, the exact command for the person, as an install's pending links are
named. A tree whose links stand pays nothing. The one line comes from `harness.py . --links --line`,
which prints that line or nothing, as `inject_rules.py --check --line` does for the installer.

**Nothing on the worktree's own branch changes.** The links and the record are outside every
commit; the exclude file the link step writes is the common one (`info/exclude` resolves there).

## Stages

Each keeps the harness's, the store's and the session's tests green.

1. **The record in the common directory.** `_record_interpreter` writes there; tests in
   `test_harness`: `--links` in a linked worktree writes the record the main checkout's hook reads,
   and a worktree's own record still wins. Each fails first: the record written in the worktree's
   own directory.
2. **The host branch reads it.** `hook.sh`'s host branch through `interpreter()`; a hook test in a
   linked worktree whose own directory holds no record draws the window. Fails first: the
   no-interpreter notice.
3. **The links made at start.** `--links --line`; the start branch running it when the host's link
   is missing; tests: a worktree without links gets them and the line, one with them gets neither,
   and a refused symlink gives the pending command — the refusal stubbed, as the harness's tests
   already stub the platform. Observed in this tree's `.claude/worktrees/` by someone who did not
   build it.

## Impact

**Must change:** `hook.sh` (the host branch; the start branch); `harness.py` (`_record_interpreter`,
`--links --line`); `test_harness`.
**Must verify:** the main checkout's hook unchanged; `pre-push` unchanged; an install and an update
in a recipient still record the interpreter and make the links; the `.claude/worktrees/` copies
stay out of the corpus.
**Hidden edges:** a hook that makes links at start spends a symlink call and the link step's git
calls once per new worktree — a fresh worktree only. On Windows without the right to make
symlinks the link stays pending until the person runs the command; the window says so at each
start until then, as the installer's check says a drift. The link step also writes the
`pre-push` hook, which already resolves to the common directory: idempotent. Another session's
work on `hook.sh` — 01-0010.0240.0010, done — is closed.
**Leave alone:** sibling clones, which share no Git directory: an install there, as today; the
`pre-push` branch; the installer's check at start.
