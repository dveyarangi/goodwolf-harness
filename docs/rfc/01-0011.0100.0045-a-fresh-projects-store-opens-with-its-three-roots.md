# A fresh project's store opens with its three roots — implementation plan

**Authored:** 2026-10-09

Implements [01-0011.0100.0045 a-fresh-projects-store-opens-with-its-three-roots](../tickets/01-0011.0100.0045-a-fresh-projects-store-opens-with-its-three-roots.md).

## The shaping facts

- **The decision** is the questions mechanism's *Three roots from the start*
  (`.agents/mechanisms/questions/questions.md`): the store opens with three roots and nothing
  else.
- **One home per part.** The words are the questions mechanism's, so they sit on its shelf. The
  entry format and the rule of when to seed are the store script's, the only writer of an entry's
  parts (the questions skill, *Records*). The installer holds none of the three — *no constants in
  the installer* (the user, 2026-10-09).
- **Precedent, followed rather than generalised.** The queue's arrival words live on the ticket
  mechanism's shelf. The installer reads them while the shipment is built, so a ref that cannot say
  them is refused before anything is written, and writes the queue whenever it is absent, install
  or update alike (`harness.py`, `arrival_state`, `_write_delivery_status`). The roots repeat the
  pattern, with one difference: the installer neither parses the shelf nor writes the entries.
  The store script does both. Two instances name the pattern; nothing is factored out of them.
- **Another precedent: the installer calls a sibling module as a library.** It already calls
  `inject_rules` that way, rooted at the target (`_inject`). Seeding calls `questions` the same
  way. No subprocess, and nothing to patch in the tests' in-process gate.

## Code shapes

**The shelf**, `.agents/skills/questions/STORE-ARRIVAL.md`, beside the questions skill, as
`QUEUE-ARRIVAL.md` sits beside the ticket skill.
- It opens with a line saying what it is: machine input for the install, read by nobody at session
  time.
- One fenced block with the info string `roots` holds the root questions one to a line, in their
  order: purpose, structure, landscape.
- Prose may surround the block. The block is found by its info string, not by its position.

**The store script**, `questions.py`:
- A constant for the shelf's path, beside `STORE`. It is the questions mechanism's own path, held by
  the questions mechanism's script.
- **A reader of the shelf's text.** It returns the questions in order, and refuses a shelf with no
  `roots` block or an empty one. It takes the shelf's text, not a path, so the installer can hand it
  the shipment's copy before writing anything.
- **`seed(root, now)`.** When the store holds any entry, live or in `done/`, it writes nothing and
  returns nothing. Otherwise it reads the shelf under `root`, then for each question applies an
  `opens` clause with no parent to a fresh `_Draft`. It rechecks and writes, and returns the
  records written.
  - No session is read or written. `declare` is not used, because it reads a session's line.
  - The draft's recheck still refuses an id another writer took in between.
  - The roots take `q-0001` onward, in the shelf's order, each `open` and struck zero, as any
    `open` writes.
- **`--seed`**, a mode of `main`. It prints each record written, or that the store holds entries
  and was left. Exit 0, or 2 on a refusal.
  - It is how a person resumes after a refused install, as `inject_rules.py <slug> --install` is.
  - The module docstring and the usage line name it.

**The installer**, `harness.py`:
- **While the shipment is built**, beside `arrival_state`: the shipment's copy of the shelf goes
  through the store script's reader. A ref whose shelf is missing or says nothing is refused before
  anything is written.
  - The shelf's path comes from the `questions` module, never from a constant of the installer's.
- **In `run`**, after `_write_delivery_status` and before the links: a step that calls
  `questions.seed(target, …)`.
  - Records written go to `report.written`.
  - A store that holds entries gets a note in `report.notes`, worded as the delivery status's: the
    project's, left as it stands.
  - A `questions.Refused` becomes the installer's `Refused`, naming the resume:
    `questions.py --seed`, then `harness.py . --check`.
- The step runs at `--install` and at `--update`, never at `--check` or `--links`.

## Code flow

```
--install | --update
  Shipment.at ── arrival_state (queue words)        refuse before writing
              └─ questions' shelf reader (roots)    refuse before writing
  _write            core lands, the shelf with it
  _write_delivery_status
  seed step ─── questions.seed(target)
                  store holds an entry? ── yes ─▶ nothing; note "left as it stands"
                  no ─▶ read target's shelf ─▶ opens × n ─▶ recheck ─▶ write ─▶ report.written
  links, inject, gate
```

## Impact

**Must change:**
- `questions.py`, its tests, and the shelf.
- `harness.py`, and its tests: the fixture's source gains a shelf. Without one, every install case
  is refused at ship time.
- The questions doc:
  - its *Three roots from the start* paragraph cites the shelf for the words and stops restating
    them;
  - the `not yet` row for seeding names `questions.py`;
  - *Install adds* gains the shelf;
  - *What it produces* gains the seeded roots, read by the first session's `/recall` and window;
  - *Not yet at the shape* goes back to four rows.
- The harness doc:
  - a moment for seeding a fresh tree's store;
  - a *Relies on* row for the store's seed, owned by `questions`.

**Must verify:**
- `test_lands_the_manifest_transformed_and_nothing_outside_it` reads `report["written"]` for
  straw dogs. The seeded entries join that list and hold none.
- The real-process gate cases need nothing, since the seed runs in the installer's process.

**Hidden edges:**
- *The ticket's fourth criterion said the harness doc lists the seeded roots among what it
  produces.* The questions mechanism produces them, and the harness only relies on its seed, so
  the criterion is amended in place to say so.
- *A store whose path is ignored by Git.* The corpus lists files Git does not ignore, so such a
  store reads as empty and would be seeded. That is the same blind spot every store call has, and
  it is left.
- *A partly written seed.* The draft writes entry by entry and stops on the first failure without
  rolling back, as every call does. The installer's refusal then names `--seed`. A store left
  holding one or two roots holds entries, so a rerun leaves it, and the person writes the rest by
  hand. Accepted as rare.

**Leave alone:** the store's turn calls and `declare`; this tree's own store; the queue's arrival
shelf and its reader.

**Recommendation:** proceed.

## Stages, each green

1. **The shelf and the store script**, test first, in `test_questions.py`:
   - an empty store seeded from the shelf holds exactly its questions as roots, open, in order,
     with nothing under them, and `--check` passes;
   - a store with one live entry, or one entry in `done/` only, is left byte for byte;
   - no sessions file is written;
   - a missing shelf, a shelf with no `roots` block, and an empty block are each refused with
     nothing written;
   - `--seed` prints what it wrote, or that the store was left.
2. **The installer**, test first, in `test_harness.py`:
   - The fixture's shelf words its roots in the fixture's own words. A fresh install seeds those,
     which proves the installer carries no words of its own (the ticket's third criterion).
   - An update into a tree whose store was emptied seeds it.
   - An update into a store holding an entry leaves it and notes it.
   - A ref whose shelf is missing is refused before anything is written.
3. **The docs**, as *Impact* lists them. The shape check is green, then the full suite.
4. **`/verify`.**
