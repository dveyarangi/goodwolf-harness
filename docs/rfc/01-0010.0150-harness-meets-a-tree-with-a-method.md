## Shapes

### The inventory, on `--install`

`_refuse_unless_empty` becomes one look over the four places, before anything is written, and
refuses if any holds something:

- the entry file `AGENTS.md`, if it exists — a file;
- the host stub `CLAUDE.md`, if it exists — a file, whatever it holds: a stub that is only the
  pointer line is a finding like any other, listed with its size, and the flow says to move it
  aside without reading it (one rule, no byte comparison);
- every path under `.agents/` the manifest writes and a file already stands at — a collision;
  the rest of a foreign `.agents/` is not a finding: the install proceeds into it and reports
  those files as the project's own, through `report.own` as an update does today;
- each loader-link location, `.claude/skills` and `.cursor/skills`, if a directory or a file
  stands there — a symlink or a junction is not the inventory's: the link plan keeps or repoints a
  symlink and refuses a junction by name, unchanged.

Core's scripts live under a directory of their own by the time this lands, so a collision under
`.agents/` is a skill, a mechanism doc, the glossary or the core README sharing a path — each of
which is `/align`'s under the flow, never overwritten.

The report gains one field, `inventory`, empty on every run that is not this refusal:

```
"inventory": {
  "files":  [{"path": "AGENTS.md", "bytes": 2210}, {"path": ".claude/skills/review/SKILL.md", "bytes": 940}, ...],
  "skills": {".claude/skills": ["review", "deploy"], ".agents/skills": ["keeper"]}
}
```

`files` lists every file found in the four places with its size in bytes, sorted by path; a
file under a found directory is listed through the corpus view (`docs_corpus.corpus`, tracked
plus untracked-unignored), the one view the scripts share. `skills` maps each found directory
that holds skills to the names of its immediate subdirectories holding a `SKILL.md`, so the agent
reads the skill names without reading the file list. The refusal string names the count and both
resumes:

    install: the tree already has a method — 14 files in 3 places, listed under inventory; a copy of
    the harness taken by hand takes --update --overwrite, anything else is carried first by the
    skill's flow

Nothing else changes: `_link_plan` still refuses a directory or a file at a link location, which
`--update` reaches and `--install` no longer does; `report.own` is filled on an install into a
foreign `.agents/` as it is on an update.

### The flow, in the skill

A new section of `SKILL.md`, *A tree that already has a method*, states the steps the align
decided. Its structure, wording at `/implement`:

1. Run `--install`. It writes nothing and returns the inventory. Read it whole before moving
   anything.
2. For each finding, carry it where it is trivial, without asking: a fact or a convention in the
   project's entry file or stub becomes a rule in `local.rules.md`; a project skill moves under
   `.agents/skills/<name>/` with a claim line as its first body line, so the loader link reaches
   it and the shape check accepts it; the old entry file and stub move aside once every line of
   them has a home; a stub that is only the pointer line moves aside unread. A copy of this
   harness taken by hand — the entry file announces a version and no `@` — is `--update
   --overwrite`'s, not the flow's, once its `<project-local>` block has become local rules.
3. `/align` with the user where it is not trivial: a rule that contradicts one of core's, which
   becomes an override naming it or a decision; a skill that collides with one of core's by name
   (the project's `plan` is not core's `plan`) or by responsibility (the project's `review` does
   what core's `verify` does) — the inventory gives the names, the agent reads the descriptions;
   a process of the project's own, met step by step — which of its steps the loop's own cover,
   which stay as local rules, which contradict. The skill wraps that step's *for now* on
   [01-0020](../tickets/01-0020-pacer.md), whose align owns making the loop's granularity and
   ceremony switchable; a recipient receives the step sheared, as the way to meet a process.
4. Run `--install` again; write the local file as *After the first install* says; install it;
   `--check`.

The section says, in one sentence, that the script deletes nothing of the project's at any step
and never rewrites a project skill: what moves, the agent moves. It ends with one line — *a
mechanism that has said how it meets an existing method installs its block below* — and a
heading that a rules file can name as its anchor; the ticket mechanism's block, for work tracked
on a board or in another shape, is that mechanism's to write and not this slice's. The
description gains the occasion: *…or bring a tree's own instructions, skills and process under
it when the install meets them…*.

## Flows

**Install into a tree with a method.** `_work_tree_root` → `Source.resolve` → `Shipment.at` →
the inventory finds something → `Refused`, `report.inventory` filled, exit 1, nothing written.
The agent follows the flow; the second `--install` finds the four places empty of collisions and
proceeds as today, the project's other files under `.agents/` in `report.own`.

**Install into a foreign `.agents/` that collides on nothing.** The same, with the inventory
empty: core lands beside the project's files, the links are made, the rules injected, and the
gate says what it says — an unclaimed skill of the project's fails the shape check by name, and
the flow's second step is what makes it pass.

## Limitations and follow-ups

- **A junction where a link goes** stays its own refusal from `_link_plan`, after the inventory:
  a tree with both a method and a junction meets two refusals in two runs. Fewer parts than a
  junction in the inventory; revisit if a real tree has both.
- **An ignored file under `.agents/`** is neither in the inventory nor in `report.own` — the
  corpus view excludes it — though a collision at a manifest path is found on the filesystem
  regardless. What the project ignores, the report ignores.
- **A responsibility collision is the agent's to see.** The inventory gives names; whether the
  project's `review` is core's `verify` is read from the two descriptions under the flow, and no
  script says so.
- **The inventory is `--install`'s.** An `--update` over a directory at a link location refuses
  as today, one path at a time. The ticket scopes the inventory to the install.
- **The flow is instruction**, verified by reading and by the grade, not by a test. What the
  agent carries and where is judgment under it.
- **The repository line** — [01-0010.0155](../tickets/done/01-0010.0155-a-tree-names-the-repository-its-core-comes-from.md).
  **What an update says about what moved** — [01-0010.0160](../tickets/01-0010.0160-harness-edge-changes-reach-an-update.md).
  Contribution back, a workspace-level harness, whether a host reads the link: parked where
  they were.

## Resolved at `/plan`

- **A foreign `.agents/` is not refused today, and will not be.** `_refuse_unless_empty` checks
  manifest paths only; a tree holding `.agents/rules.md` and nothing colliding takes the install,
  core lands beside the project's files, and the shape gate fails on an unclaimed skill with
  files already written. The first pass proposed refusing on the directory; the user, 2026-09-21:
  *we should not refuse the foreign `.agents/`, we should integrate.* So the rule is today's —
  a collision refuses, with the inventory; a directory does not — and what makes it smooth is
  that core's scripts cannot collide once they sit under their own directory, and that a skill
  collision, by name or by responsibility, is an explicit `/align` in the flow. The ticket's
  first bullet and first criterion are rewritten to say so; `architecture.md` needs no change.
- **A stub that holds only the pointer.** The ticket says *a stub with content*. Any present stub
  is a finding with its size, and the flow says to move a pointer-only stub aside unread — one
  rule instead of a byte comparison and a special case. The install still writes nothing.
- **An existing process is met at `/align`, for now.** The user, 2026-09-21: *the loop is not
  swappable* is too hard a rule; granularity and ceremony should be switchable — a level-of-ceremony
  setting, local steps, or configurable steps. That is the pacer's to design
  ([01-0020](../tickets/01-0020-pacer.md)) and reopens the cut
  [01-0017.0020](../tickets/01-0017.0020-practice-swaps-in-one-edit.md) drew; this slice writes the
  step as an `/align` and wraps the *for now* on the pacer.
- **The flow's section is an anchor.** The user's idea that the ticket mechanism should inject
  how a ticketing method is detected and integrated is the injector's existing shape — a rule in
  `ticket.rules.md` targeting the harness skill — and needs only a heading here to land under.
  The block itself is the ticket mechanism's, at its own align.
- **The repository line left for its own slice.** The first pass planned it here and found it
  carried its own comparison rule (a re-stamped line reads as an edit unless `_differs` sets it
  aside), its own proof (a subprocess of the recipient's copy, since the test process imports the
  origin's) and no dependence on the inventory or the flow; the stranger-tree grade does not
  exercise it. The `/impact` of the split carved it out; its decisions and those findings are on
  [01-0010.0155](../tickets/done/01-0010.0155-a-tree-names-the-repository-its-core-comes-from.md).
