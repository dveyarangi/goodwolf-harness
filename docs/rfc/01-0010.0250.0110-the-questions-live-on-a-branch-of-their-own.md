## The shape

**The branch and its checkout** (2). The questions are the branch `gw/questions`, which shares no
history with `main`. It is checked out once as a registered worktree at `<common>/gw/questions`.
`<common>` is `git rev-parse --git-common-dir`, so every worktree of the clone finds the same
checkout. Two things follow from registering the worktree:
- git refuses `git checkout gw/questions` in any code worktree;
- `git -C <checkout> status` names what changed in it.

Both were tried on 2026-11-17 with Git 2.32 for Windows, in a scratch repository with the
worktree inside `.git`.

**The link** (3). `docs/q` in every code worktree is a symbolic link with an absolute target, the
checkout. It is made where the skills' links are made: at install and update, and at a session's
start when the link is missing or resolves nowhere. Where Windows refuses a symlink, the
`mklink /D` command is named, the same as for the skills. The link is listed in the clone's
`info/exclude`, as the loader links are, never in a committed file. The pattern is `/docs/q`
with no trailing slash, because git sees a symlink as a file. No commit has held `docs/q`, so a
checkout of an old commit neither writes through the link nor removes it (the trial in
q-7ebz2f).

**The scripts find the store through git, not through the link.** `questions.py` locates the
checkout from `<common>`, and every other script reads the store through `questions`.

This choice is the agent's own, and it keeps decisions 2 and 3:
- the link is what agents and the person read and what links name;
- a worktree whose link Windows refused still writes and reads the store;
- the push check's temporary worktree (`harness.py` `pre_push`) has no link, and it still sees
  the store.

A tree without git, as the tests' plain folders, reads `docs/q` as a plain folder.

**A write** (12, 17, 19). Each call of `questions.py` that writes does the following, in order:

1. Write each entry atomically: a staging file, then a replace. `_Draft.write` writes in place
   today.
2. Check the entries the call touched.
3. Commit them by plumbing in the checkout, with no hook of the project's. The checkout's own
   index takes the touched paths; then `write-tree` and `commit-tree`; then
   `update-ref HEAD <new> <old>`. A ref or index lock that another session's write holds is
   retried a bounded number of times, then refused plainly, leaving the entry written but not
   committed. The next write takes it, as below.
4. The commit message is `<event> <q-id> — <session tag> @ <machine>`. `<machine>` is a short
   hash of the host name; no code gives one yet, and decision 9 will rely on the same value.
5. Push `gw/questions` to `origin` in a detached process that the call does not wait for, with
   its output logged to `<common>/gw/push.log`. A push that fails is caught up by the next one.
   With no `origin`, nothing is pushed.

The push goes through the project's `pre-push`, as decision 2 says. `hook.sh` wakes no check for
paths at the branch's root, so decision 19's "no check of the store's push" already holds; a test
pins it.

**What a session writes by hand** (5 is .0070's). An agent writes a question's body by hand today,
and decision 5's call on a fingerprint is [.0070](../tickets/01-0010.0250.0070-a-body-is-edited-on-its-fingerprint.md)'s.
This slice therefore keeps the files writable. Each write first takes in the hand changes that
`git status` names in the checkout:
- each one that passes the check is committed in a commit of its own,
  `taken <paths> — <tag> @ <machine>`, before the call's own commit;
- one that fails is left uncommitted and is named in the window, so it holds no other write
  back (12).

On one machine every session reads the checkout itself, so an edit not yet committed is already
seen by all. The commit is history and the push. The read-only flag and criterion 1's "a write to
a file there fails" move to .0070. **This needs the person's word — see *For the person*.**

**Links** (3, 6). A link into the store is `docs/q/<id>-<slug>.md` as written from its file, so
from `docs/tickets/` it is `../q/<id>-<slug>.md`. A link out of an entry is resolved by its text
from `docs/q/`, which lexically is the main checkout's `docs/`, and never through the link. The
link resolvers do the following:
- `docs_corpus.cited_record`'s users;
- `tickets.py`'s `_link_problems` and `_answers_problems`;
- `questions.py`'s `_resolves`;
- `move_doc`.

Each of them answers whether a path under `docs/q/` exists from the store's listing, not from
the file system, so a worktree without the link and the push copy resolve alike. `corpus()`
leaves the store out: it is excluded, so git lists none of it. Every reader that needs entries
goes through `questions`: `question_bindings`, the straw-dog counters and
`_records_naming_ids`.

**A record's move** (18). `move_doc` repairs the citations a move breaks in the code tree as
today. The citations inside entries it hands to one function of `questions`, which rewrites the
entries, checks them, commits them and pushes them as one write. That keeps the store to one
writer. `move_doc` takes `--session <tag>` for the commit; without it the tag is `-`. This flow
is decision 18's, and it lands in the architecture in stage 0.

**`/maintain`'s sweep** (13). `maintain.py`'s sweep mark gains the store's commit beside main's.
`landed` reads both ranges: main's, with `docs/q` out of `DECISION_HOMES`, and `gw/questions`'s
from its mark to its tip. A store mark that is not an ancestor of the tip is refused as main's
is.

**The window.** The window gains these lines:
- a line when `gw/questions` is ahead of `origin/gw/questions`, which is the store role's watch
  (17);
- a line naming each hand change that failed its check.

`_own_copy` and its `TODO q-4seese` go.

**A fresh tree** (seed). `seed` builds the roots' commit by plumbing: `hash-object`, `mktree`,
`commit-tree` with no parent, then `update-ref refs/heads/gw/questions`. It then adds the
worktree and makes the link. The installer's `_seed_store` calls it and commits nothing on the
code branch, as today.

**The migration** (6's once-run pattern; the cut-over in Where it stands' *What is open*). This
is `migrate_store.py`, of the questions mechanism, run once per tree like `migrate_ids.py`. In
order:

1. Refuse if `docs/questions` has uncommitted changes, if the branch already exists, or if
   `docs/q` stands as anything.
2. Commit the tree object `HEAD:docs/questions` with no parent, which is the store's first
   commit. Nothing is copied, and every entry's history before that stays in `main`'s log.
3. Add the worktree and make the link.
4. Remove `docs/questions` from the code tree.
5. Re-aim every link into it from `../questions/…` to `../q/…`, through `move_doc`'s citation
   repair with the mapping `docs/questions/<name>` → `docs/q/<name>`. Code under `.agents/` is
   left alone, as `migrate_ids` learned in 04e18cab.
6. List each local branch and worktree whose commits not on `main` touch `docs/questions`. Their
   changes would come back on a merge, and they are the person's to bring over.
7. Push the branch when `origin` exists. Leave the code tree's changes for the session to commit,
   as the installer and `migrate_ids` do.

A `--dry-run` names what it would do. In this tree it runs on the person's word, with every
running session told beforehand by the store role (17). The other trees get it through a note,
as with the ids.

The script carries a `TODO` naming the question its retirement waits on. The store has no such
question yet; implementation opens it beside q-ubd6uz.

**Prose.** These say `docs/q` and the new link form:
- the skills and formats that name `docs/questions/` (the survey's list in the impact below);
- `questions.md`;
- the architecture.

The straw dog on q-7ebz2f at `docs/architecture.md:83` ("Sessions share one checkout and its
main…") is rewritten when this lands, since its trigger is met.

## Stages

Each stage is test-first by `/tdd`, and the set stays green between stages.

0. **The architecture.** *Question store* gains the invariants of decisions 2, 3, 12, 18 and 19
   with pointers. Decision 17's "the script writes, commits and pushes" is wrapped as a straw dog
   bound to q-d4gf2u, since the server takes it. This stage holds markdown only.
1. **The store's place.** Add a locator of the checkout. `_entry_files` walks the checkout,
   skipping its `.git` file. `STORE` becomes `docs/q`. `_fitted_slug` measures against the longer
   of the link's path and the checkout's. The fixtures move from `docs/questions` to `docs/q`;
   `Store` stays a plain folder.
   - Tests: a store read from `<common>/gw/questions` with no link present; a worktree reading
     the main checkout's store; a tree without git reading `docs/q`.
2. **A write.** Atomic writes; the check of the touched entries before commit; the commit by
   plumbing with its message; the retry; the detached push.
   - Tests (in a real repository, `proves_a_process`): an `open` lands as one commit on
     `gw/questions` carrying the tag; no code commit holds it; a broken entry is refused with
     nothing committed; two writers at once leave two commits and no lost entry; no `origin`
     means no push; a push to a local bare `origin` arrives.
3. **Hand changes.** They are taken in before a call's commit; a failing one is named in the
   window and holds nothing back.
4. **Links and readers.** Store-aware resolution in the four resolvers; `corpus` leaves the store
   out; bindings and straw-dog counters read entries.
   - Tests: a ticket's `Answers` into `../q/` resolves in a copy with no link; a straw dog inside
     an entry is counted.
5. **The mover.** `move_doc` hands the repairs inside entries to `questions`.
   - Test: a ticket closed to `done/` leaves no `owner` link in an entry at its old place, and
     the repair is a commit on `gw/questions`.
6. **The sweep.** The two ranges and the store mark.
   - Test: a decision written on `gw/questions` after the mark is swept, and one written before
     it is not.
7. **The link and the seed.** The link in the link plan, the exclude, `hook.sh`'s start step,
   and the seed by plumbing.
   - Tests: install into a fresh tree yields the branch, the checkout and the link; a missing
     link is made at start; a refused one names the command; `git checkout` of a commit from
     before the move, and back, leaves the link and the store as they were (criterion 3).
8. **The push check.** `pre_push` reads the store through the locator.
   - Tests: a code push whose ticket links into `../q/` passes in its copy; a push of
     `gw/questions` wakes no check.
9. **The migration.** `migrate_store.py` with `--dry-run`, each refusal, and the listing of
   branches. Then the prose.
   - Test: a tree with `docs/questions` committed comes out with the branch, the checkout, the
     link, `docs/questions` gone and every `../questions/` link re-aimed, and its `--check`s
     pass.
10. **The cut-over here.** Run in this tree on the person's word, with every session told first.
    Live: on `main` and in a worktree, `docs/q/` shows the same questions; the code's
    `git status` shows nothing of them; an `open` from each lands on `gw/questions` with its tag
    (criteria 1–2). Then each other tree by its note (criterion 5).

- `move_doc.py`: `_records`, `refusal`, `_inside_repository` (it uses `resolve()`; a path
  through the link resolves outside a linked worktree), and `--session`.
- `maintain.py`: `DECISION_HOMES`, `landed`, `mark_sweep`, `_resolved`.
- `mechanisms.py`: `PAINTED_DOORS` gains `docs/q`.
- `harness.py`: the link plan, the exclude, `_seed_store`, `links_at_start`.
- `hook.sh`: the start step for `docs/q`.
- The fixtures in test_questions, test_tickets, test_product, test_maintain, test_harness,
  test_straw_dogs, test_mechanisms and test_migrate_ids.
- The prose:
  - `.agents/mechanisms/questions/questions.md`;
  - the questions skill, `QUESTION-FORMAT.md`, the ticket skill and `TICKET-FORMAT.md`;
  - `/verify`, `ADR-FORMAT.md`, `EDGE-FORMAT.md`;
  - `docs/architecture.md`;
  - every `../questions/` link in `docs/`.

**Must verify.**
- `straw_dogs.remove_straw_dog`, when a straw dog stands in an entry: its write must go through
  the store's writer, or the entry is written without a commit. That is the same rule as the
  mover's, and the same function.
- `sessions.py`'s carry-over from `docs/questions/sessions*` still runs in an old tree.
- `test/repository.py`'s `folder_listing`: `rglob` and directory symlinks.
- `harness._gate` at install.

**Hidden edges.**
- **Agents running at the cut-over.** Every running session is still writing `docs/questions`;
  the store role tells them and the person picks the moment.
- **Code branches that changed `docs/questions` before the cut-over.** Merging one brings the
  folder back. The migration lists them.
- **The store checkout is a worktree with a `.git` file.** Readers of the store skip it, and
  `git worktree prune` keeps it because it exists.
- **A deleted checkout.** If someone deletes the checkout, `git worktree prune` drops its
  registration. The locator then adds the worktree again from the branch, and the window says so.
- **Paths through a deep worktree.** These are longer than through the main checkout, hence the
  slug budget in stage 1.
- **One machine only.** Two clones pushing `gw/questions` would diverge. That is
  [q-56s4ar](../questions/q-56s4ar-how-does-a-machine-meet-the-trees-one-server.md)'s, and
  decision 15 sets a second clone aside.

**Leave alone.**
- The sessions' rows stay at `docs/sessions/rows/` on `main` until
  [.0090](../tickets/01-0010.0250.0090-the-rows-live-in-a-database.md).
- `former-ids.md` moves with the store unchanged.
- The id forms and `migrate_ids.py`'s stage 6 belong to q-ubd6uz.

**Recommendation.** Proceed. The slice is wide but mechanical once the store is found through
one locator. Its two decisions for the person are below.

## For the person

1. **Hand-written bodies until .0070.** Keep the files writable, and have every write take in
   hand changes after checking them (recommended). Or bring .0070's call on a fingerprint into
   this slice and make the files read-only now. The first moves criterion 1's "a write to a file
   there fails" to .0070.
2. **The other trees.** They migrate by running `migrate_store.py` from a note, as with the ids
   (recommended). The alternative is that the harness's update migrates them unasked. The update
   commits nothing and refuses a tree with uncommitted work, so the migration would stand half
   done until someone commits.
