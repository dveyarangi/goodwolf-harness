## The shape

**The branch and its checkout** (2). The questions are the branch `gw/questions`, which shares no
history with `main`.
- It is checked out once, as a registered worktree, at `<common>/gw/questions`, where `<common>`
  is `git rev-parse --git-common-dir`. Every worktree of the clone finds the same checkout.
- Because the worktree is registered, git refuses `git checkout gw/questions` in any code
  worktree, so nobody swaps the code for the questions by mistake.
- Tried on 2026-11-17 with Git 2.32 for Windows, in a scratch repository with the worktree inside
  `.git`.

**The link** (3). In every code worktree, `docs/q` is a symbolic link with an absolute target:
the checkout.
- It is made where the skills' links are made: at install and update, and at a session's start
  when the link is missing or points nowhere.
- Where Windows refuses a symlink, the `mklink /D` command is named, as for the skills.
- The link is listed in the clone's `info/exclude`, as the loader links are, never in a
  committed file. The pattern is `/docs/q` with no trailing slash, because git sees a symlink as
  a file.
- No commit has held `docs/q`, so checking out an old commit neither writes through the link nor
  removes it (the trial in q-7ebz2f).

**The scripts find the store through git, not through the link.** One locator decides where the
store is, by one rule:
- If `gw/questions` exists locally, or at `origin`, the store is its checkout. An `origin`-only
  branch is made local first.
- A checkout missing on disk is attached again. A stale registration is pruned first. If another
  session attached it in the meantime, that counts as done. `post-checkout` and similar hooks are
  suppressed, as `pre_push` suppresses them.
- With no such branch, the store is the folder `docs/questions`, as long as it holds entries. A
  tree not yet migrated reads and writes as today: in place and uncommitted. So every stage
  before the cut-over leaves this tree and every recipient working. This fallback carries a
  `TODO` naming the question of the migration's retirement.
- Only a tree with neither a branch nor entries is seeded.
- A tree without git, such as the tests' plain folders, reads `docs/q` as a plain folder.
- Once the branch exists, a `docs/questions/` holding entries on a code branch is a diagnostic.
  It means a session running scripts from before the move, or a branch cut before it.

Every other script reads the store through `questions`. This keeps decisions 2 and 3: the link
is what agents and the person read, and what links name. Reading through git is the agent's own
choice: a worktree whose link Windows refused still reads and writes the store, and so does the
push check's temporary worktree, which has no link.

**A write** (12, 17, 19). Each call of `questions.py` that writes does these steps, on the
branch's checkout:
1. **Check first.** It checks the entries it is about to write, counting only their own
   diagnostics, so a broken entry elsewhere holds nothing back (12). A refused write writes
   nothing.
2. **Write atomically.** Each entry is written through `questions._replace`. `_Draft.write` does
   not use it today.
3. **Commit by plumbing, with a private index.** It never uses the checkout's own index, so two
   writers at once never carry each other's paths.
   - `GIT_INDEX_FILE` is a temporary file; then `read-tree HEAD`, add the touched paths,
     `write-tree`, `commit-tree`, and `update-ref HEAD <new> <old>`.
   - If the swap is lost to another writer, it does the same again from the new `HEAD`, a
     bounded number of times. Then it refuses plainly and leaves the entry written; the next write
     takes it in (below).
   - No hook of the project's runs (2).
   - The message is `<event> <q-id> — <session tag> @ <machine>`. `<machine>` is a short hash of
     the host name; decision 9 will rely on the same value, and no code gives one yet.
4. **Push.** It pushes `gw/questions` to `origin` in a detached process the call does not wait
   for.
   - The push runs from the code worktree the call runs in, never from the checkout, which holds
     none of the project's files a hook may need.
   - It sets `GIT_TERMINAL_PROMPT=0` and allows no interactive credential prompt.
   - Its output replaces `<common>/gw/push.log` each time.
   - A failed push is caught up by the next one. With no `origin`, nothing is pushed.
   - The push goes through the project's own `pre-push` (2). `hook.sh` wakes no check for paths
     at the branch's root (`hook.sh:45`), so decision 19's "no check of the store's push" already
     holds. A test pins it.

The store's root commit carries a `.gitattributes` of `* -text`. That way an entry's bytes are
the same on every checkout, and its blob can be compared without git.

**What a session writes by hand** (decision 5 belongs to .0070). Today an agent writes a
question's body by hand. Decision 5's call on a fingerprint is
[.0070](../tickets/01-0010.0250.0070-a-body-is-edited-on-its-fingerprint.md)'s.

This slice therefore keeps the files writable. Each write first takes in the hand changes:
- **Finding them.** A hand change is an entry whose bytes differ from `HEAD`'s blob. They are
  found by hashing the files as git does, without an index.
- **One that passes its check** is committed in a commit of its own, before the call's own:
  `taken <paths> — by an unknown hand, taken by <tag> @ <machine>`. The commit says what it
  cannot know: who wrote the change.
- **One that fails** stays uncommitted and is named in the window. It holds no other write back
  (12).
- **A half-written body.** A body another session is still writing may be taken half-done, as a
  commit from a shared checkout may be today. The next write takes the rest.

On one machine, every session reads the checkout itself, so an edit not yet committed is already
seen by all. The commit only adds history and the push.

Tried on 2026-11-17:
- an agent's edit through a link into a checkout under `.git` is written;
- a search given `docs/q` finds its entries;
- a search of the whole tree does not, because neither git nor the search tools follow the link.
  So the questions skill tells an agent to search `docs/q` by name.

The read-only flag, and criterion 1's "a write to a file there fails", move to .0070.
**This needs the person's word — see *For the person*.**

**Links, and which check reads what** (3, 6, 13, 19). A link into the store is
`docs/q/<id>-<slug>.md`, written relative to the file it is in. From `docs/tickets/` it is
`../q/<id>-<slug>.md`. The checks split along the line the store now draws:

- **The store's own check** covers each entry's form and its links out. It runs on request and
  before each commit of the store (13, 19).
  - A link out of an entry is resolved by its text against `main`'s tree, with
    `git cat-file -e main:<path>` (3). It is never resolved through the link, and never against
    the worktree the script runs in.
  - A failing hand change is the store's problem alone.
- **A code tree's check** is a push of a code branch, `/verify`, or a session's `--check` in its
  worktree.
  - It reads the store as committed at `gw/questions`, never the checkout's files.
  - It checks only what the code says of the store: that a binding, an `Answers` link or a `TODO`
    names an entry that exists.
  - It runs no check of an entry itself (19).
- **A pairing across the two** is a ticket's `Answers` with its question's `owner`. It matches the
  ticket by its basename, whether live or under `done/`. This is because the mover rewrites the
  `owner` at once, while the ticket's move reaches `main` only with its branch (18).

So none of these holds a code push back: a branch behind `main`, a close on a worktree branch, or
a hand change gone wrong.

The link resolvers answer whether a path under `docs/q/` exists from the store's committed
listing. A worktree without the link and the push copy therefore resolve alike. The resolvers
are:
- the users of `docs_corpus.cited_record`;
- `_link_problems` and `_answers_problems` in `tickets.py`;
- `_resolves` in `questions.py`;
- `move_doc`.

`corpus()` leaves the store out, since git lists nothing through the link. Every reader that
needs entries goes through `questions`: `question_bindings`, `straw_dogs.survey`, the straw-dog
counters, and `_records_naming_ids`.

**A record's move** (18). `move_doc` repairs the citations a move breaks in the code tree, as
today.
- It hands the citations inside entries to one function of `questions`. That function rewrites
  the entries, checks them, commits and pushes, all as one write. The store keeps one writer.
- `straw_dogs.remove_straw_dog` hands a removal inside an entry to the same function.
- `move_doc` takes `--session <tag>` for the commit. Without it, the tag is `-`.
- Its `_inside_repository` treats a path under `docs/q/` as the store's, not by where `resolve()`
  lands.

This flow is decision 18's, and it lands in the architecture in stage 0.

**`/maintain`'s sweep.** The ticket's *What to build* says `/maintain` reads the store's history
(decision 2).
- The marks row in `docs/mechanisms/maintenance.md` holds `main`'s commit, then the store's.
- `landed` reads both ranges:
  - `main`'s range, with `docs/questions` kept in `DECISION_HOMES`, so what landed before the
    cut-over is still read;
  - `gw/questions`'s range, from its mark to its tip.
- The migration writes the store's root commit as its mark, since what that commit holds was
  already in `main`'s range. A fresh seed writes its own root commit.
- A store mark that is not an ancestor of the tip is refused, as `main`'s is.
- Decision 13's CI half has no counterpart here, because this tree runs no CI. A recipient's CI
  that checks questions reads the fetched `gw/questions`, and the arrival note says so.

**The window.** It gains three lines:
- one when `gw/questions` is ahead of `origin/gw/questions`, which is the store role's watch (17);
- one naming each hand change that failed its check;
- one when the link `docs/q` is missing in this worktree, naming the command.

Its git calls run with `--no-optional-locks`. The cost on every message is a `rev-parse`, an
ahead count, and hashing the entries against `HEAD`'s tree. Stage 3 measures it and holds it
under a tenth of a second on this tree. `_own_copy` and its `TODO q-4seese` go.

**A fresh tree** (seed). A tree is seeded only when it has no `gw/questions`, here or at
`origin`, and no entries in `docs/questions`.
- `seed` builds the roots' commit by plumbing: `hash-object`, `mktree`, and `commit-tree` with no
  parent.
- It creates the branch with `update-ref refs/heads/gw/questions <commit> ""`, which refuses a
  branch that already exists.
- It then adds the worktree and makes the link.
- The installer's `_seed_store` calls it on install and update alike. So a recipient's update
  before its migration seeds nothing, because the locator reads its old folder. A re-clone takes
  `origin`'s branch.

**The migration** (6's once-run pattern; the cut-over in Where it stands' *What is open*). It is
`migrate_store.py`, of the questions mechanism, run once per tree as `migrate_ids.py` was. It
does these steps:
1. **Refuses** if any of these hold:
   - `docs/questions` has uncommitted changes;
   - the branch already exists;
   - anything stands at `docs/q`;
   - any commit ever held `docs/q` (`git log --all -- docs/q`), since decision 3 asks for a path
     no commit has held.
2. **Commits** the tree object `HEAD:docs/questions`, plus the `.gitattributes`, with no parent,
   as the store's first commit. Nothing is copied by hand, and the history of every entry before
   that stays in `main`'s log.
3. **Sets up** the worktree, the link and the store's sweep mark.
4. **Removes** `docs/questions` from the code tree.
5. **Re-aims** every link into it from `../questions/…` to `../q/…`. It does this through
   `move_doc`'s citation repair, with the mapping `docs/questions/<name>` → `docs/q/<name>`. It
   leaves code under `.agents/` alone, as `migrate_ids` learned in 04e18cab.
6. **Lists** every local branch and worktree that lacks the cut-over commit. Each of them still
   holds `docs/questions` and writes it with its own scripts, so its changes would come back on
   a merge. Bringing them over is the person's call.
7. **Pushes** the branch when `origin` exists. It leaves the code tree's changes for the session
   to commit, as the installer and `migrate_ids` do.

A `--dry-run` names what it would do. In this tree it runs on the person's word, after the store
role has told every running session (17). The other trees get it through a note, as with the
ids. The script carries a `TODO` naming the question its retirement waits on. The store holds no
such question yet; implementation opens it beside q-ubd6uz.

**Prose.** Each of these comes to say `docs/q` and the new link form:
- the skills and formats that name `docs/questions/` (the survey's list, under Impact below);
- `questions.md`;
- the architecture;
- the questions skill, which also says to search `docs/q` by name.

The straw dog bound to q-7ebz2f at `docs/architecture.md:83` ("Sessions share one checkout and its
main…") falls due when this lands, and is rewritten then.

## Stages

Each stage is test-first by `/tdd`. This tree runs on the fallback until stage 10, so the set and
the push check stay green throughout.

0. **The architecture.** *Question store* takes in the invariants of decisions 2, 3, 12, 18 and
   19, with pointers, and the split of checks. Decision 17's "the script writes, commits and
   pushes" is wrapped as a straw dog bound to q-d4gf2u, since the server takes that over. This
   stage changes markdown only.
1. **The store's place.** The locator and its rule.
   - `_entry_files` walks what the locator gives, skipping the checkout's `.git` file.
   - `STORE` names `docs/q` for links, and `docs/questions` stays as the fallback.
   - `_fitted_slug` measures against whichever is longer, the path through the link or the
     checkout's path.
   - Fixtures keep `docs/questions` where they test the fallback, and gain `docs/q`.

   Tests:
   - with no branch, the store is read from `docs/questions`;
   - with the branch, it is read from `<common>/gw/questions`, with no link present;
   - a worktree reads the main checkout's store;
   - a branch that exists only at `origin` is made local;
   - a deleted checkout is attached again, after its stale registration is pruned;
   - a code branch that still has entries in `docs/questions` once the branch exists is a
     diagnostic.
2. **A write.** The check before writing; atomic writes; the commit by plumbing with a private
   index, its message, and the retry on a lost swap; the detached push from the code worktree.

   Tests (in a real repository, `proves_a_process`):
   - an `open` lands as one commit on `gw/questions` carrying the tag, and no code commit holds
     it;
   - a broken entry is refused, with nothing written and nothing committed: the file's bytes are
     unchanged;
   - two writers at once leave two commits, each carrying only its own paths and its own tag;
   - with no `origin`, nothing is pushed;
   - a push to a local bare `origin` arrives;
   - a push the remote refuses leaves the branch ahead, and the window says so.
3. **Hand changes.** They are found by hash against `HEAD`'s tree, and taken in before a call's
   commit as by an unknown hand. A failing one is named in the window and holds back neither a
   write nor a code push. The window's cost is measured.
4. **Links and the split of checks.** The store's own check runs against `main`'s tree. A code
   tree's check runs against the store's committed listing. The pairing matches by basename.
   `corpus` leaves the store out. Bindings, `straw_dogs.survey` and the counters read entries.

   Tests:
   - a ticket's `Answers` into `../q/` resolves in a copy with no link;
   - an entry's answer link to a doc newer than a branch does not hold back a push of that
     branch;
   - a ticket closed to `done/` on a worktree branch does not hold back a push of `main`;
   - a failing hand change does not hold back a code push;
   - a straw dog inside an entry is counted and listed.
5. **The mover and the straw-dog remover.** Both hand writes to an entry to `questions`.

   Tests:
   - after a ticket is closed to `done/`, no `owner` link in an entry points at its old place, and
     the repair is a commit on `gw/questions`;
   - a straw dog removed from an entry is a commit there;
   - a move run from a linked worktree is not refused as outside the repository.
6. **The sweep.** The two ranges, and the store's commit in the marks row.

   Tests:
   - a decision written on `gw/questions` after the mark is swept, and one written before it is
     not;
   - a decision landed in `docs/questions` on `main` before the cut-over is still swept.
7. **The link and the seed.** The link in the link plan, the exclude, `hook.sh`'s start step, and
   the seed by plumbing that only creates.

   Tests:
   - an install into a fresh tree yields the branch, the checkout and the link;
   - an update of a tree not yet migrated seeds nothing;
   - a re-clone takes `origin`'s branch;
   - a missing link is made at start, and a refused one names the command;
   - a `git checkout` of a commit from before the move, and back, leaves the link and the store
     as they were (criterion 3).
8. **The push check.** `pre_push` reads the store through the locator.

   Tests:
   - a code push whose ticket links into `../q/` passes in its copy;
   - a push of `gw/questions` wakes no check.
9. **The migration.** `migrate_store.py`, its `--dry-run`, each refusal (including a commit that
   held `docs/q`), and the listing of branches without the cut-over. Then the prose, including
   the questions skill telling an agent to search `docs/q` by name.

   Test: a tree with `docs/questions` committed comes out with:
   - the branch and its `.gitattributes`;
   - the checkout and the link;
   - the store's mark;
   - `docs/questions` gone, and every `../questions/` link re-aimed;
   - its `--check`s passing.
10. **The cut-over here.** It runs in this tree on the person's word, after every session is told.

    Live checks:
    - on `main` and in a worktree, `docs/q/` shows the same questions;
    - the code's `git status` shows nothing of them;
    - an `open` from each lands on `gw/questions` with its tag (criteria 1–2).

    Then each other tree migrates by its note (criterion 5).

**Hidden edges.**
- **Agents running at the cut-over** keep writing `docs/questions` with their own scripts. The
  store role tells every running session, and the person picks the moment. After the cut-over, a
  `docs/questions/` with entries on a code branch is a diagnostic.
- **Branches cut before the cut-over** bring the folder back on a merge. The migration lists
  them.
- **The store checkout is a worktree with a `.git` file.** Readers skip it.
- **A checkout deleted by hand stays registered**, since git prunes only after three months by
  default. So the locator prunes before it attaches, and when two sessions attach at once, each
  takes the other's attach as done.
- **Windows refuses a symlink** on this machine without the privilege, as with the skills. The
  person runs the named `mklink /D` once per checkout; the scripts work meanwhile.
- **A search of the whole tree does not see the questions.** An agent searches `docs/q` by name.
- **Paths through a deep worktree** are longer than through the main checkout, hence the slug
  budget in stage 1.
- **One machine only.** Two clones pushing `gw/questions` would diverge. That belongs to
  [q-56s4ar](../questions/q-56s4ar-how-does-a-machine-meet-the-trees-one-server.md), and decision
  15 sets a second clone aside.

**Recommendation.** Proceed. The slice is wide but mechanical once one locator finds the store

**Validation, 2026-11-17.** A reviewer that did not write the plan judged its first draft. They
confirmed the six facts it asserts in code and by trial, and found three blocking problems:
- the tree would break between the locator and the migration;
- an update would seed over a recipient's store;
- code pushes would be checked against the live store.

They also found nine to fix, chiefly the shared index, checking after writing, the authorship of
taken changes, re-attaching a checkout, and where the push runs. This amendment answers all of
them.

## For the person

1. **Hand-written bodies until .0070.** I recommend keeping the files writable: every write
   takes in the hand changes after checking them, committed as by an unknown hand. This moves
   criterion 1's "a write to a file there fails" to .0070, and we cannot know who wrote a body
   until .0070.

   The alternative is to bring .0070's call on a fingerprint into this slice and make the files
   read-only now.
2. **The other trees.** I recommend that they migrate by running `migrate_store.py` from a note,
   as they did with the ids.

   The alternative is for the harness's update to migrate them unasked. But the update commits
   nothing and refuses a tree with uncommitted work, so the migration would stand half done
   until someone commits.
