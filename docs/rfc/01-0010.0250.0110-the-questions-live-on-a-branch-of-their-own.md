## The shape

**The branch and its checkout** (2). The questions are the branch `gw/questions`, which shares no
history with `main`.
- It is checked out once, as a registered worktree, at `<common>/gw/questions`, where `<common>`
  is `git rev-parse --git-common-dir`. Every worktree of the clone finds the same checkout.
- Because the worktree is registered, git refuses `git checkout gw/questions` in any code
  worktree, so nobody swaps the code for the questions by mistake.
- Tried on 2026-11-17 with Git for Windows, in a scratch repository with the worktree inside
  `.git`; tried again on 2026-11-18 with Git 2.39.1, the version on this machine.

**The link** (3). In every code worktree, `docs/q` is a symbolic link with an absolute target:
the checkout.
- It is made where the skills' links are made: at install and update, and at a session's start
  when the link is missing or points nowhere. It is made only where `gw/questions` exists, so a
  tree still reading `docs/questions` gets no `docs/q`, and its migration is not refused for one.
- Where Windows refuses a symlink, the link is a junction, which needs no privilege, so the
  person runs nothing (decision 3 as amended 2026-11-17). Read, Edit and a search given `docs/q`
  go through a junction. The link plan's refusal of a junction stays for the loader links alone
  (ADR-0003, scoped the same day).
- The link is listed in the clone's `info/exclude`, as the loader links are, never in a
  committed file. The pattern is `/docs/q` with no trailing slash: git sees a symlink as a file
  and a junction as a folder, and the pattern matches both. With it, git lists nothing beneath a
  junction, whose target is a checkout with a `.git` of its own (tried 2026-11-17).
- **No script walks into a link** of either kind (decision 3). Every walk of a folder goes
  through one function that skips a symlink and a junction alike. The walks today are
  `questions._walked`, which walks `docs/` on every message for the counters,
  `straw_dogs.survey`, `maintain`'s skill walk, `mechanisms`' home walk, `amendment`'s skill
  walk, `harness`'s removal of empty folders, and the tests' `folder_listing`. A junction is not
  a symlink to Python, so the skip uses the check `harness` already has for one.
- No commit has held `docs/q`, so checking out an old commit neither writes through the link nor
  removes it (the trial in q-7ebz2f).

**The scripts find the store through git, not through the link.** One locator decides where the
store is, by one rule:
- If `gw/questions` exists locally, or at `origin`, the store is its checkout. An `origin`-only
  branch is made local first.
- A checkout missing on disk is attached again with `git worktree add -f <path> gw/questions`,
  which re-attaches that one stale registration and prunes no other (tried 2026-11-18). If
  another session attached it in the meantime, that counts as done. `post-checkout` and similar hooks are
  suppressed, as `pre_push` suppresses them.
- With no such branch, the store is the folder `docs/questions`, as long as it holds entries. A
  tree not yet migrated reads and writes as today: in place and uncommitted. So every stage
  before the cut-over leaves this tree and every recipient working. This fallback carries a
  `TODO` naming the question of the migration's retirement.
- Only a tree with neither a branch nor entries is seeded.
- A tree without git, such as the tests' plain folders, reads `docs/q` as a plain folder.
- Once the branch exists, a `docs/questions/` holding entries on a code branch is a diagnostic.
  It means a session running scripts from before the move, or a branch cut before it.

Every other script reads the store through `questions`. This keeps decisions 2 and 3: the link
is what agents and the person read, and what links name. Reading through git is the agent's own
choice: a worktree whose link is not yet made still reads and writes the store, and so does the
push check's temporary worktree, which has no link.

**A write** (12, 17, 19). Each call of `questions.py` that writes does these steps, on the
branch's checkout:
1. **Take the store's lock.** One writer at a time: the call creates `<common>/gw/questions.lock`
   exclusively, holding its pid and time, and removes it once its commit lands, before the push.
   - This is the one writer that A42, as narrowed on 2026-11-16, gives the store (q-ntoyr3), held
     by the scripts until the server is that writer
     ([.0030](../tickets/01-0010.0250.0030-a-session-in-a-worktree-opens-a-question-through-the-coordinator.md)).
     It carries a `TODO q-d4gf2u`.
   - A lock older than a fixed bound, far above a write's second, is dead whatever its pid, and
     the writer that meets it removes it. A writer that meets a live one waits a bounded time,
     then refuses plainly, having written nothing.
   - Under the lock no other script's write is in flight, so the hand changes taken in below are
     a hand's, and two writers never touch one entry at once. A writer that marks its paths
     instead was planned and judged on 2026-11-18: each pass found a new race in the marks.
2. **Check first.** Under the lock, it checks the entries it is about to write, counting only
   their own diagnostics, so a broken entry elsewhere holds nothing back (12). A refused write
   writes nothing.
3. **Write atomically.** Each entry is written through `questions._replace`. `_Draft.write` does
   not use it today.
4. **Commit by plumbing, with a private index.** It never uses the checkout's own index, which a
   person's git command may hold.
   - `GIT_INDEX_FILE` is a temporary file; then `read-tree HEAD`, add the touched paths,
     `write-tree`, `commit-tree`, and `update-ref HEAD <new> <old>`.
   - The swap can be lost only to a hand outside the scripts, a person's own git command on the
     branch. Then the call refuses plainly and leaves the entry written; the next write takes it
     in (below).
   - After the commit it leaves `HEAD`'s listing of blobs beside the checkout, keyed by the
     commit's id, for the window.
   - No hook of the project's runs (2).
   - The message is `<event> <q-id> — <session tag> @ <machine>`. `<machine>` is a short hash of
     the host name; decision 9 will rely on the same value, and no code gives one yet.
5. **Push.** It pushes `gw/questions` to `origin` in a detached process the call does not wait
   for.
   - The push runs from the code worktree the call runs in, never from the checkout, which holds
     none of the project's files a hook may need.
   - It sets `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so neither git nor Git
     Credential Manager opens a prompt.
   - On this host the detached child outlives the call, though Windows refuses it a break from
     the host's job (tried 2026-11-18); other hosts are untried, so stage 10 checks it live.
   - Its output replaces `<common>/gw/push.log` each time.
   - A failed push is caught up by the next one. With no `origin`, nothing is pushed.
   - The push goes through the project's own `pre-push` (2). `hook.sh` wakes no check for paths
     at the branch's root (`hook.sh:45`), so decision 19's "no check of the store's push" already
     holds. A test pins it.

The store's root commit carries a `.gitattributes` of `* -text`. That way an entry's bytes are
the same on every checkout, and its blob can be compared without git.

**What a session writes by hand** (decision 5 belongs to .0070). Today an agent writes a
question's body by hand. Decision 5's call on a fingerprint is
[.0070](../tickets/01-0010.0250.0070-a-body-is-edited-on-its-fingerprint.md)'s.

This slice therefore keeps the files writable (the person, 2026-11-18). Each write first takes in
the hand changes:
- **Finding them.** Under the lock, a hand change is an entry whose bytes differ from `HEAD`'s
  blob, or a new file in the store. They are found by hashing the files as git does, without an
  index.
- **A deleted entry** is never taken: the window names it, and its blob stays committed until a
  person restores it or removes it by git.
- **One that passes its check** is committed in a commit of its own, before the call's own:
  `taken <paths> — by an unknown hand, taken by <tag> @ <machine>`. The commit says what it
  cannot know: who wrote the change.
- **One that fails** stays uncommitted and is named in the window. It holds no other write back
  (12).
- **A half-written body.** A body another session is still writing may be taken half-done, as a
  commit from a shared checkout may be today. The next write takes the rest.

On one machine, every session reads the checkout itself, so an edit not yet committed is already
seen by all. The commit only adds history and the push.

Tried on 2026-11-17:
- an agent's edit through a link into a checkout under `.git` is written;
- a search given `docs/q` finds its entries;
- a search of the whole tree does not, because neither git nor the search tools follow the link.
  So the questions skill tells an agent to search `docs/q` by name.

The read-only flag, and criterion 1's "a write to a file there fails", move to .0070 (*Decided
by the person*). The rule that a hand change is committed as by an unknown hand lands in the
architecture in stage 0, as a straw dog bound to q-icoiq7, whose fingerprint call ends it.

**Links, and which check reads what** (3, 6, 13, 19). A link into the store is
`docs/q/<id>-<slug>.md`, written relative to the file it is in. From `docs/tickets/` it is
`../q/<id>-<slug>.md`. The checks split along the line the store now draws:

- **The store's own check** covers each entry's form and its links out. It runs on request and
  before each commit of the store (13, 19).
  - A link out of an entry is resolved by its text against the main checkout's files (3), with
    its anchor read from the file's content as `_resolves` reads it today. The main checkout is
    the folder holding the common Git directory when that directory is named `.git` and is not
    bare, found without a git call, and no branch name is assumed, so a tree on `master` resolves
    alike. A clone with a separate or bare Git directory has no main checkout to find (tried
    2026-11-18): there a link out resolves against the worktree the script runs in alone.
  - A write also accepts a link that resolves in the worktree it runs in: a close from a
    worktree cites a record on that worktree's branch, or one not yet committed. Until the branch
    reaches the main checkout, the store's own check there names the link, and it holds back
    neither a write elsewhere nor a code push.
  - It is never resolved through the link.
  - A failing hand change is the store's problem alone.
- **A code tree's check** is a push of a code branch, `/verify`, or a session's `--check` in its
  worktree.
  - It reads the store as committed at `gw/questions`, never the checkout's files.
  - It checks only what the code says of the store: that a binding, an `Answers` link or a `TODO`
    names an entry that exists.
  - It runs no check of an entry itself (19).
- **A pairing across the two** is a ticket's `Answers` with its question's `owner`. It matches the
  ticket by its basename, whether live or under `done/`. This is because the mover rewrites the
  `owner` at once, while the ticket's move reaches `main` only with its branch (18).

So none of these holds a code push back: a branch behind `main`, a close on a worktree branch, or
a hand change gone wrong.

The link resolvers answer whether a path under `docs/q/` exists from the store's committed
listing. A worktree without the link and the push copy therefore resolve alike. The resolvers
are:
- the users of `docs_corpus.cited_record`;
- `_link_problems` and `_answers_problems` in `tickets.py`;
- `_resolves` in `questions.py`;
- `move_doc`.

`corpus()` leaves `docs/q` out, since git lists nothing through the link; it keeps
`docs/questions`, which a tree not yet migrated still holds. Every reader that
needs entries goes through `questions`: `question_bindings`, `straw_dogs.survey`, the straw-dog
counters, and `_records_naming_ids`.

**A record's move** (18). `move_doc` repairs the citations a move breaks in the code tree, as
today.
- It hands the citations inside entries to one function of `questions`. That function rewrites
  the entries, checks them, commits and pushes, all as one write. The store keeps one writer.
- `straw_dogs.remove_straw_dog` hands a removal inside an entry to the same function.
- `move_doc` takes `--session <tag>` for the commit. Without it, the tag is `-`.
- Its `_inside_repository` treats a path under `docs/q/` as the store's, not by where `resolve()`
  lands.

This flow is decision 18's, and it lands in the architecture in stage 0.

**`/maintain`'s sweep.** The ticket's *What to build* says `/maintain` reads the store's history
(decision 2).
- The marks row in `docs/mechanisms/maintenance.md` holds the code's commit, then the store's.
  The code's range ends at `HEAD` where the sweep runs, as today's does (`maintain.py:425`).
- `landed` reads both ranges:
  - the code's range, with `docs/questions` kept in `DECISION_HOMES`, so what landed before the
    cut-over is still read; the cut-over commit's deletions of `docs/questions` are the
    migration's, not decisions, and the sweep passes over them;
  - `gw/questions`'s range, from its mark to its tip.
- The migration writes the store's root commit as its mark, since what that commit holds was
  already in `main`'s range. A fresh seed writes its own root commit.
- A store mark that is not an ancestor of the tip is refused, as `main`'s is.
- Decision 13's CI half has no counterpart here, because this tree runs no CI. A recipient's CI
  that checks questions reads the fetched `gw/questions`, and the arrival note says so.

**The window.** It gains three lines:
- one when `gw/questions` and `origin/gw/questions` stand at different commits, which is the
  store role's watch (17);
- one naming each hand change that failed its check, and each deleted entry;
- one when the link `docs/q` is missing in this worktree where the branch exists.

It makes no git call on a message as a rule: one costs 83–95 ms on this machine (measured
2026-11-18).
- The two tips are read from the ref files, loose or in `packed-refs`. A read that fails while
  `update-ref` renames the file, an `OSError`, shows no line and says so. A reftable repository
  has no ref files, and the window says it reads none there.
- `HEAD`'s listing of blobs is the one the last writer left beside the checkout, keyed by the
  commit's id. Only when it is missing, after a fetch or a person's own commit, does the window
  run one `ls-tree` and leave the listing for the next.
- An entry's hash is kept by its size and time, as `_walked` keeps the counters, so only a
  changed file is hashed again.

The window already costs about half a second on this tree before any change (`read_store`,
measured 2026-11-18). Stage 3 measures what the three lines add with the caches warm and holds
that under a tenth of a second.
`_own_copy` and its `TODO q-4seese` stay while a tree reads `docs/questions`, where their warning
still holds, and go with the fallback. The window's `(root/STORE).is_dir()` and the session
script's own test of the store's folder (`sessions.py:726`) go through the locator.

**A fresh tree** (seed). A tree is seeded only when it has no `gw/questions`, here or at
`origin`, and no entries in `docs/questions`.
- `seed` builds the roots' commit by plumbing: `hash-object`, `mktree`, and `commit-tree` with no
  parent.
- It creates the branch with `update-ref refs/heads/gw/questions <commit> ""`, which refuses a
  branch that already exists.
- It then adds the worktree and makes the link.
- The installer's `_seed_store` calls it on install and update alike. So a recipient's update
  before its migration seeds nothing, because the locator reads its old folder. A re-clone takes
  `origin`'s branch.

**The migration** (6's once-run pattern; the cut-over in Where it stands' *What is open*). It is
`migrate_store.py`, of the questions mechanism, run once per tree as `migrate_ids.py` was. It
does these steps:
1. **Refuses** if any of these hold:
   - `docs/questions` has uncommitted changes;
   - the branch already exists;
   - anything stands at `docs/q`;
   - any commit ever held `docs/q` (`git log --all -- docs/q`), since decision 3 asks for a path
     no commit has held;
   - an entry still bears an id from before the ids' migration, since the converted ids must
     exist before the store leaves `main` (q-7ebz2f). `migrate_ids.py` keeps a `docs/questions`
     of its own rather than `questions.STORE`, so it never writes under `docs/q`.
2. **Commits** the tree object `HEAD:docs/questions`, plus the `.gitattributes`, with no parent,
   as the store's first commit. Nothing is copied by hand, and the history of every entry before
   that stays in `main`'s log.
3. **Sets up** the worktree, the link and the store's sweep mark.
4. **Removes** `docs/questions` from the code tree.
5. **Re-aims** every link into it from `../questions/…` to `../q/…`. It does this through
   `move_doc`'s citation repair, with the mapping `docs/questions/<name>` → `docs/q/<name>`.
   `move_doc` refuses a destination that exists and a source missing from the corpus
   (`move_doc.py:187–209`), so its repair gets an entry point of its own that moves nothing. It
   leaves code under `.agents/` alone, as `migrate_ids` learned in 04e18cab.
6. **Lists** every local branch and worktree that lacks the cut-over commit. Each of them still
   holds `docs/questions` and writes it with its own scripts, so its changes would come back on
   a merge. Bringing them over is the person's call.
7. **Pushes** the branch when `origin` exists. It leaves the code tree's changes for the session
   to commit, as the installer and `migrate_ids` do.

A `--dry-run` names what it would do. In this tree it runs on the person's word, after the store
role has told every running session (17). The other trees get it through a note, as with the
ids. The script carries a `TODO` naming the question its retirement waits on. The store holds no
such question yet; implementation opens it beside q-ubd6uz.

**Prose.** Each of these comes to say `docs/q` and the new link form:
- the skills and formats that name `docs/questions/` (the survey's list, under Impact below);
- `questions.md`;
- the architecture;
- the questions skill, which also says to search `docs/q` by name.

The straw dog bound to q-7ebz2f at `docs/architecture.md:83` ("Sessions share one checkout and its
main…") falls due when this lands, and is rewritten then.

**The rows' place** ([q-k5r3qw](../questions/q-k5r3qw-where-does-a-session-whose-hook-and-shell-stand-in-two-trees-of-one-clone-find-its-row-and-the-store.md) 1). The sessions' rows stay files under
`docs/sessions/rows/`, read and written in the main checkout, found as for links out of an entry,
and in the calling tree where a clone has no main checkout to find.
- Every reader and writer of the rows reaches them through the session script's module, whose
  callers pass different roots today: `sessions.py` the current directory, `questions.py` the tree
  its file stands in, the hook the tree the host starts it in. The rows' folder is resolved there
  from whatever root is passed, once, so no caller changes.
- The code carries `TODO q-pl3fwk`: .0090 moves the rows into the server's database.
- A worktree branch's own copy of the rows stays in its history, read by nothing. A row that
  stands only in a worktree's copy is not carried over: that session's next `--wake` registers it
  in the main checkout.
- A row written from a worktree changes the main checkout's files, committed there as any row
  is now.

## Stages

Each stage is test-first by `/tdd`. This tree runs on the fallback until stage 10, so the set and
the push check stay green throughout.

0. **The architecture.** *Question store* takes in the invariants of decisions 2, 3, 12, 18 and
   19, with pointers, and the split of checks. Decision 17's "the script writes, commits and
   pushes" is wrapped as a straw dog bound to q-d4gf2u, since the server takes that over, and so
   is the store's lock: its straw dog *it locks nothing* comes to say that the store's scripts
   take one short lock per write until the server is the store's one writer. This stage changes
   markdown only.
1. **The store's place.** The locator and its rule.
   - `_entry_files` walks what the locator gives, skipping the checkout's `.git` file.
   - `STORE` names `docs/q` for links, and `docs/questions` stays as the fallback. What derives
     from `STORE` — `_ENTRY_NAME`, `NOT_HOMES`, `FORMER_IDS`, record names
     (`questions.py:94,120,144,2354`) — accepts both prefixes until the fallback goes, tested on a
     tree that still reads `docs/questions`.
   - `_fitted_slug` measures against whichever is longer, the path through the link or the
     checkout's path.
   - Fixtures keep `docs/questions` where they test the fallback, and gain `docs/q`.
   - The rows' place, sharing the main checkout's finder with stage 4.

   Tests:
   - with no branch, the store is read from `docs/questions`;
   - with the branch, it is read from `<common>/gw/questions`, with no link present;
   - a worktree reads the main checkout's store;
   - a branch that exists only at `origin` is made local;
   - a deleted checkout is attached again, after its stale registration is pruned;
   - a code branch that still has entries in `docs/questions` once the branch exists is a
     diagnostic;
   - a session registered from the main checkout is taken by `at` run from a worktree, its cwd
     there, and the window drawn there lists the same rows;
   - in a clone with a separate Git directory, a worktree reads its own rows.
2. **A write.** The check before writing; atomic writes; the commit by plumbing with a private
   index, its message, and the retry on a lost swap; the detached push from the code worktree.

   Tests (in a real repository, `proves_a_process`):
   - an `open` lands as one commit on `gw/questions` carrying the tag, and no code commit holds
     it;
   - a broken entry is refused, with nothing written and nothing committed: the file's bytes are
     unchanged;
   - a writer holding the lock makes a second wait: the second, forced to start between the
     first's write and its commit, takes nothing of the first's in, and two commits land, each
     carrying only its own paths and its own tag;
   - a writer that waits past the bound refuses, having written nothing;
   - a lock past its age is removed by the next writer, whatever its pid;
   - a swap lost to a person's own commit on the branch refuses, the entry left for the next
     write;
   - with no `origin`, nothing is pushed;
   - a push to a local bare `origin` arrives;
   - a push the remote refuses leaves the branch ahead, and the window says so.
3. **Hand changes.** They are found by hash against `HEAD`'s tree, and taken in before a call's
   commit as by an unknown hand; a new file is taken, a deleted entry is named and not taken. A
   failing one is named in the window and holds back neither a write nor a code push. The
   window's cost is measured with its caches, cold and warm.
4. **Links and the split of checks.** The store's own check runs against the main checkout's
   files, and a write against its own worktree's too. A code tree's check runs against the
   store's committed listing. The pairing matches by basename. `corpus` leaves `docs/q` out.
   Bindings, `straw_dogs.survey` and the counters read entries.

   Tests:
   - a close citing a doc not yet committed lands;
   - a tree whose branch is `master` resolves an entry's links out;
   - a ticket's `Answers` into `../q/` resolves in a copy with no link;
   - an entry's answer link to a doc newer than a branch does not hold back a push of that
     branch;
   - a ticket closed to `done/` on a worktree branch does not hold back a push of `main`;
   - a failing hand change does not hold back a code push;
   - a straw dog inside an entry is counted and listed.
5. **The mover and the straw-dog remover.** Both hand writes to an entry to `questions`.

   Tests:
   - after a ticket is closed to `done/`, no `owner` link in an entry points at its old place, and
     the repair is a commit on `gw/questions`;
   - a straw dog removed from an entry is a commit there;
   - a move run from a linked worktree is not refused as outside the repository.
6. **The sweep.** The two ranges, and the store's commit in the marks row.

   Tests:
   - a decision written on `gw/questions` after the mark is swept, and one written before it is
     not;
   - a decision landed in `docs/questions` on `main` before the cut-over is still swept.
7. **The link and the seed.** The link in the link plan, the exclude, `hook.sh`'s start step, and
   the seed by plumbing that only creates.

   Tests:
   - an install into a fresh tree yields the branch, the checkout and the link;
   - an update of a tree not yet migrated seeds nothing and makes no `docs/q`;
   - a re-clone takes `origin`'s branch;
   - a missing link is made at start;
   - where a symlink is refused, a junction is made, an entry is read through it, and git lists
     nothing beneath it;
   - a walk of `docs/` skips a symlink and a junction alike, so a straw dog in an entry is
     counted once, by the counters' walk and the survey both;
   - a `git checkout` of a commit from before the move, and back, leaves the link and the store
     as they were (criterion 3).
8. **The push check.** `pre_push` reads only the code's references into the store, against the
   store as committed at `gw/questions`, which the locator finds.

   Tests:
   - a code push whose ticket links into `../q/` passes in its copy;
   - a push of `gw/questions` wakes no check.
9. **The migration.** `migrate_store.py`, its `--dry-run`, each refusal (including a commit that
   held `docs/q`, and an id not yet converted), `move_doc`'s repair-only entry point, and the
   listing of branches without the cut-over. Then the prose, including
   the questions skill telling an agent to search `docs/q` by name.

   Test: a tree with `docs/questions` committed comes out with:
   - the branch and its `.gitattributes`;
   - the checkout and the link;
   - the store's mark;
   - `docs/questions` gone, and every `../questions/` link re-aimed;
   - its `--check`s passing.
10. **The cut-over here.** It runs in this tree on the person's word, after every session is told.

    Live checks:

    Then each other tree migrates by its note (criterion 6).

A lock is needed: the ref's own swap cannot tell a write in flight from a hand change. Found, each
shown by running it unless said otherwise:
1. *Overlapping pushes leave the tip unpushed*, likely daily: two writes within a second, the remote
   taking one or two, the second rejected in four of four runs, unpushed until a later write. The
   pusher re-reads the tip and repeats, bounded, until origin holds it.
2. *The checkout's own index goes stale at every plumbing commit*: a person's `git add` and bare
   commit there took the writers' entry back and deleted a new one; `git checkout -- .` restored the
   old text, which the next write committed. `read-tree HEAD` on the real index after the swap,
   0.07 s, leaves the status clean.
3. *`update-ref HEAD` writes whatever `HEAD` names*: detached, mid-rebase or on another branch the
   call answers success and `gw/questions` does not move. The branch is named, and `HEAD` elsewhere
   refuses.
4. *A dead writer stops the store until the lock's age bound.*
5. *A waiter that reads the lock file keeps its holder from deleting it on Windows*, and waiters met
   a half-written lock and `PermissionError`.
6. *Breaking by age admits two holders*: two waiters on one stale lock, a holder slower than the
   bound, a machine asleep between the recheck and the write, where another session's line vanished
   from `HEAD` with no refusal, `old` being read after the write; a clock that jumps; and a release
   that removes its successor's lock.
7. *A lost swap invites a second `open`* of one question, the refused call having left its entry.
8. *`_replace` meets readers* on Windows, 5 refusals in 300 under readers with no pause: a short retry.

In place of the lock file, an operating-system lock on a file that stays (`msvcrt`, `fcntl`), as the
[plan of .0030](01-0010.0250.0030-a-session-in-a-worktree-opens-a-question-through-the-coordinator.md)
already takes for the coordinator: the same five crash points, no call refused, freed 0.02 s after a
kill. It ends 4 to 6; `old` is then captured as the lock is taken. One write holds about 1 to 1.5 s;
with ten sessions writing twice, a wait of 5 s refused ten calls of twenty, 20 s none, and the plan
gives no number.

*Tests.* With no lock three of the four fail; a check before creating, a lock taken after the read
and an unhandled `PermissionError` pass all four. To add: several writers on one entry, a killed
writer with the next landing promptly, a slow holder, a detached `HEAD`, a clean status after a
write, two overlapping pushes.

*Contradictions.* Stage 2's "retry on a lost swap" against step 4, which refuses; that refusal,
leaving the entry written, against decision 12; "the one writer that A42 gives", where A42 says the
coordinator alone and decision 17 is the warrant; stage 0 leaving the architecture's "Nor does it
promise safe simultaneous writers". *Unstated:* whether `at` with only a row, the worktree's attach,
the seed and the migration take the lock; that taking hand changes in precedes step 3; that the
mover takes it before it moves a file; that a `.tmp` left over is no new entry. *Not tried:* network
and synced drives, sleep itself, a live scanner, other systems, GitHub, attach and migration races.

Each pass found blocking problems the other did not. Both sets sit where the slice meets what
already exists: recipients' trees, concurrent writers, the scripts' own walks. The design's core
