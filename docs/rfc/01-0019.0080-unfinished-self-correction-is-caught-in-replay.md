## Scope and shaping facts

The question's accepted scope is one offline experiment: no live hooks, service or voice stage.
All files live under `docs/research/repair-replay/`; none ships in core. The architecture's
**Responsibilities** leaves semantic judgement to the reader and mechanical validation to the
script. The question's **Where it stands** owns that separation for this experiment.

`replay.py packet CASES` produces a reader packet containing the brief and unlabelled cases.
Each case carries its sources and a SHA-256 digest of its canonical JSON. `replay.py evaluate
CASES REVIEWS` validates one review per case before producing any report. Reviews name the case,
digest, verdict (`allow`, `return`, `unknown`), reason and quotations with source names. A return
requires quotations from the rule, conversation and work trace; every quote must occur in that
source. This validates support locations, never entailment.

An allow previews `{}`; a return previews the documented Stop block with the reader's reason.
Unknown and `stop_hook_active` produce an inconclusive or limit result with no hook preview.
They never masquerade as a passed check. Malformed or stale input exits unsuccessfully with no
stdout decision. This command is a replay tool, not a hook executable.

## Stages and verification

1. One CLI test for a supported return, seen red before the implementation; implement that path.
2. Add public-CLI tests and implementation for legitimate stops, uncertainty, the retry bound,
   stale or fabricated evidence, and incomplete/duplicate review sets.
3. Have fresh readers evaluate the unlabelled packets, save their verbatim readings, and report
   agreement with the previous independent readings on the four recorded cases. A constructed
   completed-repair control and an insufficient-context control remain labelled as constructed
   in the research record, never presented as events that occurred.
4. An independent verifier reviews the implementation and evidence without the builder's
   conclusion. Run the research tests and the project's verification set.

## Impact

### Impact

One local research tool and saved evidence; it implements the question's scoped experiment.

### Hidden edges

An independent reader can still be wrong. Quotation validation cannot prove a missing action.
The full host transcript and a real Stop execution are absent. No labelled expected outcomes
enter a reader packet. A model/provider adapter is outside this slice.

### Leave alone

Core, host configuration, live turn continuation, voice and other sessions' units.

### Recommendation

Proceed with the offline experiment. The recorded omission is the cheapest falsifying case;
the three legitimate stops catch a check that merely demands a next-step sentence.
