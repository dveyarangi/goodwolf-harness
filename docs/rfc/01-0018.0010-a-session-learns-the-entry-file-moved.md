# A session learns the entry file moved under it — implementation plan

and once, the lines that changed, each as it was and as it is now.

## What governs it

  never as a turn of its own — and then "хорошо, делаем хук". The changed lines as was → now in
  place of a re-read, so the context's cached head stays, and the messages about the entry
  file's changes going, were the path's session's proposal, agreed by that word and not said by
  the person *(corrected 2026-11-24, on that session's own report: it had handed its proposal on
  as the person's)*.
- [q-2zouxq](../questions/q-2zouxq-how-does-an-installed-method-put-its-own-records-into-the-path-and-the-counters-so-that-the-store-and.md),
  decisions 1 and 2: the store's window reads only questions; a mechanism adds its own through its
  own hook line, run by the hooks' wrapper.
- [harness.md](../../.agents/mechanisms/harness/harness.md), *Install adds, uninstall removes*: the
  entry file is the harness mechanism's whole file. The line is that mechanism's.
- [The hosts edge](../edge/hosts.md): a hook never fails the host; a host's message hook reaches the
  agent or it does not, per its sidecar. Claude Code's and Codex's do; Cursor's does not.
- The store's session, 2026-11-22, by message, on its two files: the handed line is printed at a
  message event too; the payload has one reader, a public function of the store's script that
  `hook` itself calls; the line's memory stands beside the window's.
- Claude Code's documentation, read 2026-11-22: `CLAUDE.md` is loaded at launch and, after a
  compaction, *re-injected from disk* ([context window](https://code.claude.com/docs/en/context-window.md),
  [memory](https://code.claude.com/docs/en/memory.md)); a hook's output is capped at 10,000
  characters, past which the host saves it to a file and places its first 2,000 in context
  ([hooks](https://code.claude.com/docs/en/hooks.md)). That a running session keeps the text it
  loaded is observed here: rule failure 34's occurrence of 2026-10-11, and the hosts edge's Claude
  Code sidecar, *Helper*, 2026-10-25.

## Decisions this plan makes

1. **The line is the harness mechanism's, a script of its own** — `.agents/scripts/gw/entry_notice.py`,
   run by the hooks' wrapper as a second process, printing plain text or nothing. Not the window:
   the store reads only questions. Not `harness.py`: the installer's script loads slowly, and
   this one runs before every message.
2. **It reaches the host through the seam the installer's line takes**: the wrapper hands the text
   as `GW_NOTICE` and the store's hook prints it in the host's own form — at a message too, and
   on the path where the start was never seen. The handed line leads the store's own text at
   every event *(the store's session, 2026-11-22)*: a wake or a window drawn whole passes the
   host's cap, and a line printed last is past the 2,000 characters left in context — the
   installer's line at a start was cut so until now.
3. **The wrapper runs the line wherever it runs the store's hook for a session** — a start, a
   message, a compaction, a sign of life — and the script decides by the event. The wrapper's
   branch for a host's call before a tool leaves before it, so that call starts no interpreter
   for the line.
4. **What a session holds is remembered as the file's whole text**, beside the window's memory,
   under the session's tag. Not a version: a recipient's announce line moves only at an update,
   and its local block moves between them. Not a Git object: an unreferenced blob is pruned while
   a session that holds a role still sleeps.
5. **The memory moves to the file as it stands, and nothing is printed**, at a start of any
   source, at a compaction, and at a message that finds no memory — a session whose start no hook
   saw. At a message that finds the file other than the memory, the notice is printed and the
   memory moves, so the same change is never printed twice and several changes between two
   messages are one notice.
6. **The session is read by the store's function**, `session_of(host_name, payload)`: the host's
   row, the event, the tag — the conversation variable first, then the host's field. `hook` does
   not call it whole: its answers to a failure need the event before the tag, and its branch
   before a tool leaves before either; the two share the payload's parsing and the tag's
   derivation, and the payload's bytes have one decoder, the store's `hook_input`. A message
   event is the row's `messages`; a host with none — Cursor — is never shown a notice, and its
   sign of life moves no memory.
7. **A change is a difference in the lines that carry text**, their endings and trailing spaces
   aside. Each passage that differs is numbered and placed under the nearest heading above it; a
   new passage also names the line it follows. A file that differs only in its line endings or in
   blank lines moves the memory and prints nothing, and no blank line is shown.
8. **The notice's text**, fixed here because the tests and the judge read against it:

   > entry file changed: AGENTS.md differs from the text your context holds — 2 passages, each
   > below as it was and as it is now. Read `was` as replaced by `now`; the rest of the file stands
   > as your context holds it. Where this text is cut short, its whole stands at the head of the
   > output the host saved: read it there, or read AGENTS.md again.
   >
   > 1. under `## General rules`\
   > was:\
   > \<the old lines\>\
   > now:\
   > \<the new lines\>
   >
   > 2. under `## Autonomy`, new after `- 💬 Above it, it settles nothing: …`\
   > now:\
   > \<the new lines\>

   A single passage reads `1 passage, below as it was`. A passage removed reads `N. under
   <heading>, removed` and its `was`; one above every heading is placed `at the file's head`; the
   line a new passage follows is cut at 80 characters, and left out where it is the heading
   already named; a line opening with `#` inside a code fence is no heading. The count and the
   last sentence stand in the first paragraph, within the 2,000 characters a host leaves in
   context of an output it saved: on a turn whose window is drawn whole the rest is cut there
   and read from the saved output, the memory having moved already.
9. **Past 8,000 characters the notice carries no lines**: `entry file changed: AGENTS.md differs
   from the text your context holds in N passages, too many lines to show here. Read AGENTS.md
   again; it replaces the text your context holds.` The seam is an environment variable and the
   host caps a hook's output at 10,000 characters; a notice longer than the file's changed half
   costs more than the read it was built to save.
10. **It never fails the host and never speaks of its own trouble**: an unreadable payload, a host
    it does not know, a tree with no entry file, a memory it cannot write — each prints nothing
    and exits clean, and the wrapper drops its error stream. The store's hook already names an
    unreadable payload; a second voice on the same fault is noise.
11. **It ships as core.** The need is this tree's regime
    ([q-kt3ntt](../questions/q-kt3ntt-what-does-the-harness-need-while-its-own-rules-are-amended-many-times-a-day-under-sessions-still.md)),
    but a recipient's entry file moves under its sessions too — an update, a local rule
    re-installed — and a setting to switch the line off is a part nothing asks for yet. Its cost
    is in *Limits*.

## Impact — 2026-11-22

**Impact.** One new script and its tests; two small edits in the store's script, with the store's
word; the wrapper; the harness mechanism's doc, the mechanism shape's row for the wrapper, the
questions mechanism's row for it; the hosts edge and its three sidecars. Every session of every
tree at its next start; no rule's text.

**Hidden edges.**
- A turn whose window is drawn whole passes the host's cap — a drawn window here measures 12,000
  to 60,000 characters — and only the output's first 2,000 stay in context: decision 2's order
  puts the notice's head there, and a notice longer than that head is read on from the saved
  output, as its first paragraph says (the judge's first finding, 2026-11-22).
- A store's hook that fails at a message still prints the handed line before its own notice: the
  line's memory has moved by then.
- The seam is an environment variable handed from Git's `sh` to a Windows interpreter: the entry
  file's glyphs and Cyrillic cross it, so the script writes UTF-8 whatever the console's code
  page, and a wrapper test carries text outside ASCII.
- A session running when this lands has no memory: its next message sets it, silently. What
  changed between its start and that message it is not shown.
- The memory lives where the window's does, in the machine's temp folder; a session whose memory
  was cleaned away is treated as the line above.
- Whether Codex re-reads the entry file after a compaction is not documented; the plan moves the
  memory there as it does in Claude Code, where it is.
- A helper agent has no hook and carries the entry file as its parent loaded it — the hosts edge's
  existing gap, unchanged.

## Cheapest refutation

That the old text stays in a running session's context, so *was* can be found there: the Claude
Code sidecar's *Helper* observation of 2026-10-25 — v110 in context, v117 on disk — and this
ticket's live criterion, judged by a session that did not build it.

## Code shapes and flows

- `questions.session_of(host_name, payload)` — the one reader of a hook's payload.
- `entry_notice.py --hook <host>`, the payload on standard input: the event read as one of the
  script's two acts — the context taking the file in anew, a message asking what changed since —
  or as neither. Decision 5 is the two acts' whole logic.
- Flow at a message: host → wrapper → `entry_notice.py` (text or nothing) → `GW_NOTICE` → the
  store's hook → the host's form → the agent's context, with the message.

## Stages

Each stage is test first, one behaviour at a time, and leaves the suite green.

1. **The line's two acts**, new files only, as the script's two functions over a tree and a
   session's tag — the context taking the file in anew, and a message asking what changed since:
   a message after a change gives the passages as was and now; then, in turn — unchanged,
   nothing; the following message, nothing; several changes, one notice; taken in anew, the
   memory moves and the next message gives nothing; a message with no memory gives nothing; a
   passage new, a passage removed; line endings alone, nothing; past the budget, the read; no
   entry file, nothing.
2. **The store's script**, after the store's own pending commit, from `HEAD`: `session_of`
   extracted and called by `hook`, with a test of its own; the handed line printed at a message
   and on the path where the start was never seen, with the two tests the store named.
3. **The line's entry**, `--hook <host>`: the session read by `session_of`, the event mapped to
   one of the two acts or to neither; an unreadable payload and an unknown host each print
   nothing and exit clean.
4. **The wrapper**: the line run before the store's hook and handed on, joined to the
   installer's at a start; a tree without the script fails nothing.
5. **The records**: the harness mechanism's doc — the moment, the parts, what it relies on, what
   it produces; the mechanism shape's and the questions mechanism's rows for the wrapper; the
   hosts edge's promise, invariant and check, and the three sidecars — Cursor's naming the gap.
6. **The judge and `/verify`**, then the live observation, the close, and the one message each to
   the keeper's and the store's sessions.

## Tests

- `test_entry_notice.py`, the script's two acts over a fixture tree and a patched memory: each
  behaviour of stage 1 asserts the text given and, where the memory matters, the next message's
  — a notice shown once is proved by the second message giving nothing, never by reading the
  memory file; its entry through `main` with a host's payload, for stage 3.
- `test_sessions.py`, where the hook's cases and their fixture live: `session_of` returns the
  row, the event and the tag, the conversation variable winning over the field; a handed line
  leads a message's answer, the wake of a start never seen, and the notice of a hook that could
  not draw its window; no line leaves the answer as it was.
- `test_harness.py`, `TheWrapper`: with stand-in scripts, the line's text reaches the store's
  hook as `GW_NOTICE` at a message and carries text outside ASCII whole; a tree without the
  script hands nothing and fails nothing.
- The whole path in a host is the ticket's live criterion; no test runs a host.

## Limits and follow-ups

- **Cost.** Measured here 2026-11-22, medians of seven: the message hook today 3.2 s; an
  interpreter that imports the store's script 0.5 s, which this adds to every message, in every
  tree.
- **The line as a hook entry of its own** in each host's file — as the call before a tool is —
  would be run beside the store's hook rather than before it, and capped apart from the window:
  neither the cost above nor the cut of a long notice on a drawn-window turn would remain. It
  changes the hook wiring's shelf and every host's file, which are the store's and the hosts
  edge's, not this ticket's.
- A session with no memory is told nothing (the two edges above).
- The messages between sessions about the entry file, and the rule that asks for them, stand until
  their owners change them.

## Out of scope

What the entry file says; the window; the rules on messages between sessions; a notice for a
skill's text or a rules file moving under a session.
