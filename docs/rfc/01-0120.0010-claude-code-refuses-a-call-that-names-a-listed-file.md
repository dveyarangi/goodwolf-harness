## The shape

**The list** *(keeps: The list)*. `local.closed.txt` beside the entry file, the project's and
tracked: one file a line, its path from the tree's root. It is read as UTF-8 with a leading mark
and every `\r` dropped, `\` read as `/`, the space round a line and a leading `./` or `/`
dropped; an empty line and one opening with `#` are skipped. A line is a file: there are no
patterns and no folders, and a folder is closed by listing its files. The file's presence is the
switch: a tree without it has no refusal wired.

**The script** *(keeps: No mechanism is added — one script answers the host's call)*.
`.agents/scripts/gw/before_tool.py`, the harness mechanism's, answers a host's call before a
tool: `before_tool.py --hook <host>`, the host's payload on its input, the host's own form of a
refusal on its output, exit 0 always. One function knows the host's payload and its form of a
refusal. It holds one refusal, this one, and no table of refusals.

**What "names" means** *(keeps: decision 3 — every call of an agent's that names a listed file;
Not held — a read that never names the file to the host)*. Letters are compared without their
case, separators as one.

- *A path field* — `file_path`, `notebook_path`, `path`, and a `glob` or `pattern` that holds no
  wildcard — names a listed file when, made whole against the call's `cwd`, it is that file
  under the tree's root.
- *A shell command* — the `command` of either shell tool, and a field so named in any tool the
  script does not know — names a listed file when the text holds the path as the list writes
  it, or the path's last part as a whole word — so `cd config && cat secrets.yml` is refused. The
  match is coarse on purpose: a command that only mentions the name is refused too.
- *Any other string of a tool the script does not know*, an outside server's included, is read
  as a path field and never as text: the try saw a helper's prompt and a task list's lines pass
  the hook, and a file's name in them is no call upon the file.
- Never searched: `content`, `old_string`, `new_string` and `new_source` of the host's file
  tools, so text that mentions a listed file is written with them.

A search over a folder, and a pattern that merely matches a listed file, name nothing and pass:
*Not held* already says so of a pattern, and what could hold a search is under *The search*.

**The refusal's text** says the file is closed to agents because the list names it as holding
secrets, that another way to read it is not to be tried, and that what is needed from it is
asked of the person; the reader's command joins it with
[01-0120.0020 an-agent-reads-a-listed-file-without-its-values](../tickets/01-0120.0020-an-agent-reads-a-listed-file-without-its-values.md).
It is text an agent acts by, drafted through `/skill-up` when it is written.

**The wrapper** *(keeps: The list — a tree that keeps none pays nothing)*.
`.agents/scripts/gw/hook.sh`, the mechanism-shape's, gains the branch `before-tool` it lost at
19356b62, launched as `gw-hook claude-code before-tool`, and nothing else of this: where the
tree holds no list it leaves at once; otherwise it runs the script under the clone's interpreter
and hands on what it prints; what it does where the script cannot answer is under *Failure*. It
reads no payload. At a session's start it also runs the script's
line, as it runs the installer's and the entry notice's.

**Failure** *(keeps: decision 4 — where the check cannot run, the call is refused)*. At two
places, and at both for every call, since nothing but the check can tell which call names a
listed file:

- *The wrapper.* Where the tree holds the list and no interpreter is recorded in the clone, or
  the script ends otherwise than cleanly, the wrapper prints the refusal in the host's form, as
  it prints its notice of a missing interpreter in the host's form today. Its text says the
  check of closed files could not run, that no call passes until it is mended, and which step
  the person runs in a terminal.
- *The host.* The entry carries `onFailure: "block"`, so a hook the host cannot start, or stops
  at its time limit, refuses too. The try saw the host take the key, and saw the hook found at
  every call in the desktop app, whose shell never stays outside the project's folder. The
  terminal was not seen: a shell that stays in a nested repository would find no wrapper there
  and be refused the command that brings it back, so the entry's launch is anchored to the
  project's folder, which the host names to a hook in `CLAUDE_PROJECT_DIR`.

The price, said where the limits are said: a fresh clone of a tree with a list refuses every
call until the person has run the link step once, and a fault of core's script stops every
session of such a tree until it is mended or the person takes the entry out.

**The wiring** *(keeps: No mechanism is added — the harness mechanism wires this hook as it wires
the others; The list — a tree that keeps none has no refusal wired)*. A second shelf, the harness
mechanism's own, `.agents/skills/harness/hooks/`, holds Claude Code's entry for the call before
a tool, with no matcher. For one host file the two shelves' entries are joined event by event
before the merge. Where the target holds the list the harness shelf's entries are merged in;
where it holds none, that shelf's entries of this ref and of the previous one are taken out, an
event they emptied staying as an empty list, as the merge leaves one today. The check's ref gate
holds a tree with the list to those entries and a tree without it to their absence — still
core's entries alone. The questions mechanism's shelf and `questions.py` are not touched.

A project that writes its list runs the update at the ref it announces, `--update --at <ref>`,
which clones the source and refuses over an edited core file, as every update does. Until it
has, the script's line at a session's start says the tree keeps a list whose refusal is not
wired, and names that command; the harness skill, which tells how a file is closed, names it
too.

**Where the limits are said** *(keeps: Not held)*. The run that wires the entry, and every run
after it while the list stands, carries one note in the installer's report: what the refusal
does not hold — a read that never names the file to the host: a script, a pattern, a search
over a folder, a link, a program that loads it; a copy in a file no line names, another
worktree's or clone's among them; a value already printed; a file the person hands over with
`@`. It says too what a check that cannot run costs. The same note names every line of the
list that is no file on disk.

**The search**
([q-5lck5x](../questions/q-5lck5x-does-the-projects-list-make-the-hosts-own-search-skip-its-files.md)).
The list makes no search skip a file, and no hook can: a search over a folder names nothing. An
ignore file does, for a search with no including `glob` only. The host's own deny rule does,
whole — the try saw it. Whether core writes such rules from the list is *To decide*.

**The hosts edge** carries the promise since this plan, marked pending on this ticket: Contract,

## To decide

Put to the person, 2026-11-27: by what Claude Code's refusal is held, now that its own deny rule
was seen to hold more than its documentation says.

- **The hook alone**, as planned: every call naming the file, a shell's any command among them,
  with the method's own reason. A search over a folder stays open; a process before every call;
  a check that cannot run stops the session.
- **The host's rule alone**, written from the list by the installer into the same committed
  file: the file tools, the search, the shell's file commands the host recognises. No process,
  nothing to fail, a fresh clone held with no step run. A program the host does not recognise
  passes, and its refusal says neither why nor what to do instead.
- **Both**, the recommendation: the rule as the floor and for the search, the hook for the
  reason and for a shell's any command. The installer's merge then writes rules as well as an
  entry, and a rule written for a line that later leaves the list is taken out with it.

Stages 1 to 3 are written for the hook and gain the rule's part once this is decided.

## Code flow

A tool call in a tree with the list: the host runs the entry → Git runs the wrapper at the
tree's top → `before-tool`: no list, leave; else the interpreter runs
`before_tool.py --hook claude-code` on the payload → it reads the list, decides by the tool, and
prints nothing or the refusal → the host runs the call or shows the agent the reason.

An install or update: the shelves are read and joined, the harness mechanism's counted where the
target holds the list → merged into `.claude/settings.json` beside the project's own → the ref
gate reads the same.

## Limits and follow-ups

- **A check that cannot run stops the session**, by the person's decision: a clone with no
  interpreter recorded, and a fault of the script, refuse every call until mended.
- **The host's own deny rules are not written by core** until stage 0 has seen what they hold.
  Against them: they are one host's, their text names no reader, and a rule derived from the
  list stays behind when a line leaves it.
- **`onFailure: "block"`** is a key from version 2.1.295; what an older host does with it in a
  file the project shares is not known, and the report's note says which version it needs.
- **Names proposed here and not yet the person's**: `local.closed.txt`, `before_tool.py`, the
  shelf's place.
- The reader, Codex and Cursor are the parent's other slices.
- A process a command starts that outlives its call would be a second refusal for this script;
  it is
