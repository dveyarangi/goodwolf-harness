# A doc is due when its parts move — implementation plan

## What it changes

The clock keeps two levels per mechanism. At `rules` a mechanism's doc is due when the
meta-rules — the entry file, the mechanism shape's rules file and its skill — moved since the
mark; at `output` its records are due when its own doc, rules file or skill did. A script, a test
or a shelf a mechanism owns can move and make nothing due, and `mechanisms.py` holds only that
each listed path exists. Decisions 1, 2, 5 and 7 of
[q-0024.0009.0006](../questions/q-0024.0009.0006-how-is-a-record-paired-with-the-thing-it-is-of-so-that-drift-between-them-is-noticed.md)
*(the user, 2026-10-10 and 2026-10-11)*: a record is due when what it depends on moved, and there
are two dependences — a doc on the parts its mechanism is made of, at `parts`; a mechanism's
outputs on what governs them, at `output`. Today's `rules` is no third dependence: the shape
produces instructions, so every mechanism's doc and skill are its outputs, and `rules` is the
shape's `output` read one mechanism at a time. A due pair is re-checked to one of three outcomes,
by whether a decision stands behind the move.

## Shape

**The levels are `parts` and `output`; `rules` is no level.** A `--mark` at `rules` is refused as
any unknown level is, and a marks row at it is a diagnostic as any unknown level's is. One row per
mechanism per level stays.

**`parts`: the doc against what the mechanism is made of.** The surface is every `where` of the
doc's *Install adds, uninstall removes* table but the doc itself — the doc is the record side of
this pair, so its own edit makes `output` due, never `parts`. Each part is a whole file, read as
the whole-surface fingerprint reads every file today (LF, installed blocks out): a part that is a
directory, or does not resolve, is unreadable — a diagnostic, never guessed around as current.
The *Relies on* table is not read: a part a mechanism relies on is its owner's doc's to watch, so
one edit makes one doc due *(decision 2)*. For an `always on` mechanism the same table is read;
its title then means what a person moving the mechanism takes.

**`output`: the outputs against what governs them, the shape's outputs read per mechanism.** A
mechanism's `output` surface is its own doc, rules file and skill files — today's `output`,
unchanged — joined with the mechanism shape's own: the shape's doc, rules file and skill files.
The join is how *the shape's `output`, read one mechanism at a time* is keyed: the shape's outputs
are every mechanism's doc and skill, and the row that reads them is the mechanism's own, so
marking stays per mechanism and no third row kind exists. A due `output` row names the files that
moved, and the re-check reads in the direction the file gives: a shape file moved — the
mechanism's doc and skill are read against it; one of its own moved — its records are read
against it. For the shape itself the two sets are one. The entry file leaves the surface: it
governs every file as a meta-principle, read by every session, and the sentence that lagged it
this week stood in the harness mechanism's doc, whose `parts` names the entry file as a part. A
recipient's docs never read it either way.

**Three outcomes.** A due pair is re-checked to one of three, by whether a decision stands behind
the move *(decision 7)*: a landed decision moved the part and the record lagged — the record is
amended; none did — the thing is repaired to the record, or the question is taken to `/align`;
the move touches nothing the record says — nothing to change. The kind says which side is right
when no decision stands behind the move; the landing that moved a file is found by its history.
The marks' `outcome` takes a third word, `repaired`, for the second, so the record of a
maintenance says which side moved; `amended` keeps meaning the record.

**No row kind for the entry file, no third level, no note on a mark.** What was refused: a
`rules` row kept beside the two levels; a row keyed `mechanism-shape` per output, which would
need a column the marks do not have; reading the *Relies on* table at `parts`; a reader that
tolerates and drops `rules` rows, a permanent path for a one-time event.

## Migration

This tree's marks hold a `rules` row per mechanism and their file rows. The landing removes them
by hand in the same commit, the one exception to *written only by `--mark`* — the format says so
for this landing and nothing else — and every `output` row falls due at once, its surface having
grown, while every `parts` row reads *never maintained* until a maintenance marks it. Being due is
news, not a defect; the next `/maintain` pass reads the files the check names.

A recipient clocks none of the mechanisms it received with core and holds no marks (`maintain.py`,
`_received_core`); its line in the edge record says the levels' names and that a `rules` row,
should a recipient have written one by hand, fails its check until removed.

## Stages

Red first; the suite green at the end of each.

1. **`parts`.** The fixture's sample mechanism declares a script as a part and a shape file as
   relied on. Tests: the script moving makes `sample | parts` due naming it under `moved`; the
   relied-on file moving leaves `parts` current; the doc itself moving leaves `parts` current and
   makes `output` due; a part that is a directory, and one that does not resolve, are each a
   diagnostic naming the part and refuse a mark on that level; `--mark sample parts` writes the
   row and its file rows.
2. **`output` folds the shape.** Tests: the shape's skill, rules file or doc moving makes every
   mechanism's `output` due naming the file, one row each, and no `parts`; the sample's own doc,
   rules file or shelf moving makes its `output` alone due; the entry file moving makes nothing
   due; `rules` is refused by `--mark` and reported as a row; `repaired` is accepted as an outcome
   and a fourth word is not. Every existing case of `AfterEveryLevelIsMarked` reads at its new
   level.
3. **The words and the marks.** `MARKS-FORMAT.md`; the maintain doc; `/maintain`'s A1 and B4; the
   script's docstring; the marks file's `rules` rows removed; the edge line written.
