another session's unstaged write is read by this commit's check.

## Decisions

1. **The nine checks, each run when a file it reads changed** *(the user, 2026-10-26)*: the six
   record checks — `questions.py`, `sessions.py`, `tickets.py`, `product.py`, `edges.py`,
   `maintain.py` — `inject_rules.py`, `mechanisms.py` and `harness.py <tree> --check`. At commit a
   check runs only when a staged file is one it reads, its own records or another's; a commit
   that touches no file a check reads runs none, so a recipient's code-only commit pays nothing.
   In CI all nine run on every run, since a wrong map of what a check reads would skip it in
   silence and CI is the last gate. `harness.py --check` clones the source and needs the network,
   so it runs in CI alone. The map of what each check reads stands in the runner until each
   mechanism's table of its records, decided in
   [q-0037.0006.0005.0001](q-0037.0006.0005.0001-which-skill-must-be-read-before-a-file-is-edited-or-a-rule-proposed-and-how-does-the.md)'s
   decision 2, can carry it. The tests stay with the tree that develops the harness. Not: the
   install's list today, the record checks alone with core's own two only in a tree that changes
   the harness — a recipient's edited core and its rules edited and not re-installed would then go
   unseen; nor every check at every commit — 2.6 s side by side, paid on each code-only commit for
   records it did not touch.
