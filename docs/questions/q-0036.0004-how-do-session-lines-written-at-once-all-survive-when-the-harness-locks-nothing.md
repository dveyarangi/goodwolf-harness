# q-0036.0004 How do session lines written at once all survive, when the harness locks nothing?

- **record of** what it intends to become
- **part of** q-0036
- **state** open

The sessions file's writer re-reads the file, replaces its own line and renames a staged copy over
it; between the read and the rename another session's line can be lost. The outside audit of
2026-10-13 saw 5 lines of 20 survive twenty simultaneous session starts
([the audit](../research/external-audit-2026-10-13.md)); the writer's docstring promises one
session's write never undoes another's.

A lock is ruled out while the harness locks nothing
([Interruption and recovery](../architecture.md#interruption-and-recovery), the user, 2026-10-11).
Two shapes stand:

- **A file per session.** No two sessions ever write one file, so nothing can be lost; every
  reader of the sessions file — the wake, the window, `--check`, the conclude — reads a directory
  instead. Closes the race.
- **Re-read, compare, retry.** Before the rename the writer reads the file again and starts over
  if it changed. Touches the writer alone; narrows the race to the instant between the compare and
  the rename, so it does not close it.

The agent leans to a file per session: it is the only shape that keeps the promise without a lock.

## Decision

**A file per session, in one folder shared by all sessions** *(the user, 2026-10-13)*: each
session's line is its own file under `docs/questions/sessions.d/`, named by its tag, so no two
sessions write one file. The folder has a name of its own, beside the single file rather than at
its path, so a store from before is read with both and carried over at its first write by copies
that never overwrite — no step there can race another.
