## Where it stands

The harness's checks run without an agent: at push, through a Git hook, and in the project's CI,
through a workflow of core's own — beside the project's gates, never in their place, and over the
records the method keeps in the tree, never the project's code.

**Which checks.** Nine: `questions.py`, `sessions.py`, `tickets.py`, `product.py`, `edges.py`,
`maintain.py`, `inject_rules.py`, `mechanisms.py` and `harness.py <tree> --check`. A push whose
commits carry a file under the method's roots — `docs/`, `.agents/`, the entry file, its host stub
and the local rules file — runs the eight local checks; a push that carries none runs nothing;
`harness.py --check` clones the source and runs in CI alone. In CI all nine run on every run. The
roots stand in the launcher until each mechanism's table of its records, decided in
[q-0037.0006.0005.0001](q-0037.0006.0005.0001-which-skill-must-be-read-before-a-file-is-edited-or-a-rule-proposed-and-how-does-the.md)'s
decision 2, carries them. Core's tests stay with the tree that develops the harness.

**At push.** A launcher core tracks matches the paths the pushed commits carry in the shell — a
push of code starts no interpreter and pays only the listing of its files — and otherwise checks
out what the push sends into a temporary copy, runs the checks there side by side and removes the
copy, about 6.5 s here with ten sessions running, holding no lock another session's `git add` or
`git commit` waits on. Any finding in the copy refuses the push: what is checked is what is sent,
and no other session's unfinished write is in it. A refused push leaves its commits in the clone,
mended by the next. `harness.py . --links` writes the clone's one-line
`pre-push` where Git names it, only where none or core's stands; beside another hook it leaves that
hook alone and gives the line and its place.

**In CI.** Where the project runs GitHub Actions, `.github/workflows/goodwolf.yml` — checkout,
Python 3.13, the nine checks — a check of its own on every pull request, required or not by the
project's branch setting, none of the project's workflow files touched. Elsewhere the step is a
line in the report. This tree takes the same file.

**At install.** The hook is written unasked, and the person told in one sentence among what the
install spares them that a push carrying a broken record of the method stops and names it, pushes
of code untouched. The workflow file is a fourth ask — checked in CI as well, beside their own
checks, or only at push from this computer — the first proposed, the file written only on it.

**Left to the build**, none of it a decision of this question: whether a recipient's verification
set names the launcher in place of its own list of checks; the lowest Python core states, while
`inject_rules.py` needs 3.13; and, in a tree with a method, the report made before anything is
written listing the hook and the workflow file, the work of

## Decisions

1. **The nine checks, each run when a file it reads changed** *(the user, 2026-10-26)*: the six
   record checks — `questions.py`, `sessions.py`, `tickets.py`, `product.py`, `edges.py`,
   `maintain.py` — `inject_rules.py`, `mechanisms.py` and `harness.py <tree> --check`. At commit a
   check runs only when a staged file is one it reads, its own records or another's; a commit
   that touches no file a check reads runs none, so a recipient's code-only commit pays nothing.
   In CI all nine run on every run, since a wrong map of what a check reads would skip it in
   silence and CI is the last gate. `harness.py --check` clones the source and needs the network,
   so it runs in CI alone. The map of what each check reads stands in the runner until each
   mechanism's table of its records, decided in
   [q-0037.0006.0005.0001](q-0037.0006.0005.0001-which-skill-must-be-read-before-a-file-is-edited-or-a-rule-proposed-and-how-does-the.md)'s
   decision 2, can carry it. The tests stay with the tree that develops the harness. Not: the
   install's list today, the record checks alone with core's own two only in a tree that changes
   the harness — a recipient's edited core and its rules edited and not re-installed would then go
   unseen; nor every check at every commit — 2.6 s side by side, paid on each code-only commit for
   records it did not touch.
2. **At commit the checks read the working tree, and the commit fails only on a finding in a file
   it carries** *(the user, 2026-10-26)*: the files of the commit are read from the index the hook
   is handed, so a commit named by paths fails on its own files alone; a finding in any other file
   — another session's write half done — is printed as a warning and holds nothing. What a
   commit's file reads clean on the disk and broken in the index passes, and CI, which checks the
   commit itself, catches it. Not: the working tree with every finding failing — in this tree's
   shared checkout the question and ticket checks failed twice in an hour on other sessions'
   writes and passed a minute later, and an agent may not skip a hook; nor the index exported and
   checked apart — 2.8 s to export 1716 files, and every check reads the tree through
   `git ls-files`, which fails outside a repository; nor stashing what is unstaged around the
   check — it touches the shared checkout, other sessions' work.
3. **The checks run at commit, and a commit of code pays nothing for them** *(the user,
   2026-10-26)*: a commit that carries no file a check reads costs only the listing of its files,
   the paths matched by the shell with no interpreter started; a commit of records runs the checks
   it wakes side by side, measured 2026-10-26 with ten sessions running at up to 3 s for a question.
   Where the commit of records runs longer when the slice is verified, what a commit wakes is
   narrowed first. The commit is the only gate before the shared main in a tree that pushes each
   commit as it lands and has no CI, this one; where a project has CI, the author hears the finding
   in the work, not from a red run after it. Not: CI alone — here it would see the broken record
   once it stands on main, and elsewhere it waits on someone reading the red run.
4. **The hook is one line written per clone, calling a launcher core tracks** *(the user,
   2026-10-26)*: the launcher — the paths matched in the shell, the woken checks run, decision 2's
   rule — is a tracked file of core and moves with it; `harness.py . --links` writes the clone's
   `pre-commit` where Git names it, `git rev-parse --git-path hooks/pre-commit`, so a
   `core.hooksPath` is honoured, and only where none stands or the one standing is core's. Where
   another hook stands it is left untouched, and the report gives the one line and where it goes —
   `.husky/pre-commit`, `lefthook.yml`, `.pre-commit-config.yaml` — for the person, or the agent on
   their word, to add: the project's own stays where it is and core's stands beside it, as the
   host hooks' merge already holds, the line given because a hook file cannot be merged. Not:
   renaming the standing hook and calling it from core's — husky and lefthook rewrite their file

   turns husky off, standing in the place of the project's gates.
5. **CI takes a workflow file of core's own, beside the project's** *(the user, 2026-10-26)*: where
   the project runs GitHub Actions, the install writes `.github/workflows/goodwolf.yml` — checkout,
   Python 3.13 set up, the nine checks — and touches none of the project's own workflow files;
