**Who sits on the adoption panel.** The needs it must span, at least: a project that already
has its own agent instructions; a large existing codebase with none; a greenfield prototype; a
single-host user; someone who wants minimal ceremony. The first two runs
([record](../research/adoption-panel-2026-09-26.md)) sat only those five, all wanting less
process, and none is the user the harness is built for — someone running a product with agents
over months who wants the discipline. The panel keeps those five *(the user, 2026-09-26)*: the
lighter process [01-0020](../tickets/01-0020-pacer.md) owns is meant to serve exactly them. The question
is split in two *(the user, 2026-09-26)*, since in the first three runs the project's age and
adoption, which any reader finds on the host, swamped what the panel exists to learn: first, on
the method and its tooling alone, would it serve this project better than the alternatives, and
**what would change that answer**; then, separately, what would the reader need to see before
trusting it there. The first is the verdict and the list of what to build; the second is adoption
evidence. The fourth run asked the trust question *in place of* what would change the answer, and
lost the most actionable part — the question is kept, never traded. **A panel runs clean-room**:
its readers start outside this repository, since a subagent started here inherits the entry file,
the user's memory index and the recent commit subjects before it reads anything — one run's
readers asked for exactly the measurement a commit subject had just named. Not met by the runs of
2026-09-26, all started from this session. Whether
the panel's verdicts gate a publish or only inform it is this ticket's `/plan`.
