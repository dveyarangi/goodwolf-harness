**Why it is open, the user, 2026-10-24.** Two rules that were in place and did not fire, on the
same day: the reply-layout rule says a proposed rule is *written through /skill-up*, and
`/skill-up`'s own description says *use whenever writing any agent instructions, whether to a file
or directly in a reply*; the session proposed a rule for the product skill and amended the harness
skill and its shelf several times without reading `/skill-up`. And it rewrote the front page without
reading `/product`, whose mechanism lists *the root README told from the document* as its own. Register
entry 50 has now been struck three times, each amendment a rewording; rewording has not made it fire.
The user: *every file of ours must be edited through its skill or mechanism, and this must be
enforced mechanically, through hooks.*

**What the hosts allow, as known today.** Claude Code passes a hook before a tool runs the tool's
name, the file's path and the session's transcript path, and an exit with code 2 refuses the call
and hands the agent the reason: a hook can refuse an edit to a file whose owning skill was not read
in the session, read from the transcript. A hook at the end of a reply can refuse to stop and send
the agent back, so a reply proposing a rule with no `/skill-up` read can be returned. Codex and
Cursor: which of their hooks can refuse an edit is not verified — today the harness wires only their
session and prompt events. A write through the shell is not seen at the edit; git's pre-commit can
refuse a commit whose records fail their checks, on every host.

**What is to be settled.** The map from file to the skill that must be read before it is edited —
the mechanism docs' parts tables already say which mechanism owns which file; what an edit
proves by the skill being read, and what it does not; which acts besides an edit — a proposed rule,
a commit — are held this way; and what the hosts that cannot refuse an edit get instead.

## Facts gathered at the align, 2026-10-24

**The tree.** Nine mechanisms declare their parts: 73 paths, each with exactly one owner, none
disputed. The records the mechanisms keep — the question store, the tickets, the product document,
the edge records — are not in the parts tables; they are named in prose under *What it produces*.
Fifteen of the twenty-four skills have no mechanism (`Mechanism: not yet`), so their files have no
owner by the tables.

**Codex CLI**, from its hooks documentation (learn.chatgpt.com/docs/hooks), read 2026-10-24 through
a summarising fetch, field names to be spot-checked: a PreToolUse event covers `apply_patch` and
Bash, and denies with `permissionDecision: "deny"` and a reason, or exit code 2; a Stop event takes
`decision: "block"` and its reason becomes the next prompt, with a `stop_hook_active` guard; every
hook gets `transcript_path`, whose format the documentation calls not a stable interface; project
hooks load only when the project's `.codex/` layer is trusted. The documentation calls tool hooks
*a useful guardrail, not a complete enforcement boundary*.

**Cursor**, from cursor.com/docs/agent/hooks, the same day and caveat: `afterFileEdit` cannot block;
a generic `preToolUse` can deny with a message to the agent, but which tools it covers is not
documented; `beforeShellExecution` can deny a command; `stop` cannot block, but its
`followup_message` is submitted as the next user message, under a loop limit; every hook gets
`transcript_path`, and nothing says whether it records the rules or skills read.

**Claude Code**: asked of its documentation, not in yet.
