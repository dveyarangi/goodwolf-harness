## Where it stands

The method's files are kept through their skills, and a session that forgets the skill goes
unrefused: register entry 50 has been struck three times, each amendment a rewording. The host is
to refuse the act instead. Agreed so far: every mechanism declares its controlled outputs — the
files that need a skill read before they are edited, and which skill — and one generic script
checks an edit against all the declarations; nothing undeclared is held. The declaration is one
table in each mechanism's doc — the records it writes and the parts it guards, each with the skill
an edit needs — which is also where a mechanism declares its records for a script to read, so the
shape check's hand-held list of record paths retires into it. The check asks whether the skill
is loaded in the session's context as the host keeps it, not whether it was read lately; what
each host keeps, and what its hooks can see, is the hosts edge's. Open: how the check knows a
skill is loaded on each host — on Claude Code the two events that load a skill and the compaction
events, not the transcript, whose format is internal; which acts besides an edit are held — a
reply proposing a rule, a commit; and what Codex and Cursor get.

## Decisions

1. Each mechanism declares its controlled outputs — the files that need a skill read before an
   edit, and which skill — and one generic script checks every edit against the declarations
   *(the user, 2026-10-24)*. Not: a fixed split by kind of file — instruction files to
   `/skill-up`, parts to `/mechanism`, records to their keeper — hard-coded in the check; the map is
   each owner's to say.
2. The declaration is one table in each mechanism's doc: the records the mechanism writes and the
   parts it guards, each with the skill that must be read before an edit. It is also the
   declaration of a mechanism's records that a script reads, answering
   [q-0037.0010.0004](done/q-0037.0010.0004-where-does-a-mechanism-declare-the-records-it-writes-so-a-script-can-read-them.md);
   the shape check's hand-held list of record paths retires into it, and the instruction files —
   skills, rules files, the entry file — are declared under `/skill-up` by the mechanism that owns
   it *(the user, 2026-10-24)*. Not: two declarations, one of where records live and one of what
   needs a skill — a record's path would stand in two places, with the hand-held list a third.
3. The check asks whether the skill is loaded in the session's context, as the host keeps it —
   not whether it was read in the last turn; a read is not repeated by rote. How long a host keeps
   a skill loaded, and how a hook knows it, is that host's own behaviour, held at the
   [hosts edge](../edge/hosts.md) *(the user, 2026-10-24)*. Not: a read counting for one turn —
   on Claude Code a second read of an unchanged skill adds only a note, so the rote gives nothing;
   nor a read counting for the whole session — a compaction can drop or truncate the skill.

## Why it is open, the user, 2026-10-24

Two rules that were in place and did not fire, on the
same day: the reply-layout rule says a proposed rule is *written through /skill-up*, and
`/skill-up`'s own description says *use whenever writing any agent instructions, whether to a file
or directly in a reply*; the session proposed a rule for the product skill and amended the harness
skill and its shelf several times without reading `/skill-up`. And it rewrote the front page without
reading `/product`, whose mechanism lists *the root README told from the document* as its own. Register
entry 50 has now been struck three times, each amendment a rewording; rewording has not made it fire.
The user: *every file of ours must be edited through its skill or mechanism, and this must be
enforced mechanically, through hooks.*

**What the hosts allow, as known today.** Claude Code passes a hook before a tool runs the tool's
name, the file's path and the session's transcript path, and an exit with code 2 refuses the call
and hands the agent the reason: a hook can refuse an edit to a file whose owning skill was not read
in the session, read from the transcript. A hook at the end of a reply can refuse to stop and send
the agent back, so a reply proposing a rule with no `/skill-up` read can be returned. Codex and
Cursor: which of their hooks can refuse an edit is not verified — today the harness wires only their
session and prompt events. A write through the shell is not seen at the edit; git's pre-commit can
refuse a commit whose records fail their checks, on every host.

**What is to be settled.** The map from file to the skill that must be read before it is edited —
the mechanism docs' parts tables already say which mechanism owns which file; what an edit
proves by the skill being read, and what it does not; which acts besides an edit — a proposed rule,
a commit — are held this way; and what the hosts that cannot refuse an edit get instead.

## Facts gathered at the align, 2026-10-24

**The tree.** Nine mechanisms declare their parts: 73 paths, each with exactly one owner, none
disputed. The records the mechanisms keep — the question store, the tickets, the product document,
the edge records — are not in the parts tables; they are named in prose under *What it produces*.
Fifteen of the twenty-four skills have no mechanism (`Mechanism: not yet`), so their files have no
owner by the tables.

**Codex CLI**, from its hooks documentation (learn.chatgpt.com/docs/hooks), read 2026-10-24 through
a summarising fetch, field names to be spot-checked: a PreToolUse event covers `apply_patch` and
Bash, and denies with `permissionDecision: "deny"` and a reason, or exit code 2; a Stop event takes
`decision: "block"` and its reason becomes the next prompt, with a `stop_hook_active` guard; every
hook gets `transcript_path`, whose format the documentation calls not a stable interface; project
hooks load only when the project's `.codex/` layer is trusted. The documentation calls tool hooks
*a useful guardrail, not a complete enforcement boundary*.

**Cursor**, from cursor.com/docs/agent/hooks, the same day and caveat: `afterFileEdit` cannot block;
a generic `preToolUse` can deny with a message to the agent, but which tools it covers is not
documented; `beforeShellExecution` can deny a command; `stop` cannot block, but its
`followup_message` is submitted as the next user message, under a loop limit; every hook gets
`transcript_path`, and nothing says whether it records the rules or skills read.

**Claude Code**, from code.claude.com/docs/en/hooks and the sessions page, 2026-10-24: a PreToolUse
hook receives `session_id`, `transcript_path`, `tool_name` and `tool_input` — for Write and Edit an
absolute `file_path` — and, in a subagent, `agent_id`; it refuses with `permissionDecision: "deny"`
and a reason *shown to Claude*, or exit code 2; a matcher lists tools with `|`, and Bash and
PowerShell are separate tools whose `command` is seen. A Stop hook refuses to stop with
`decision: "block"` and a reason that becomes the next instruction, guarded by `stop_hook_active`
and capped at eight continuations; it receives `last_assistant_message`. The transcript's entry
format is internal and changes between versions, and how a skill read is recorded there is not
documented. A skill reaches the session two ways, each with its own event: a PreToolUse on `Skill`
when the agent calls it, a `UserPromptExpansion` with `command_name` when the person types the slash
command. Subagents fire the same hooks. **So the documented route is not to read the transcript but
to have those two events write that a skill was read, keyed by the session**, which the store's
session rows already are.

## How long a skill read lasts, by host, 2026-10-24

**Claude Code**, from code.claude.com/docs/en/skills, quotes checked against the page, and the
context-window, hooks and sub-agents pages through a summarising fetch: an invoked skill's text
*enters the conversation as a single message and stays there across later turns*, and the file is
not read again. A second invocation whose text is unchanged adds *a short note that the skill is
already loaded rather than a second copy*; the full text is added again only when it differs. At
compaction the most recent invocation of each skill is re-attached after the summary, its first
5,000 tokens, within 25,000 tokens for all skills together, filled from the most recent, so older
skills can be dropped entirely. `PreCompact`, `PostCompact` and `SessionStart` with source `compact`
fire around it, each with `session_id`. A subagent does not see the skills its parent invoked,
save a fork; whether a hook fired in a subagent carries `agent_id` on PreToolUse is not stated.

**Codex CLI**, from learn.chatgpt.com/docs/build-skills and /docs/hooks: a skill's full text is
loaded *when they decide to use that skill*, how it is delivered is not documented, and no hook
fires on a skill; explicit invocation is `$skill`. How long the text stays and what compaction does
to it are not documented. `PreCompact` and `PostCompact` exist, with `session_id`; `SessionStart`
has source `compact`. PreToolUse covers Bash, `apply_patch`, MCP and other local function tools, so
a `cat` of a SKILL.md is seen in the command, and no file-read tool is named.

**Cursor**, from cursor.com/docs/context/skills and /docs/agent/hooks: the agent *decides when they
are relevant*, delivery is not documented, and a skill typed as `/name` *attaches to one message*;
no hook fires on a skill. Lifetime and what summarising does to a skill are not documented.
`preCompact` observes and cannot block, with `conversation_id`; `preToolUse` covers Read, Shell,
Write and others, and `beforeReadFile` sees a file's path before it is read.

**So**: only Claude Code documents a lifetime, and it is the session's until a compaction that
does not carry the skill forward; on every host a compaction is seen by a hook keyed by the
session or conversation. Re-reading a skill in Claude Code does not bring its text forward again.

## Each host's skill load and lifetime, read deeper, 2026-10-24

The results stand at the [hosts edge](../edge/hosts.md), in each host's sidecar under **Edit
