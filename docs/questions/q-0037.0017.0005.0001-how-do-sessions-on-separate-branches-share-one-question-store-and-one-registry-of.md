## The problem, 2026-10-25

Everything a session needs to see the others, and to be seen, lives in one checkout:

- **The question store**, `docs/questions/`, 201 live entries and 109 done, tracked in git. A
  worktree holds its own copy; a question opened in one is not in the other's window, and an id
  is minted by reading the local files, so two worktrees give the same id to different questions.
- **The registry of sessions**, the rows under `docs/sessions/rows/`, tracked in git: a session in
  a worktree writes its row into its own copy, and no other session reads it. The case of
  2026-10-12: a session registered in the main checkout had every call refused as *not
  registered* from its worktree.
- **The window memory**, the session's sign of life, in the system's temp folder keyed by the
  tree's resolved path: a worktree is another key.
- **The hooks' interpreter record**, `git rev-parse --git-path gw-interpreter`, which resolves to
  the worktree's own Git directory; and **the loader links**, `.claude/skills`, ignored by git and
  made by the link step in each clone. In this tree's worktree `suspicious-faraday-766026` neither
  exists: its hook says only that no interpreter is recorded, and no skill loads — the harness is
  off there.

xuanxue-cabinet runs sessions in worktrees under `.claude/worktrees/` and in sibling clones
(`xuanxue-cabinet-15`, `xuanxue-cabinet-fix`), which share no Git directory with it. live-spec
runs its lanes as worktrees, made outside the clone (`git worktree add /private/tmp/ls-director/wt`,
its 2026-08-26 handoff); GoodWolf's study of it, 2026-10-25, names this hole as one of two limits
in its migration plan's way (live case 5 of q-0037.0006.0020.0001.0004).

The entries are also documents: 350 links from 121 files outside the store point into
`docs/questions/`, and a decided entry's answer links to the doc that holds it — on the branch
where that work was done.

## Discover, 2026-10-26

A separate pass, given the situation and the nine requirements in plain words and told not to read
this repository, returned the material below as it came. What it found smuggled in is kept with it.

**Families.**

1. *A shared ref outside every branch.* Questions live on a dedicated ref — an orphan branch or a
   custom namespace — so no code branch carries them; worktrees of one clone share refs, other clones
   sync by fetch and push, a rejected non-fast-forward push serving as compare-and-swap; ids may be
   content hashes. Systems: git-bug (per-issue operation chains under `refs/bugs/<id>`, Lamport
   clocks, id the hash of the first operation; 0.11 with a web UI reported 2026-10-02), Gerrit NoteDb
   (review metadata as commits on `refs/changes/*/meta`), git-appraise (JSON lines in git notes).
   Ladder: an orphan branch of markdown files checked out as one dedicated worktree → snapshot commits
   on a custom ref by plumbing → a per-entity operation log; this case at rung 1 or 2. Known failures:
   custom refs are not fetched or pushed by default; code-host web views show branches and tags, not
   notes or custom refs; push races need a retry loop; many writers in one worktree contend on
   `index.lock`. Meets poorly: req 3 for anything but an orphan branch; req 1 across machines, as
   fresh as the last fetch; req 5, a link from code docs to a file on another ref needing a host URL or
   a convention.
2. *A separate repository of files.* A sibling or submodule repository at a fixed path, one checkout
   per machine or a worktree per session, committed and pulled and pushed. Systems: git-issue
   (issues as directories of plain files in a `.issues` repository), Sit, notes vaults synced through
   git. Known failures: header and hand-written body in one file conflict in the frontmatter; a
   forgotten pull gives a stale view; cross-repository links are fragile. Meets poorly: req 5; req 1
   across machines; req 2 with sequential ids.
3. *Event sourcing.* Each open, reword, move, close, lean and counter bump is an immutable event —
   a file named by a ULID and the session, or a line in a union-merged JSONL — folded into the tree;
   storage never conflicts, semantic conflicts (two rewords, a cyclic move, a close against an edit)
   are found in the fold and shown; the markdown files become rendered views; counters stop being a
   hot spot. Systems: git-bug, Fossil tickets, Beads (SQLite plus JSONL in git, hash ids adopted after
   sequential ids collided across agents and branches; since moved to Dolt, keeping SQLite and JSONL
   aligned through worktrees, pulls, merges, deletions and crashes having been the pain). Known
   failures: union merge duplicates or reorders lines; deletes are hard; two representations drift;
   wall-clock last-writer-wins skews across machines. Meets poorly: req 4, a hand edit to a rendered
   view must be ingested back or is lost; req 3, the authoritative form is not the readable file.
4. *CRDTs.* A replicated tree with a move operation (Kleppmann et al., 2021), multi-value registers
   keeping both concurrent values, a text CRDT or register for the body, a G-counter. Systems:
   Automerge, Yjs, Loro, cr-sqlite; a hand-rolled standard-library version of the lower rungs is
   feasible at 300 nodes. Known failures: last-writer-wins loses data silently; text CRDTs interleave;
   formats are opaque; tree moves are subtle. Meets poorly: req 7; req 3 and 4 unless rendered
   markdown is kept beside, which brings back family 3's ingest problem.
5. *A version-controlled database.* One table with cell-level merge and a conflicts table. Systems:
   Dolt (Beads' sole backend now; multiple writers need `dolt sql-server`), Fossil's SQLite, Irmin,
   TerminusDB. Known failures: Beads' 2026 release notes fix Dolt pull and merge breakage. Meets
   poorly: req 7, req 3, req 4.
6. *A single serialization point.* One authority hands out ids and holds the truth — the code host's
   tracker, or a branch on one remote whose atomic push is the lock; positions become leased presence.
   Systems: GitHub Issues with sub-issues, Jira, Linear, Gerrit's server. Known failures: outages and
   rate limits; the offline queue turns into family 3. Meets poorly: req 6, req 7, req 3 and 4 in part.

**What the tasking smuggled in.** Presence fused with record: a session's position is ephemeral and
wants a lease, no merge or history. Two writers in one file: a script-owned header and a hand-owned
body; most merge pain in families 1 and 2 comes from that, not from distribution. Polling at every
turn prefers a local replica. Branch-per-session taken as fixed, where a record always written to one
place is the alternative. "No server" while relying on a git remote a second machine reaches. Ids
framed as minting: random or content-addressed ids need no coordinator; if an id encodes its parent
path, a move renames ids and breaks req 5, which the requirements do not settle. A strict tree, one
parent each. The body as a decision log raises the cost of a lost merge, and who resolves a body
conflict between two agents is not said. Counters as mutable fields are a self-made hot spot. Req 9
against req 5: a record that outlives a branch points at documents only that branch held. At 300
nodes every family meets the read time, so scale decides nothing.

**Nothing to take.** Real-time collaborative editors (family 6 with a text CRDT); gossip and
anti-entropy protocols, right for presence but with no system applying them to a git-carried
record; git-appraise's own use of notes not confirmed.

## Decisions

1. **What the store must do** *(the user, 2026-10-26)*: the designs are weighed against these.
   1. Every session sees the current tree of questions at each step, from any working tree, any
      clone and, later, any machine; a local read takes tens of milliseconds.
   2. An id is given once, everywhere.
   3. A question reads easily to an agent and to the person; a file can link to it, and it can
      link to a file — not necessarily a file itself *(amended by the user, 2026-10-26)*.
   4. A body is written by hand, as free text; the header only by the script.
   5. Links hold: the docs' and tickets' links into the store, and the questions' links out of it.
   6. It works without a network; edits from different machines merge without loss, and a
      conflict is shown, never lost.
   7. Python's standard library only, and no server anyone must keep running.
   8. History is kept: who changed what, and when.
2. **A question outlives its branch** *(the user, 2026-10-26)*: a question, and the decisions its
   body holds, are kept though the branch it was opened or changed on is abandoned, unless they
   were consciously dropped. The store is not scoped to a branch. A closed question holds only
   its answer's link, so an abandoned branch leaves at worst a link to a doc that never reached
   main; when a branch counts as abandoned, and who puts it to the person, is
   q-0037.0017.0006.0003's.
3. **Not a separate branch of questions** *(the user, 2026-10-26; superseded by decision 24)*: a branch outside the code, checked
   out in one shared folder, sounds slow and unobservable to the person; refused unless argued back.
4. **Modes, and a coordinator in the branch-per-session mode** *(the user, 2026-10-26; its modes
   superseded by decision 17)*: in the
   first mode every session works on one shared branch, as today. In the second each session has a
   branch of its own on one machine, and a coordinator holds the questions' truth: every change to
   a question goes through its server, applied mechanically, and everything about how sessions
   coordinate — who holds what, what changed under whom — is its too. On a network, someone raises
   the same coordinator at home or on a server. A server is acceptable for that mode, so
   requirement 7 holds per mode: the first runs none. Who raises the server is still open.
5. **The coordinator's server is raised on demand** *(the user, 2026-10-26)*: on one machine, a
   session's hook that finds no coordinator answering starts it as a process of its own and
   records its address in the clone's Git directory, which every worktree reads; the server stops
   by itself when nobody has called it for a while, and every session's window shows that it runs.
   It lives apart from any chat; an agent it needs for a conflict, it calls. On a network the
   person raises it, and its address is a setting of the project.
6. **The coordinator starts no /maintain, for now** *(the user, 2026-10-26)*: it is built without
   it, and whether it ever does is decided later, at q-0037.0010.0009.0009; no case is recorded of
   drift doing harm between two scheduled passes.
7. **In the second mode every read and write of a question goes through the coordinator**
   *(the user, 2026-10-26; for every session since decision 17)*: the copy of `docs/questions/` a
   branch carries decides nothing, is neither read nor written there, and a check refuses a branch
   that changes it, so merging the branch leaves main's store as it stands. The truth stays files on
   main, kept and committed by the coordinator in its checkout. The seam is `questions.read_store`,
   through which the other six scripts already read the store.
8. **A body is edited through the coordinator, on the condition it has not changed**
   *(the user, 2026-10-26)*: the session takes the body from the coordinator into a local file with
   the fingerprint of the version it began from, edits it by ordinary means, and gives it back with
   that fingerprint; the coordinator takes it only if its body is still that version, and otherwise
   refuses and returns three versions — the one begun from, the other's, and this one's — for the
   session to bring together. One writer of the truth catches every race with one check.
9. **A branch's links to a moved question are repaired by the coordinator's map of renames**
   *(the user, 2026-10-26; retired by decision 23)*: a move already computes its pairs of old and new ids, and `move_doc`
   already repairs citations by pairs; the coordinator keeps the pairs, and before a branch is
   merged a check runs its links through them. Not: ids that do not encode their place in the
   tree — the cleaner end, a large work of its own that this mode does not need; nor refusing a
   move while a branch links into the subtree, which stalls the work.
10. **When the coordinator does not answer, a write is refused and the window read from main's
    files** *(the user, 2026-10-26)*: the session is told plainly that the change was not taken;
    the window is drawn from the files in the checkout where the coordinator keeps the truth,
    marked as such. The next step of any session raises the coordinator again, so the refusal
    lasts about one step. Not: a queue of changes kept until it returns — the event log with all
    its merging, for a rare case; weighed again for the networked mode.
11. **In the second mode the sessions' rows go through the coordinator, in today's form**
    *(the user, 2026-10-26; for every session since decision 17, the rows in `gw.sqlite` since
    q-0037.0017.0005.0003)*: registering, seen, silence, the end, a hold, a take, a release and
    the sign of life are calls into the coordinator, which runs the session script's same
    functions over the rows' folder in its checkout; one code for both modes. Whether the rows
    stay tracked in git is q-0037.0017.0005.0003's.
12. **The mode is a setting of the tree** *(the user, 2026-10-26; superseded by decision 17)*: a knob the session mechanism
    declares, set by the person in `local.rules.md`, its default the one shared branch. A session
    that starts in a worktree of its own while the tree is in the first mode is told so in its
    window — it sees no other session. Not: the mode read from where the session stands — a
    sibling clone is no main checkout either, and the mode would change unseen mid-work.
    Read from the main checkout's local file, the working tree of the common Git directory:
    switching that checkout to a branch whose file sets another value changes the mode for every
    session — the person's act in their own folder *(the user, 2026-10-30, through
    01-0010.0250.0010's plan)*.
13. **The server stays; the narrowing is refused** *(the user, 2026-10-29)*: the impact's narrower
    step — sessions writing the main checkout's store directly — is not taken; a session reaches
    the store only through the coordinator, which alone writes and commits it. A host may keep an
    agent out of folders beyond its worktree; the server does not need it there.
14. **The coordinator commits in the person's checkout of main, naming its paths**
    *(the user, 2026-10-30; its push since decision 20, always)*: one more committer there, as
    every first-mode session is under S5, touching the store alone; while the index is held — a
    merge under way — the commit waits for its next write, the files already written; it pushes as
    the project's way with git says, in the background, so no session waits on the checks. Not:
    commits past the working copy, which leave the person's checkout showing the store's files
    changed backwards; nor main's folder given to the coordinator, the person moved to a worktree
    of their own.
15. **An answer link into a branch not yet merged is a finding naming the branch**
    *(the user, 2026-10-30)*: the coordinator records the branch a close came from, and main's
    check finds the linked doc on that branch mechanically; while it is there, the check names
    the branch and the push goes on; once the branch is gone with the doc never on main, it is a
    diagnostic — the abandoned branch of q-0037.0017.0006.0003. Not: the close held back until
    the merge — the decision is taken when the question closes, and main shows it then.
16. **The server runs always, in every mode** *(the user, 2026-10-30)*: its purpose is not
    coordination alone but observability, which the person wants in the first mode too; a first
    mode apart from it is not built. The coordinator is raised on demand in every tree, and the
    rows, and what the web page shows, go through it whatever the mode. What the mode setting
    still chooses then is open.
17. **One way for every session; no mode, no setting** *(the user, 2026-10-30)*: with the server
    always running and holding the questions and the rows, a session in the main checkout and one
    in a worktree of its own reach them alike, and there is nothing left for a mode to choose; the
    setting, and 01-0010.0250.0010 which would have built it, are withdrawn. A branch never changes
    the store, a body is edited through the server on its fingerprint, and the rows go through it,
    for every session. Supersedes decision 12 and the modes of decision 4.
18. **The store's check is the coordinator's** *(the user, 2026-10-30)*: it checks the truth it
    holds, on request — `questions.py --check` asks it — and before each commit of its own; a
    branch's copy of the store is not checked, 01-0010.0250.0060's guard keeping it unchanged; every other
    check that reads the store — a branch's tickets and docs at its push — reads it from the
    coordinator. Only where no coordinator can be — an install's gate in a recipient, the tests —
    a check reads its own tree, by an explicit mark. A check at push then reads the live truth,
    not the pushed commit's copy, as one truth asks.
19. **The coordinator runs the main checkout's scripts, and restarts when they change**
    *(the user, 2026-10-30)*: whoever raises it, it starts the main checkout's own scripts, so a
    branch's unfinished code never serves the other sessions; after each answer it compares the
    fingerprint of its scripts with the files and, when they moved, restarts. A client and the
    coordinator share only argument lists.
20. **The coordinator always pushes the store's commits** *(the user, 2026-10-30)*: no setting; it
    has nothing to do with how a recipient or a session commits and pushes its own work. Whatever
    stands on the shared main may be published (the architecture), so a push of main carries it.
21. **A call never waits on a commit or a push** *(the user, 2026-10-30)*: the coordinator answers
    once the write is made; the store's check, the commit and the push follow in the background,
    apart from the calls it serves.
22. **One coordinator for every machine** *(the user, 2026-10-30)*: a second machine reaches the
    store through the one coordinator, set up as shared for the network; no machine writes the
    store offline to merge it later. So the store need not be merged by git, and a database whose
    snapshot is committed for backup and a fresh clone is eligible beside text files. Weighed
    after the material of *Discover, 2026-10-30*: the conflicts a coordinator leaves are between it
    and the folder it writes in, not between sessions.
23. **A question's id is stable; its place is an address derived from the tree** *(the user,
    2026-10-30)*: an id is given once by the coordinator and never changes — a short count, `q-412`,
    the file named by it alone, its place only in its `part of` header, no `done/` folder, its
    state in the header. The dotted chain — today's `0037.0017.0005.0001` — stays as an address the
    coordinator derives from the headers: written into each entry's header, rewritten in the moved
    subtree's headers in the move's own commit inside the ref, shown in the window, the web page
    and replies beside the id, resolvable as the question now standing there, stored nowhere
    outside the store. Every link, binding, `Answers` and lean names the id. Old ids are converted
    once at the cut-over, today's addresses kept as the first ones; a frozen table of old ids to
    new reads history. Retires decision 9's map of renames, the forwarding of old ids and every
    rewrite of ids beyond the store; reverses decision 9's refusal of ids that do not encode their
    place — the store under a ref needed either this or a resolver of old ids for ever.
24. **The store's own ref, checked out by the coordinator alone** *(the user, 2026-10-30)*:
    decision 3 is superseded — what it refused was a branch of questions in one shared folder the
    person and the sessions use, slow and unseen; the questions live under `refs/gw/questions`,
    outside branches, its one checkout the coordinator's, the person seeing them through the window
    and the web page.
25. **The coordinator's push goes through the project's own hooks** *(the user, 2026-10-30)*: the
    harness's `pre-push` lets `refs/gw/questions` through; a recipient's own hooks are not skipped,
    and a push they refuse is said in the window's coordinator line, for the person to settle.
26. **Every read of a question goes through the coordinator** *(the user, 2026-10-30)*: an agent
    reads the tree, a body and a search by calls — the window, `show`, `--grep` — never the
    coordinator's folder; a body is edited on a scratch copy and given back on its fingerprint
    (decision 8). A fresh clone and CI need no copy of the questions: the coordinator fetches its
    own ref, and checks the store before each commit (decision 18).
27. **No home of the coordinator's own; no setup** *(the user, 2026-10-30)*: the coordinator stays
    in the clone, its address, lock, log, `gw.sqlite` and checkout of the store in the clone's
    common Git directory, raised by the first call (decision 5). An important goal is to remove
    setup friction: not a folder per user and project.
28. **A second clone on one machine is not provided for** *(the user, 2026-10-30)*: no case for one
    stands — the sibling clones seen beside xuanxue-cabinet are temporary folders of no use any
    more; worktrees of one clone run many agents with no setup. A second clone raises its own
    coordinator, whose pushes the lease on the ref refuses, its window saying so.

## Where it stands

*Rewritten 2026-10-30 after decisions 16 and 17, and accepted again the same day.*

**The problem.** The store, the sessions' rows, the window memory, the hooks' interpreter record
and the loader links each live in one checkout; a session in a worktree of its own sees no other,
mints ids blind, and here runs with the harness off. Two recipients work so — xuanxue-cabinet's
worktrees and sibling clones, live-spec's lanes.

**The shape.** One way for every session, in the main checkout or in a worktree of its own: a
coordinator holds the truth — a server, raised on demand by the hook of the first session that finds
none answering, its address in the project's common Git directory every worktree reads, stopping
when idle, shown in every window, living apart from any chat; its purpose observability as much as
coordination. Every read and write of a question goes through it, and every call on a session's row —
registering, seen, silence, the end, a hold, a take, a release; it runs the store's and the session
script's same code, the questions as files in the checkout it keeps, committed there by path, the
rows in `gw.sqlite` in the common Git directory, out of git. A branch's copy of the store decides
nothing, and a check refuses a branch that changes it. A body is taken into a local file with the
fingerprint it began from, edited by ordinary means, and given back on the condition the
coordinator's is still that version; otherwise refused, with three versions to bring together. A
move's pairs of old and new ids are kept, and a branch's links are run through them before its
merge; an answer link into a branch not yet merged is a finding naming it. A coordinator that does
not answer refuses the write plainly, and the window is read from the files it keeps, marked so. The
seams already stand: the other scripts read the store through `read_store`, every change to it is
one of the store's events, and the row's life is functions of the session script — the only way
to a row, so the same calls carry over to a network.

The worktree's own setup — the interpreter record resolved through the project's common Git
directory, the loader links made in a worktree that lacks them — is a worktree session's first
need.

**What is open.** The networked mode: who raises the coordinator, its address a setting of the
project; a queue for writes while it is away is weighed there. Whether the coordinator starts
`/maintain`, q-0037.0010.0009.0009, set aside. An agent the coordinator calls for a conflict, when
refusals turn frequent. When a branch counts as abandoned, q-0037.0017.0006.0003.

## Impact, 2026-10-29

A separate pass read the tree against the accepted shape.

**Impact.** `hook.sh`'s host branch reads the interpreter through `--git-path`, per worktree,
while its pre-push branch already falls back to the common directory; `_record_interpreter`
writes the per-worktree path. The loader links are missing in a new worktree while the tracked
`.claude/settings.json` still fires the hooks. The writer, not `read_store`, is the seam for
writes: `_declared`, the check, `_archive_finished` and `_files_holding` read entries directly;
`read_store` serves the readers alone. `memory()` is both the sign of life `tend` reads and the
window's fingerprint, so both must sit on the coordinator's side or every session ends after three
hours. The mode is the first setting read at run time: today `debug` is read only by the
installer. Docs that change: the architecture's *it locks nothing* and its straw dog on a store
that does not travel through git — under this shape the store still travels on main; the session
mechanism's doc on one folder; `questions.md`'s moments. Skills that edit bodies by hand — align,
questions, plan, ticket, discover, maintain's repairs — need the get/put path in the second mode.
Must verify: the first mode's output unchanged, the window included; 249 store tests, 128 session
tests, the worktree tests of the harness.

**Hidden edges.** Link validation runs against the coordinator's checkout: closing a question
decided, or assigning its owner, from a branch is refused while the doc or ticket lives only on
the branch — or, loosened, main's check fails until the branch merges, and for ever if it is
abandoned; the writer needs one root where entries live and another where links resolve. Git
checks a branch out in one worktree only, and main is the person's: the coordinator commits in
that checkout, sharing its index with merges, or moves the ref under it and leaves it stale. A
rename or an archive rewrites citations across `docs/`, so the coordinator's commits meet the
branches' edits as merge conflicts; rewords and archives move files without new ids, and
`move_doc` has no repair-only mode. The pre-push checks and the ticket check resolve against the
branch's stale copy. Every `at` after twelve hours writes the strike count, and every position a
row: commits on main, pushed with checks — q-0037.0017.0005.0003 first. A server started from a
hook: the host may kill the hook's process tree, the Git environment of a linked worktree is
inherited, two first hooks can start two coordinators, an address or port can go stale. Skills
may be discovered before the start hook makes their links, and a link on Windows may need
elevation. The setting sits in a branch-tracked file, so a branch can carry another mode; sibling
clones share no common directory. A local merge runs no pre-push hook, so the guard on a branch's
store belongs with the edit guard of 01-0010.0125.0010. This question's dependency,
q-0037.0017.0005.0002, leaned on a git ref its own decision 4 withdrew. 01-0010.0240.0010, in
progress, edits `hook.sh` and the pre-push half of `harness.py`.

**Leave alone.** The store/session cut, deferred: the store keeps importing the session script.
Scheduled maintain and its tickets; abandoned branches; the networked mode; the pre-push copies;
the historical records of the 2026-10-12 case. Recipients default to the first mode; an update
ships one settings row, the hook's fallback and dormant code, the guard gated on the second mode
or frost_map's branches that touch its store are refused.

**Recommendation.** Proceed, narrowed. The problem is demonstrated; the server is the general
abstraction, its second shape — the networked mode — still open, and on one machine it adds only
commits and transport, while the first mode already runs many writers against one folder with a
recheck on write. Narrower: the second mode on one machine first points the store's root and the
rows' root at the main worktree's files with the same code; the coordinator later replaces that
redirect behind the same function. Slices, smallest first: the harness on in a worktree with the
first mode's notice; the mode setting; two roots in the writer and the check; rows in git

## Discover, 2026-10-30: how such a body is kept

Asked of a separate pass that read nothing of this tree, the store's conditions as the user
accepted them, 2026-10-30 — readable, linked both ways surviving restructuring, a graph, many
writers each kept apart yet seeing the current truth at every step, nothing lost and conflicts

such a body: where does its truth live, how do concurrent writers reach it, and how does it stay
linked with the project's files?* Its material as it came back; answered from prior knowledge,

### Families

**1. Snapshot version control — the body is files in the project's own repository
("docs-as-code").** Records are text files (Markdown/YAML front matter) in the same Git repository
as the code; each writer works on a branch or worktree; truth is whatever has been merged to the
main branch; links are relative paths or IDs, checked in CI. Concrete: ADR collections (adr-tools,
MADR, Log4brains), Backstage TechDocs, Sphinx/Docusaurus, Obsidian or Foam vaults in Git, Fossil —
wiki and tickets inside the repository, an "autosync" mode pushing every commit at once (H).
Ladder: a folder of Markdown on one branch → a branch per writer, merged through review →
schema-checked front matter and a CI link check → stable IDs, indexes and backlinks generated from
forward links → the repository as a database: records as operation logs in Git refs (git-bug,
git-appraise), or a VCS-native tracker (Fossil). This situation sits between rungs 3 and 4,
pushing at 5 (M). Requirement 4 is where the family's model breaks: a branch sees its own truth,
not "the current truth"; a writer sees others' work only after a merge or a rebase onto it (H).
Fossil's autosync is the family's partial answer, giving up some isolation for it (M). Failure
modes: renames are guessed — Git infers them from content similarity, 50% by default; a move with
heavy edits, or two records merged into one, loses the identity, and path links break (H, git
diff `-M` docs); clean merges can still be wrong — a semantic conflict raises no marker (H;
Fowler, *SemanticConflict*); hot shared index, registry and counter files — sequential IDs minted
on parallel branches — conflict chronically, generated files committed worse (H); abandoned work
is lost once garbage collection runs — unreachable reflog entries after 30 days, others after 90;
"lose nothing" holds only if every line of work is pushed or tagged (H); backlinks stored in the
files drift unless generated, and generated ones conflict unless left out of version control (M).

**2. Change-based version control — the body is a set of changes, conflicts recorded as state.**
History is changes rather than snapshots, and an unresolved conflict is a value the repository
holds. Pijul and Darcs: patches commute, a conflict "a normal state", recorded and resolved later
(H). Jujutsu (jj): first-class conflicts committed and shown, not blocking; a change ID stable
through rebases; an operation log of every repository operation, so any can be undone and
abandoned work stays reachable; Git as storage backend (H). Sapling a neighbour, stacked commits
and stable identity across amends (M). Ladder: Git with rerere and disciplined rebasing → stable
change identity across rewrites (jj, Sapling) → conflicts as committed objects plus an operation
log (jj) → patch algebra with commutation and a formal model of conflicts (Pijul). Requirement 5 is
close to this family's own design statement — rung 3 or higher (M); requirement 2, identity of
*records* surviving moves and merges, is still not addressed: change identity is not record
identity (M). Failure modes: committable conflicts can be left unresolved and stack up across
writers (M; jj's docs warn about descendants of conflicted commits); Pijul immature at scale (M);
line-level guarantees only, semantic conflicts undetected (H); no live view — each writer sees its
own working state until it pulls others' changes, so requirement 4's current truth is not given (H).

**3. Central system of record — the body is rows on one server.** Truth in one service: a wiki
(MediaWiki, Confluence), a tracker (Jira, Linear, GitHub Issues), Notion, a graph database behind
an API (Neo4j). Stable server IDs, so moves and renames break no link (H); a revision table answers
who changed what, and when (H); concurrency by optimistic locking — MediaWiki's edit-conflict
screen; Confluence and Notion merge live, OT- or CRDT-like; trackers often last write per field
(M); links from code are string conventions — `Fixes #123`, Jira smart commits — that the server
scans to build backlinks (H). Ladder: a shared document → a wiki → a tracker with typed links and
VCS integration → a graph database with schema and API, temporal tables (SQL:2011) for history.
Requirement 4's one current truth is the family's strength (H); "kept apart until brought
together" is not native, drafts and sandboxes an add-on (M); requirement 6 fails for most, Linear's
local sync engine a partial exception (M). Failure modes: offline impossible or degraded (H); links
from code one-way strings that rot on migration, re-keying or retirement — issue keys change on a
Jira project move (M–H); live co-editing and last-write-wins resolve conflicts silently, breaking
requirement 5 (H); map and code versioned apart, the record unreadable at the code's commit (H);
vendor lock-in or discontinuation (M).

**4. Local-first replicated documents — the body is a CRDT every writer holds whole.** Every writer
holds a full replica, converging without a server: Automerge, Yjs, Loro, Ditto, Anytype's any-sync,
the Logseq DB version (M for the last two). Founding statement: Kleppmann, Wiggins, van Hardenberg,
McGranaghan, *Local-first software* (Onward! 2019) (H). History is the operation log; Automerge
exposes concurrent values rather than dropping them, a multi-value register showing the conflict
(H). Ink & Switch's *Upwelling* (2023) and *Patchwork* (2024) add branches, private drafts and
diffs on Automerge (M). Ladder: last-write-wins file sync (Dropbox, Syncthing) → a CRDT document
with live sync → CRDT with surfaced conflicts and history browsing → CRDT with branches, review and
merge (Patchwork). Requirements 4–6 together put it at rung 4 (M); the family's own research found
writers want privacy before merging — exactly the "kept apart, yet seeing the whole" tension (M;
Upwelling). Failure modes: automatic resolution by default breaks "never silently resolved" unless
concurrent values are surfaced deliberately (H); invariants across records not kept — concurrent
moves in a tree create cycles or duplicates without a dedicated move operation (Kleppmann et al.,
*A highly-available move operation for replicated trees*, IEEE TPDS 2021), referential integrity
neither (H); schema change across replicas hard (Ink & Switch, *Cambria*, 2020) (M); the bridge to
files weak — files on disk are not in the CRDT, and a two-way bridge reintroduces family 1's
problems (M); metadata and history grow (M).

**5. Event sourcing and immutable fact logs — the body is the append-only record of what
happened.** Truth is the log of operations, the current body a projection of it. EventStoreDB;
Datomic — immutable datoms, `as-of` queries, a single transactor; XTDB, bitemporal; Secure
Scuttlebutt and Hypercore, per-author append-only logs replicated peer to peer; git-bug, per-entity
operation logs in Git refs ordered by Lamport clocks (M–H). Ladder: a changelog file → an
append-only journal per writer plus a projection → a shared event store with versioned event
schemas → a bitemporal fact store. "Lose nothing" and "who changed what, when" come free (H); a
per-writer log covers requirement 6 (M); merges and renames become events, identity surviving them
only if the projection defines what a merge means (M). Failure modes: event schema evolution the
main reported pain (H; Overeem, Spoor, Jansen, Brinkkemper, *JSS* 2021); current truth lags with
the projection, projections from different log prefixes disagree (H); the raw log hard for a person,
requirement 1 resting on the rendering (M); concurrent events still need a choosing policy, which
can be silent (H); erasure hard in an immutable log (M); Datomic's single transactor central, not
offline (M).

**6. Versioned databases — the body is a database with Git semantics.** Structured records in a
database that branches, merges, clones, pushes and pulls. Dolt: SQL tables, cell-by-cell merge,
conflicts left visible in `dolt_conflicts` tables (H). TerminusDB: a document and graph database
with branches, commits, clone, push and pull, its stewardship passed to DFRNT around 2023 (M).
Neon and PlanetScale branch without record-level merge (M). Ladder: database snapshots →
branchable databases → branch, merge and conflict tables (Dolt) → a graph with schema, branches and
distributed clones (TerminusDB). Requirements 3, 5 and 6 put it near rung 4 (M); requirement 1 weak
for a person, read through a query or UI (M); requirement 2 needs a bridge, the database a second
repository beside the code (H). Failure modes: two histories, the database's and the code's, to be
kept in step (M); small single-vendor ecosystems (M); conflicts only cell-deep, semantic conflicts
across rows pass (H).

**7. Linked data and persistent identifiers — the body is a web of resources named independently
of where they sit.** Every record an URI/IRI, links typed triples (RDF), queried with SPARQL;
persistence by a resolver between name and location — PURL, DOI, ARK, Handle (H); versioning by
Memento (RFC 7089), the Quit Store (RDF versioned in Git; Arndt et al., 2019), PROV-O for provenance
(M); OSLC links requirements, tests and code across tools (M); Nelson's Xanadu at the far end — two-
way links, permanent addresses, transclusion, versioning, never shipped (H). Ladder: hyperlinks →
stable IDs plus a resolver → a typed RDF graph with provenance → a federated graph with versioned
named graphs → Xanadu, design only. Requirements 2 and 3 are the family's core statement —
Berners-Lee, *Cool URIs don't change* (1998): identity is what you promise, location incidental
(H); requirements 4–6 outside its core, added through Git-backed stores (M). Failure modes:
persistence an institutional promise, holding only while someone keeps the resolver; link rot the
default without one — about 50% of URLs in U.S. Supreme Court opinions, about 70% in some law
journals no longer pointing to the cited material (H; Zittrain, Albert, Lessig, *Perma*, 2014); RDF
hard to read and write by hand (M); the open-world assumption lets contradictory assertions coexist
unflagged (M); blank nodes complicate graph merges (M).

**8. Requirements traceability — the body is trace items, links carrying a review state.**
Systems engineering's practice for linking requirements, decisions and tests to code in both
directions. ALM databases: IBM DOORS, Polarion, Jama Connect. Text in VCS: Doorstop — YAML items
in Git with UIDs, links to parents, and fingerprints marking a link "suspect" when its parent
changes after review (M–H; Browning and Adams, 2014); StrictDoc and sphinx-needs; OpenFastTrack,
scanning ID tags in code into a coverage report. Interchange: ReqIF (H). Code links back by the
item's ID in a comment or tag; a scanner builds the reverse direction, so backlinks are derived,
never stored (H). Ladder: a trace matrix in a spreadsheet → ID tags in code plus a scanner →
file-based items with UIDs and suspect-link detection → an ALM database with baselines, change
requests and impact analysis. This situation sits at rung 3: links survive restructuring by binding
to IDs, not paths; a link has a state, reviewed or suspect, partly answering "a conflict is shown"
(M). Failure modes: trace matrices go stale when tracing is not mechanical (H); suspect flags
cleared without looking (M); sequential UIDs minted on parallel branches collide at merge, one
reason tools moved to random or hash IDs (M); tracing for audit rather than use, costing more than
it gives (M).

**9. Note graphs (Zettelkasten, personal knowledge management) — structure is the links, not the
location.** Small notes with identity independent of location — Luhmann's addresses, timestamp
IDs; hierarchy emergent; backlinks computed, never authored (H). Obsidian, Logseq, Roam, Foam,
org-roam (org IDs), Dendron, development stopped 2023 (M). Ladder: a folder with wikilinks →
backlinks computed by the tool → IDs decoupled from file names, a rename breaking no link → typed
links and queries (Dataview, the Logseq DB version). Requirements 2 and 3 at rungs 3–4; the family
is native to a single writer, its multi-writer story borrowed from family 1 or 4; requirement 4
outside its scope (M). Failure modes: a link is rewritten on rename only inside the app — a move by
another writer or tool (`mv`, a Git merge, an agent) breaks wikilinks (H for Obsidian); orphans and
link inflation (M); tools die — Roam's stagnation, Dendron's end stranding vaults (M).

**10. Federated, fork-everything wiki — no single truth; each writer keeps a copy, the copies
linked.** Ward Cunningham's Federated Wiki: each writer's own site, pages forked freely, every page
carrying its journal including where it was forked from; nothing merges back automatically; readers
move through a "neighborhood" of versions (M). Secure Scuttlebutt's per-author logs and hosted Git
forks share the stance (M). Ladder: personal copies → forks with provenance journals → a
neighborhood view across forks. Meets "kept apart" and "lose nothing" fully (M); *rejects* "the
body's current truth" as a coherent target — what is current depends on the fork read; that
disagreement with the tasking is the material point (M). Failure modes: forks multiply and never
converge (M); readers cannot tell which fork is authoritative (M); a small community, few
deployments (M).

**11. Blackboard and tuple space — the body is a shared working memory autonomous writers react
to.** Independent knowledge sources read from and write to one shared blackboard, a controller
scheduling who acts next: Hearsay-II (Erman et al., *Computing Surveys*, 1980), BB1 (Hayes-Roth),
Linda tuple spaces (Gelernter, 1985) (H); recent LLM multi-agent work has brought blackboards back
for agent coordination, 2024–2025 papers (M; recency, not depth). Ladder: a shared scratch file → a
blackboard with posting conventions → a blackboard with a controller and focus of attention → a
hierarchical or partitioned blackboard with knowledge-source triggers. "Every writer sees the
current truth at every step", orienting by a shared map, is exactly the blackboard's premise, rung
3 or higher (M); nothing native for requirements 2, 5 or 6 — no isolation, history or files (H).
Failure modes: the controller a bottleneck, control the hard part (H; classic critique); no
isolation, writers seeing each other's half-finished entries (H); consistency unsolved without a
transaction layer (M).

### What the tasking smuggled in

- *Its truth*, singular: one current truth assumed; families 4, 5 and 10 hold truth a projection,
  a convergence, or several forks.
- Requirements 4 and 6 conflict: every writer seeing the current truth at every step, and working
  without a network, later across machines, asks for a global *current* during partition — CAP
  (Brewer, 2000; Gilbert and Lynch, 2002) says it is traded away; the wording does not name the
  trade.
- Requirement 4 conflicts with itself: work kept apart until brought together, yet the current
  truth at every step, assumes the map can be current while the work it maps is not — the map split
  from the territory, updated ahead of or apart from the work it describes.
- *Without a network* may mean one machine: then many writers can share one store with locking and
  being current is cheap; putting several machines *later* may hide that the first design rests on
  a shared filesystem.
- Records and files cut apart in advance: "linked with the other files" makes them two sides; in
  families 1 and 8 the body *is* project files, in 3 and 6 not files at all.
- Moves presuppose a hierarchy: "moved, merged, renamed" assumes location matters, which a pure
  graph has not; links surviving restructuring assumes identity apart from location — stable IDs,
  already a design choice.
- Merging records is a loss: "merged" beside "lose nothing" — merging two records is lossy unless
  the merge is recorded, so "lose nothing" quietly means history kept, not records kept.
- Not every conflict can be shown: each family detects conflicts only at its own granularity (line,
  cell, field, triple), none semantic ones.
- "In both directions" may mean stored backlinks; families 7, 8 and 9 derive them, and stored ones
  drift and conflict.
- People and agents treated as one kind of writer: agents differ in rate, conflict resolution,
  trust and identity; "who changed what" assumes a stable identity for each agent.
- "A graph" rules out the tree and log accounts several families use.
- "Read easily by a person and by a machine" may assume one representation; families 3, 5 and 6
  keep a machine form and render a view for people.
- "Kept apart until brought together" chooses integration by merging branches, not trunk-based or
  continuous integration of small changes, which would ease requirement 4's tension.
- "How do others keep such a body" assumes one recognised kind of thing with peers; the answer is
  spread across version control, databases, hypertext, systems engineering and AI architectures.

### Nothing to take

- Blockchain and Byzantine-fault-tolerant ledgers: tamper-evidence among distrustful writers; no
  adversary stated, global consensus at odds with offline; the resemblance only "append-only and
  shared".
- Live co-editing over operational transformation (Google Docs): a central server, no isolation; a
  sub-case of family 3 or 4 here.
- Vector stores and retrieval (RAG) agent memory: topical — no identity, links, conflict model or
  authorship history.
- Headless CMSs and enterprise knowledge graphs: instances of families 3 and 7, no account of their
  own.
- Patches by email (the Linux kernel, public-inbox): coordinates integrating work, not a shared map;
  nothing maps to requirements 2 or 3.
- Monorepo build graphs (Bazel): a graph of build targets, not records; "a graph linked to files"
  only.
