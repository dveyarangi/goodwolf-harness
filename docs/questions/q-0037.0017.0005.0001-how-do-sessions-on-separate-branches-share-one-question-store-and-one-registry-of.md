## The problem, 2026-10-25

Everything a session needs to see the others, and to be seen, lives in one checkout:

- **The question store**, `docs/questions/`, 201 live entries and 109 done, tracked in git. A
  worktree holds its own copy; a question opened in one is not in the other's window, and an id
  is minted by reading the local files, so two worktrees give the same id to different questions.
- **The registry of sessions**, the rows under `docs/sessions/rows/`, tracked in git: a session in
  a worktree writes its row into its own copy, and no other session reads it. The case of
  2026-10-12: a session registered in the main checkout had every call refused as *not
  registered* from its worktree.
- **The window memory**, the session's sign of life, in the system's temp folder keyed by the
  tree's resolved path: a worktree is another key.
- **The hooks' interpreter record**, `git rev-parse --git-path gw-interpreter`, which resolves to
  the worktree's own Git directory; and **the loader links**, `.claude/skills`, ignored by git and
  made by the link step in each clone. In this tree's worktree `suspicious-faraday-766026` neither
  exists: its hook says only that no interpreter is recorded, and no skill loads — the harness is
  off there.

xuanxue-cabinet runs sessions in worktrees under `.claude/worktrees/` and in sibling clones
(`xuanxue-cabinet-15`, `xuanxue-cabinet-fix`), which share no Git directory with it. live-spec
runs its lanes as worktrees, made outside the clone (`git worktree add /private/tmp/ls-director/wt`,
its 2026-08-26 handoff); GoodWolf's study of it, 2026-10-25, names this hole as one of two limits
in its migration plan's way (live case 5 of q-0037.0006.0020.0001.0004).

The entries are also documents: 350 links from 121 files outside the store point into
`docs/questions/`, and a decided entry's answer links to the doc that holds it — on the branch
where that work was done.

## Discover, 2026-10-26

A separate pass, given the situation and the nine requirements in plain words and told not to read
this repository, returned the material below as it came. What it found smuggled in is kept with it.

**Families.**

1. *A shared ref outside every branch.* Questions live on a dedicated ref — an orphan branch or a
   custom namespace — so no code branch carries them; worktrees of one clone share refs, other clones
   sync by fetch and push, a rejected non-fast-forward push serving as compare-and-swap; ids may be
   content hashes. Systems: git-bug (per-issue operation chains under `refs/bugs/<id>`, Lamport
   clocks, id the hash of the first operation; 0.11 with a web UI reported 2026-10-02), Gerrit NoteDb
   (review metadata as commits on `refs/changes/*/meta`), git-appraise (JSON lines in git notes).
   Ladder: an orphan branch of markdown files checked out as one dedicated worktree → snapshot commits
   on a custom ref by plumbing → a per-entity operation log; this case at rung 1 or 2. Known failures:
   custom refs are not fetched or pushed by default; code-host web views show branches and tags, not
   notes or custom refs; push races need a retry loop; many writers in one worktree contend on
   `index.lock`. Meets poorly: req 3 for anything but an orphan branch; req 1 across machines, as
   fresh as the last fetch; req 5, a link from code docs to a file on another ref needing a host URL or
   a convention.
2. *A separate repository of files.* A sibling or submodule repository at a fixed path, one checkout
   per machine or a worktree per session, committed and pulled and pushed. Systems: git-issue
   (issues as directories of plain files in a `.issues` repository), Sit, notes vaults synced through
   git. Known failures: header and hand-written body in one file conflict in the frontmatter; a
   forgotten pull gives a stale view; cross-repository links are fragile. Meets poorly: req 5; req 1
   across machines; req 2 with sequential ids.
3. *Event sourcing.* Each open, reword, move, close, lean and counter bump is an immutable event —
   a file named by a ULID and the session, or a line in a union-merged JSONL — folded into the tree;
   storage never conflicts, semantic conflicts (two rewords, a cyclic move, a close against an edit)
   are found in the fold and shown; the markdown files become rendered views; counters stop being a
   hot spot. Systems: git-bug, Fossil tickets, Beads (SQLite plus JSONL in git, hash ids adopted after
   sequential ids collided across agents and branches; since moved to Dolt, keeping SQLite and JSONL
   aligned through worktrees, pulls, merges, deletions and crashes having been the pain). Known
   failures: union merge duplicates or reorders lines; deletes are hard; two representations drift;
   wall-clock last-writer-wins skews across machines. Meets poorly: req 4, a hand edit to a rendered
   view must be ingested back or is lost; req 3, the authoritative form is not the readable file.
4. *CRDTs.* A replicated tree with a move operation (Kleppmann et al., 2021), multi-value registers
   keeping both concurrent values, a text CRDT or register for the body, a G-counter. Systems:
   Automerge, Yjs, Loro, cr-sqlite; a hand-rolled standard-library version of the lower rungs is
   feasible at 300 nodes. Known failures: last-writer-wins loses data silently; text CRDTs interleave;
   formats are opaque; tree moves are subtle. Meets poorly: req 7; req 3 and 4 unless rendered
   markdown is kept beside, which brings back family 3's ingest problem.
5. *A version-controlled database.* One table with cell-level merge and a conflicts table. Systems:
   Dolt (Beads' sole backend now; multiple writers need `dolt sql-server`), Fossil's SQLite, Irmin,
   TerminusDB. Known failures: Beads' 2026 release notes fix Dolt pull and merge breakage. Meets
   poorly: req 7, req 3, req 4.
6. *A single serialization point.* One authority hands out ids and holds the truth — the code host's
   tracker, or a branch on one remote whose atomic push is the lock; positions become leased presence.
   Systems: GitHub Issues with sub-issues, Jira, Linear, Gerrit's server. Known failures: outages and
   rate limits; the offline queue turns into family 3. Meets poorly: req 6, req 7, req 3 and 4 in part.

**What the tasking smuggled in.** Presence fused with record: a session's position is ephemeral and
wants a lease, no merge or history. Two writers in one file: a script-owned header and a hand-owned
body; most merge pain in families 1 and 2 comes from that, not from distribution. Polling at every
turn prefers a local replica. Branch-per-session taken as fixed, where a record always written to one
place is the alternative. "No server" while relying on a git remote a second machine reaches. Ids
framed as minting: random or content-addressed ids need no coordinator; if an id encodes its parent
path, a move renames ids and breaks req 5, which the requirements do not settle. A strict tree, one
parent each. The body as a decision log raises the cost of a lost merge, and who resolves a body
conflict between two agents is not said. Counters as mutable fields are a self-made hot spot. Req 9
against req 5: a record that outlives a branch points at documents only that branch held. At 300
nodes every family meets the read time, so scale decides nothing.

**Nothing to take.** Real-time collaborative editors (family 6 with a text CRDT); gossip and
anti-entropy protocols, right for presence but with no system applying them to a git-carried
record; git-appraise's own use of notes not confirmed.

## Decisions

1. **What the store must do** *(the user, 2026-10-26)*: the designs are weighed against these.
   1. Every session sees the current tree of questions at each step, from any working tree, any
      clone and, later, any machine; a local read takes tens of milliseconds.
   2. An id is given once, everywhere.
   3. A question reads easily to an agent and to the person; a file can link to it, and it can
      link to a file — not necessarily a file itself *(amended by the user, 2026-10-26)*.
   4. A body is written by hand, as free text; the header only by the script.
   5. Links hold: the docs' and tickets' links into the store, and the questions' links out of it.
   6. It works without a network; edits from different machines merge without loss, and a
      conflict is shown, never lost.
   7. Python's standard library only, and no server anyone must keep running.
   8. History is kept: who changed what, and when.
2. **A question outlives its branch** *(the user, 2026-10-26)*: a question, and the decisions its
   body holds, are kept though the branch it was opened or changed on is abandoned, unless they
   were consciously dropped. The store is not scoped to a branch. A closed question holds only
   its answer's link, so an abandoned branch leaves at worst a link to a doc that never reached
   main; when a branch counts as abandoned, and who puts it to the person, is
   q-0037.0017.0006.0003's.
3. **Not a separate branch of questions** *(the user, 2026-10-26)*: a branch outside the code, checked
   out in one shared folder, sounds slow and unobservable to the person; refused unless argued back.
4. **Modes, and a coordinator in the branch-per-session mode** *(the user, 2026-10-26)*: in the
   first mode every session works on one shared branch, as today. In the second each session has a
   branch of its own on one machine, and a coordinator holds the questions' truth: every change to
   a question goes through its server, applied mechanically, and everything about how sessions
   coordinate — who holds what, what changed under whom — is its too. On a network, someone raises
   the same coordinator at home or on a server. A server is acceptable for that mode, so
   requirement 7 holds per mode: the first runs none. Who raises the server is still open.
5. **The coordinator's server is raised on demand** *(the user, 2026-10-26)*: on one machine, a
   session's hook that finds no coordinator answering starts it as a process of its own and
   records its address in the clone's Git directory, which every worktree reads; the server stops
   by itself when nobody has called it for a while, and every session's window shows that it runs.
   It lives apart from any chat; an agent it needs for a conflict, it calls. On a network the
   person raises it, and its address is a setting of the project.
6. **The coordinator starts no /maintain, for now** *(the user, 2026-10-26)*: it is built without
   it, and whether it ever does is decided later, at q-0037.0010.0009.0009; no case is recorded of
   drift doing harm between two scheduled passes.
7. **In the second mode every read and write of a question goes through the coordinator**
   *(the user, 2026-10-26)*: the copy of `docs/questions/` a branch carries decides nothing, is
   neither read nor written there, and a check refuses a branch that changes it, so merging the
   branch leaves main's store as it stands. The truth stays files on main, kept and committed by
   the coordinator in its checkout. The seam is `questions.read_store`, through which the other
   six scripts already read the store.
8. **A body is edited through the coordinator, on the condition it has not changed**
   *(the user, 2026-10-26)*: the session takes the body from the coordinator into a local file with
   the fingerprint of the version it began from, edits it by ordinary means, and gives it back with
   that fingerprint; the coordinator takes it only if its body is still that version, and otherwise
   refuses and returns three versions — the one begun from, the other's, and this one's — for the
   session to bring together. One writer of the truth catches every race with one check.
9. **A branch's links to a moved question are repaired by the coordinator's map of renames**
   *(the user, 2026-10-26)*: a move already computes its pairs of old and new ids, and `move_doc`
   already repairs citations by pairs; the coordinator keeps the pairs, and before a branch is
   merged a check runs its links through them. Not: ids that do not encode their place in the
   tree — the cleaner end, a large work of its own that this mode does not need; nor refusing a
   move while a branch links into the subtree, which stalls the work.
10. **When the coordinator does not answer, a write is refused and the window read from main's
    files** *(the user, 2026-10-26)*: the session is told plainly that the change was not taken;
    the window is drawn from the files in the checkout where the coordinator keeps the truth,
    marked as such. The next step of any session raises the coordinator again, so the refusal
    lasts about one step. Not: a queue of changes kept until it returns — the event log with all
    its merging, for a rare case; weighed again for the networked mode.
11. **In the second mode the sessions' rows go through the coordinator, in today's form**
    *(the user, 2026-10-26)*: registering, seen, silence, the end, a hold, a take, a release and
    the sign of life are calls into the coordinator, which runs the session script's same
    functions over the rows' folder in its checkout; one code for both modes. Whether the rows
    stay tracked in git is q-0037.0017.0005.0003's.
12. **The mode is a setting of the tree** *(the user, 2026-10-26)*: a knob the session mechanism
    declares, set by the person in `local.rules.md`, its default the one shared branch. A session
    that starts in a worktree of its own while the tree is in the first mode is told so in its
    window — it sees no other session. Not: the mode read from where the session stands — a
    sibling clone is no main checkout either, and the mode would change unseen mid-work.
13. **The server stays; the narrowing is refused** *(the user, 2026-10-29)*: the impact's narrower
    step — sessions writing the main checkout's store directly — is not taken; a session reaches
    the store only through the coordinator, which alone writes and commits it. A host may keep an
    agent out of folders beyond its worktree, and a commit in the person's checkout would share
    its index; the server meets neither.

## Where it stands

**The problem.** The store, the sessions' rows, the window memory, the hooks' interpreter record
and the loader links each live in one checkout; a session in a worktree of its own sees no other,
mints ids blind, and here runs with the harness off. Two recipients work so — xuanxue-cabinet's
worktrees and sibling clones, live-spec's lanes.

**The shape.** Two modes, a setting of the tree the person sets. In the first, every session works
on one shared branch, as today. In the second, each session has a branch of its own on one
machine, and a coordinator holds the truth: a server, raised on demand by the hook of the first
session that finds none answering, its address in the clone's Git directory every worktree reads,
stopping when idle, shown in every window, living apart from any chat. Every read and write of a
question goes through it, and every call on a session's row — registering, seen, silence, the
end, a hold, a take, a release; it runs the store's and the session script's same code over the
same files, in the checkout it keeps, and commits them to main. A branch's copy of the store
decides nothing, and a check refuses a branch that changes it. A body is taken into a local file
with the fingerprint it began from, edited by ordinary means, and given back on the condition the
coordinator's is still that version; otherwise refused, with three versions to bring together. A
move's pairs of old and new ids are kept, and a branch's links are run through them before its
merge. A coordinator that does not answer refuses the write plainly, and the window is read from
the files it keeps, marked so. The seams already stand: the other scripts read the store through
`read_store`, every change to it is one of the store's events, and the row's life is nine
functions of the session script.

The worktree's own setup — the interpreter record resolved through the clone's common Git
directory, the loader links made in a worktree that lacks them — is the second mode's first need.

**What is open.** The networked mode: who raises the coordinator, its address a setting of the
project; a queue for writes while it is away is weighed there. Whether the rows stay tracked in
git, q-0037.0017.0005.0003. Whether the coordinator starts `/maintain`, q-0037.0010.0009.0009,
set aside. An agent the coordinator calls for a conflict, when refusals turn frequent. When a
branch counts as abandoned, q-0037.0017.0006.0003.

## Impact, 2026-10-29

A separate pass read the tree against the accepted shape.

**Impact.** `hook.sh`'s host branch reads the interpreter through `--git-path`, per worktree,
while its pre-push branch already falls back to the common directory; `_record_interpreter`
writes the per-worktree path. The loader links are missing in a new worktree while the tracked
`.claude/settings.json` still fires the hooks. The writer, not `read_store`, is the seam for
writes: `_declared`, the check, `_archive_finished` and `_files_holding` read entries directly;
`read_store` serves the readers alone. `memory()` is both the sign of life `tend` reads and the
window's fingerprint, so both must sit on the coordinator's side or every session ends after three
hours. The mode is the first setting read at run time: today `debug` is read only by the
installer. Docs that change: the architecture's *it locks nothing* and its straw dog on a store
that does not travel through git — under this shape the store still travels on main; the session
mechanism's doc on one folder; `questions.md`'s moments. Skills that edit bodies by hand — align,
questions, plan, ticket, discover, maintain's repairs — need the get/put path in the second mode.
Must verify: the first mode's output unchanged, the window included; 249 store tests, 128 session
tests, the worktree tests of the harness.

**Hidden edges.** Link validation runs against the coordinator's checkout: closing a question
decided, or assigning its owner, from a branch is refused while the doc or ticket lives only on
the branch — or, loosened, main's check fails until the branch merges, and for ever if it is
abandoned; the writer needs one root where entries live and another where links resolve. Git
checks a branch out in one worktree only, and main is the person's: the coordinator commits in
that checkout, sharing its index with merges, or moves the ref under it and leaves it stale. A
rename or an archive rewrites citations across `docs/`, so the coordinator's commits meet the
branches' edits as merge conflicts; rewords and archives move files without new ids, and
`move_doc` has no repair-only mode. The pre-push checks and the ticket check resolve against the
branch's stale copy. Every `at` after twelve hours writes the strike count, and every position a
row: commits on main, pushed with checks — q-0037.0017.0005.0003 first. A server started from a
hook: the host may kill the hook's process tree, the Git environment of a linked worktree is
inherited, two first hooks can start two coordinators, an address or port can go stale. Skills
may be discovered before the start hook makes their links, and a link on Windows may need
elevation. The setting sits in a branch-tracked file, so a branch can carry another mode; sibling
clones share no common directory. A local merge runs no pre-push hook, so the guard on a branch's
store belongs with the edit guard of 01-0010.0125.0010. This question's dependency,
q-0037.0017.0005.0002, leaned on a git ref its own decision 4 withdrew. 01-0010.0240.0010, in
progress, edits `hook.sh` and the pre-push half of `harness.py`.

**Leave alone.** The store/session cut, deferred: the store keeps importing the session script.
Scheduled maintain and its tickets; abandoned branches; the networked mode; the pre-push copies;
the historical records of the 2026-10-12 case. Recipients default to the first mode; an update
ships one settings row, the hook's fallback and dormant code, the guard gated on the second mode
or frost_map's branches that touch its store are refused.

**Recommendation.** Proceed, narrowed. The problem is demonstrated; the server is the general
abstraction, its second shape — the networked mode — still open, and on one machine it adds only
commits and transport, while the first mode already runs many writers against one folder with a
recheck on write. Narrower: the second mode on one machine first points the store's root and the
rows' root at the main worktree's files with the same code; the coordinator later replaces that
redirect behind the same function. Slices, smallest first: the harness on in a worktree with the
first mode's notice; the mode setting; two roots in the writer and the check; rows in git
decided; the roots redirected in the second mode, with who commits on main; the branch's store
guard; bodies on a fingerprint, returning on mismatch only the current version; the rename map
with path pairs and a repair-only mover; the server, postponed until contention or the network
calls for it.
