## The problem, 2026-10-25

Everything a session needs to see the others, and to be seen, lives in one checkout:

- **The question store**, `docs/questions/`, 201 live entries and 109 done, tracked in git. A
  worktree holds its own copy; a question opened in one is not in the other's window, and an id
  is minted by reading the local files, so two worktrees give the same id to different questions.
- **The registry of sessions**, the rows under `docs/sessions/rows/`, tracked in git: a session in
  a worktree writes its row into its own copy, and no other session reads it. The case of
  2026-10-12: a session registered in the main checkout had every call refused as *not
  registered* from its worktree.
- **The window memory**, the session's sign of life, in the system's temp folder keyed by the
  tree's resolved path: a worktree is another key.
- **The hooks' interpreter record**, `git rev-parse --git-path gw-interpreter`, which resolves to
  the worktree's own Git directory; and **the loader links**, `.claude/skills`, ignored by git and
  made by the link step in each clone. In this tree's worktree `suspicious-faraday-766026` neither
  exists: its hook says only that no interpreter is recorded, and no skill loads — the harness is
  off there.

xuanxue-cabinet runs sessions in worktrees under `.claude/worktrees/` and in sibling clones
(`xuanxue-cabinet-15`, `xuanxue-cabinet-fix`), which share no Git directory with it. live-spec
runs its lanes as worktrees, made outside the clone (`git worktree add /private/tmp/ls-director/wt`,
its 2026-08-26 handoff); GoodWolf's study of it, 2026-10-25, names this hole as one of two limits
in its migration plan's way (live case 5 of q-0037.0006.0020.0001.0004).

The entries are also documents: 350 links from 121 files outside the store point into
`docs/questions/`, and a decided entry's answer links to the doc that holds it — on the branch
where that work was done.

## Discover, 2026-10-26

A separate pass, given the situation and the nine requirements in plain words and told not to read
this repository, returned the material below as it came. What it found smuggled in is kept with it.

**Families.**

1. *A shared ref outside every branch.* Questions live on a dedicated ref — an orphan branch or a
   custom namespace — so no code branch carries them; worktrees of one clone share refs, other clones
   sync by fetch and push, a rejected non-fast-forward push serving as compare-and-swap; ids may be
   content hashes. Systems: git-bug (per-issue operation chains under `refs/bugs/<id>`, Lamport
   clocks, id the hash of the first operation; 0.11 with a web UI reported 2026-10-02), Gerrit NoteDb
   (review metadata as commits on `refs/changes/*/meta`), git-appraise (JSON lines in git notes).
   Ladder: an orphan branch of markdown files checked out as one dedicated worktree → snapshot commits
   on a custom ref by plumbing → a per-entity operation log; this case at rung 1 or 2. Known failures:
   custom refs are not fetched or pushed by default; code-host web views show branches and tags, not
   notes or custom refs; push races need a retry loop; many writers in one worktree contend on
   `index.lock`. Meets poorly: req 3 for anything but an orphan branch; req 1 across machines, as
   fresh as the last fetch; req 5, a link from code docs to a file on another ref needing a host URL or
   a convention.
2. *A separate repository of files.* A sibling or submodule repository at a fixed path, one checkout
   per machine or a worktree per session, committed and pulled and pushed. Systems: git-issue
   (issues as directories of plain files in a `.issues` repository), Sit, notes vaults synced through
   git. Known failures: header and hand-written body in one file conflict in the frontmatter; a
   forgotten pull gives a stale view; cross-repository links are fragile. Meets poorly: req 5; req 1
   across machines; req 2 with sequential ids.
3. *Event sourcing.* Each open, reword, move, close, lean and counter bump is an immutable event —
   a file named by a ULID and the session, or a line in a union-merged JSONL — folded into the tree;
   storage never conflicts, semantic conflicts (two rewords, a cyclic move, a close against an edit)
   are found in the fold and shown; the markdown files become rendered views; counters stop being a
   hot spot. Systems: git-bug, Fossil tickets, Beads (SQLite plus JSONL in git, hash ids adopted after
   sequential ids collided across agents and branches; since moved to Dolt, keeping SQLite and JSONL
   aligned through worktrees, pulls, merges, deletions and crashes having been the pain). Known
   failures: union merge duplicates or reorders lines; deletes are hard; two representations drift;
   wall-clock last-writer-wins skews across machines. Meets poorly: req 4, a hand edit to a rendered
   view must be ingested back or is lost; req 3, the authoritative form is not the readable file.
4. *CRDTs.* A replicated tree with a move operation (Kleppmann et al., 2021), multi-value registers
   keeping both concurrent values, a text CRDT or register for the body, a G-counter. Systems:
   Automerge, Yjs, Loro, cr-sqlite; a hand-rolled standard-library version of the lower rungs is
   feasible at 300 nodes. Known failures: last-writer-wins loses data silently; text CRDTs interleave;
   formats are opaque; tree moves are subtle. Meets poorly: req 7; req 3 and 4 unless rendered
   markdown is kept beside, which brings back family 3's ingest problem.
5. *A version-controlled database.* One table with cell-level merge and a conflicts table. Systems:
   Dolt (Beads' sole backend now; multiple writers need `dolt sql-server`), Fossil's SQLite, Irmin,
   TerminusDB. Known failures: Beads' 2026 release notes fix Dolt pull and merge breakage. Meets
   poorly: req 7, req 3, req 4.
6. *A single serialization point.* One authority hands out ids and holds the truth — the code host's
   tracker, or a branch on one remote whose atomic push is the lock; positions become leased presence.
   Systems: GitHub Issues with sub-issues, Jira, Linear, Gerrit's server. Known failures: outages and
   rate limits; the offline queue turns into family 3. Meets poorly: req 6, req 7, req 3 and 4 in part.

**What the tasking smuggled in.** Presence fused with record: a session's position is ephemeral and
wants a lease, no merge or history. Two writers in one file: a script-owned header and a hand-owned
body; most merge pain in families 1 and 2 comes from that, not from distribution. Polling at every
turn prefers a local replica. Branch-per-session taken as fixed, where a record always written to one
place is the alternative. "No server" while relying on a git remote a second machine reaches. Ids
framed as minting: random or content-addressed ids need no coordinator; if an id encodes its parent
path, a move renames ids and breaks req 5, which the requirements do not settle. A strict tree, one
parent each. The body as a decision log raises the cost of a lost merge, and who resolves a body
conflict between two agents is not said. Counters as mutable fields are a self-made hot spot. Req 9
against req 5: a record that outlives a branch points at documents only that branch held. At 300
nodes every family meets the read time, so scale decides nothing.

**Nothing to take.** Real-time collaborative editors (family 6 with a text CRDT); gossip and
anti-entropy protocols, right for presence but with no system applying them to a git-carried
record; git-appraise's own use of notes not confirmed.

## Decisions

1. **What the store must do** *(the user, 2026-10-26)*: the designs are weighed against these.
   1. Every session sees the current tree of questions at each step, from any working tree, any
      clone and, later, any machine; a local read takes tens of milliseconds.
   2. An id is given once, everywhere.
   3. A question reads easily to an agent and to the person; a file can link to it, and it can
      link to a file — not necessarily a file itself *(amended by the user, 2026-10-26)*.
   4. A body is written by hand, as free text; the header only by the script.
   5. Links hold: the docs' and tickets' links into the store, and the questions' links out of it.
   6. It works without a network; edits from different machines merge without loss, and a
      conflict is shown, never lost.
   7. Python's standard library only, and no server anyone must keep running.
   8. History is kept: who changed what, and when.
2. **A question outlives its branch** *(the user, 2026-10-26)*: a question, and the decisions its
   body holds, are kept though the branch it was opened or changed on is abandoned, unless they
   were consciously dropped. The store is not scoped to a branch. A closed question holds only
   its answer's link, so an abandoned branch leaves at worst a link to a doc that never reached
   main; when a branch counts as abandoned, and who puts it to the person, is
   q-0037.0017.0006.0003's.
3. **Not a separate branch of questions** *(the user, 2026-10-26)*: a branch outside the code, checked
   out in one shared folder, sounds slow and unobservable to the person; refused unless argued back.
