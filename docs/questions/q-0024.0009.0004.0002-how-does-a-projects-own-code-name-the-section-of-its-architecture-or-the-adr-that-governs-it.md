## Decisions

1. **A pointer names the rule as its doc names it** *(the user, 2026-10-12)*: a heading or the bold
   lead of a paragraph, word for word, never a date or a line number; a rule a pointer needs that
   has no such name gets one in its doc. frost_map's code holds 13 such pointers today, written
   loosely — *the Station page* names no heading or lead, *2026-09-17* names a date — and two of
   them resolve.
2. **A pointer sits in the comment it supports** *(the user, 2026-10-12)*: at the end of the phrase
   it backs, as `(<path from the tree's root>: "<the rule's name>")`, as many to a file as the
   comment needs — never one line per file, since a component follows several rules and frost_map
   already points phrase by phrase. The pointer stands whole on one line, the comment wrapped before
   it and never inside it, so one pattern finds every pointer in any language; two of frost_map's
   13 are wrapped today *(the user, 2026-10-12, at the plan)*.
3. **Whatever holds the pointers holds that each resolves; whether code carries one is the writer's
   judgement** *(the user, 2026-10-12; who holds them is decision 5's)*: a rule reaching `/implement` says *where the code you write follows a
   rule that a load-bearing record of the project states — its architecture or an ADR — name the
   rule in the comment beside that code*, a rule with no name getting one in its record first; no
   file is required to carry a pointer, since only the writer sees whether code follows a rule, and
   a pointer on every file would be a label for show.
4. **The rule and the pointer's form are written by hand in `/implement`** *(the user, 2026-10-12)*,
   wrapped as a straw dog bound to q-0023.0011, what `/implement` owns — the skill belongs to no
   mechanism, so nothing installs into it yet; the maintain mechanism and the mechanism shape were
   weighed and not taken.
5. **The check waits for `/implement`'s mechanism** *(the user, 2026-10-12)*: every core script must
   name a mechanism whose parts list it, and `/implement` has none, so no script can hold the
   pointers yet; until then `/verify` reads the pointers in a slice's code by eye, a sentence in
   `/verify`'s own body bound to q-0023.0011 too — not beside the rule in `/implement`, since an
   agent running `/verify` reads its own skill *(the user, 2026-10-12, at the plan)* — and the tested criterion — a pointer that does not resolve is
   reported — moves to the work that makes `/implement` a mechanism.
6. **The trial runs in frost_map, updated first** *(the user, 2026-10-12)*: frost_map takes the
   core that carries the rule, and the pointers are brought to the form there, in its own code and
   architecture, under its own switches — not on paper from here. The queue's hold on frost_map's
   update until the releases chain is set aside for it; frost_map stood at `6586a6b` already,
   updated by its own session (its `a2d05ca`) while the queue still said `2c733f0`.
7. **A fresh session in frost_map brings the pointers to the form** *(the user, 2026-10-12)*: this
   session writes the rule and updates frost_map; a session opened there is given the task alone and
   works from the installed rule, so the trial shows whether the rule reaches an agent that did not
   write it, and where it stumbles is a finding for the rule. frost_map's own switches hold there,
   `commit=ask` among them.
8. **frost_map takes the rule from the published repository** *(the user, 2026-10-12, at stage 2)*:
   a recipient takes core only from a source of the name it announces, so frost_map updates with no
   `--from` once this session's work is published, its repository line staying the URL; the trial
   runs in the next session.

## Evidence — the trial, 2026-10-13

frost_map took core `goodwolf-harness@f0fae24` in its `cb9072a` *(the user, 2026-10-13)*. A fresh
session there was given the task alone and worked from the installed rule; its report was brought
here by the user, and its diff, uncommitted under frost_map's `commit=ask`, was read here the same
day.

- **What it did.** The 13 comments that pointed at the architecture now carry 15 pointers to seven
  names. Five rules had no name and got one, each by bolding words already opening the paragraph or
  by splitting a paragraph at a bold already in it; one sentence's order turned, *That statement is
  the page's introduction* to *The page's introduction is that statement*. Every name is a bold lead
  the architecture holds word for word, read here with the record's lines joined. Its typecheck,
  build and 83 unit tests passed; the browser suites were not run.
- **Not a rule failure.** The rule arrived with the update and every comment predates it.
- **Where the rule left it guessing**, in its words reduced:

     it split paragraphs; three splits would be unneeded otherwise.
  2. Whether a lead naming a paragraph that holds several rules names each of them.
  3. A phrase two rules back, one in an unnamed paragraph (`App.tsx:260`) — it could not choose,
     and left the phrase with no pointer.
  4. Whole on one line runs one pointer to about 135 characters, past the ~120 the files use; the

  5. The old pointers carried the decision's date; the form has no place for one, so the dates were

  6. A pointer to an RFC — the rule speaks of the architecture and ADRs only; left alone.
  7. Eighteen `(user, date)` comments back rules the architecture also states; outside its brief.
  8. The collector, a second repository: its docs check refuses `docs/` paths in its code, and the
     path from the tree's root is unclear across two repositories; left alone.
