# q-0018.0011.0004 How does an arrival find what a project exists to solve and the answers it already has, in its documents and its code?

- **part of** q-0018.0011
- **state** open
- **struck** 0, last 2026-10-09T13:17Z

Opened 2026-10-09 from q-0033.0005. A project's product answers may already exist in its own
docs, or only in its code. For that project's product, who owns an instruction does not matter:
instructions are not part of the product, as they are not for the harness *(the user)*.

**The user's plan, two stages:**

1. **After the install, an align** on what the project exists to solve, and on how the person
   sees the causes and the ways of answering them. The user would find a softer word than
   *pains*. The align is not done until the person approves its closing, as with any question.
2. **An agent's pass over the existing docs and code** to pull out the ways already built.

The user: *I'm not sure we can count on the code or the docs being marked and reorganized the
way we like, so that the second pass goes by marks — that probably can't be done even in the
harness itself, unless you see a way.*

**Generate the missing question tree** — the user's idea, *the question is whether it's
realistic*. The second pass then writes its findings as questions, not as marks in code: each
answer it finds becomes a question hung under the cause it answers, pointing at where the answer
lives. The code and docs stay untouched. The store becomes the index of the product's answers,
old and new alike, and the product document derives from it as from any other question.

The agent's reading, 2026-10-09:

- **Structure is realistic.** The align's seed gives the upper levels — the problems, the causes
  — and the pass hangs what it finds under them. Nothing has to be guessed about where a finding
  goes, only whether it answers a cause.
- **Volume is realistic only through the load-bearing test.** A codebase holds hundreds of
  implicit decisions. Only those whose violation would break several parts get a question, which
  is the same line *document load-bearing, code and comment the rest* already draws.
- **The *why* is not realistic.** Code shows what was built, not what was asked or what was
  refused. A question reverse-engineered from an answer is a rationalization. A generated
  question must therefore say it is reconstructed: found, not decided. It stays so until the
  person confirms it, and an invented rationale presented as settled is the false memory the
  harness exists to prevent.
- **The cheapest test is the harness itself.** Its own rules that no mechanism owns are few —
  about a dozen in the entry file — and their real history is on record: the entry contract's
  evidence, the rule-failure register, the session records. Generate the questions from the
  rules alone, then compare them against the record. That measures how much of the *why* a pass
  invents.
