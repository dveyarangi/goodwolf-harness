# q-0018.0011.0004 How does an arrival find what a project exists to solve and the answers it already has, in its documents and its code?

- **part of** q-0018.0011
- **state** open
- **struck** 0, last 2026-10-09T13:17Z

Opened 2026-10-09 from q-0033.0005. A project's product answers may already exist in its own
docs, or only in its code. For that project's product, who owns an instruction does not matter:
instructions are not part of the product, as they are not for the harness *(the user)*.

**The user's plan, two stages:**

1. **After the install, an align** on what the project exists to solve, and on how the person
   sees the causes and the ways of answering them. The user would find a softer word than
   *pains*. The align is not done until the person approves its closing, as with any question.
2. **An agent's pass over the existing docs and code** to pull out the ways already built.

The user: *I'm not sure we can count on the code or the docs being marked and reorganized the
way we like, so that the second pass goes by marks — that probably can't be done even in the
harness itself, unless you see a way.*

**Generate the missing question tree** — the user's idea, *the question is whether it's
realistic*. The second pass then writes its findings as questions, not as marks in code: each
answer it finds becomes a question hung under the cause it answers, pointing at where the answer
lives. The code and docs stay untouched. The store becomes the index of the product's answers,
old and new alike, and the product document derives from it as from any other question.

The agent's reading, 2026-10-09:

- **Structure is realistic.** The align's seed gives the upper levels — the problems, the causes
  — and the pass hangs what it finds under them. Nothing has to be guessed about where a finding
  goes, only whether it answers a cause.
- **Volume is realistic only through the load-bearing test.** A codebase holds hundreds of
  implicit decisions. Only those whose violation would break several parts get a question, which
  is the same line *document load-bearing, code and comment the rest* already draws.
- ~~The *why* is not realistic.~~ Struck by the user the same day: *if we know the user
  recognized the named causes and wants to solve them, they are the answer to your "why".* The
  agent had run two *why*s together:
  - **Why the thing exists** is the product's question, answered by the cause it serves. The
    align supplies it; nothing is reconstructed.
  - **Why it was built this way rather than another** is the architecture's question, not the
    product's.

  What stays uncertain is narrower: whether a thing found in code answers a cause the person
  recognized, or exists by accident. That is why a found answer waits on the person.

**Corrected, the user, 2026-10-09.** The two stages are only the upper levels of the tree, and
the user gave two concrete anchors, both of which land in sections `docs/product.md` already has:

1. **What exactly is hard** — the pains.
2. **What causes the difficulty**, which the person has recognized and is solving — the causes.

Two more halves follow from the second:

- **Causes the person has not recognized.** They are found by discovery, and they are the
  responsibility of the root that keeps the landscape and the evolution.
- **Causes the person recognized but did not name at the align, and built somewhere.** The
  second stage finds these in the docs and the code, and each becomes a question hung under the
  cause it answers.

**The align's gate at the scale of a project** *(the user, correcting the agent's "until the
person approves its closing")*: the arrival's align is not done until at least one difficulty
the project solves is found. It is the align's necessity gate applied to the whole project.

**A found answer is HITL** *(the user)*. *"Found, not confirmed" is in effect a HITL ticket. We
need that mark, because some questions the agent may close itself under an authorization
mechanism.* That mechanism does not exist yet; what exists is the implied rule that the person
steps in on what bears load. Its home is q-0027.0002 "Which questions stop for a human?".

**The test, on the harness itself** *(the user)*: the mechanism, once written, generates the
harness's own question tree, compared against the list
[the audit of 2026-10-09](../research/product-audit-2026-10-09.md) produced. The agent's caution:
that list is one agent's judgement too, so comparing two passes measures their agreement, not
their truth. The oracle is the list after the person has ruled on each item.
