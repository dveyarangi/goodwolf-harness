## Where it stands

A spec as a document of its own is retired: the question a piece of work answers is its working
document. Its `Where it stands` holds the whole picture for a reader arriving cold, rewritten as
decisions land; its decisions list holds what was agreed and what was refused; its children hold
what is open; its trace link to the product document holds coverage, where user stories did. The
person accepts the `Where it stands` before tickets are minted from the question. What remains is
the work: the `/spec` skill, the loop's `/spec` route and *spec accepted* checkpoint in the entry
file, the ticket format's spec parent and *Parent scope addressed*, `/maintain`'s P4, a check that a
question a ticket answers carries its `Where it stands`, and the five live specs folded into their
questions at their next touch.

## Decisions

1. A spec is no separate document: the question a piece of work answers holds its rationale, the
   ticket its status, the standing documents current truth *(the user, 2026-10-15)*. Not: a spec
   beside the question — it repeated the question's case and decisions, its user stories were read
   only as a slice's coverage, which the trace link already holds, and the discovery found per-change
   specs for agents seldom carried forward and skimmed when approved.
2. A question's body runs `Where it stands`, rewritten whole; `Decisions`, each refused alternative
   named; dated evidence, appended only — and a question a ticket answers carries its `Where it
   stands`, held by a check *(the user, 2026-10-15)* → [the questions skill, *The body*](../../.agents/skills/questions/SKILL.md).

## Discovery, 2026-10-15

A pass told nothing of this tree. Its material, as it came back, condensed by dropping links:

### Families

1. **Tracker-centred** — an issue for a small task, an epic with children for a large one; size
   scales by hierarchy, never by turning into argument; a design doc is linked when one is needed.
   Gives visibility and queue order; rationale fragments across comments, tickets turn to
   one-line placeholders. An issue-to-PR agent takes the issue body as its prompt, so a thin
   ticket becomes bad output: a teammate filled gaps from shared context, an agent cannot (H/M).
2. **Design doc / RFC** — a prose argument before code (context, goals and non-goals, design,
   alternatives), reviewed by peers; PEPs, KEPs, RFDs, Amazon's six-pager. Threshold: more than a
   few weeks, crossing boundaries, or hard to reverse; below it a ticket and the PR description.
   Gives problems found while cheap, agreement, alternatives recorded. Usually frozen and stale
   after; rubber-stamp or committee review; written after the fact; later rationale never back in
   it. With an assistant writing becomes cheap and reading and judging stay dear (H/M).
3. **Requirements → design → verification chain** — specifications and a traceability matrix,
   mandatory in regulated work; scaled by assurance tier, not size — a one-line change at the top
   tier still gets a change request and re-verification. Auditability; documents for the auditor
   diverging from the system, traceability theatre (H/M).
4. **Bet-sized shaping (Shape Up)** — a pitch with the problem, a fixed appetite, the solution at
   fat-marker level, rabbit holes and no-gos; nothing kept centrally after, losing pitches dropped.
   Bounded risk, little paper; heavy on a few shapers, weak for multi-cycle work. A fixed appetite
   is one of the few explicit controls on an agent's scope creep — an inference (M/L).
5. **Conversation-first** — the story as a placeholder for a conversation, cards torn up when
   done, code and tests the durable record; its AI descendant is prompt-and-iterate with the chat
   as the only record. Breaks by headcount, turnover and time, not size; carries over to an AI
   worst, since it relied on a memory the assistant lacks (H/M).
6. **Executable specification** — acceptance tests, contracts, types, TDD; read by a machine
   first; the only family whose documents cannot silently go stale. Says nothing of why or of
   alternatives; agents weaken tests to pass (H/M).
7. **Change-record-centred** — the commit's why, a patch series with a cover letter for larger
   work; permanent and tied to the lines. Commit messages restating the diff — an AI's especially;
   no home for intent spanning many series (H/M).
8. **Living docs in the repository** — every change updates the standing documents in the same
   change; ADRs short and superseded, never edited; the work leaves no separate artefact. Drifts
   anyway, since nothing enforces it as tests do; standing files swell. A 2026 study found
   repository context files slightly reduced agents' task success and raised cost; minimal content
   recommended. Every line in a standing file is paid in every session (H/M).
9. **Per-change spec pipeline for agents** — requirements, design and tasks per feature (Kiro,
   Spec Kit, Harper Reed's spec and plan files), co-written with the assistant before code. The only
   family whose default user is one person directing an agent. Usually discarded or left on the
   branch, not carried forward; scales badly downward — a small bug turned into sixteen acceptance
   criteria; masses of AI-written Markdown to review, skimmed and approved; stale intent read by the
   next session; *waterfall revived* (M/L).
10. **Journal-centred** — one chronological stream, decisions lifted out when someone else must
    read them. Near-zero friction; retrieval costs, contradictory entries with no mark of which won;
    an agent weights old entries like new ones (M/L).

Across them, for an assistant: no memory between sessions degrades the families relying on shared
memory most; writing became cheap and reading did not, so authoring-heavy families now produce more
than anyone reads; the assistant is a literal reader, so stale or excess text costs more than with
people who skim; one person directing an assistant is author, reviewer, approver and maintainer at
once, so families whose value came from separating those roles lose part of their mechanism;
executable checks gain value.

### What the tasking smuggled in

A clean arc from intent to done — much work is continuous. That documents carry the work — in
several families state, talk, tests or the diff carry it. **That size is the axis: the families
scale on risk and reversibility, boundaries crossed, appetite, novelty and the decision's lifespan;
a one-line change can deserve more paper than a large routine feature.** That scaling is a
continuous ladder. That one person with an assistant fits an existing ladder — family 9 exists
because it did not. That the families are alternatives — **in practice they are layered, and the
choices that matter are which family owns rationale, which owns status, and which owns current
truth.** That working documents end. That the reader builds software. That give and cost hold per
family in general.

### Nothing to take

Vendor claims of spec-driven gains; quantitative claims that documentation cuts defects or
onboarding by some percentage — no head-to-head study found; the 2026 study's exact figures as
summaries report them; IEEE 830 as a template; *Agile means no documentation*; Shape Up's
reach beyond small product companies.
