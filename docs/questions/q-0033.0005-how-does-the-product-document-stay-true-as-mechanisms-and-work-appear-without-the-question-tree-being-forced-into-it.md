# q-0033.0005 How does the product document stay true as mechanisms and work appear, without the question tree being forced into it?

- **struck** 0, last 2026-10-08T23:16Z

**Two ways the document goes stale.**

- **A row's status changes.** Every partial or absent row is a straw dog bound to the question it
  waits on. When that question closes, the wake reports the straw dog due. This part is already
  kept.
- **A new mechanism or piece of work appears with no row.** Nothing catches this. Sweeping the
  question tree for it is wrong: the tree serves the harness's structure and its evolution as well
  as the product *(the user, 2026-10-09)*, and a matrix mirroring every question would be a
  second index of the store.

**The link is authored at the thing, as the mark back** (q-0024.0009.0004). A ticket or a
mechanism names what it serves. For a row already bound to a question, a ticket that answers that
question is linked through its `Answers` field, and needs no more. The mark is needed only where
that chain is missing.

**The mark, as the agent sees it, 2026-10-09.** One header field on a ticket and on a mechanism's
declaration:

- `- **Serves:** product C5, C12` — the causes it answers, by the ids in `docs/product.md`. The
  pains follow from the matrix.
- `- **Serves:** structure` — how the harness holds together.
- `- **Serves:** evolution` — how the method changes and moves in its landscape.

The three values are the user's three domains of the tree. A cause id is never renumbered, only
retired, as a question id is. Questions carry no mark; a root may, if that helps read the tree.

**Collecting the marks is a mechanism's work** *(the user, 2026-10-09)*, possibly the release
mechanism reincarnated. The release mechanism is planned as a change writing its line at the
occasion that made it (01-0010.0185), lines collected at each publish into a note for an
instance (01-0010.0190). The product mark is a second line for a second reader. At a release:

- the marks of the work landed since the last one become the product half of the note — which
  causes moved;
- a product mark naming a cause with no matching row is a missing row;
- a mechanism declared without a mark is a diagnostic of the shape check.

**Against it.**

- Releases don't exist yet, so collection would wait on them; meanwhile the straw dogs keep the
  statuses.
- A mark people must fill in tends toward a cause chosen just to have one. `structure` and
  `evolution` must be honest values, not a failure.
- Only 5 of 24 skills are declared mechanisms, so for now the mark on tickets carries most of the
  load.

**Kept as an intention, 2026-10-09** *(the user)*: *write it down as an intention; we come back
when the queue reaches it.*

- **The release tickets carry it.** [01-0010.0185](../tickets/01-0010.0185-an-edge-change-writes-its-line.md)
  writes the product line at the occasion, and [01-0010.0190](../tickets/01-0010.0190-core-is-published-as-a-release.md)
  gathers it into the note's second half.
- **Clean core needs an owner of the product document's coherence.** The user: *for this to work
  in clean core, something must instruct the coherence of product.md, and that check is probably
  triggered on answering the group of questions about why the project exists.* In a recipient,
  `docs/product.md` holds that project's own pains. Some mechanism must therefore declare it as a
  painted door, and run the check when a question under the root that asks why the project
  exists is answered — here, q-0033's subtree. Which mechanism that is stays open.
- **The `Serves` values are not settled.** The user is not sure of `product` / `structure` /
  `evolution`.
