# A project's local facts are answered once and installed, not written into each skill

- **Status:** Planned (the injector precedes)
- **Type:** HITL
- **Depends on:** [01-0011.0020](./01-0011.0020-rules-one-home.md) (the injector, which is the
  machinery this would aim at project facts rather than at mechanism rules)
- **Outcome:** A project answers the harness's questions about its own facets once — its
  verification set, its gate commands, its host loaders — and those answers are installed into the
  places that need them, so no core skill carries a hand-written override and a recipient project
  has one place to answer rather than a corpus to edit.

## Parent

[Shared harness across projects](./01-0010-dev-harness-shared-and-local.md). This takes the
deferred open issue the queue has carried since inception — *local overrides* — and gives it an
owner.

## Why this exists

On 2026-09-07 `/commit` arrived carrying another project's gate set inside its `<project-local>`
block: `ruff check`, `ruff format --check`, `pyright`, `pytest`, and a `docs/cicd.md` this project
does not have. This project has no linter, no formatter and no type checker.

**The block is what made the wrong values look legitimate.** It is the designated place for local
facts, so a reader has no way to tell an answer from an import. Two defects sit under that, and
only one of them is about `/commit`:

- Another project's facts travelled inside a core file, which is what
  [Core and instance](../../AGENTS.md) forbids for `docs/` and does not yet say about local blocks.
- **The block was being used as an override rather than as an answer.** A local block that
  overrides is a second source for something core already states. A local block that answers a
  question core asked is an instance filling in its own value, and only the second kind is safe to
  ship.

The repair on landing was to delete it: `/commit`'s body already carries the global practice — *run
the checks the repository defines for itself* — and the project states its checks in its
verification set. That works for one skill. It does not answer how a **new** project comes to have
those facts in the first place, or how a skill reaches them without naming a file the project may
never have received. This ticket is that question.

## What to build

This is the decision-bearing phase. Its `/align` produces a spec; `/ticket` then decomposes it.

- The facet set: what the harness asks a project at bootstrap, and what it does with no answer.
- The delivery: how an answer reaches the skill that needs it, given that
  [Core and instance](../../AGENTS.md) substitutes `docs/` whole.
- Where onboarding sits — its own mechanism, or a mode of one that exists.

## Decisions this ticket's align owns

- **What the facets are.** Verification commands, gate commands, host loader links, release steps,
  the autonomy switches, the project's own name for its records, and the language its dreams are
  written in. The list is the first question and it decides the rest; a facet set that grows per
  skill is the defect wearing a new coat.
- **Whether a facet may be an expression choice and not only a command.** Dream language is the
  case that forces it: every other facet names something the harness *executes* or *links to*, and
  a wrong answer fails loudly. This one names how a record reads. `/dream` is core; the dreams in
  this tree are in Russian, which is this project's answer and nobody's default. If the facet set
  admits it, the set is not "what the harness runs here" but "what the harness could not know about
  this project" — a wider question, and the one that decides whether the list has a boundary at all.
- **Injected, or declared once and read.** Injection makes each skill self-contained at the cost of
  copies to keep in sync — which the injector already handles mechanically. A single declaration
  read on demand costs a lookup at the moment of use and a reference core is not allowed to make.
  These pull opposite ways and the answer is not obvious.
- **Where the answers live.** `docs/` is substituted whole, so a facet file there is honestly the
  instance's — but core may then reference it only from a `<project-local>` block, which is the
  shape this ticket exists to constrain. `AGENTS.md`'s local block is the other candidate and is
  already carrying the autonomy switches.
- **Whether a `<project-local>` block may override at all**, or only answer. Stating the rule is
  cheap; the question is what a legitimate exception looks like, because *"as much as possible"* is
  not a test.
- **What a project that answers nothing gets.** Silence, a refusal, or defaults — and if defaults,
  whose.

### A facet raised 2026-09-07, from `01-0011.0022`'s amendment

**Which of mechanism, documentation and code a project actually has** *(the user)*. The
distinction between the three is core — each obliges a different kind of maintenance pass. Which
of them a given project holds is not: in this repository there is no product code at all, so
code-maintenance and mechanism-maintenance coincide, and in a recipient project they will not.
Recorded here rather than as a `<project-local>` block in every skill that touches code, which
would be N copies of one fact. This ticket's align decides whether the facet set is the right
home; [01-0011.0022](./01-0011.0022-shape-survives-second-mechanism.md) carries the question from
the other side.

## Acceptance criteria — provisional, firmed at the align

- [ ] The facet set is named and recorded in a durable home.
- [ ] A spec exists and is accepted, and this ticket is rewritten to feature altitude or decomposed.
- [ ] No installed skill carries a hand-written project override; each either reads a declared facet
  or states the global practice and says where the local answer lives.
- [ ] `/commit`'s checks arrive by that route rather than by a block someone typed.
- [ ] A project that has answered nothing is distinguishable from one whose answer is *none*.
- [ ] Dream language is asked at bootstrap and reaches `/dream` by the same route as every other
  facet, or the align records why it is not a facet after all.
- [ ] `/verify` has been run on this ticket against its ticket, RFC, and governing docs.
