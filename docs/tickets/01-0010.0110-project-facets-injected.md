# A project's local facts are answered once and installed, not written into each skill

- **Status:** Ready (aligns with 01-0010.0130)
- **Type:** HITL
- **Depends on:** [01-0011.0020](./done/01-0011.0020-rules-one-home.md) (the injector, which is the
  machinery this would aim at project facts rather than at mechanism rules) — **landed 2026-09-08**
- **Related:** [01-0010.0130](./01-0010.0130-harness-installs-into-another-tree.md) — co-aligned on
  the user's direction, 2026-09-09: this ticket's answer says what a `<project-local>` block *is*,
  and that one cannot say what an installer localises until it is settled
- **Outcome:** A project answers the harness's questions about its own facets once — its
  verification set, its gate commands, its host loaders — and those answers are installed into the
  places that need them, so no core skill carries a hand-written override and a recipient project
  has one place to answer rather than a corpus to edit.

## Parent

## Why this exists

On 2026-09-07 `/commit` arrived carrying another project's gate set inside its `<project-local>`
block: `ruff check`, `ruff format --check`, `pyright`, `pytest`, and a `docs/cicd.md` this project
does not have. This project has no linter, no formatter and no type checker.

**The block is what made the wrong values look legitimate.** It is the designated place for local
facts, so a reader has no way to tell an answer from an import. Two defects sit under that, and
only one of them is about `/commit`:

- Another project's facts travelled inside a core file, which is what
  [Core and instance](../../AGENTS.md) forbids for `docs/` and does not yet say about local blocks.
- **The block was being used as an override rather than as an answer.** A local block that
  overrides is a second source for something core already states. A local block that answers a
  question core asked is an instance filling in its own value, and only the second kind is safe to
  ship.

The repair on landing was to delete it: `/commit`'s body already carries the global practice — *run
the checks the repository defines for itself* — and the project states its checks in its
verification set. That works for one skill. It does not answer how a **new** project comes to have
those facts in the first place, or how a skill reaches them without naming a file the project may
never have received. This ticket is that question.

## What to build

This is the decision-bearing phase. Its `/align` produces a spec; `/ticket` then decomposes it.

- The facet set: what the harness asks a project at bootstrap, and what it does with no answer.
- The delivery: how an answer reaches the skill that needs it, given that
  [Core and instance](../../AGENTS.md) substitutes `docs/` whole.
- Where onboarding sits — its own mechanism, or a mode of one that exists.

## Resolutions

### Ownership is one axis: who owns the content — 2026-09-10, the user

Core owns the slot wherever it installs. The only question is who owns what sits in it.

- **Core's content in core's slot** — an installed rule. Redeployment overwrites, and that is the
  point.
- **The project's content in core's slot** — an answer or an override: the autonomy switches, the
  verification set, the evidence path, where delivery state lives. **Redeployment must preserve
  it.**

**The rule: redeployment overwrites only where core owns the content.**

**The harness asks the instance to run its loop — that is the whole purpose — and the instance may
override, and the override survives redeployment** *(the user, 2026-09-10)*. frost_map is the case
that proves the second half is not optional: `tickets.py` demanded `Status` and `Type` against a
Notion board that already held them, no override was expressible, and the recipient's only
remaining move was to stop running the check. An override that cannot be written is a rule that
gets silently dropped.

**Retracted the same day: a second axis, who owns the *slot*.** It was adopted an hour earlier on
one case — frost_map's loader link, read as core seizing a slot the project owned. **The user's
ruling is that repointing the loader is correct**; what was actually missing is a defined
deployment target, which is
[01-0010.0130](./01-0010.0130-harness-installs-into-another-tree.md)'s. With that case gone the
second axis had no shape forcing it, and the entry file's first general rule says not to keep it.
Recorded rather than deleted because it is the fourth observed instance of generalising from one
shape in this repository, and the first caught inside the hour.

### One local rules file, injected — 2026-09-10, the user

Stated at session fourteen and adopted here. An instance writes every local override and
appendage into **one file, each entry in installed-rules format**; the injector installs from it
after a deployment lands; and a tier-1 rule requires every change an instance makes to a rule to be
written there.

It reuses the only seam that survived the trip with no repair, and three properties come free:
local content becomes enumerable in one place rather than grep-able across the tree; redeployment
is the existing `--install --overwrite` path; and `inject_rules.py --check` already fails on a
block that differs from its source **and on a block nothing owns**, so the tier-1 rule is enforced
by a check that exists rather than by obedience.

- **`<project-local>` stops being written.** Instance content reaches a core file only as
  `<installed by="local">`. The tag disappears from core, and the *Core and instance* exemption
  that let such a block carry a `docs/` reference goes with it.
- **The local file lives outside `.agents/`**, beside `AGENTS.md`. A redeploy that replaces the
  core directory wholesale would otherwise delete the file that restores the local content.
- **Rules only** *(the user)*. Nothing else needs injecting: `commit=ask` is a rule, not a value.
- **Both blocks install, local last, and a local entry overriding a core rule cites that rule's
  id** *(the user)*. An override is explicit and auditable rather than positional.
- ~~A header field saying whether the tree is core's own home or a recipient.~~ **Closed** — it
  existed to decide whether a `docs/` reference was a leak, and the precondition below rules that
  none survive anywhere. The fact becomes an ordinary local rule.

**Precondition** *(the user, 2026-09-10)*: **accounting for every `docs/` reference in core comes
first, and none survives deployment unless it is a painted door** — a path convention the recipient
creates for itself. The 2026-09-10 probe puts the split at 52 painted doors (`docs/tickets/`,
`docs/glossary.md`, `docs/adr/`) against 22 references to a particular document, which are the ones
that go. [01-0010.0140](./01-0010.0140-core-stands-alone.md) is that work and blocks this.

**How the rule is expressed is deferred to the RFC** *(the user, 2026-09-10)* — the local file's
name, its grammar, and how the injector distinguishes a local block from a mechanism's are
implementation questions.

## Decisions this ticket's align owns

- **What the facets are.** Verification commands, gate commands, host loader links, release steps,
  the autonomy switches, and the project's own name for its records. The list is the first question
  and it decides the rest; a facet set that grows per skill is the defect wearing a new coat.
- ~~**Whether a facet may be an expression choice and not only a command.**~~ **Closed 2026-09-10,
  the user: the dream language is random, not a setting** — picked afresh for each dream, landed in
  [`/dream`](../../.agents/skills/dream/SKILL.md) where it travels as core. It was the only case
  that raised this question, and every other candidate names something the harness *executes* or
  *links to*, where a wrong answer fails loudly. With no case left, the wider reading — that the
  set is "what the harness could not know about this project" rather than "what the harness runs
  here" — has nothing forcing it and is not carried.
- **Injected, or declared once and read.** Injection makes each skill self-contained at the cost of
  copies to keep in sync — which the injector already handles mechanically. A single declaration
  read on demand costs a lookup at the moment of use and a reference core is not allowed to make.
  These pull opposite ways and the answer is not obvious.
- **Where the answers live.** `docs/` is substituted whole, so a facet file there is honestly the
  instance's — but core may then reference it only from a `<project-local>` block, which is the
  shape this ticket exists to constrain. `AGENTS.md`'s local block is the other candidate and is
  already carrying the autonomy switches.
- **Whether a `<project-local>` block may override at all**, or only answer. Stating the rule is
  cheap; the question is what a legitimate exception looks like, because *"as much as possible"* is
  not a test.
- **What a project that answers nothing gets.** Silence, a refusal, or defaults — and if defaults,
  whose.

### A facet raised 2026-09-07, from `01-0011.0022`'s amendment

~~**Which of mechanism, documentation and code a project actually has** *(the user)*. The
distinction between the three is core — each obliges a different kind of maintenance pass. Which
of them a given project holds is not: in this repository there is no product code at all, so
code-maintenance and mechanism-maintenance coincide, and in a recipient project they will not.~~
**Restated the same evening at `01-0011.0022`'s `/align`** *(the user, 2026-09-07)*: the facet is
**which documentation-and-implementation pairs the project has**. `/maintain` holds, per pair,
that the docs apply the meta-rules and take their format, and that the docs and what they
describe agree both ways; the roles — documentation, implementation, record, meta-rule — are the
method's vocabulary and core. Which files play them is this facet. This repository's answer is
one row: mechanism docs under `.agents/mechanisms/` against `.agents/`, whose skills and scripts
are its implementation. A code project's answer is two rows, the second being its architecture
against its code. The harness's records — tickets, RFCs, sessions, marks — are not a pair and
not a facet: every project has them, because the mechanisms that write them travel.
Recorded here rather than as a `<project-local>` block in every skill that touches code, which
would be N copies of one fact. This ticket's align decides whether the facet set is the right
home; [01-0011.0022](./done/01-0011.0022-shape-survives-second-mechanism.md) carries the decision from
the other side.
