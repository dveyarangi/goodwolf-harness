## Why this exists

The entry file already states the behavior — "/impact determines the scope and load-bearingness of
the shape. Use it to evaluate work volume and its ticketing shape (spec for load-bearing work,
tickets for mechanical)". `/impact`'s own body does not produce it, and
[`/ticket` §3.1](../../.agents/skills/ticket/SKILL.md) records the gap in so many words: "It does
not yet recommend spec / ticket / RFC / re-slice; that extension is the parent's, not this skill's."

Two skills therefore call `/impact` expecting a routing answer and receive only a balance verdict.
The caller supplies the missing judgement silently, which is how a decomposition comes to look
assessed without having been.

## What to build

- `/impact` returns a work-shape recommendation as part of its output, covering spec, ticket, RFC
  and re-slice, with the reason it chose that shape.
- The recommendation is derived from what the pass already establishes — blast radius, boundaries
  crossed, load-bearingness — not from a new investigation step.
- `/ticket` §3.1 and `/plan` stop describing the extension as absent and consume the answer.
- The entry file's Helpers line and `/impact`'s description agree with the body.

## Acceptance criteria

- [ ] `/impact`'s output includes a work-shape recommendation with its reason.
- [ ] A run against a load-bearing shape recommends a spec, and a run against a mechanical one
  recommends a ticket or an RFC; both are demonstrated on real work in this repository.
- [ ] `/ticket` and `/plan` carry no statement that the extension is missing.
- [ ] `/verify` has been run on this ticket against its ticket, RFC, and governing docs.
