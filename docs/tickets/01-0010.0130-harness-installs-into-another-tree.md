## Why the recipient is the grader

This tree is the one configuration in which the install's defects are invisible: core and instance
are the same repository here, and every reference resolves. A check written for separation and run
here passes and proves nothing. The install is therefore graded where it can fail —
frost_map, which has had the harness on `main` since 2026-09-09, has built on it, and has already
refused one of its checks by leaving it unrun. The first real test is an *update* into a tree with a
history, not an install into an empty one, and it is graded by the user rather than by this tree's
suite. That is the mechanism shape's own sixth step, *graded by someone who did not build it*, and
it is this ticket's last acceptance box rather than a ticket of its own.

## What to build

One mechanism, **`harness`** *(the user: named `deploy` at the second align of 2026-09-20, renamed `harness` at `/implement` on 2026-09-21 — deploy has its own meaning in a real development environment)* — skill
`/harness`, script `harness.py`, modes `--install`, `--update`, `--check` — one instruction file,
relying on the injector for localisation rather than owning it. **Its source is a repository at a
ref, never a working tree** *(the user, the same align)*: `--from <repository>` names a git URL or
path, `--at <ref>` a tag or commit, and the installer clones it whole, without a checkout, into a temporary directory
and installs from the clone — **always the repository, wherever the script runs from, a fresh
clone every time** *(the user, 2026-09-20; whole rather than shallow at /plan, since a short commit cannot be fetched by itself)*: a working tree is never read, so the
announce line is always a commit that holds what shipped; the harness's own repository is the
default. **The repository's root `README.md` is written for an agent, not a person** *(the user,
2026-09-20)* — the repository's front page, never shipped and so not a part *(`/plan`,
2026-09-21)*: in a new environment the user hands their agent
the repository's link and asks for the harness, so the README must carry enough for that agent to
clone, read `/harness`'s instruction file inside the clone, and run the install from the link alone;
it names no document of this tree. A pure core repository
published by a later *release* mechanism is then one more `--from`, and the shear below is
idempotent over text already sheared. An install is the sequence below; an update is the same
sequence over a tree that already has a local file, which it never touches. Each step refuses
rather than guesses.

1. **Refuse a target it cannot satisfy.** One installation is one tree: `.agents/` sits directly
   under the directory holding `AGENTS.md`, because every script computes its root as two levels
   above itself. A workspace holding several projects is refused, not guessed at.
2. **Copy the manifest** — every file under `.agents/` at the ref, plus `AGENTS.md` and
   `CLAUDE.md`, nothing else; what ships and what is claimed stay one question through the
   reverse pass at the origin, which is the gate the allowlist was meant to be *(corrected at
   `/implement`, 2026-09-21; there is no allowlist)*.
3. **Record the revision — as the entry file's announce line, and nowhere else** *(the user,
   2026-09-20, at this ticket's second align; the spec's content hash is withdrawn)*. The line
   becomes `Entry contract: <repository>@<ref>, <date>.` — the repository's name from its URL, the
   tag when the commit has one and the short commit otherwise, the commit's own date — so every
   session in the recipient announces where core came from and at which ref, and a tree whose
   line carries the `@` is a recipient. Integrity is asked of the source, not of a record:
   `--check` clones that ref again, rebuilds what the install writes, and compares file by file
   with line endings normalised and local blocks removed, naming an edited or missing file and
   reporting a file under the core directory outside the manifest as the recipient's own. The
   URL is `--from`, defaulting to the harness's own repository, which the script knows as its home.
4. **Make the loader links.** A symlink — no junction, no copy, no substitute; an existing link is
   repointed, and one that already resolves is left alone. Where the platform refuses to create
   one, the run finishes everything else and ends with the exact elevated command for the person,
   and arrival stays false until the link resolves *(the user, 2026-09-21, on ADR-0003, replacing
   "stop and escalate"; Developer Mode is asked of nobody)*.
5. **Install the entry file.** `AGENTS.md` and each host's entry stub are parts of this mechanism,
   not something a person types.
6. **Shear.** A `<straw-dog>` wrapper is removed and its content stays as an ordinary rule. A
   `docs/` reference that [01-0010.0140](./done/01-0010.0140-core-stands-alone.md)'s check would flag
   stops the install here; it is not repaired here. The entry file's *follow a straw dog until its
   condition is visibly met* is worded so a recipient does not read it as applying to content that
   arrived unwrapped.
7. **Inject** — every mechanism's rules file, then the local file last.
8. **Verify arrival, and report done only when it passes**: the shipped tests green, the injector's
   check clean, the shape check clean, the copy matching the ref its line announces, and each
   loader link a symlink resolving to a directory of skill files. Whether the host *reads* the link is
   [01-0010.0120](./01-0010.0120-host-delivery-surfaces.md)'s and is named as unverified here.

**Core checks itself through `harness.py --check`, and the project's verification set stays the
project's** *(the user, 2026-09-20, at the second align)*: the shape check, the injector's check
and the comparison against a fresh clone are one command, the harness mechanism's, run as the
arrival gate and on any later day, in seconds; the loader links are reported beside its verdict
and never decide it, and the shipped suite is not in it *(the user, 2026-09-21, at the live run:
an install is seconds, not minutes)*; a recipient that wants core re-checked, or the suite run, at
every `/verify` names those commands in its own set. `/verify`'s definition of the set — the
project's typechecker, tests and every command required of landed work, named in its local file —
is generic already and gains no rule. **The install ends with the agent populating
`local.rules.md` from the environment it stands in**: the project's facts for the entry file, its
switches, and its verification set read off its own toolchain; `/harness` instructs that step and
the README points at it. The entry contract's hand-bumped version retires in favour of the
recorded revision.

## Acceptance criteria

- [x] Into an empty temporary tree, the manifest lands with `.agents/` directly under the directory
      holding `AGENTS.md`; a target where it would not is refused with the reason and no file is
      written.
- [x] What is copied is every file under `.agents/` at the ref plus the entry file and the host
      stub; a file outside the manifest does not travel.
- [x] The recipient's announce line reads `<repository>@<ref>, <date>` after install; `--check`
      compares the tree against a fresh clone of that ref and reads a line-ending difference as
      equal and a one-byte edit as an edit, naming the file. An update refuses over an edited
      core file unless told `--overwrite`, and then reports what it replaced; a line with no ref
      requires `--overwrite` and deletes nothing.
- [x] Each loader link is a symlink resolving to the skills directory, or the install stops and says
      which link and why; an existing link is repointed *(the repoint and the created link are proved only where the platform creates symlinks; on the origin's machine that case skips and the pending path is what runs)*.
- [x] `AGENTS.md` and each host's entry stub are installed by the mechanism and match their source.
- [x] No `<straw-dog>` wrapper survives in the shipped copy and every wrapped rule's content does;
      a reference the `.0140` check would flag stops the install with the reference named.
- [x] After install, the injector's check is clean in the recipient with every mechanism's blocks
      present and the local file's blocks last.
- [x] The install reports done only after the revision match, the injector's check and the shape
      check pass in the recipient; any one failing reports the install unfinished; the links are
      reported beside the verdict *(the shipped tests and the link check left the verdict at the
      live run of 2026-09-21, the user's decision)*.
- [x] An update over a tree with a populated local file leaves that file byte-identical and its
      blocks restored, and overwrites every core-owned file.
- [ ] frost_map takes an update: its `tickets.py` override is written in its local file and
      survives; its `docs/` is untouched; its links resolve; its revision is recorded; its
      verification set passes — **graded by the user in that tree, not by this one's suite.**
- [x] The entry contract's version line *is* the recorded revision in every recipient; the
      origin's hand-bumped line stays, since its entry file cannot carry its own commit, and the
      version record says so.
- [x] Behavioural tests, in the shape of the existing suite, cover each refusal, the revision's
      normalisation, the shear on wrapped and nested content, injection order, the arrival gate,
      and the update path.
- [x] `/verify` has been run on this ticket against its ticket, RFC, and governing docs — 2026-09-21: verification set green (304 tests, one skipped where the platform makes no symlink; three checks clean), four stale statements repaired in the ticket and the spec under the repair policy, no leakage found; the live install from the pushed repository into a scratch tree and the frost_map grade remain.
