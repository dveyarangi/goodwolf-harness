## What to build

- **The hook unasked**, through the link step every install and every fresh clone runs, and one
  sentence among what the install spares the person: a commit carrying a broken record of the
  method stops and names it; commits of code are untouched (decision 6).
- **The workflow file on the fourth ask**, numbered and in the person's terms — *1. checked in CI
  as well, beside your own checks, a check of its own on every pull request; 2. only at commit, on
  this computer* — the first proposed, the file written only on it; a CI that is not GitHub's gets
  the step as a line in the report (decisions 5 and 6).
- **Beside a standing hook** — husky, lefthook, pre-commit — the hook left untouched and the line
  given with its place (decision 4).
- Settled at this ticket's plan, none of them a decision of the question: whether a recipient's
  verification set names the launcher in place of its own list of checks; the lowest Python core
  states.

## Acceptance criteria

- [ ] A fresh install into an empty tree writes the hook, says the sentence, asks the fourth ask,
      and writes the workflow file only on its first answer — observed live by someone who did not
      build it.
- [ ] An install into a tree whose commits husky holds leaves `.husky/` and `core.hooksPath` as
      they were and reports the line and its place.
- [ ] In the recipient, a commit carrying a broken record is refused and names it, and its CI run
      on a pull request is red for the same record.
- [ ] An update leaves a hook and a workflow file of core's current, and a project's own hook and
      workflow files untouched.
- [ ] `/verify` passes against this ticket and the governing docs.
