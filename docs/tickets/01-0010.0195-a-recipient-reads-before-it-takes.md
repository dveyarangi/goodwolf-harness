# A recipient reads what stands between it and the latest before it takes it

- **Status:** Planned
- **Type:** HITL
- **Depends on:** [01-0010.0190](./01-0010.0190-core-is-published-as-a-release.md) (the releases
  there are to stand between a ref and the latest);
  [01-0010.0155](./01-0010.0155-a-tree-names-the-repository-its-core-comes-from.md) (the
  repository line, so the core repository's URL is written once in its final home rather than into
  the script and again into the line)
- **Outcome:** A recipient runs `--check` and learns which releases stand between its announced
  ref and the latest, reads what each asks of it, and decides — instead of taking a change blind
  or never learning one exists.

## Two trees are stranded right now

frost_map announces `goodwolf-harness@2c733f0` and ai-game-1 `goodwolf-harness@47516ce`. Both hold
verification sets naming `.agents/scripts/`, which `.0145` moved to `.agents/scripts/gw/`. Neither
has been told, and neither has any way to ask. That is this slice's demonstrated problem, and both
trees are its acceptance.

The pre-release case is not a compatibility path. An old recipient's announce line carries its
*own* repository, so `--check` against it keeps working unchanged; what it cannot report is a
pending-release count, because this repository has no releases. The migration is therefore one
note and one re-stamped `--update --from`, which is why the fourth drafted slice folded in here.

## What to build

- `--check` reports the releases standing between the announced ref and the source's latest. It
  already clones and resolves the ref, so this is a walk, not a new capability.
- `--update` defaults to the core repository's `HEAD` and reports the notes it crossed beside the
  verdict.
- The three gates keep deciding `arrived` alone. An acknowledgement flag and a refusal on
  unamended local rules were both refused at the align: a refusal on what the script cannot check.
  Whether a recipient amended a path in a file of its own is not observable from here.
- The harness skill's flow becomes check, read the notes, `/align` with the user on what they ask
  of this tree, then update or not.
- A tree whose announced ref predates the core repository is re-pointed by one
  `--update --from`, and the first release's note says so in the instance's vocabulary.

## Open issues

- Whether `--check` in a tree with no network says *unknown* or refuses. Today `--check` clones,
  so it already fails without one; whether a pending-release count deserves a softer failure than
  the integrity check is this ticket's.

## Acceptance criteria

- [ ] `--check` in a recipient names the releases between its announced ref and the latest, before
      anything is written.
- [ ] `--update` with no `--from` resolves the core repository and reports the notes it crossed.
- [ ] `arrived` is still decided by the three gates alone; no flag and no refusal on a recipient's
      own files.
- [ ] frost_map takes its scripts-move release by the flow — read, align, update — and needs
      nothing the note did not say.
- [ ] ai-game-1, whose ref also predates the core repository, is re-pointed by one
      `--update --from` and afterwards reports its pending releases like any other tree.
- [ ] `/verify` passes against this ticket, the RFC and the governing docs.
