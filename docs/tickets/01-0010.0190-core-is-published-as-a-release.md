# Core is published as a release to a repository of its own

- **Status:** Planned
- **Type:** HITL
- **Depends on:** [01-0010.0185](./01-0010.0185-an-edge-change-writes-its-line.md) (the mechanism
  and the record whose accumulated lines the note is derived from)
- **Answers:** [q-0018.0020.0002.0002](../questions/q-0018.0020.0002.0002-how-is-core-published-as-releases-to-a-repository-of-its-own.md)
- **Outcome:** Core is published to a repository of its own, each publish a release carrying a
  note in two halves — for an instance, what to amend; for a person, which causes the release
  moved — so a recipient installs from what was published rather than from this working tree.

## Parent

[A change to the harness's edge reaches a recipient as a release](./01-0010.0160-harness-edge-changes-reach-an-update.md),
whose [split](./01-0010.0160-harness-edge-changes-reach-an-update.md#the-split--2026-09-23) holds
the `/impact`. Second of three slices.

## The shipment already exists; nothing writes it anywhere

`harness.py` computes the clean shipment on every install — the manifest at the ref, local blocks
stripped, wrappers and bindings sheared, held to the leak rule — and throws it away into the
target. A release writes that same shipment somewhere it can be installed from. Nothing about
*what* ships changes: the manifest, the shear, the stamp and the leak rule are untouched, which is
what makes this slice small despite what it unblocks.

## What to build

- The publish act, as the `releases` mechanism's skill: derive the note from the lines accumulated
  in the edge record since the last release, rewritten in the instance's vocabulary — what moved,
  from where to where, what an instance amends — and write the shipment plus that note to the core
  repository.
- The note's second half, for a person: the product lines of the work landed since the last
  release, gathered by cause — which causes in [the product document](../product.md) this release
  moved *(the user, 2026-10-09)*. A product line naming a cause with no row in the document is
  reported as a missing row. The front page's account of what changed is derived from this half,
  never written beside it.
- The record marks the release, so the next note knows where to start.
- Every publish there is a release and `HEAD` is the latest; a tag is only a name.
- The destination is **this repository's answer**, a local rule, not core's: a recipient has
  nothing to publish and a fork publishes to its own.
- **An adoption panel runs at every release** *(the user, 2026-09-26)*. Several independent agents,
  each given a different project and different needs, read what the release publishes — the front
  page and core, never this repository's `docs/` *(the user, 2026-09-26)* — and say
  whether they would install it over the alternatives they know — and if not, why not. The answers
  are recorded at the origin beside the release; a recipient never sees them. It is the one
  recurring occasion that exists for a check nobody else
  owns, and *would not install* is the most important signal the front page can return: at the
  front-page align, two cold readers of the draft both declined, on the same two gaps.
- **Who sits on the adoption panel.** The needs it must span, at least: a project that already
  has its own agent instructions; a large existing codebase with none; a greenfield prototype; a
  single-host user; someone who wants minimal ceremony. The first two runs
  ([record](../research/adoption-panel-2026-09-26.md)) sat only those five, all wanting less
  process, and none is the user the harness is built for — someone running a product with agents
  over months who wants the discipline. The panel keeps those five *(the user, 2026-09-26)*: the
  lighter process [01-0020](./01-0020-pacer.md) owns is meant to serve exactly them. The question
  is split in two *(the user, 2026-09-26)*, since in the first three runs the project's age and
  adoption, which any reader finds on the host, swamped what the panel exists to learn: first, on
  the method and its tooling alone, would it serve this project better than the alternatives, and
  **what would change that answer**; then, separately, what would the reader need to see before
  trusting it there. The first is the verdict and the list of what to build; the second is adoption
  evidence. The fourth run asked the trust question *in place of* what would change the answer, and
  lost the most actionable part — the question is kept, never traded. **A panel runs clean-room**:
  its readers start outside this repository, since a subagent started here inherits the entry file,
  the user's memory index and the recent commit subjects before it reads anything — one run's
  readers asked for exactly the measurement a commit subject had just named. Not met by the runs of
  2026-09-26, all started from this session.
- **The published repository has no front page.** The manifest is `.agents/`, the entry file
  and the host stub; the root README is kept out of it on purpose, since an install would
  overwrite a recipient's own. So the product's repository, as this slice publishes it, opens on
  nothing. A release needs a front page that is published and never installed — outside the
  manifest, beside it — and held to the leak rule, because a reader there has core and none of
  this tree's `docs/`. The page links two root files beside it — the license and the loop's
  diagram ([01-0010.0167](./done/01-0010.0167-the-front-page-says-what-the-harness-is.md)) — so a
  release publishes them with it. Raised by the user on 2026-09-26, reading an outside review of the front
  page ([external-review-front-page](../research/external-review-front-page.md)); what the front
  page says is the front-page align's, where it is published from is this ticket's.

## Acceptance criteria

- [ ] A publish writes the clean shipment to the core repository, and a fresh install from that
      repository is byte-identical to one from this tree at the same ref.
- [ ] The note is derived from the edge record's lines since the last release, not from the commit
      log, and names what an instance amends.
- [ ] The note's product half lists, by cause, the product lines of the work landed since the
      last release, and reports any line whose cause has no row in the product document.
- [ ] The record marks the release, and a second publish derives its note from that mark forward.
- [ ] The destination is a local rule; nothing in core names this repository's publish target.
- [ ] The history decision is landed in its durable home with its provenance.
- [ ] A publish runs the adoption panel and its answers are recorded at the origin beside the
      release.
- [ ] `/verify` passes against this ticket, the RFC and the governing docs.
