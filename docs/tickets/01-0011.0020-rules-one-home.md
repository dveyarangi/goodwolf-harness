## Why this exists

A rule that must hold in a skill its mechanism does not own has two roads: someone writes it there,
or something installs it there. This tree has taken the first road throughout, and both defects the
parent spec was written from are what that road produces — a duty written in one skill's files while
another skill is the one who must act on it, and a policy restated in two skills with no owner
between them.

Writing each such rule by hand fixes the instance in front of you and leaves the next one to
chance. Installing it makes the copy derivable, removable and checkable: **injection is mechanical
in both directions or it is not injection.**

This slice builds only the machinery, and proves it on one rule. It comes before the declarations
it will serve because it is the tool they lean on — a declaration that installs its rules by hand
is a declaration whose central claim is false on the day it is written.

was written as* paired close's rules move home *when paired close was believed to be the first

## What to build

- `<slug>.rules.md` in a mechanism's own directory — one demarcated section per rule, each naming
  its **target**, its **anchor** and its **tier**. That file is the rule's only home, and a rule
  states its authority inline: who may change it, at what strength.
- **One generic installer**, not a per-mechanism one. Life built per-mechanism installers and
  reverted: rule bodies in a `.js` while the doc asserted it held them is two homes with the skill
  claiming the false one, and bespoke installers outweigh the thing they install.
- **No default mode.** Install and retract are not points on a spectrum with an obvious middle, so
  a bare invocation refuses. Life's bare invocation meant *retract*, and on 2026-08-29 one was
  aimed at an always-on mechanism by a session that believed it was re-installing; an unrelated
  guard is the only reason it did not land.
- Delimited, visibly owned blocks in the targets, so a reader can see what may be edited and what
  may not. **The delimiter is this ticket's plan to choose** *(raised 2026-09-07 at
  [.0022](./01-0011.0022-shape-survives-second-mechanism.md)'s align)*. Life uses HTML comments,
  `<!-- BEGIN INJECTED <slug> -->` … `<!-- END INJECTED <slug> -->`, invisible in rendered
  markdown and read raw by the agent. This tree already demarcates with tags a reader sees —
  `<temporary until= ticket=>` and `<project-local>` — and `docs_corpus.py` already parses a
  tag's attributes, so a tag of the same family, carrying the owning slug, is the consistent
  choice; the plan weighs it against Life's.
- Removal that leaves each target byte-identical to before installation. What can be written can be
  removed, or it is not injection.
- Drift detection: a hand-edited block is reported, never silently overwritten. A local fix must not
  become a second source.
- **Proven on one real rule**: `/mechanism`'s maintainer-script convention — *a record-bearing
  mechanism has a script checking its records against their declared shape* — installed into
  `/maintain`, which is a skill `/mechanism` does not own. One rule, one target, no record
  migration riding along.

## Acceptance criteria

- [ ] A mechanism's rules exist in one file, each section naming target, anchor and tier, and each
  rule stating its authority.
- [ ] Installing writes an owned, delimited block into a skill the mechanism does not own;
  `/maintain` carries `/mechanism`'s maintainer-script rule as an installed block.
- [ ] Installing twice changes nothing the second time.
- [ ] Removing leaves the target byte-identical to its pre-installation bytes.
- [ ] A hand-edited block is reported as drift and is not overwritten.
- [ ] A bare invocation with no mode is refused, with nothing written.
- [ ] An unknown target and a missing anchor are each refused, with nothing written.
- [ ] Behavioral tests cover install, re-install, removal round-trip, drift, and all three refusals.
- [ ] `/verify` has been run on this ticket against its ticket, RFC, and governing docs.

## Input from `01-0011.0022`'s align, 2026-09-07

**Installed text, never pointers** *(the user)*. `/mechanism`'s body said both; the second holds.
A rules file is a rule's only authored home; every reader carries an installed block, the owning
mechanism's own skill included when it reads the rule in its own work; no body restates one.
**Meta-rules are never injected**: they live in `/mechanism` or the entry file, and a skill
applying one reads it there.

What `mechanism-shape.rules.md` holds, read against *when is this read* — seven rules, two
targets; the proven-on-one-rule scope of this slice is R1:

| | rule | target |
|---|---|---|
| R1 | A record-bearing mechanism's records are checked by its maintainer script, format never content, live rows only, archived history exempt; where the script is missing, writing it is the maintenance | `/maintain` |
| R2 | A mechanism is re-checked when what governs it moved: doc against `/mechanism`, instruction file against doc, records against their declared shape; comparison excludes evidence and installed blocks | `/maintain` |
| R3 | Story in a doc belongs in its evidence, which lives outside `.agents/` | `/maintain` |
| R4 | An index is derived on request and never committed beside its records | `/maintain` |
| R5 | An installed block is never edited by hand; the installer reports drift | `/maintain`, `/skill-up` |
| R6 | A skill is a mechanism's one instruction file or sits in the allowlist with its reason; it holds the act and the rules read in its work, and the *why* goes to the doc | `/skill-up` |

Not injected: membership, the three homes, the moment kinds, incept and retire — read while doing
mechanism work; D1 and D2 — meta-rules; the incept agenda — `/mechanism` invokes `/align` and
brings it; the check's place in the verification set — a facet. With R1–R6 out of the body as
prose, `/mechanism` loses its *Records* section and half of *Amend and retire*.
