## Why this exists

A rule that must hold in a skill its mechanism does not own has two roads: someone writes it there,
or something installs it there. This tree has taken the first road throughout, and both defects the
parent spec was written from are what that road produces — a duty written in one skill's files while
another skill is the one who must act on it, and a policy restated in two skills with no owner
between them.

Writing each such rule by hand fixes the instance in front of you and leaves the next one to
chance. Installing it makes the copy derivable, removable and checkable: **injection is mechanical
in both directions or it is not injection.**

This slice builds only the machinery, and proves it on one rule. It comes before the declarations
it will serve because it is the tool they lean on — a declaration that installs its rules by hand
is a declaration whose central claim is false on the day it is written.

## What to build

- `<slug>.rules.md` in a mechanism's own directory — one demarcated section per rule, each naming
  its **target**, its **anchor** ~~and its **tier**~~. That file is the rule's only home, and a rule
  states its authority inline: who may change it~~, at what strength~~.
  **The section grammar, decided at this ticket's align, 2026-09-08 (the user)** — the doc's own
  grammar, named bullets for values and one tag for the span, so the code that reads a doc's
  header reads this:

  ```markdown
  ## R1 — records are checked by their maintainer script

  - **target** `.agents/skills/maintain/SKILL.md`
  - **target** `.agents/skills/mechanism/SKILL.md`
  - **anchor** `## Installed from other mechanisms`
  - **authority** the user, 2026-09-07

  <rule>
  Check a record-bearing mechanism's records with its maintainer script — format never
  content, live rows only. Where the script is missing, write it: that is the maintenance.
  </rule>
  ```

  The heading's first token is the id; **target** may repeat, one path per bullet, so a rule
  going to two skills has one body; **anchor** is the verbatim line the block follows, in a code
  span; **authority** is provenance, a name and a date — strength was withdrawn at
  [.0022](./done/01-0011.0022-shape-survives-second-mechanism.md) and the glossary's entry is
  repaired with it; **no tier bullet**, since a block's tier is its target's and a restated
  derivable fact can only disagree. The `<rule>` span is taken byte for byte. The id appears once
  in the source, in the heading, and once in the target, in the tag the installer writes:

  ```markdown
  <installed by="mechanism-shape" rule="R1">
  Check a record-bearing mechanism's records with its maintainer script — format never
  content, live rows only. Where the script is missing, write it: that is the maintenance.
  </installed>
  ```

  `by` exists only in the target, where nothing else says where the text came from: it is how
  the retractor finds its own blocks and how a reader sees which lines are not the skill's to
  edit. A body holding a literal closing tag is refused, not guessed around.
- **One generic installer**, not a per-mechanism one. Life built per-mechanism installers and
  reverted: rule bodies in a `.js` while the doc asserted it held them is two homes with the skill
  claiming the false one, and bespoke installers outweigh the thing they install.
- **No default mode.** Install and retract are not points on a spectrum with an obvious middle, so
  a bare invocation refuses. Life's bare invocation meant *retract*, and on 2026-08-29 one was
  aimed at an always-on mechanism by a session that believed it was re-installing; an unrelated
  guard is the only reason it did not land.

  may not. ~~**The delimiter is this ticket's plan to choose** *(raised 2026-09-07 at

- **Invocation and failure contract, decided at this ticket's align, 2026-09-08 (the user):**
  `inject_rules.py <slug> --install [--overwrite]`, `inject_rules.py <slug> --retract`, and

  verification set, so drift is caught at every `/verify`. **The installer never writes a doc**:
  `state` there means whether the mechanism can be installed at all, and the always-on mechanism
  is the one injecting most.
- Drift detection: a hand-edited block is reported, never silently overwritten. A local fix must not

## Where each piece lands, agreed at the 2026-09-08 align (the user)

- The rules file grammar: `MECHANISM-FORMAT.md`, which already names the sections as the
  installer's seam. The example above is the input; the shelf is the home.
- The amend step — amend a rule in its rules file, then install it — and the incept step's
  *write the rules file and install it*: `/mechanism`'s body, authored there as the shape's own
  instruction about its own machinery, with the script's name and modes beside them.
- `--check`: the verification set in `docs/process.md`, beside the mechanism check — a facet,
  project-local.
- The shape's doc: the installer and its tests as parts, the entry-file sentence as an anchored
  part, and three moment rows from `not yet` to instructed — installing, retracting, and telling
  an inceptor what to hand `/maintain`, the last instructed by the block that then sits in
  `/mechanism`.
- `/maintain`'s body loses its R1–R5 hand copy and its temporary wrapper and gains four installed
  blocks; `/mechanism`'s body loses the *Records* paragraphs and their wrapper and gains three;
  `/skill-up` gains one. The three temporary statements bound to this ticket retire at its
  `/maintain`, by the enumerator, after the installer has proven the blocks present.
- **Reachability, named rather than assumed**: the install rules reach a session through
  `/mechanism`, which the entry file's trigger routes to; the installed rules reach it through the
  skill they sit in, as this morning's `/maintain` invocation showed by loading the hand copy;
  `--check` catches drift at `/verify`. An agent editing a skill without invoking `/mechanism`
  meets only the entry file's sentence, and the drift is caught at the next `/verify` rather than
  at the edit — [01-0018](./01-0018-reachability-coherent.md)'s gap, unchanged here except that
  the drift becomes detectable.

## Acceptance criteria

- [ ] A mechanism's rules exist in one file, each section naming target, anchor ~~and tier~~, and
  each rule stating its authority *(tier dropped at the 2026-09-08 align: derivable from the
  target)*.
- [ ] Installing writes an owned, delimited block into a skill the mechanism does not own;
  `/maintain` carries `/mechanism`'s maintainer-script rule as an installed block.
- [ ] Installing twice changes nothing the second time.
- [ ] Removing leaves the target byte-identical to its pre-installation bytes.
- [ ] A hand-edited block is reported as drift and is not overwritten.
- [ ] A bare invocation with no mode is refused, with nothing written.
- [ ] An unknown target and a missing anchor are each refused, with nothing written.
- [ ] Behavioral tests cover install, re-install, removal round-trip, drift, and all three refusals.
- [ ] `/verify` has been run on this ticket against its ticket, RFC, and governing docs.
