# A rule that applies in two skills is written once and installed into both

- **Status:** Planned (the declaration precedes)
- **Type:** AFK
- **Depends on:** [01-0011.0010](./01-0011.0010-mechanism-declared.md) (a declared mechanism whose
  rules have somewhere to live)
- **Outcome:** Paired close's rules live in one file, are installed as visibly owned blocks into
  `/ticket` and `/maintain`, are removable leaving each target byte-identical, and a hand-edited
  block is reported as drift rather than accepted as a second opinion.

## Parent

[A mechanism has one home for its rules, and a derived index](../spec/01-0011-mechanism-shape.md).
`/impact`: [the 2026-09-06 split assessment](../spec/01-0011-mechanism-shape.md#impact--2026-09-06).

## Why this exists

The archive duty is written in `/ticket`'s two files while `/maintain` owns archiving. `/maintain`
carries only the permission form — *a ticket moves only when every acceptance box is checked* — and
never the duty. On 2026-09-06 five tickets sat finished and unarchived, and three `/maintain` passes
each correctly declined to touch records they had not examined.

That is not a filing mistake. It is what happens when a mechanism spanning two skills has no owner
for where its rules go. Writing the duty into `/maintain` by hand would fix this instance and leave
the next one to chance.

## What to build

- `.agents/mechanisms/paired-close/paired-close.rules.md` — one demarcated section per rule, each
  naming its target and anchor. That file is the rule's only home.
- A generic installer, not a per-mechanism one. An installer holding rule text puts the rules in two
  places and makes the doc assert the wrong one.
- Delimited, visibly owned blocks in the targets, so a reader can see what may be edited and what
  may not.
- Removal that leaves each target byte-identical to before installation. What can be written can be
  removed, or it is not injection.
- Drift detection: a hand-edited block is reported, never silently overwritten. A local fix must not
  become a second source.
- The rules paired close owns leave `docs/process.md`. What belongs to mechanisms not yet declared
  stays there and waits for them.

## Acceptance criteria

- [ ] Paired close's rules exist in one file, each section naming its target and anchor.
- [ ] Installing writes owned, delimited blocks into `/ticket` and `/maintain`; `/maintain` then
  carries the archive duty, not only the permission form.
- [ ] Installing twice changes nothing the second time.
- [ ] Removing leaves both targets byte-identical to their pre-installation bytes.
- [ ] A hand-edited block is reported as drift and is not overwritten.
- [ ] An unknown target and a missing anchor are each refused, with nothing written.
- [ ] `docs/process.md` no longer states a rule paired close owns.
- [ ] Behavioral tests cover install, re-install, removal round-trip, drift, and both refusals.
- [ ] `/verify` has been run on this ticket against its ticket, RFC, and governing docs.

## Out of scope

Injecting any other mechanism's rules. The remainder of `docs/process.md`, whose final disposition
is [01-0020](./01-0020-pacer.md)'s. Wake-time delivery, which this harness has no hook for.
