## Nothing registers an edge change when it happens

The update path as landed can say that a rule left — `harness.py`'s injector refusal names an
override *naming a rule this ref no longer sends there* — and that a part left — its `deleted`
list — and cannot say where either went, because nothing wrote that down at the moment it moved.
The version record for the entry file ([entry-contract-findings](../research/entry-contract-findings.md))
is a release record for one file, hand-kept, in the instance half, and does not ship; mechanism
evidence records what was refuted, not what moved. The harness mechanism's own doc names the
gap: *the transformation is unguarded*.

Twice in one day it cost something real. The scripts' move under
[01-0010.0145](./01-0010.0145-core-scripts-under-one-directory.md) breaks every recipient's
verification set, and the only moment that fact was known was its `/plan`; nothing asked for it
to be written anywhere a later release could find it. And the injector's placement rule moved
every recipient's installed blocks with no name changing at all.

## What to build

Decided at the align of 2026-09-21 *(the user)*.

- **The edge is the whole core–instance interaction.** Everything an instance needs to know to
  integrate core, to customise it, and to keep its process coherent across core changes: a rule
  id, a target and its anchor, a script's path and command, a skill's name, the announce form —
  and a behaviour a recipient's files rely on, since the injector's placement moved every
  recipient's blocks without a name changing. Not on it: what a recipient never meets — a
  skill's body, a declaration's prose, a script's internals.
- **Two homes.** The edge's engineering record is `docs/edge/install.md`, in `/edge`'s shape,
  the origin's and never shipped; `docs/edge/` is this mechanism's painted door. What a client
  instance meets is the **manifested edge**, derived from that record as help pages are from a
  product's: today the root README and the harness skill.
- **Registered at the occasion.** A rule of this mechanism, installed into `/implement`,
  `/verify` and `/edge`, says: a change to the edge writes its line in the edge record in the
  same pass. Deriving the notes at release time from the commit log and the record's diff was
  refused — it reads the change's vocabulary, and only what its author remembered to change.
- **Derived at the release.** At a release the agent, under this mechanism's skill, rewrites the
  lines accumulated since the last release into a note in the instance's vocabulary — what moved,
  from where to where, what an instance amends — and the record marks the release.
- **The release publishes the clean core.** Core stops being shared from this working tree: a
  release writes the shipment `harness.py` already computes — the manifest at the ref, local
  blocks stripped, wrappers and bindings sheared, held to the leak rule — into a repository of
  core's own, the note in that commit. Every publish there is a release and `HEAD` is the latest,
  so `--update` defaults to `HEAD` of the core repository and a tag is only a name. The act is a
  core skill of this mechanism; the destination is this repository's answer, a local rule, since
  a recipient has nothing to publish and a fork publishes to its own.
- **The installing agent decides.** `--check` in a recipient reports the releases standing
  between its announced ref and the source's latest — it already clones and resolves the ref —
  and the skill's flow is check, read the notes, `/align` with the user on what they ask of this
  tree, then update or not. `--update` reports the notes it crossed beside the verdict; the three
  gates keep deciding `arrived` alone, since whether a recipient amended a path in a file of its
  own is not observable from here. An acknowledgement flag, and a refusal on unamended local
  rules, were refused: a refusal on what the script cannot check.

## The split — 2026-09-23

Three slices, `.0155` → [`.0185`](./01-0010.0185-an-edge-change-writes-its-line.md) →
[`.0190`](./01-0010.0190-core-is-published-as-a-release.md) →
[`.0195`](./01-0010.0195-a-recipient-reads-before-it-takes.md), minted at `/ticket` on the user's
approval. `/impact`: **proceed, narrowed to three.** The six parts the align counted are the
registration (`.0185`), the publish and its note (`.0190`), and the recipient's read-then-decide
(`.0195`); the fourth drafted slice — a tree holding a ref older than the first release — folded
into `.0195`, because an old recipient's announce line carries its own repository and `--check`
against it keeps working unchanged: what breaks is only the pending-release count, so the
migration is one note and one re-stamped `--update --from`, not a compatibility path.

Blast radius: a new mechanism directory and its skill; an installed block in `/implement`,
`/verify` and `/edge`, each needing an anchor that occurs once; `harness.py`'s default source,
`--check`'s report and `--update`'s default and notes; the harness skill's flow; the local file's
publish destination; `docs/edge/` created. Leave alone: the manifest, the shear, the stamp, the
leak rule and the gate's three checks — a release writes the shipment `harness.py` already
computes, and nothing about *what* ships changes; `/edge`'s declaration, which stays
[01-0010.0100](./01-0010.0100-remaining-named-corpus.md)'s; contribution back and release cadence,
both parked.

Two hidden edges moved to the slices that own them: **whether core may name the edge record at
all** went to `.0185`, which is decision-bearing until its align answers it, and **the publish's
history question** to `.0190`. A third stays here as the calibration worry: the occasion rule
lands in two of the most-run skills, so every `/implement` and `/verify` pass will carry it —
`.0145`, a script-path move, is the case that says whether it is drawn wide enough to catch and
narrow enough to be worth carrying.
