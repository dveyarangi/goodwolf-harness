# A rule's block leaves a file once its rules file stops naming it

- **Status:** Ready
- **Type:** AFK
- **Trigger:** a fresh recipient, 2026-10-09 — removing its local L3 left the block in
  `.agents/skills/verify/SKILL.md`, and the only way out was to restore the earlier local file by
  hand and retract
- **Answers:** [q-0024.0010](../questions/q-0024.0010-how-does-a-block-leave-a-file-its-rules-file-no-longer-names-as-a-target.md)
- **Outcome:** Installing a rules file also removes that file's own blocks from every file it no
  longer names as a target, and says which, so dropping a target is one edit and one install.

## Parent

[Mechanism shape](../spec/01-0011-mechanism-shape.md), whose installer landed with
[rules in one home](./done/01-0011.0020-rules-one-home.md). The mirror case, a target that should
now be named, is q-0024.0003's.

## What to build

- `--install` walks the blocks of its own source in every file, not only the targets it names;
  a block of its source in a file it no longer names is removed, and the report names the file
  *(the user, 2026-10-09)* — `--check` already finds such a block, and no mode removed it.
- Only the installing source's blocks are touched: another source's block, an orphan of a source
  with no rules file, stays what `--check` reports.
- The removal leaves the file as it was before that block was installed, as retraction does.
- Every target is still validated before anything is written; a refusal changes no file.

## Acceptance criteria

- [ ] With a target dropped from a rules file, one `--install` removes the block from that file,
      names it in the report, and `--check` passes.
- [ ] The file is byte-identical to its state before the block was first installed.
- [ ] A block of another source in that file is left in place.
- [ ] A refusal on any named target leaves the dropped target's block in place too.
- [ ] `/verify` passes against this ticket, its RFC and the governing docs.
