## What to build

Today this tree's roles are a list in its local rules: each role's zone in a sentence, no brief,
and its session known by its title alone. The parent question's accepted
[Where it stands](../questions/q-ja5mp4-does-the-method-have-one-session-direct-the-others-an-orchestrator-and-what-does-it-owe-the-sessions-it.md#where-it-stands)
— *What carries a role*, *Who holds which*, *This tree* — puts them elsewhere:

- Every role this tree has opened has a mechanism of its own: its skill is the role's brief,
  which a successor reads without the chat that held the role before; its parts and what it
  produces are the role's zone. Where what a role produces is itself a mechanism, the role's
  mechanism names it, and the name stands for the paths that mechanism declares. The shape check
  reads that naming, since a declaration no script reads is a label.
- The roles are this tree's own and reach no recipient: their mechanisms are declared local, the
  first in this tree that are.
- Which session holds which role is a table in the local rules file, installed into the entry
  file, a session named by its name and never by a chat's id. It replaces the list. What the
  table does not name is held by the session that holds the harness, and so is a path no role's
  mechanism names.
- The roles are the four that have a session, and the work on how rules are made, cut off the
  keeper now that the whole is accepted
  ([q-dyc63i](../questions/q-dyc63i-which-standing-roles-does-this-tree-have-where-every-session-develops-the-harness-itself.md),
  decision 2): the table gives it to the keeper's session until the person opens one for it. The
  landing on main stays a role not opened.
- A file several roles still write is allowed until the files are moved apart, and is marked
  where each of those roles' zones is written, the person told what follows.
- Each role's skill is written, and put to the person, by the session that holds the role; the
  table and what the mechanism format gains by the keeper.

Every instruction's text is shown to the person before it lands: the work changes the way of
working. Each step is written in [the journal](../research/standing-sessions-journal.md) with
what a fresh tree would need to do the same.

## Acceptance criteria

- [ ] Each role this tree has opened has a mechanism of its own, and a fresh reader given a
      role's skill, its doc and the entry file says what the role answers for, what its zone
      holds and whom it asks for a change outside it; judged by someone who did not build it.
- [ ] Every path a mechanism of this tree declares is in one role's zone, or is marked shared in
      each zone that writes it; the shape check refuses a role's mechanism that names a mechanism
      the tree does not hold.
- [ ] The entry file holds the table of which named session holds which role, installed from the
      local rules file; the list of roles is gone from the local rules, and the rule that holds
      the table names each rule of the entry file it replaces for this tree.
- [ ] Each standing session's row bears the name the table gives it.
- [ ] A fresh session asked whose a given file of this tree is, and which session to ask for a
      change in it, answers from the table and the roles' mechanisms, untold; judged by someone
      who did not build it.
- [ ] A recipient updated from this ref receives none of the roles' mechanisms, and the ship's
      check passes.
- [ ] Each skill's text, the table's and the local rule's were shown to the person before they
      landed, by the session that wrote them.
- [ ] `/verify` passes against this ticket and the governing docs.
