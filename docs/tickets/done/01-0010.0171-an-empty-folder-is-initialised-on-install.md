## Why a repository, and why the installer may make one

Every script of core reads a tree through Git's listing, and the top level of the work tree is
where one installation ends; the install's own gate runs the shape check in the target, so a
plain folder would receive core and fail its own gate. The decision and its reason are in
[the architecture](../../architecture.md#installing) *(the user, 2026-10-07)*: in an empty folder
inside no repository the root is not in question and the person asked for an install, so the
installer runs `git init` there and reports it. A folder with files of its own is where the root
becomes the person's decision, so it is refused with the step; a subfolder of a repository is
not the top, and is refused naming the parent.

## What to build

- **The work-tree check tells three cases apart.** Git says *not a git repository*: an empty
  target is initialised and the run continues, the init reported among what was written; a
  non-empty target is refused — `target: <path> is not a git repository; run git init there, or
  install at the root you mean, then run again`. Git names a top level that is not the target:
  refused as today, naming that top level as the parent. Git's ownership refusal keeps its own
  wording.
- **The init writes nothing else.** No commit, no remote, no setting; the first-install sequence
  that follows writes the switches, and whether the tree ever pushes is decided there.
- **The harness skill's refusal list** names the non-empty-folder case and the subfolder case,
  each with what the person does, and says that an empty folder is initialised.
